# KV-cache management, attention kernels and long-context memory for local LLM inference (state as of 2026-10-08)

Scope: input for the design of LLMario's planned from-scratch Rust engine (CPU + any local GPU/NPU, 8–128 GB machines, 32K–256K contexts, several concurrent requests). Labels used below: **[measured]** = numbers from a reproducible run with stated hardware/version; **[vendor-claimed]** = paper/blog claim by the method's authors; **[self-reported]** = community/third-party numbers without independent check; **[unverified]** = could not be confirmed against a primary source; **[background]** = pre-2025 work that current engines build on. ## KQ1. Memory accounting: per-token KV size for MHA, GQA/MQA, MLA, sliding-window, hybrid SSM/attention, linear attention, with worked examples

### Takeaway
For attention layers the cache is linear in context: `bytes/token = Σ_layers 2 · n_kv_heads · head_dim · bytes_per_element`, so GQA (fewer KV heads), MLA (a single 576-wide latent per layer), interleaved sliding-window layers (fixed `window × per-layer` cost) and hybrid SSM/linear layers (fixed per-sequence state, zero per-token cost) are the four levers that take 2025–2026 models from ~130–160 KiB/token (Llama 3.1 8B, Mistral Small 3.2) down to 6–25 KiB/token (Nemotron 3 Nano, Qwen3-Next, Qwen3.5/3.6). Recurrent state is small per sequence (24–75 MiB for the models below) but is paid **per concurrent sequence** and in llama.cpp/vLLM lives in a separate pool with separate rollback/checkpoint rules.

### Cited Findings

**Formulas (as used by engines and analysts)**
- Standard GQA/MHA cache per sequence: `KV bytes = B × T × L_attn × 2 × H_kv × D × bytes`; MLA: `KV bytes = B × T × L × (kv_lora_rank + qk_rope_head_dim) × bytes` (2 bytes for BF16) — [Kaitchup, 2026-03-18](https://kaitchup.substack.com/p/the-kv-cache-of-small-moes-qwen3).
- vLLM's recurrent-state shapes (`mamba_utils.py`, main branch, fetched 2026-10): Mamba-2 temporal state = `(num_heads, head_dim, state_size)`, conv state = `(intermediate_size + 2·n_groups·state_size) × (conv_kernel − 1)`; Gated DeltaNet (Qwen3-Next family) temporal = `(num_v_heads, head_v_dim, head_k_dim)`, conv = `(head_k_dim·num_k_heads·2 + head_v_dim·num_v_heads) × (conv_kernel_size − 1)`; plain linear attention temporal = `(num_heads, head_dim, head_dim)` with no conv; KDA (Kimi Linear) keeps its recurrent state in **float32** by default; speculative decoding adds `num_spec` to conv length — [vllm/model_executor/layers/mamba/mamba_utils.py](https://github.com/vllm-project/vllm/blob/main/vllm/model_executor/layers/mamba/mamba_utils.py).
- llama.cpp pads `n_ctx` to a multiple of 256 (`GGML_PAD(cparams.n_ctx, 256)`); with a unified cache `n_ctx_seq = n_ctx`, otherwise `n_ctx_seq = n_ctx / n_seq_max` (re-padded to 256) — [src/llama-context.cpp](https://github.com/ggml-org/llama.cpp/blob/master/src/llama-context.cpp).
- llama.cpp SWA cache size: `PAD(n_swa·n_seq_max + n_batch)` — keeps the last `n_swa` tokens of every sequence plus one batch; pruned after each committed batch — [PR #13194, merged 2025-05-20](https://github.com/ggml-org/llama.cpp/pull/13194).
- llama.cpp KV quant storage: q8_0/q8_0 = 8.50 bits per weight, q8_0/q5_1 = 7.25 average (→ q5_1 = 6.0), q8_0/q4_0 = 6.50 average (→ q4_0 = 4.5); 34 KiB/token for a Qwen3.8-27B at q8_0/q8_0 — [llama.cpp discussion #23470, 2026-05/09](https://github.com/ggml-org/llama.cpp/discussions/23470) [measured].

- The Gemma 3 27B row uses `sliding_window_pattern` 6 → layers 6, 12, …, 60 global (10 global, 52 local). Per-layer cost is 2 × 16 × 128 × 2 B = 8 KiB/token; the ~6× saving matches the report's qualitative claim. A naive engine that caches local layers over the full context (what llama.cpp's `--swa-full` does) loses the whole saving.
- Llama 4's chunked attention (`attention_chunk_size` 8192) is block-local, so an engine can cap the 36 RoPE layers at one 8192-token chunk per sequence; llama.cpp handles Llama 4 with its iSWA cache (`llm_build_llama_iswa`, PR #13194). The 10M-token context is not a local-hardware target: even the 12 global layers alone need 480 GiB at 10M.
- MLA matters only if the engine implements weight absorption / "MQA mode": the expanded-per-head cache for DeepSeek-V3.2 would be 128 × (192 + 128) × 2 B × 61 ≈ 4.8 MiB/token (≈ 610 GiB at 128K). The DSA indexer adds one `index_head_dim`-wide key per token per layer (7.8 KiB/token at FP8), i.e. ≈11% on top of the bf16 latent cache, and llama.cpp stores it as a second cache inside `llama_kv_cache_dsa` (see KQ3/KQ5).
- Recurrent states are paid per sequence, not per token: 32 concurrent Granite H-Small sequences hold 2.3 GiB of Mamba state before any token is cached; llama.cpp's `~75 MiB` checkpoint files for Qwen3-Coder-Next (issue #19794/#20225) are consistent with the Qwen3-Next-class GDN state stored in f32 (37.7 MiB in bf16 → 75 MiB in f32) — this is my inference; the issues do not state the dtype.
- Falcon-H1's parallel design does **not** reduce per-token KV versus a GQA-2 transformer of the same depth; only sequential hybrids (Granite, Nemotron, Qwen3-Next, Qwen3.5/3.6) cut the per-token term.
- For an 8 GB machine the only comfortable 128K single-stream targets in the table are the hybrids, gpt-oss-20b, and GQA models with q8_0/q4_0 KV; 24 GB machines fit 4 × 32K of Qwen3-8B at q8_0 (9.6 GiB) but not f16 (18 GiB).

### Gaps
- The Phi-4-mini-flash layer composition (how many SWA vs Mamba layers; Mamba state dims) is not in the config (custom modelling code) and the paper excerpt did not list it; the row above assumes 8 SWA layers of 16 self-decoder layers.
- NemotronH conv-state size depends on the SSM intermediate size (heads × head_dim = 4096 vs `expand × hidden` = 5376); the table uses 4096. Not verified against NVIDIA's code.
- IBM's ">70% RAM reduction" is a chart without stated context length, batch, or hardware; no independent measurement was found.
- The Gemma 3 report's 60% vs 15% "overhead" baseline is not defined on the page fetched.
- Qwen3.5/3.6 and GLM-4.7-Flash numbers (20,480 and 54,144 B/token) come from a third-party article and were not checked against config files.

## KQ2. KV-cache quantization: q8_0/q4_0 in llama.cpp, KIVI, KVQuant, QuaRot/SpinQuant, PolarQuant, TurboQuant, engine implementations, accuracy/speed, flash-attention requirements

### Takeaway
As of October 2026 the production-safe choices are 8-bit (llama.cpp q8_0 with the Hadamard "attn-rot" merged 2026-04; vLLM FP8 on tensor-core GPUs) — both within noise of F16/BF16 on most measurements — while 4-bit and below are model-dependent: llama.cpp q4_0 on K collapses some models (Qwen2.5-7B PPL 7.96 → 1,561) while 4-bit V is nearly free; TurboQuant's own "3-bit, no loss" claim did not survive vLLM's long-context/reasoning study (4-bit variant loses 1–4 points and costs 10–68% latency; 3-bit variants lose up to 20 points), and llama.cpp closed the TurboQuant PR as not better than same-bpw formats. Quantized V in llama.cpp requires flash attention, and backend kernel coverage (Metal: K and V must share a type; CUDA: some combos need `GGML_CUDA_FA_ALL_QUANTS`) silently decides whether you get GPU speed or a 25× CPU fallback.

### Cited Findings

- "attn-rot" (merged 2026-04-01, ggerganov): a normalized Hadamard rotation is applied to Q/K/V before the KV cache is written (64×64 blocks for V, separately for K and V), attention runs in the rotated space, output rotated back; backend-agnostic, no new tensor types, **MLA not supported**; env `LLAMA_ATTN_ROT_DISABLE` turns it off. Quality: gpt-oss-20b AIME25 ×8 (low reasoning) F16 37.9%, Q8_0 KV 31.7% → 37.1% with rotation, Q4_0 KV 2.0% → 21.7%; Qwen3.5-9B q4_0/q4_0 KLD 0.00798 → ≈0.0048; Qwen3-0.6B q4_0 PPL 62.0 → 46.3. Speed (CUDA, Qwen3-30B-A3B Q4_0, q4_0 KV): pp 0.97–0.99× master, tg 0.88× (depth 0) to 0.93× (depth 32K) — [llama.cpp PR #21038](https://github.com/ggml-org/llama.cpp/pull/21038) [measured by contributors].

**TurboQuant (Google, 2025–2026)**
- Paper (submitted 2025-04-28; Zandieh, Daliri, Hadian, Mirrokni): random rotation → concentrated Beta-distributed coordinates → optimal scalar quantizer per coordinate; inner products via MSE quantizer + 1-bit QJL residual; "absolute quality neutrality with 3.5 bits per channel" and "marginal quality degradation with 2.5 bits per channel"; data-oblivious (no calibration); within ≈2.7× of information-theoretic lower bound — [arXiv 2504.19874](https://arxiv.org/abs/2504.19874) [vendor-claimed].
- Google Research blog (2026-03-24): "quantize the key-value cache to just 3 bits without requiring training or fine-tuning"; "key value memory size by a factor of at least 6x" on needle-in-haystack; 4-bit gives "up to 8x performance increase over 32-bit unquantized keys" for attention-logit computation on H100; benchmarks LongBench, NIAH, ZeroSCROLLS, RULER, L-Eval on Gemma/Mistral/Llama-3.1-8B-Instruct; combines PolarQuant + QJL; "to be presented at ICLR 2026"; PolarQuant at AISTATS 2026 — [research.google blog](https://research.google/blog/turboquant-redefining-ai-efficiency-with-extreme-compression/) [vendor-claimed; the 8× is logits-only vs **32-bit** keys].
- vLLM study (2026-05-11, vLLM 0.20.2, Qwen3-30B-A3B on 2×H100, Llama-3.3-70B on 4×H100, also Qwen3-30B-Thinking and MiniMax-M2.7): enable with `--kv-cache-dtype turboquant_k8v4 | turboquant_4bit_nc | turboquant_k3v4_nc | turboquant_3bit_nc`; capacity FP8 2×, k8v4 ≈2.4×, 4bit-nc up to 3.4×; accuracy recovery on Qwen3-30B-Thinking reasoning: FP8 and k8v4 >98%, 4bit-nc ≈96%, k3v4-nc/3bit-nc drop ≈20 points; MRCR long-context AUC Qwen3-30B-Instruct: BF16 45.8%, FP8 43.1%, k8v4 43.0%, 4bit-nc 42.3%, k3v4-nc 33.5%, 3bit-nc 31.2%; latency vs BF16: FP8 ≈0 overhead, TurboQuant +10–60% (Qwen3-30B) / +10–68% (Llama-70B); throughput 66–80% of BF16; burst TTFT Llama-70B P99: BF16 ≈17 s, TurboQuant <3.5 s, FP8 ≈1.3 s. Recommendations: FP8 is the best default; k8v4 "no significant advantage over FP8"; 4bit-nc is a memory-for-throughput trade to validate per workload; avoid 3-bit variants — [vLLM blog](https://vllm.ai/blog/2026-05-11-turboquant) [measured].
- AMD (2026-06-11, 2× MI355X TP=2, MiniMax M2.5 / Qwen 3.5 35B A3B / GPT-OSS 120B): open-source vLLM TurboQuant kernels reached ≈32% of BF16 throughput at 32K/1K, C=64; AMD's HIP kernel ≈89%, FlyDSL 4-bit kernel ≈95% of BF16 and 88% of FP8-KV; ≈3.8× KV compression for TQ4/4; agentic workload P50 TTFT 13.9 s (FP8) → 0.89 s (TQ4/4), throughput 1.63×, cache hit rate 5.3% → 67.7%; helps only under KV-capacity pressure, MLA unsupported, 3-bit variants "degrade accuracy on some tasks" — [AMD ROCm blog](https://rocm.blogs.amd.com/artificial-intelligence/turboquant-vllm-agentic/README.html) [measured by vendor; internally inconsistent on FlyDSL-vs-BF16].
- llama.cpp PR #21089 (TBQ3_0 ≈3.06 bpw, TBQ4_0 ≈4.06 bpw, CPU only; Qwen3.5-4B, ctx 256, 4 wikitext chunks): f16 PPL 13.8387 / 64 MiB; q8_0 13.8348 / KLD 0.0032 / 34 MiB; q4_0 13.8400 / 0.0091 / 18 MiB; tbq3_0 14.3198 / 0.0265 / 12.25 MiB; tbq4_0 13.8323 / 0.0096 / 16.25 MiB; generation roughly halved (8.3 vs 15.7 tok/s). **Closed unmerged 2026-06-02**; maintainers: no KLD advantage over same-bpw quants, "the Hadamard rotation novelty is already upstream" — [llama.cpp PR #21089](https://github.com/ggml-org/llama.cpp/pull/21089) [measured, tiny context].
- vllm-metal (vLLM on Apple Silicon via MLX + Metal kernel): TurboQuant enabled with `VLLM_METAL_USE_PAGED_ATTENTION=1` and `--additional-config '{"turboquant": true, "k_quant": …, "v_quant": …}'`; keys per-block affine q8_0 (default)/q5_0/q4_0/int2, values Lloyd-Max 2/3 (default)/4/5/8-bit; cache-size reductions vs fp16 (Qwen3-0.6B shape): q8_0/q3_0 2.56×, q4_0/q3_0 3.76×, uint2/q3_0 4.92×; qualitative: q8_0/q3_0 "matches bf16 within noise", int2/q2_0 degenerates; requires paged attention; only SDPA layers compressed in hybrid models; MLA raises `NotImplementedError`; head dims 64/128/256 only; no speed numbers — [vllm-metal docs](https://docs.vllm.ai/projects/vllm-metal/en/latest/turboquant/) [vendor-claimed, no hardware named].
- Third-party plugin README claims GQA/MHA TurboQuant was upstreamed in vLLM PR #38479 on 2026-04-15 — [Alberto-Codes/turboquant-vllm](https://github.com/Alberto-Codes/turboquant-vllm) [unverified; the vLLM blog itself does not name the PR].

**Academic methods (mostly background)**
- KIVI (2024-02, ICML 2024): per-channel keys, per-token values, 2-bit, tuning-free; 2.6× lower peak memory, up to 4× batch, 2.35–3.47× throughput on Llama/Falcon/Mistral — [arXiv 2402.02750](https://arxiv.org/abs/2402.02750) [background, vendor-claimed]. Rival papers report plain 2-bit KIVI well below FP16 on GSM8K/MATH for Qwen3/Llama3 (Kitty, 2025-11) and Wiki2 PPL 5.47 → 6.42 for 2-bit KIVI* on Llama-2-7B (XQuant) — [Kitty, arXiv 2511.18643](https://arxiv.org/pdf/2511.18643); [XQuant, arXiv 2508.10395](https://arxiv.org/pdf/2508.10395) [self-reported by competitors].
- KVQuant (2024-01, NeurIPS 2024): per-channel pre-RoPE keys, non-uniform per-layer datatypes, dense-and-sparse outliers; "<0.1" PPL degradation at 3-bit; LLaMA-7B with 1M context on one A100-80GB, 10M on 8 GPUs; ≈1.7× kernel speedup — [arXiv 2401.18079](https://arxiv.org/abs/2401.18079) [background, vendor-claimed].
- QuaRot (2024-03): Hadamard rotations make weights/activations/KV outlier-free; 4-bit everything on LLaMA2-70B loses ≤0.47 Wiki2 PPL, ≈99% zero-shot retained — [arXiv 2404.00456](https://arxiv.org/abs/2404.00456) [background]. (SpinQuant was not fetched; see Gaps.)
- PolarQuant (2025-02; Han, Kacham, Karbasi, Mirrokni, Zandieh): random preconditioning + recursive polar transform, quantize angles, no per-block zero-point/scale; ">4.2×" KV compression with best long-context quality among compared methods; no speed numbers in abstract — [arXiv 2502.02617](https://arxiv.org/abs/2502.02617) [vendor-claimed]. A second, differently-authored "PolarQuant" (key cache only, lookup-table decoding) exists — [arXiv 2502.00527](https://arxiv.org/html/2502.00527v1).
- FP8 KV on hybrids: vLLM's FP8 KV gives 2.00× capacity on attention-only models but 1.84× (32K) → 1.00× (≤1K) on Falcon-H1 because the bf16 Mamba page dominates block alignment; "SGLang and Quamba2 already use int8 for state" — [vLLM RFC #55196](https://github.com/vllm-project/vllm/issues/55196) [measured].

### Inferences
- Error asymmetry is structural: key error is amplified through softmax, value error averages out (vllm-metal says this explicitly and the #23470 K-only collapse confirms it). An engine should expose K and V precision separately, default to 8-bit K (or FP8 where tensor cores exist) and allow 4-bit V, and should never ship 4-bit K without a per-model guard (a quick KLD or answer-churn test on load would catch Qwen2.5-class failures).
- A rotation (Hadamard, per 64-wide block) before quantizing the cache is now the cheap, type-agnostic baseline (llama.cpp mainline); TurboQuant-style codebooks add little over rotated q4_0 at the same bits (llama.cpp PR data) and cost 2× in decode without hand-tuned kernels (vLLM, AMD data). For a new engine: implement rotation + simple block formats first; treat sub-4-bit codebook quantization as optional.
- Bits/token budget examples (Qwen3-8B, 128K): f16 18 GiB, q8_0 9.6 GiB, q8_0K/q4_0V 7.3 GiB, q4_0 5.1 GiB, 3-bit-class 3.4 GiB; the step from 8.5 → 6.5 bpw is where quality is still near-lossless.
- Every quantized-V path must run through the fused attention kernel (dequant inside the kernel); the engine's kernel matrix must be explicit per backend (head dims × K type × V type × mask/sink flags) and must fall back loudly, not silently to CPU.
- Quantizing recurrent state (int8 as SGLang/Quamba2 do) is the only way FP8/INT8 KV pays off on hybrids at short contexts; otherwise it only helps at ≥8K.

### Gaps
- SpinQuant (learned rotations) was not fetched; no 2025–2026 KV-specific SpinQuant numbers collected.
- Which exact K/V type pairs have CUDA FA kernels by default in llama.cpp (vs needing `GGML_CUDA_FA_ALL_QUANTS`) was not confirmed from source; only the asymmetric q8_0/q4_0 fallback is documented in #24485.
- The hardware for discussion #23470's main run is not stated.
- No independent (non-vendor, non-competitor) benchmark comparing KIVI, KVQuant, PolarQuant and TurboQuant on the same 2025–2026 models was found; "Ablation, Statistical Inference, and Validation for KV-Cache Compression" (arXiv 2607.09683) and "KVLinC" (arXiv 2510.05373) appeared in search results but were not read.
- Whether vLLM upstream TurboQuant kernels have improved since 2026-05 (AMD's custom kernels suggest a 3× headroom) is unknown.

## KQ3. Paged and virtual memory for KV: PagedAttention, block tables, RadixAttention, vLLM V1 prefix caching, llama.cpp unified/SWA/DSA caches and 2025–2026 refactors, CUDA VMM growth (vAttention, kvcached), fragmentation on Metal unified memory and CPUs

### Takeaway
Server engines converged on fixed-size token blocks (vLLM: block tables + parent-chained SHA-256 block hashes, one block pool shared by all layer groups; SGLang: token-granular radix tree + LRU) while llama.cpp still pre-allocates one contiguous `n_ctx × n_seq_max` buffer per layer (unified or split per slot) with a separate windowed cache for SWA layers, a recurrent-state pool for hybrids, and a two-cache wrapper for DSA; a community paged-KV design (April 2026, draft PR #22569) showed 2.5× more sequences on an A10G but is unmerged. CUDA VMM-based growth (vAttention, kvcached, 2 MiB physical pages) is NVIDIA/ROCm-only; on Metal the allocator itself is the hazard (MLX's buffer pool retained ~74 GB of dead buffers at 1M context) and the practical answer is one up-front reservation carved into blocks.

### Cited Findings
- PagedAttention/vLLM (SOSP 2023): KV memory "significantly wasted by fragmentation and redundant duplication" in prior systems; vLLM "near-zero waste"; 2–4× throughput vs FasterTransformer/Orca — [arXiv 2309.06180](https://arxiv.org/abs/2309.06180) [background, vendor-claimed].
- vLLM V1 prefix caching design: block hash = `hash(parent_hash, block token ids, extra keys)` where extra keys include LoRA ID, multimodal image hashes and `cache_salt`; only full blocks are hashed; default hash algorithm is `sha256` since v0.11 (`--prefix-caching-hash-algo sha256 | sha256_cbor | xxhash | xxhash_cbor`; the doc warns xxhash "raise[s] collision risk … [may] leak private information in multi-tenant setups"); pre-allocated `KVCacheBlock` pool with `ref_cnt`, a doubly-linked free queue (LRU eviction from head; a request's last block is freed first), hash→block map; "almost a free lunch" — [vLLM design doc](https://docs.vllm.ai/en/stable/design/v1/prefix_caching.html).
- vLLM hybrid KV-cache manager: all layer types share one pool of equal-size blocks; layers grouped by attention type; regular ratios (Gemma-2 1:1, Llama 4 3:1) reuse block IDs across a repeating unit; Mamba layers force attention `block_size` up to match the state size (can exceed 400 tokens, "too large"); sliding-window layers free blocks outside the window into the shared LRU queue; prefix-cache hits for SWA only need the last `sliding_window − 1` tokens; `HybridKVCacheCoordinator` supports exactly two groups, one of which must be full attention; Mamba prefix caching is "work in progress" — [vLLM hybrid KV cache manager doc](https://docs.vllm.ai/en/latest/design/hybrid_kv_cache_manager.html).
- SGLang RadixAttention: radix tree over token sequences holding prompts and outputs, LRU eviction, cache-aware scheduling; "up to 6.4× higher throughput" on agent/RAG/multi-turn workloads — [SGLang paper, 2023-12/2024-06](https://arxiv.org/abs/2312.07104) [background, vendor-claimed]. Token-granular matching vs vLLM's block-boundary matching (often 16 tokens) is the usual comparison — [Momento blog](https://www.gomomento.com/blog/vllms-hash-chain-and-why-prefix-caching-is-still-prefix-caching/) [secondary].
- llama.cpp unified cache: `--kv-unified` "use single unified KV buffer shared across all sequences (default: enabled if number of slots is auto)"; `--parallel N` default −1 = auto; `--ctx-size` 0 = from model; `--defrag-thold` is DEPRECATED — [tools/server/README.md](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md). Padding/sizing in [llama-context.cpp](https://github.com/ggml-org/llama.cpp/blob/master/src/llama-context.cpp) (see KQ1).
- llama.cpp SWA cache (PR #13194, merged 2025-05-20): `llama_kv_cache_unified_iswa` wraps two unified caches (non-SWA layers, SWA layers); SWA cache sized `PAD(n_swa·n_seq_max + n_batch)` and pruned after each commit; "advanced cache operations such as removing tokens or shifting their positions are not possible when using SWA cache"; `--swa-full` falls back to a full-size SWA cache — [PR #13194](https://github.com/ggml-org/llama.cpp/pull/13194). A fork's quote of later code says the SWA size uses `n_ubatch`, is capped at the base size and padded to 256 — [ik_llama.cpp issue #1607](https://github.com/ikawrakow/ik_llama.cpp/issues/1607) [unverified against mainline].
- llama.cpp DSA cache (PR #23346, merged 2026-05-29): `llama_kv_cache_dsa` wraps two `llama_kv_cache` instances — one for MLA latents, one for lightning-indexer keys; sparsity is applied by masking KQ entries the indexer did not select; the generic indexer "uses very large compute buffers, so long contexts or large ubatch sizes can run out of memory"; tested on CUDA (RTX PRO 6000 Blackwell, experts in CPU RAM) and CPU; Metal/Vulkan not mentioned — [PR #23346](https://github.com/ggml-org/llama.cpp/pull/23346); shipped in [release b9411](https://github.com/ggml-org/llama.cpp/releases/tag/b9411).
- llama.cpp paged-KV proposal (discussion opened 2026-04-15, draft PR #22569 2026-05-01): motivation "the unified KV cache preallocates a contiguous `n_ctx × n_seq_max` buffer per layer … concurrency ceiling depends on maximum context rather than average use"; A10G, Llama-3 8B f16: unified OOM at 26 sequences, paged reached 247 sequences at 1,256 vs 496 tok/s aggregate, ≈3% slower at 25 sequences; design: 16-token blocks, per-sequence block tables, GPU+CPU pools with watermarks/refcounts/swapping, `llama_kv_cache_paged` as a parallel `llama_memory_i`, FCFS token-budget scheduler; Phase 1 excludes SWA (gemma3, llama4), multi-device, partial offload; no maintainer reply; a prototype of prefix sharing on the unified cache reported ≈2.5× more slots at fixed VRAM — [llama.cpp discussion #21961](https://github.com/ggml-org/llama.cpp/discussions/21961) [measured by proposer].
- vAttention (ASPLOS 2025): CUDA VMM APIs keep KV contiguous in virtual memory while physical pages arrive on demand; existing attention kernels run unchanged; "up to 1.23×" throughput over PagedAttention-based FlashAttention/FlashInfer kernels — [arXiv 2405.04437](https://arxiv.org/abs/2405.04437) [vendor-claimed; hardware/models not on abstract page].
- kvcached (Apache-2.0, v0.1.6, 2026-10): engines reserve virtual GPU address space up front and physical memory is mapped as tokens arrive; default physical page 2 MiB (`KVCACHED_PAGE_SIZE_MB` override, larger multiples when a KV block exceeds 2 MiB); supports SGLang ≥0.5.11 and vLLM ≥0.17.0 (tested to 0.30.0), PyTorch ≥2.10; "2–28× TTFT reduction" with three Llama-3.1-8B models sharing one A100-80G under bursty load; ROCm supported with non-contiguous layout — [github.com/ovg-project/kvcached](https://github.com/ovg-project/kvcached) [vendor-claimed].
- MLX Metal allocator: issue #3350 (2026-04-01, Mac Studio M2 Ultra 128 GB, MLX 0.31.2-dev, 1M-token request): footprint 108 GB vs ≈34 GB expected (3 GB weights + 30.5 GB KV); freed buffers "are never returned to the OS" when sizes keep growing, the pool is capped only by `max_pool_size_` (defaults to the block limit, ≈192 GB), `MLX_METAL_CACHE_LIMIT=4GB` did not help because it applies after a successful allocation, GC triggers only near `gc_limit_` (≈107 GB); workaround `mx.clear_cache()` after each request or `mx.set_cache_limit()` at startup; closed without a linked fix — [MLX issue #3350](https://github.com/ml-explore/mlx/issues/3350) [self-reported]. API: `set_memory_limit`, `set_cache_limit` ("limit on free cached memory"), `set_wired_limit`, `clear_cache`, `get_active_memory`, `get_peak_memory`, `get_cache_memory` — [MLX memory management docs](https://ml-explore.github.io/mlx/build/html/python/memory_management.html).
- llama.cpp hybrid/recurrent memory field reports: partial `seq_rm` on recurrent state fails, so the server "forc[es] full prompt re-processing" on Qwen3-Next/Qwen3-Coder-Next/Qwen3.5 turns; a Qwen3.5-27B user saw ≈8-minute stalls per turn of a 15K-token chat; erased checkpoints of ≈75 MiB at positions 16,485 and 19,255 (size independent of position) — [issue #20225](https://github.com/ggml-org/llama.cpp/issues/20225), [issue #21831](https://github.com/ggml-org/llama.cpp/issues/21831), [issue #19794](https://github.com/ggml-org/llama.cpp/issues/19794), [issue #18497](https://github.com/ggml-org/llama.cpp/issues/18497) [self-reported]. PR #28123 adds recurrent-state rollback so MTP drafting need not copy state to host RAM every round — [PR #28123](https://github.com/ggml-org/llama.cpp/pull/28123) [status unverified].
- Per-slot recurrent state multiplies with parallel slots and lives outside the unified KV buffer (Jan, Qwen3.8 + MTP, 4 auto slots → 2–4× slowdown from VRAM spill) — [janhq/jan issue #9183](https://github.com/janhq/jan/issues/9183) [self-reported].

### Inferences
- For a Rust engine on Metal/CPU unified memory: reserve the KV arena once (sized from the model's per-token formula × configured budget), carve it into fixed token blocks (16–64 tokens; vLLM's hybrid doc shows why a single page size across layer groups is painful — pick the attention block so that Mamba/GDN state pages are integer multiples, or keep separate pools as llama.cpp does), and never grow by reallocating — MLX #3350 shows what a growing-buffer pattern does to a Metal pool. Keep the arena in one `MTLBuffer`/`MTLHeap` so there is nothing for the driver to fragment; on CPU use one large anonymous mapping (optionally `madvise`/huge pages) and free blocks by index, not by `free()`.
- Block tables cost little on the kernel side if the attention kernel takes a block table (FlashAttention-2 `block_table` requires page size multiple of 256; FlashInfer and MLX's vector kernel take contiguous K/V — see KQ5), so on Metal/CPU where the engine owns its kernels, a block-table-aware kernel is the natural fit and avoids llama.cpp's "max context × max slots" reservation.
- Prefix sharing should be hash-chained per block (vLLM) rather than a radix tree only if the engine wants O(1) lookups and simple multi-modal/LoRA keys; a radix tree gives token-granular reuse for agent branches. Either way SWA and recurrent layers need their own rules: SWA blocks older than the window are freeable (vLLM), and recurrent state must be checkpointed at block boundaries to allow rollback (llama.cpp's `--ctx-checkpoints`, KQ6).
- CUDA VMM growth is worth it only for the optional CUDA backend when sharing a GPU with other processes; it does not apply to Metal (no equivalent API documented) or CPU.
- The DSA cache is a template for "two caches per layer group" (latents + indexer keys) that the memory manager must treat as one unit for allocation, eviction and save/restore.

### Gaps
- No documentation was found on how ggml's Metal backend allocates KV buffers (heap vs individual buffers) or on fragmentation inside ggml on Metal; the only Metal allocator evidence is MLX's.
- The exact current llama.cpp SWA-cache sizing formula (post-2025 refactor) was not verified from mainline source.
- Whether llama.cpp's draft paged-KV PR #22569 has progressed beyond August 2026 is unknown.
- SGLang's handling of hybrid (Mamba) models in the radix cache was not researched.
- vAttention hardware/model details and license were not confirmed (abstract page only).

## KQ4. Runtime KV eviction and compression: StreamingLLM sinks, H2O, SnapKV, PyramidKV, token merging, KV offload to RAM/SSD (LMCache etc.), and what production local engines actually use

### Takeaway
Production local engines ship almost none of the attention-score eviction literature: what they ship is (a) sink-plus-window truncation (llama.cpp context shift, off by default; mlx-lm rotating cache; learned sinks baked into gpt-oss), (b) offload/tiering rather than lossy eviction (llama.cpp host-RAM prompt cache with checkpoints, vLLM OffloadingConnector, SGLang HiCache, LMCache), and (c) quantization (KQ2). SnapKV/PyramidKV/H2O remain research code whose benchmarks come from competing papers; no local engine was found implementing them.

### Cited Findings
- StreamingLLM (ICLR 2024): keeping the KV of the first tokens ("attention sink") plus a sliding window restores window-attention quality; stable up to ~4M tokens on Llama-2/MPT/Falcon/Pythia; up to 22.2× faster than sliding-window recomputation — [arXiv 2309.17453](https://arxiv.org/abs/2309.17453) [background, vendor-claimed]. gpt-oss bakes the sink in as "a learned bias in the denominator of the softmax" — [gpt-oss model card](https://arxiv.org/abs/2508.10925); MLX's SDPA and llama.cpp FA both accept sinks (KQ5).
- SnapKV (2024-04): per-head selection of clustered important positions from an observation window at the end of the prompt, before decoding; "3.6× increase in generation speed and 8.2× memory efficiency" at 16K; 380K context on one A100-80GB with HF code — [arXiv 2404.14469](https://arxiv.org/abs/2404.14469) [background, vendor-claimed].
- PyramidKV (2024-06, v4 2025-05): layer-wise budgets (more cache in lower layers); matches full KV on LongBench with 12% of the cache; with 0.7% of the cache up to +20.5 points on TREC vs baselines; LLaMA-3-70B NIAH 100.0 with 128 entries — [arXiv 2406.02069](https://arxiv.org/abs/2406.02069) [background, vendor-claimed]. A 2025 paper's LongBench table has SnapKV ≈38.9, PyramidKV ≈38.3, H2O ≈35.7, StreamingLLM ≈34.6 (its own method ≈40.2; budget not visible) — [Lookahead Q-Cache, arXiv 2505.20334](https://arxiv.org/pdf/2505.20334) [self-reported].
- A 2026 characterization study compares vLLM, InfiniGen and H2O (offloading, eviction heuristics, speculative scheduling) on latency/throughput/memory across request rates, model sizes and sparsity — [arXiv 2604.05012](https://www.alphaxiv.org/abs/2604.05012) [abstract only].
- llama.cpp context shift: `--context-shift` "whether to use context shift on infinite text generation (default: disabled)"; `--keep N` "number of tokens to keep from the initial prompt (default: 0, −1 = all)" — [server README](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md); the server implementation discards `n_discard = n_left / 2` tokens after the kept prefix and shifts the rest with `llama_kv_cache_seq_shift` — [commit "server : fix context shift (#5195)"](https://cdn04132025.gitlink.org.cn/replica/llama.cpp/commit/e6f291d15844398f8326940fe5ad7f2e02b5aa56) [background; replica of upstream commit]. SWA caches cannot shift/remove tokens — [PR #13194](https://github.com/ggml-org/llama.cpp/pull/13194).
- mlx-lm: `--max-kv-size n` "enables a rotating fixed-size key-value cache" (512 uses very little RAM at lower quality; 4096+ better); `--prefill-step-size` default 2048 trades peak memory vs prompt speed — [mlx-lm README](https://github.com/ml-explore/mlx-lm/blob/main/README.md).
- llama.cpp host-RAM prompt cache (PR #16391, merged 2025-10-09): automatic offload of prompt state to system RAM with prefix-similarity matching and hot-swap into the context; `--cache-ram` default 8192 MiB (−1 unlimited, 0 off); also caps cached tokens at the context size; works for dense, MoE, SWA and SSM models; incompatible with multimodal (`server_tokens` not copyable); default context checkpoints raised 3 → 8 — [PR #16391](https://github.com/ggml-org/llama.cpp/pull/16391). Current flags: `--ctx-checkpoints N` "max number of context checkpoints to create per slot (default: 32)", `--checkpoint-min-step N` "minimum spacing between context checkpoints in tokens (default: 8192)", `--cache-idle-slots` (default enabled, requires cache-ram) — [server README](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md).
- vLLM native CPU offload (`OffloadingConnector`, V1 only): inactive blocks move to a pre-allocated pinned CPU pool with LRU eviction; D2H/H2D on separate streams overlapping compute; `kv_connector_extra_config` has `cpu_bytes_to_use`, `blocks_per_chunk`, `spec_name: CPUOffloadingSpec`; a `TieringOffloadingSpec` adds filesystem tiers — [vLLM-Ascend feature guide (mirrors upstream connector)](https://docs.vllm.ai/projects/ascend/en/latest/user_guide/feature_guide/kv_cache_cpu_offload.html); llm-d lists the native connector plus LMCache/Mooncake/NVIDIA KVBM — [llm-d KV offloader doc](https://llm-d.ai/docs/architecture/advanced/kv-management/kv-offloader) [upstream vLLM page returned 404 twice; see Gaps].
- SGLang HiCache: three tiers (GPU, host "private to a single inference instance", external `hf3fs | mooncake | nixl | aibrix | file | dynamic`); flags `--enable-hierarchical-cache`, `--hicache-ratio` (host = N × GPU), `--hicache-size` GB, `--hicache-write-policy write_through`, `--hicache-io-backend kernel | direct`, `--hicache-mem-layout page_first | page_first_direct | layer_first`, `--hicache-storage-prefetch-policy best_effort | wait_complete | timeout`; no benchmark numbers on the page — [SGLang HiCache best practices](https://docs.sglang.io/advanced_features/hicache_best_practices.html).
- LMCache (Apache-2.0): tiers GPU → pinned CPU DRAM → local disk/NVMe GDS → remote (Redis/Valkey, Mooncake, InfiniStore, S3, NIXL); default chunk 256 tokens; connector hooks vLLM's paged KV manager; pluggable KV transformation (compression, token dropping); no numeric TTFT/throughput on the pages fetched — [LMCache repo](https://github.com/LMCache/LMCache), [architecture doc](https://docs.lmcache.ai/developer_guide/architecture.html).
- Edge-device research keeps a persistent Q4 KV cache across agents in MLX and documents a pitfall: tensors loaded from disk read as zeros unless evaluated after load — [arXiv 2603.04428](https://arxiv.org/pdf/2603.04428) [self-reported].

### Inferences
- For LLMario's targets (single machine, few concurrent requests), the high-value pieces are: (1) sink+window truncation as an explicit opt-in with chat-boundary-aware cut points (llama.cpp's default is off for a reason: it changes outputs and breaks SWA/recurrent models); (2) host-RAM and SSD tiers for whole prompt states keyed by prefix hash (llama.cpp `--cache-ram`, LMCache), which are lossless; (3) quantization. Score-based eviction (SnapKV/PyramidKV) is only worth adding behind a flag for prefill-heavy RAG, and must be validated per model because the published comparisons are all self-reported.
- Checkpointing (snapshot of SWA window + recurrent state every N tokens) is what makes truncation/rollback possible on Gemma-3/Qwen3-Next-class models; the engine should treat a "checkpoint" as a first-class object sized `SWA fixed part + recurrent state` (e.g., Gemma 3 27B ≈416 MiB, Qwen3-Next ≈38–75 MiB) and budget them (llama.cpp default 32 per slot, ≥8192 tokens apart).
- SSD offload is bandwidth-bound: a 128K Qwen3-8B f16 state is 18 GiB; at ~3 GB/s NVMe that is ~6 s to restore versus ~10 s prefill on an A100 (SOTAAZ) and far longer on consumer GPUs, so disk tiers pay off most on slow-prefill hardware and with q8_0 states.

- Upstream vLLM's own `kv_offloading` documentation page could not be fetched (404 at two URLs); the connector description above comes from the Ascend plugin docs and llm-d.
- H2O's original paper was not fetched; its numbers appear only via competitors' tables.
- No token-merging (e.g., KV merging) engine implementation or 2025–2026 measurement was found in this session.
- No independent measurement of llama.cpp `--cache-ram` benefits was found (the PR gives none).

## KQ5. Attention kernels: FlashAttention 2/3/4, FlashInfer, Metal (llama.cpp, MLX SDPA), CPU flash attention, sparse-attention kernels (NSA, DSA, MInference), chunked prefill

### Takeaway
CUDA has a mature stack (FA2 BSD-3 with paged KV/GQA/sliding window/softcap; FA3 on Hopper 740 TFLOP/s FP16; FA4 on Blackwell 1,613 TFLOP/s BF16, `pip install flash-attn-4`; FlashInfer Apache-2.0 with paged/ragged/MLA/cascade/block-sparse kernels), but on Apple Silicon the only production fused kernels are ggml's Metal `flash_attn_ext` family (head sizes 32–576, same-type K/V, quantized K/V) and MLX's `sdpa_vector` (≤8 queries, 2-pass for long K) / `steel_attention` (prefill) with hard head-dim and mask constraints and an unfused fallback. Sparse attention exists in local engines only as llama.cpp's "generic" DSA (masking, no compute saving, large indexer buffers); NSA/MInference kernels are Triton/CUDA research code.

### Cited Findings
- FlashAttention repo (BSD-3-Clause): FA2 supports Ampere/Ada/Hopper, fp16/bf16, head dims up to 256, MQA/GQA, sliding window via `window_size`, softcap (2.6+), rotary and in-place KV update in `flash_attn_with_kvcache`, paged KV via `block_table` with page size a multiple of 256; FA3 beta for H100 (FP16/BF16 fwd+bwd, FP8 fwd, CUDA ≥12.3); FA4 "written in CuTeDSL and optimized for Hopper and Blackwell", `pip install flash-attn-4`, `from flash_attn.cute import …` — [github.com/Dao-AILab/flash-attention](https://github.com/Dao-AILab/flash-attention).
- FA3 (2024-07): 1.5–2.0× over FA2 on H100, "740 TFLOPs/s (75% utilization)" FP16, close to 1.2 PFLOPs/s FP8; warp specialization, async TMA, block quantization + incoherent processing — [arXiv 2407.08608](https://arxiv.org/abs/2407.08608) [background, vendor-claimed].
- FA4 (2026-03-05; Zadouri, Hoehnerbach, Shah, Liu, Thakkar, Dao): up to 1,613 TFLOPs/s BF16 on B200 (≈71% utilization), up to 1.3× over cuDNN 9.13 and 2.7× over Triton; async MMA pipelines, software-emulated exponential, conditional softmax rescaling, tensor memory and 2-CTA MMA; CuTe-DSL in Python with 20–30× faster compiles; paper text licensed CC BY-NC-SA 4.0 (code is in the BSD-3 repo) — [arXiv 2603.05451](https://arxiv.org/abs/2603.05451) [vendor-claimed].
- FlashInfer (MLSys 2025; Apache-2.0): block-sparse composable KV formats, JIT attention templates, paged/ragged KV, MLA kernels, cascade attention for shared prefixes, block-sparse and variable-block-sparse attention, FP8/FP4 for attention/GEMM/MoE, CUDA graphs; SM 7.5 through 12.x (RTX 50, DGX Spark); 29–69% inter-token-latency reduction vs compiler backends, 28–30% long-context latency reduction, 13–17% for parallel generation; used by SGLang, vLLM, MLC — [arXiv 2501.01005](https://arxiv.org/abs/2501.01005), [repo](https://github.com/flashinfer-ai/flashinfer) [vendor-claimed].
- MLX Metal SDPA dispatch (`scaled_dot_product_attention.cpp`, main, 2026-10): query length ≤ 8 → `sdpa_vector` (one pass) or `sdpa_vector_2pass` (when `k.shape(2) >= 1024` on some device classes, or GQA with ≥4096 keys; a GQA-specialized 2-pass needs no mask, no sinks, one query token, ≥8192 keys, factors 8/12/16); vector path requires `query_len × gqa_factor <= 32`; full attention → `steel_attention_*` (NAX variant for head dims {64, 96, 128, 256, 512} on NAX hardware; D=72/80 zero-padded to 96 under `MLX_SDPA_PAD_HEAD_DIM`); supported head dims: full {64, 72, 80, 96, 128, 192, 256} (+512 on NAX), vector {64, 96, 128, 192, 256, 512} plus (96,64) and (192,128); causal requires `q_len <= k_len`; sinks supported (`has_sinks`); unfused fallback whenever `has_fused_kernel` is false (e.g., head dims 192/256 without NAX below thresholds) — [mlx/backend/metal/scaled_dot_product_attention.cpp](https://github.com/ml-explore/mlx/blob/main/mlx/backend/metal/scaled_dot_product_attention.cpp). Correctness report: fused op gave wrong scores vs manual attention on MLX 0.31.2/M4 — [MLX issue #3585 (mirror)](https://upd.dev/ml-explore/mlx/issues/3585) [self-reported].
- ggml Metal FA: head sizes 32…576 (hk576/hv512 covers MLA decode), same-type K and V, quantized K/V types Q8_0/Q4_0/Q4_1/Q5_0/Q5_1 accepted, kernel libraries `FA_F16/F32/Q4_0…Q8_0` and `FA_VEC_*` (vector kernels for small query counts); `return has_simdgroup_mm; // TODO: over-restricted for vec-kernels` — [ggml-metal-device.m](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-metal/ggml-metal-device.m). Origin: PR #5021 (merged 2024-04-30) added `ggml_flash_attn_ext()` fusing scale/mask/softmax/V-matmul with online softmax on CPU ("ggml : online attention (CPU)"), Metal and CUDA; F16 KQ mask padded to 32, `n_kv` padded to 128; min `n_batch` 32 — [PR #5021](https://github.com/ggml-org/llama.cpp/pull/5021) [background].
- Third-party Metal FA: Draw Things' Metal FlashAttention 2.0 (Swift/C++), `mlx-mfa` (PyPI; backward 2.2–2.4× slower than Apple's SDPA-VJP at D=128), HF `kernels-community/metal-flash-sdpa` (PyTorch tensors; GQA/MQA, softcap, head dims 32–256) — [Draw Things blog](https://engineering.drawthings.ai/metal-flashattention-2-0-pushing-forward-on-device-inference-training-on-apple-silicon-fe8aac1ab23c), [mlx-mfa](https://pypi.org/project/mlx-mfa/), [metal-flash-sdpa](https://huggingface.co/kernels-community/metal-flash-sdpa) [self-reported].
- CPU flash attention numbers (llama.cpp CPU, 4 threads, Qwen3.5-4B Q4_K_M, ctx 256): prompt ≈50 tok/s f16 KV; TurboQuant types ≈46; generation 15.7 tok/s f16/q4_0 vs 8.3 TBQ — [PR #21089](https://github.com/ggml-org/llama.cpp/pull/21089) [measured, tiny context].
- NSA (ACL 2025): hierarchical sparse attention = coarse token compression + fine-grained selection (+ sliding branch, per the full paper), "arithmetic intensity-balanced" hardware-aligned kernels, "substantial speedups over Full Attention on 64k-length sequences" for decode/forward/backward — [arXiv 2502.11089](https://arxiv.org/abs/2502.11089) [vendor-claimed; secondary posts cite 11.6× decode]. Triton kernels for NSA, Gated DeltaNet (with a FlashQLA backend, 2026-07), Mamba2, KDA, GLA, RetNet, RWKV6/7, MLA, Mamba3 live in `fla-org/flash-linear-attention` (MIT; NVIDIA/AMD/Intel/Ascend; Metal not mentioned) — [flash-linear-attention](https://github.com/fla-org/flash-linear-attention).
- DSA in llama.cpp: "generic" implementation masks unselected tokens, so attention is still computed densely over the context; perplexity dense Q8_0 2.9115 vs sparse Q8_0 2.9126 (wiki.test, 4K chunks); pp512 ≈22–42 tok/s, tg ≈11 tok/s with experts in CPU RAM on an RTX PRO 6000; no long-context sparse-vs-dense timing; the indexer "is not yet a separate GGML op" — [PR #23346](https://github.com/ggml-org/llama.cpp/pull/23346) [measured, short context]. A port of DeepSeek V4 Flash reports Metal could not yet run DSA-based V3.2 — [Blob Blog](https://blog.teamblobfish.com/posts/deepseek-v4-flash-llama-cpp/) [unverified].
- MInference 1.0 (NeurIPS 2024): three offline-assigned sparse patterns per head (A-shape, vertical-slash, block-sparse), up to 10× lower prefill latency on an A100 for 1M-token prompts without fine-tuning — [arXiv 2407.02490](https://arxiv.org/abs/2407.02490) [background, vendor-claimed]. No local engine implementation found.
- Chunked prefill: vLLM V1 "chunked prefill is enabled by default whenever possible"; "Smaller values (e.g., 2048) achieve better ITL because there are fewer prefills slowing down decodes"; "Higher values achieve better time to first token (TTFT)"; recommends `max_num_batched_tokens > 8192` for small models on large GPUs; default preemption `RECOMPUTE` (lower overhead than `SWAP` in V1) — [vLLM optimization docs](https://docs.vllm.ai/en/latest/configuration/optimization.html). llama.cpp: `--batch-size` default 2048 (logical), `--ubatch-size` default 512 (physical) — [server README](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md); mlx-lm `--prefill-step-size` default 2048, "smaller steps lower peak memory during prompt reading but slow prompt processing" — [mlx-lm README](https://github.com/ml-explore/mlx-lm/blob/main/README.md). SOTAAZ measured TTFT at 32K prompt of 10.0 s (f16) on an A100 with llama.cpp's defaults — [SOTAAZ](https://sotaaz.com/post/llamacpp-server-kv-cache-quantization-en).

### Inferences
- The engine's kernel matrix (what the kernel must support to run the KQ1 models): head dims 64 (gpt-oss, Phi), 128 (most), 256 (Qwen3-Next, Gemma 3 uses 128), asymmetric 192/128 (DeepSeek MHA mode) and 576/512 (MLA absorbed decode); GQA ratios 2–32; causal + sliding-window/chunked masks; per-head sink logits (gpt-oss); logit softcap (Gemma 2 legacy); K/V in f16/bf16/q8/q4 with optional per-block rotation; block-table addressing. ggml's Metal list already covers all of these except block tables; MLX's fused path does not cover 576/512 or arbitrary masks, so MLX-style dispatch with an unfused fallback is the pattern to copy, with an explicit "fused kernel unavailable" diagnostic.
- Decode and prefill need different kernels on every backend (MLX: vector 1-pass/2-pass vs steel; ggml: `FA_VEC_*` vs `FA_*`); the 2-pass split-K decode kernel is what keeps long-context single-stream decode GPU-saturated, and its thresholds (≥1024/4096/8192 keys in MLX) are a tunable the engine should expose.
- Chunked prefill's memory effect is through the compute buffer (scales with `ubatch × hidden` and, for the DSA indexer, with `ubatch × context`), not the KV cache; a 512–2048-token ubatch bounds it. TTFT at 32K–128K on consumer hardware is tens of seconds, so prefix/prompt caching (KQ6) matters more than a few percent of kernel speed.
- Sparse attention is not yet a practical requirement for a local engine: the only sparse model family of interest (DeepSeek V3.2/V4) is 400–700 GB and llama.cpp's implementation yields no compute savings; implement the DSA cache layout for correctness later, not sparse kernels now.

- Whether vLLM/SGLang DSA kernels (FlashMLA sparse, DeepGEMM indexer) exist and their speedups were not fetched.
- MInference's license and any vLLM integration status were not verified.

## KQ6. Prompt caching across requests and across sessions (saved to disk), including security/isolation for a multi-request local API

### Takeaway
All three local stacks cache by token-prefix: llama.cpp (slot KV reuse `cache_prompt` default on, `--cache-reuse` KV shifting, host-RAM LRU `--cache-ram` 8 GiB default, periodic context checkpoints for SWA/recurrent models, and explicit `/slots/:id?action=save|restore` files of 1–4.4 GB per 100K-token session that cut per-message prefill from >1 min to ≈0.2 s on an RTX 3090), mlx-lm (`mlx_lm.cache_prompt` → `.safetensors`, no server persistence after PR #1405 was closed), and vLLM (SHA-256 block hashes with an optional per-request `cache_salt`). The security facts are concrete: cross-tenant prefix-hit timing leaks (CVE-2025-46570, AUC 0.99 with an 8-token prefix on vLLM <0.9.0), non-cryptographic hashes can leak private data via collisions (vLLM docs), and plaintext KV files can be inverted back to prompts (NDSS 2026 "Shadow in the Cache").

### Cited Findings
- llama.cpp server flags: `--cache-prompt` (default enabled; per-request `cache_prompt` "Re-use KV cache from a previous request if possible", default true, results "may not be bit-for-bit reproducible"); `--cache-reuse N` "min chunk size to attempt reusing from the cache via KV shifting, requires prompt caching"; `--cache-ram` default 8192 MiB; `--ctx-checkpoints` default 32 and `--checkpoint-min-step` default 8192; `--cache-idle-slots`; `--slot-save-path PATH` enabling `POST /slots/{id}?action=save|restore|erase` with a `filename` body; `--swa-full` — [server README](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md). A later blog notes `--checkpoint-every-n-tokens` was removed by PR #22929 on 2026-05-25 — [particula.tech](https://particula.tech/blog/prompt-reprocessing-swa-hybrid-models-kv-cache) [unverified].
- Persistent per-session KV with hooks (2026-03-15, RTX 3090 24 GB, Qwen 27B UD-Q4_K_XL, 100K ctx, `-np 1`): prefill per message >1 min without restore vs ≈0.2 s with restore; generation ≈30 tok/s either way; slot files ≈1 GB for short sessions, ≈4.4 GB near 100K tokens; `--swa-full` required for SWA models (Qwen 3.5) or the restored cache is not fully usable — [llama.cpp discussion #20572](https://github.com/ggml-org/llama.cpp/discussions/20572) [self-reported].
- Upstream declined automatic disk persistence; a proxy that snapshots prefixes claims 99 s → 1.8 s follow-ups on a 30K-token document — [hearth-llm](https://pypi.org/project/hearth-llm/), [ai-muninn blog](https://ai-muninn.com/en/blog/kv-cache-disk-restore-7x) [self-reported].
- Hybrid-model caveat: the server's checkpoint logic assumed SWA, so recurrent models repeatedly "forc[e] full prompt re-processing" despite matching prefixes (issues #20225, #21831, #19794) — [issue #20225](https://github.com/ggml-org/llama.cpp/issues/20225) [self-reported].
- mlx-lm: `mlx_lm.cache_prompt --model … --prompt - --prompt-cache-file file.safetensors`, then `mlx_lm.generate --prompt-cache-file …` ("The cached prompt is treated as a prefix to the supplied prompt"; model read from the cache) — [mlx-lm README](https://github.com/ml-explore/mlx-lm/blob/main/README.md). PR #1405 (`--prompt-cache-dir`: one safetensors per cached prompt + `manifest.json` with LRU order, model keys, tokens; restore on startup, save on `atexit`/`SIGTERM`) was closed unreviewed on 2026-08-21 ("the number of PRs is way beyond our capacity to review") — [mlx-lm PR #1405](https://github.com/ml-explore/mlx-lm/pull/1405).
- vLLM: `cache_salt` is folded into the first block's hash so "only requests with the same salt can reuse cached KV blocks … This prevents timing-based attacks where an adversary could infer cached content by observing latency differences", at no performance cost; default hash `sha256`; xxhash option carries collision/leak risk — [vLLM prefix caching design](https://docs.vllm.ai/en/stable/design/v1/prefix_caching.html).
- CVE-2025-46570 / GHSA-4qjh-9fv9-r85r (published 2025-05-28, CVSS 2.6 Low, fixed in 0.9.0 via PR #17045): a shared cached prefix shortens TTFT; with chunk-level matching an attacker on the same backend distinguishes hit/miss with AUC 0.571 for a 1-token prefix and 0.99 for 8 tokens — [OSV advisory](https://osv.dev/vulnerability/GHSA-4qjh-9fv9-r85r). The InputSnatch paper showed cleanly separable hit/miss prefill timings on a local LLaMA-2 70B — [arXiv 2411.18191](https://arxiv.org/pdf/2411.18191) [background].
- "Shadow in the Cache" (NDSS 2026): inversion, collision and injection attacks reconstruct user inputs from KV caches held in plaintext on servers; direct inversion needs invertible projections (works for MHA, underdetermined for GQA/MLA, mainly first layer), hence the collision/injection attacks; KV-Cloak (reversible matrix obfuscation + operator fusion) reduces reconstruction to "random noise" with minimal overhead — [arXiv 2508.09442](https://arxiv.org/abs/2508.09442) [vendor-claimed].
- LMCache/HiCache disk and remote tiers persist across process restarts (KQ4 sources).

### Inferences
- Cache key design for LLMario: `hash(model file digest + quant/KV types + rope/context params + chat-template + block tokens + parent hash + per-client salt)`; use a cryptographic hash (vLLM's own warning); the salt should be derived server-side per API key/session, not supplied by untrusted clients, so that one local user's agents share and other users do not.
- On-disk state is sensitive in proportion to the prompt: write save files with 0600 permissions under the app's data directory, include a header (model digest, token count, dtype, rotation flag) and refuse to restore on mismatch; treat SWA and recurrent models as needing full checkpoints (llama.cpp's `--swa-full` lesson) or store the checkpoint set rather than a window.
- Size planning: file size ≈ KQ1 bytes/token × tokens (+ recurrent state), so q8_0 saves roughly halve restore time; an SSD tier only beats re-prefill when `bytes / disk_bandwidth < prefill_time` — true for most consumer GPUs and all CPU-only runs at ≥16K tokens.
- Timing leaks matter for a local API only when it is exposed to multiple principals; the mitigation (salt-scoped reuse) is cheap and should be default-on whenever more than one API key is configured.

### Gaps
- No primary documentation of llama.cpp's slot save-file format or of validation performed on restore (model/params mismatch) was found.
- No measurement of save/restore throughput on Apple Silicon or CPU-only setups was found.
- Whether vLLM's `cache_salt` isolation is supported by the V1 engine in every current version was not re-checked (older docs said "not supported on V0").

## KQ7. Context extension at inference time: YaRN, RoPE scaling variants, iRoPE (Llama 4), and what the engine must support

### Takeaway
Shipping 2025–2026 models require the engine to implement, from metadata: plain RoPE with per-model θ (1e4 to 1e11), partial rotary (Qwen3-Next 25%), YaRN with its attention-scale term (Qwen3 opt-in factor 4; DeepSeek factor 40; gpt-oss factor 32), Llama-3-style piecewise frequency scaling (Llama 3.1 factor 8, Llama 4 factor 16), linear scaling with per-layer base frequencies (Gemma 3 global 1e6 ×8, local 1e4), NoPE layers (Llama 4 every 4th, Granite 4.0 everywhere) with Llama 4's inference-time attention temperature, plus the masks that go with them (sliding window, chunked). Static YaRN is applied by all open-source runtimes and degrades short prompts, so the factor must be a per-request/engine setting, not baked in.

### Cited Findings
- YaRN (2023-08, v3 2026-02): "10x less tokens and 2.5x less training steps than previous methods", extrapolates LLaMA far beyond pretraining length — [arXiv 2309.00071](https://arxiv.org/abs/2309.00071) [background].
- Qwen3-8B card: native 32,768; validated to 131,072 with YaRN; `rope_scaling: {rope_type: yarn, factor: 4.0, original_max_position_embeddings: 32768}` (regenerate GGUF after editing); llama.cpp flags `--rope-scaling yarn --rope-scale 4 --yarn-orig-ctx 32768`; "open-source frameworks apply a constant scaling factor regardless of input length … potentially impacting performance on shorter texts"; use factor 2.0 for typical 65,536 contexts; do not enable if average context ≤32K; `max_position_embeddings` 40,960 reserves 32,768 for output and 8,192 for prompts — [Qwen3-8B model card](https://huggingface.co/Qwen/Qwen3-8B).
- Qwen3-Next: native 262,144, YaRN factor 4 → 1,010,000 validated; factor 2.0 suits ≈524K — [model card](https://huggingface.co/Qwen/Qwen3-Next-80B-A3B-Instruct); `partial_rotary_factor` 0.25 (64 of 256 dims rotated), `rope_theta` 1e7 — [config.json](https://huggingface.co/Qwen/Qwen3-Next-80B-A3B-Instruct/blob/main/config.json).
- DeepSeek-V3.2-Exp: YaRN factor 40, `beta_fast` 32, `beta_slow` 1, `mscale` 1.0, `mscale_all_dim` 1.0, original 4096, `rope_theta` 10000, max 163,840 — [config.json](https://huggingface.co/deepseek-ai/DeepSeek-V3.2-Exp/blob/main/config.json).

### Inferences
- Minimal RoPE engine interface: `(theta, rotary_dims, scaling ∈ {none, linear(f), yarn(f, orig, beta_fast, beta_slow, mscale, mscale_all_dim, attn_factor), llama3(f, low, high, orig)}, per-layer overrides (base freq, NoPE), temperature tuning (floor_scale, attn_scale) for NoPE layers)` — every model above maps onto it. Precomputing cos/sin tables per distinct (theta, scaling) pair (two for Gemma 3) is enough.
- Because the KV cache stores post-RoPE keys in most engines, changing the YaRN factor invalidates saved prompt caches; the cache key (KQ6) must include the RoPE configuration. (KVQuant's pre-RoPE key quantization is the exception and would let the engine re-rotate, at the cost of applying RoPE in the attention kernel.)
- Dynamic YaRN (scale chosen from the actual prompt length, as Alibaba's service does) is implementable locally if the engine recomputes position tables per request and does not share caches across factors; a middle ground is to expose the factor as a per-request parameter with a default of 1 and a server-side cap.
- Local-GPU memory, not RoPE, bounds usable context: the KQ1 table shows that for 8–32 GB machines the realistic ceilings are 32K–128K for GQA-8 models and 256K for hybrids/MoE-with-SWA models even before compute buffers.

### Gaps
- GGUF keys actually written by llama.cpp's converter for sliding windows, per-layer KV heads (hybrids), YaRN betas and SSM group count are newer than the spec document fetched; they were not verified from the converter source.
- Llama 4's exact temperature-tuning formula was not read from code; only the config fields and Meta's description were captured.
- No 2025–2026 measurement of static-vs-dynamic YaRN quality on short prompts was found beyond Qwen's qualitative warning.
