# CPU execution for local LLM inference (x86-64, ARM, Apple Silicon) — state as of 2026-10-08

Scope: kernels, ISA paths, threading, memory layout, CPU-side MoE/sparsity and prefill, with measured numbers, for a from-scratch Rust engine (Apache-2.0) that must match or beat llama.cpp on CPU.

Labeling conventions used below: **[measured]** = numbers posted with hardware + build by the person who ran them; **[vendor]** = manufacturer spec/claim; **[paper]** = authors' self-reported results; **[secondary]** = taken from a search-engine summary of a page I could not fetch in full; **[unverified]** = claim I could not confirm; **(background)** = older than 2025. Licenses are given per project where known.

Method note: research used web search plus direct fetches of GitHub PRs/issues/discussions, arXiv abstracts and vendor docs. The per-turn web-search budget ran out before some gaps (Core Ultra 200V/300, Strix Halo CPU-side bandwidth, Llama 4 Scout on CPU, Phoronix AMX article) could be closed; those are listed in the Gaps sections. Phoronix and openbenchmarking.org returned HTTP 403 to the fetch tool; justine.lol had an expired TLS certificate.

## Key question 1 — Roofline: memory bandwidth, bytes/token and realistic tokens/s per machine class

### Takeaway
Single-stream decode on CPU runs at roughly 50–80% of theoretical DRAM bandwidth divided by bytes-read-per-token on dense models (e.g., 3.54 tok/s for a 19 GB Q4_K_M 32B model on dual-channel DDR5-5600 ≈ 65 GB/s effective), while prefill is compute-bound and has roughly doubled on x86 in the last year through int8-VNNI/interleaved kernels. MoE models on CPU fall 3–4x short of the bytes/token roofline in llama.cpp today, which is the biggest open opportunity.

### Cited Findings

**Formula and measured anchors**
- A Feb 2026 llama.cpp issue (Ryzen AI 9 HX PRO 370, 12c/24t Zen 5, 96 GB DDR5-5600 dual-channel, Ollama 0.15.6 / llama.cpp build 7973, CPU-only) worked the roofline explicitly: assumed ~65 GB/s real-world bandwidth; dense qwen2.5-coder 32B Q4_K_M (19 GB) predicts ~3.4 tok/s, measured 3.54 tok/s **[measured]**; MoE qwen3-coder-next 80B-A3B Q4_K_M (51 GB, ~3B active) should read 2–3 GB/token → 20–30 tok/s predicted, measured 7.74 tok/s (3–4x short). Thread scaling for the dense model: 4 thr 2.72, 6 thr 3.37, 8 thr 3.49, 12 thr 3.54, 24 thr (SMT) 2.84 tok/s — [llama.cpp issue #19480](https://github.com/ggml-org/llama.cpp/issues/19480) (opened 2026-02-10, closed without a stated resolution; the reporter hypothesised the CPU MoE path reads far more than the active 3B parameters).
- Cross-reference in the same issue (from #17936): AMD EPYC 9454P (48c/96t, server DDR5) CPU-only: Qwen3-30B-A3B 63.10 tok/s; Qwen3-Next-80B-A3B 11.76 tok/s; gpt-oss-120b 35.75 tok/s **[measured, quant not stated]** — [issue #19480](https://github.com/ggml-org/llama.cpp/issues/19480).
- Decode scales with bytes/token on the same machine: llama.cpp mainline on Apple M2 Max CPU (NEON, 4 threads for TG, LLaMA-3.1-8B, llama-bench tg128, Dec 2024, background): F16 7.89 tok/s, Q8_0 14.04, Q4_0 23.89 — i.e. ~2x per halving of weight bytes — [ik_llama.cpp discussion #164](https://github.com/ikawrakow/ik_llama.cpp/discussions/164) **[measured]**.
- SMEPilot (arXiv, 2026-06-15) measured on an Apple M4 Pro CPU: 247 GB/s read bandwidth from the CPU cores, 224 GB/s from the SME unit, and "mixed execution did not raise the roof" (Apple's spec for M4 Pro is 273 GB/s) — [SMEPilot](https://arxiv.org/html/2606.16332) **[paper]**. It also states single-token decode is memory-bound so SME adds little there.

### Inferences
- Predict decode as `tok/s ≈ η · BW_peak / (W_active_bytes + KV_bytes_read(ctx))`, with η ≈ 0.6–0.8 for a well-threaded dense model on desktop DDR5 (the #19480 reporter's 65/89.6 ≈ 0.73 for DDR5-5600; 79/96 ≈ 0.82 for the 9950X/DDR5-6000 run; ~0.6 for Apple GPUs at 7B Q4_0), where `W_active_bytes` is the on-disk size of the weights touched per token (all weights for dense; shared + routed-expert slices for MoE) and `KV_bytes_read` grows linearly with context (at long context it dominates for small models). Prefill tok/s is unrelated to bandwidth and tracks int8 MAC throughput per core × cores.
- Apple unified-memory CPUs cannot pull the full fabric bandwidth from the CPU cluster (247 of 273 GB/s on M4 Pro per SMEPilot; the CPU-only M2 Max 7B result of 23–28 tok/s versus 71 on Metal implies far less than 400 GB/s reachable from the CPU side); so on Max/Ultra parts, CPU decode is capped well below the GPU, while on base/Pro parts CPU decode of small models can equal or beat Metal.
- For LLMario's 8–128 GB target machines, the realistic single-stream CPU decode envelope is: 7–8B Q4 ≈ 10–12 tok/s on dual-channel DDR5 desktops, ≈ 23–45 tok/s on Apple M2–M4 Pro/Max CPU cores, and MoE-A3B models ≈ 8 tok/s today on laptops (should be 20–30 with a better expert path), ≈ 60 on 12-channel EPYC.

### Gaps
- No measured CPU-side (not GPU) STREAM-style bandwidth for Strix Halo, M5 base/Pro/Max, Core Ultra 200V (Lunar Lake) or Core Ultra 300 (Panther Lake) was found; the Chips and Cheese Strix Halo page has only qualitative statements.
- No llama.cpp CPU-only numbers for Core Ultra 200V/200S/300 or for Intel Core i9 desktop with DDR5 were found (Phoronix pages returned 403).
- The discussion #4167 M5 (base) row lists only four values; the assignment to F16/Q8_0 columns is uncertain.

## Key question 2 — SIMD and matrix ISA paths, who uses them, and what Rust can reach

### Takeaway
Production CPU inference today is int8-dot-product centric: AVX2 `maddubs`, AVX-512/AVX-VNNI `vpdpbusd`, NEON `sdot`/`smmla` (i8mm) and, on Arm's newest cores, SME2 outer products via KleidiAI; Intel AMX is Xeon-only and Apple's AMX co-processor is only reachable through Accelerate or reverse-engineered encodings. Stable Rust exposes AVX2/AVX-512 (incl. VNNI/BF16/FP16 features) and NEON intrinsics; SVE is nightly-only (merged April 2026), SME intrinsics do not exist in stdarch, and AMX intrinsics are nightly-only — so SME/AMX paths in a Rust engine must go through inline `asm!` or an FFI'd assembly/C kernel library.

### Cited Findings

**x86-64**
- Arrow Lake / Core Ultra 200: AVX-512 disabled in firmware for homogeneity with Skymont E-cores; AVX-VNNI present — [Wikipedia: Arrow Lake](https://en.wikipedia.org/wiki/Arrow_Lake_(microprocessor)). llama.cpp's build docs mention `avx_vnni` for Intel CPUs "without AVX512 and AVX512-VNNI" (via oneAPI compilers) — [llama.cpp docs/build.md](https://github.com/ggml-org/llama.cpp/blob/master/docs/build.md).
- Zen 5 ISA list (Wikipedia): AVX-512 incl. VP2INTERSECT, AVX-VNNI; "greater bfloat16 throughput"; AMX and AVX512-FP16 not listed — [Wikipedia: Zen 5](https://en.wikipedia.org/wiki/Zen_5). WikiChip's Zen 5 page lists AMX, which conflicts with other reporting (heise: AMX is in Xeon server cores; consumer desktop/laptop processors lack it) — [heise](https://heise.de/-11075632) **[secondary; treat AMD AMX as absent]**. AMD and Intel have published a joint "ACE" matrix-extension spec layered on AVX10 vector registers; retail CPUs with ACE are expected around 2028+ and hwcooling notes AMX code may not port cleanly to ACE — [hwcooling](https://www.hwcooling.net/en/intel-and-amd-agree-on-future-of-x86-cpus-amx-and-ram-tagging/), [Tom's Hardware](https://www.tomshardware.com/pc-components/cpus/intel-and-amds-new-ace-cpu-extensions-bring-an-efficient-ai-oriented-instruction-set-to-x86-a-new-design-makes-matrix-multiplication-more-power-and-density-efficient) **[secondary]**.
- Intel AMX in llama.cpp: the original AMX backend (PR by mingfeima, merged 2024-10-18, background) enabled AMX only for Q4_0/Q4_1 at merge; Q8_0/Q4_K/Q5_K/Q6_K/IQ4_XS kernels existed but were disabled ("TODO: fix padding for vnni format"); weights are prepacked into a VNNI-style layout in `set_tensor`; a VNNI kernel covers GEMV and AMX covers GEMM; a user reported ~2x faster prompt eval and unchanged generation on a Xeon with gemma-2b Q4_0 — [llama.cpp PR #8998](https://github.com/ggml-org/llama.cpp/pull/8998) **[measured, anecdotal]**. In 2026 the AMX path was fixed for batched mul_mat (PR #19925, merged 2026-02-26), de-coupled from OpenMP (#20074, 2026-03-03), and re-optimised: on a Xeon Platinum 8488C with qwen35 0.8B, pp512 went Q4_K_S 732 → 1077, Q4_K_M 719 → 1009, IQ4_XS 725 → 1023, Q4_0 821 → 924 tok/s; tg128 flat (80–92 tok/s) — [PR #24806](https://github.com/ggml-org/llama.cpp/pull/24806) (merged 2026-06-20) **[measured]**. The project currently has no AMX CI machine (job commented out). A `--amx` toggle was added for CPU/GPU hybrid use (PR #16310, Sept 2025) and a per-thread XFD/XTILEDATA permission fix is still open (PR #26954, Aug 2026) — [GitHub API listing of AMX PRs](https://api.github.com/search/issues?q=repo:ggml-org/llama.cpp+is:pr+amx+in:title).
- KTransformers' AMX kernels (Apache-2.0): up to 21.3 TFLOPS sustained on one Xeon socket, 3.9x PyTorch native; kernels switch between AMX for prefill and AVX-512 for decode; `AMXINT4` pre-quantized CPU weights — [LMSYS blog, 2025-10-22](https://www.lmsys.org/blog/2025-10-22-KTransformers/) **[vendor/paper]**.
- oneDNN (Apache-2.0): runtime ISA detection with JIT code generation; optimised for Xeon through Xeon 6 and Core Ultra; future AVX10.2 parts (Nova Lake, Diamond Rapids) listed; low-precision types f32/bf16/f16/fp8/fp4/u8/s8/u4/s4 incl. OCP microscaling; AArch64 via Arm Compute Library (min 53.1.0) with KleidiAI in its third-party license list — [oneDNN README](https://raw.githubusercontent.com/uxlfoundation/oneDNN/main/README.md).
- SparAMX (Intel Labs, arXiv 2025-02-18): unstructured sparsity + AMX for the memory-bound decode stage, 1.42x end-to-end on linear layers vs PyTorch and 1.14x on attention; code at IntelLabs/Hardware-Aware-Automated-Machine-Learning (license not stated on the abstract page) — [SparAMX](https://arxiv.org/abs/2502.12444) **[paper]**.

**ARM (NEON, i8mm, SVE, SME/SME2)**
- Apple M4 Max feature set (macOS 27, Apple clang 21): FEAT_SME=1, FEAT_SME2=1, `sme_max_svl_b=64` (512-bit streaming vector length), FEAT_I8MM, FEAT_BF16, FEAT_DotProd; FEAT_SVE absent ("Apple ships SME2 without non-streaming SVE") — [llama.cpp issue #26547](https://github.com/ggml-org/llama.cpp/issues/26547) (2026-08-04).
- Cortex-X925 and Neoverse-N2 are 128-bit SVE2 cores; llama.cpp's SVE kernels are gated on `ggml_cpu_get_sve_cnt() == QK8_0` (32 bytes = 256-bit VL), so they never run on 128-bit SVE2 parts, and Apple/Windows report VL as unknown — [issue #26547](https://github.com/ggml-org/llama.cpp/issues/26547), [docs/build.md](https://github.com/ggml-org/llama.cpp/blob/master/docs/build.md).
- Snapdragon X2 Elite (Oryon v2) exposes SME: a KleidiAI-enabled Windows ARM64 build crashed with STATUS_ILLEGAL_INSTRUCTION in the SME matmul path — [llama.cpp issue #22182](https://github.com/ggml-org/llama.cpp/issues/22182) **[secondary]**. MediaTek Dimensity 9500 (C1-Ultra/Premium/Pro) supports SME and SME2; HiSilicon KunPeng 920 72F8 supports SME only — [SMEPilot](https://arxiv.org/html/2606.16332).
- KleidiAI (Apache-2.0; Arm GitLab, read-only GitHub mirror) provides micro-kernels for Neon, SVE, SME and SME2, named like `matmul_clamp_f32_qsi8d32p_qsi4c32p` (f32 out, int8 dynamically-quantised LHS, int4 per-block RHS) — [KleidiAI README](https://raw.githubusercontent.com/ARM-software/kleidiai/main/README.md). The SME2 Q4_0 path repacks the RHS at model load (`kai_run_rhs_pack_nxk_qsi4c32ps1s0scalef16_qsu4c32s16s0_neon`, signed int4 → unsigned int4, mr=16, nr=64, kr=4, sr=2) and quantises activations to int8 at run time, feeding `kai_..._matmul_clamp_f32_qai8dxp1vlx4_qsi8cxp4vlx4_1vlx4vl_sme2_mopa` (outer-product accumulate into ZA tiles) — [Arm learning path: SME2 ukernel explained](https://learn.arm.com/learning-paths/mobile-graphics-and-gaming/kai_sme2_matmul_ukernel_explained/explain_with_an_example_p1/).
- llama.cpp's KleidiAI integration (`GGML_CPU_KLEIDIAI=ON`, aarch64 only): runtime dispatch by CPU features (dotprod, i8mm, SVE, SME/SME2), tensor type, op shape and backend priority; `GGML_KLEIDIAI_SME` env var: unset = auto, `0` = disable SME kernels, `n` = enable and cap quantised SME kernels at n threads (recommended on Windows arm64 until SMCU detection is verified) — [docs/build.md](https://github.com/ggml-org/llama.cpp/blob/master/docs/build.md). On Apple Silicon the SME thread cap comes from a hard-coded brand-string table (`detect_num_smcus()`: M4 Max/Pro/Ultra → 2); above the cap, decode-shaped ops (`ne11 == 1`) silently fall back to NEON/DotProd, while long prefill uses a hybrid SME2+NEON path that requires `ne11 >= 128` and `ne01/n_threads >= 2`. lldb breakpoint counts on M4 Max (Qwen2.5-0.5B Q4_0): decode at 1/2 threads 996/5826 SME2 hits, at 4/8/16 threads 0 SME2 hits; prefill at 16 threads 1403 SME2 vs 21509 other. The banner prints `SME2 = 1` regardless. Issue closed as stale without a fix — [issue #26547](https://github.com/ggml-org/llama.cpp/issues/26547).

### Inferences
- ISA matrix a Rust engine should target in priority order: (1) AVX2 + FMA with `vpmaddubsw` int8 dots (every x86 machine); (2) AVX-VNNI (Intel Core 12th gen → Core Ultra 300) and AVX-512 VNNI/VBMI (Zen 4/5, Xeon) — the 2026 llama.cpp PRs show 1.5–3.9x prefill from VNNI alone; (3) NEON dotprod + i8mm (all Apple M-series, Snapdragon X, Cortex-A7xx/X); (4) SME2 via KleidiAI/own asm for prefill on M4/M5, X2 Elite, Dimensity 9500; (5) AMX only if LLMario targets Xeon workstations (nightly Rust or asm). SVE can be skipped: no consumer core has 256-bit SVE and Apple has none.
- Do not plan on Apple's AMX co-processor directly; use Accelerate `cblas_sgemm`/BNNS for fp32/fp16 prefill GEMM as an optional path (it is what MLX does), and own int8 kernels for quantised weights where Accelerate has nothing.
- Rust `std::arch` intrinsics for AVX2/AVX-512/NEON are sufficient for the dot-kernel layer; SME2 and AMX need `asm!` blocks or FFI. Because `asm!` has been stable since 1.59 (background), nothing here forces nightly.

## Key question 3 — Low-bit CPU matmul kernels and repacking

### Takeaway
The winning recipe on every CPU is: keep weights in 4–8-bit blocks, quantise activations to int8 on the fly, run integer dot products, and reorder ("repack") weight blocks at load into an ISA-specific interleaved tile layout so one SIMD multiply-add consumes 4–16 rows at once; measured gains are mostly in prefill (1.5–8x) with flat-to-modest decode gains, and the load-time cost of repacking is real (seconds to minutes).

### Cited Findings

**ggml repack lineage**
- Online repack for aarch64 Q4_0 (PR #9921, merged 2024-11-15, background): repacks Q4_0 into `block_q4_0x4`/x8 interleaved layouts at load through a dedicated CPU buffer type so the tensor type stays Q4_0 (slaren insisted layout changes go through the backend buffer interface, keeping `get_tensor` semantics and quantised KV cache working). Graviton 3, phi-2 Q4_0, 4 threads: pp512 38.0 → 110.8, tg128 17.0 → 39.4 tok/s **[measured]**. On x86 the results were mixed (slaren, 16 threads WSL 7B Q4_0: pp 50.6 → 64.8 but tg 20.8 → 15.8; Intel i5-13600K Q4_0_8_8 tg −31% at 8 threads), and loading got slower — [PR #9921](https://github.com/ggml-org/llama.cpp/pull/9921). Separate Q4_0_4_4/4_8/8_8 model files stopped loading at build b4282 — [Bartowski model card](https://huggingface.co/bartowski/Qwen_Qwen3-14B-GGUF) **[secondary]**. **Lookup-table and ternary kernels**

**Dequantise-on-the-fly vs pre-dequantised**
- Mainline llama.cpp F16/BF16 CPU matmul was far slower than quantised int8 paths before 2025 (7950X pp512 BF16 78.6 vs Q8_0 147.9; M2 Max F16 29.0 vs Q4_0 114.6) — [ik_llama.cpp #164](https://github.com/ikawrakow/ik_llama.cpp/discussions/164) **[measured, background]**.
- SMEPilot ablation (M4 Pro): naive layout packing raised decode GEMV latency from 0.52 ms to 1.71 ms; removing tile partitioning raised GEMM latency 1.46x — [SMEPilot](https://arxiv.org/html/2606.16332) **[paper]**.
- KleidiAI requantises q8_0 to per-row scales (lossy, 1.4% relative L2 on a TTS model) because it lacks per-32-block int8 kernels — [gradium xn #102](https://github.com/gradium-ai/xn/pull/102) **[measured]**.

### Inferences
- A Rust engine should implement, per GGUF family, (a) a scalar reference kernel, (b) a GEMV kernel on the native block layout for decode (bandwidth-bound; repack buys ≤10% here), and (c) a GEMM kernel on an interleaved layout (4x4/4x8 NEON, 8x8 AVX2, 8x4/16x4 VNNI, mr16×nr64 SME2) used when n_tokens ≥ ~8–32. The 2026 llama.cpp numbers show that decode speed is set by bytes/token, not by kernel cleverness, while prefill is where kernels differ 2–8x.
- Repack should be a cached artifact (on-disk sidecar keyed by model hash + layout id), not a per-load transform: llama.cpp pays 17 → 77 s load on a Xeon for Phi-4, and has an open PR for a KleidiAI weight cache for the same reason. Repacking also defeats `mmap` sharing (weights are copied into anonymous memory), which matters for LLMario's "do not starve other apps" goal.
- T-MAC/bitnet-style LUT kernels pay off only for ≤2-bit weights or ternary models; for Q4/Q8 the int8 dot path is within ~1.2x and simpler.

### Gaps
- No controlled repack-on/off measurement on Apple M4/M5 CPU for 7B+ models was found (only the 1B Q4_0 example and the SME2 PRs).
- Vec-LUT and SMEPilot code licenses/availability were not confirmed.
- The exact AMX tile configuration and int8 packing used by ggml's `amx/mmq.cpp` was not read (source not fetched).

## Key question 4 — Threading and scheduling

### Takeaway
llama.cpp's CPU backend uses a fork-join graph executor with one barrier per op, a spin-then-sleep worker wait (`--poll`, default 50 ≈ 100 ms of spinning before parking), optional affinity masks/strict pinning and priorities, and a default thread count equal to physical "math" cores (excluding SMT siblings and E-cores). Barrier cost is 30% of CPU decode time on MoE offload paths, oversubscription with pure spinning is pathological, SMT threads reduce decode throughput, and macOS has no affinity control (QoS classes are the lever).

### Cited Findings
- Threadpool design (PR #8672, merged 2024-08-29, background): explicit pools that can be created/paused/resumed; separate pools for batch vs single-token; polling (spinning) vs interrupt-driven waits — polling removed context switches in token generation and matched OpenMP, but "hurt when BLAS or GPU backends were running"; CPU masks with strict or relaxed placement; thread priority helper; default thread count switched from `hardware_concurrency()` to `cpu_get_num_math()`, which excludes efficiency cores and SMT siblings; llama-bench creates a fresh pool per test because idle spinning threads interfered with core boosting. Numbers: Snapdragon X Elite (llama-v2-115m Q4_0_4_8, 4 thr) tg128 744 → 1007; Apple M2 Max (`-ngl 0`, 4 thr) tg128 818 → 1004; Intel i7-10750H flat vs OpenMP — [PR #8672](https://github.com/ggml-org/llama.cpp/pull/8672) **[measured]**.
- Current flags (Debian llama.cpp-tools 0.4.1 manpage): `-t/--threads N` (default: number of CPUs), `-tb/--threads-batch`, `-C/--cpu-mask` (hex), `--cpu-range lo-hi`, `--cpu-strict 0|1`, `--prio` low(−1)…realtime(3), `--poll 0…100` ("0 - no polling, default: 50"), `--numa distribute|isolate|numactl` (drop the page cache first), `-b` 2048 / `-ub` 512 defaults, `--mlock`, `--no-mmap`, `-ncmoe/--n-cpu-moe N`, `-cmoe/--cpu-moe`, `-ot` — [llama-server(1)](https://manpages.debian.org/testing/llama.cpp-tools/llama-server.1.en.html).
- `--poll` semantics: at the default 50, each thread spins through ~6.5 million `pause` iterations (~100 ms measured) before sleeping on a condition variable; `--poll 0` sleeps right after each CPU graph; Ollama proposed passing `--poll 0` whenever a GPU is present — [ollama PR #18613](https://github.com/ollama/ollama/pull/18613) **[secondary]**; with everything offloaded, one core can still spin because of CUDA's wait, fixed by `cudaDeviceScheduleBlockingSync` — [llama.cpp discussion #22238](https://github.com/ggml-org/llama.cpp/discussions/22238) **[secondary]**.
- Barrier spin/yield (PR #29258, closed unmerged 2026-09-22): `ggml_barrier` is a pure `cpu_relax` spin; with threads > cores a waiter can hold the scheduler slot of the thread it waits for (2-vCPU VM: 147 s → 4.4 s with yield after 2048 spins; Windows runner 900 s timeout → 7 s); but on an uncontended M4 Pro the yield cost 5.5–9.7% tg on small models, so the author closed it and recommended OpenMP builds (blocking pool) for CI — [PR #29258](https://github.com/ggml-org/llama.cpp/pull/29258) **[measured]**. The secondary threads' `ggml_graph_compute_poll_for_work` loop spins up to `poll` then sleeps on a condvar.
- Barrier share in MoE decode: in `--n-cpu-moe` token generation the barrier was ~30% of CPU run time (ggerganov's profile: cycles in `barrier_wait` from uneven chunk completion); per-thread activation quantisation removed one barrier (30% → 7%), plus a fused gated-activation path for n_tokens=1, cache-line padding and work-stealing; gains 1.04–1.14x on x86 (Qwen3.5-35B-A3B Q4_K_S: 16 thr 40.3 → 43.3 tok/s with an RTX 5090 host; EPYC 9B14 32 thr 103.6 → 108.7) but regressions on Apple M2 Ultra (0.75–0.79x at 2–4 threads Q8_0) and M2 Studio/DGX Spark (0.87–1.00x); high run-to-run variance — [PR #20596](https://github.com/ggml-org/llama.cpp/pull/20596) (open) **[measured]**.
- SMT and thread count: Ryzen AI 9 HX 370 dense 32B: 12 threads 3.54 tok/s, 24 threads 2.84 — [issue #19480](https://github.com/ggml-org/llama.cpp/issues/19480); 9950X tg declines 4 → 16 threads (6.25 → 5.91 on 8B Q8_0) — [PR #30036](https://github.com/ggml-org/llama.cpp/pull/30036); ik_llama's author used 2 threads for TG on a 7950X and 3–4 on M2 Max — [#164](https://github.com/ikawrakow/ik_llama.cpp/discussions/164); an older M2 Max write-up found TG peaked at ~6 cores — [Medium (andreask)](https://medium.com/@andreask_75652/llama-cpp-performance-apple-silicon-051241dd6eae) **[secondary, background]**.
- Apple core clusters and defaults: M5 Max = 6 "Super" + 12 "Performance" cores; llama.cpp's macOS default took only perflevel0 (6 threads), halving pp and costing ~33% tg versus 18 threads; fix proposed in PR #29784 (open) — [issue #29782](https://github.com/ggml-org/llama.cpp/issues/29782) (2026-10-01) **[measured]**. M4 Max is 12P + 4E — [issue #26547](https://github.com/ggml-org/llama.cpp/issues/26547). SMEPilot used 10 workers on the 10P+4E M4 Pro — [SMEPilot](https://arxiv.org/html/2606.16332).
- macOS QoS (Apple Energy Efficiency Guide, background): classes user-interactive, user-initiated, default, utility, background (+ unspecified); background is tuned for energy efficiency and "minutes or hours" work; Apple recommends running at utility or lower ≥ 90% of the time when the user is not active; APIs `pthread_set_qos_class_self_np`, `pthread_attr_set_qos_class_np`, `dispatch_queue_attr_make_with_qos_class`; the system raises a lower-QoS lock holder's QoS to resolve inversions (`pthread_mutex_lock`, `dispatch_sync`) — [Prioritize Work with QoS](https://developer.apple.com/library/archive/documentation/Performance/Conceptual/EnergyGuide-iOS/PrioritizeWorkWithQoS.html). A Medium post argues `--cpu-mask`/`--poll` have no effect on macOS because the OS schedules P/E cores itself and recommends `--prio 2` only on dedicated machines — [Medium (hannecke)](https://medium.com/@michael.hannecke/tuning-llama-cpp-on-apple-silicon-843f37a6c3dc) **[secondary]**.
- Affinity on Linux: `--cpu-range 0-7 --cpu-strict 1` binds one thread per core; `--numa distribute` is incompatible with `--cpu-mask/--cpu-range/--cpu-strict` (max-krasnyansky, Oct 2024) — [llama.cpp discussion #9996](https://github.com/ggml-org/llama.cpp/discussions/9996).
- NUMA / multi-socket: `--numa distribute` spreads threads across nodes and disables mmap prefetch/readahead so pages fault in near the threads that touch them — [HF discussion](https://huggingface.co/TheBloke/Mixtral-8x7B-v0.1-GGUF/discussions/9) **[secondary]**; a CPU tensor-parallel RFC (multi-process, rank = socket, row-parallel all-reduce, experts in EP or TP mode) reported 4.0x decode on Llama-70B Q8 (4-way, one node), 2.18x decode / 1.84x prefill on Phi-3-mini (2 sockets), +36% decode on Qwen3-235B-A22B Q8 (2-socket TP), but was withdrawn the same day (2026-07-01) after the bot flagged it as AI-generated/too large — [PR #25209](https://github.com/ggml-org/llama.cpp/pull/25209) **[author-reported]**; KTransformers' NUMA-aware TP gives up to +63% decode on dual-socket Xeons — [LMSYS](https://www.lmsys.org/blog/2025-10-22-KTransformers/) **[vendor]**.
- Repack under NUMA hurts: see the dual-Xeon-4216 results above (tg −7.5 to −15%) — [PR #12332](https://github.com/ggml-org/llama.cpp/pull/12332).
- Hybrid SME2+NEON scheduling: static split ratios under-used both units at low thread counts; a global chunk queue gave +36–85% pp512 at 2–8 threads on Exynos — [PR #23819](https://github.com/ggml-org/llama.cpp/pull/23819) **[measured]**. KleidiAI SME2 decode kernels on Apple are only dispatched at ≤ 2 threads (SMCU count) — [issue #26547](https://github.com/ggml-org/llama.cpp/issues/26547).
- Race fixes in the threadpool continued through 2025 (dynamic n_threads changes, PR #17748 merged 2025-12-04) and a "skip threadpool for graphs with no CPU work" PR is open (#28785, Sep 2026) — [GitHub API listing](https://api.github.com/search/issues?q=repo:ggml-org/llama.cpp+is:pr+threadpool+in:title).

### Inferences
- A Rust engine should (1) size the decode pool to physical P-cores (Apple: sum of all performance-class `hw.perflevelN.physicalcpu`; Intel hybrid: P-cores only by default; AMD: physical cores, not SMT threads), with a smaller count (2–6) often sufficient for bandwidth-bound decode on desktop DDR5; (2) use a bounded spin (tens of µs) followed by futex/condvar parking rather than 100 ms spinning, and never spin when a GPU backend owns the critical path; (3) reduce barriers by fusing quantise-activations → matmul → gating in one parallel region with work-stealing over row chunks (the 30% → 7% barrier result); (4) expose priority/QoS: `QOS_CLASS_UTILITY` for background generation on macOS, `SCHED_BATCH`/nice on Linux, `THREAD_PRIORITY_BELOW_NORMAL`/EcoQoS on Windows, with an "interactive" mode that raises it; (5) treat NUMA as first-touch allocation per node plus per-node thread groups, since the interleaved-repack + NUMA combination measurably regresses.
- Rayon-style work stealing is appropriate for GEMM tiles in prefill; decode GEMV chunks are better statically partitioned by rows across a fixed pool to keep each thread's weight stream contiguous and prefetchable.

### Gaps
- No measured llama.cpp numbers for P-core-only vs P+E on Intel 12th–14th gen / Core Ultra were found within the search budget.
- No measured data on QoS-class placement (e.g., whether `QOS_CLASS_BACKGROUND` threads are confined to E-cores on M-series) — Apple's "tuning your code's performance for Apple silicon" page did not render; treat E-core confinement of background QoS as unverified.
- No measured consumer dual-CCD (9950X) NUMA/CCD-affinity effect on decode was found.

## Key question 5 — Memory layout and caches

### Takeaway
Weights should stay in their quantised block form (no dequantised copies), be packed once into the kernel's tile layout, and be read in long sequential streams; huge pages show only slight gains for models that fit in RAM, and software prefetch/pinning/2-D tiling were measured as non-improvements on Apple's matrix unit, whereas B-panel packing and the right panel width are worth up to 2x.

### Cited Findings
- Huge pages: a 2025 request to mmap with `MAP_HUGETLB` reported "more than 10x" faster loading of a ~377–400 GB DeepSeek-R1 671B GGUF on a 1.5 TB Dell server with ~800 GB pre-reserved hugetlbfs pages (baseline unspecified); no PR was merged and the issue went stale — [llama.cpp issue #12444](https://github.com/ggml-org/llama.cpp/issues/12444) **[unverified]**. Phoronix's Linux 6.18 THP comparison found `madvise` mode fastest in 8 of 9 llama.cpp (CPU BLAS) results with only a slight gap — [Phoronix](https://www.phoronix.com/review/thp-madvise-always/4) **[secondary; page 403'd]**. The 2023 llamafile mmap post reported no measurable benefit from `madvise` because every weight page is touched almost immediately — [justine.lol/mmap](https://justine.lol/mmap/) **[secondary, background]**.
- `--mlock` keeps the model in RAM; `--no-mmap` slows load but may reduce page-outs — [llama-server(1)](https://manpages.debian.org/testing/llama.cpp-tools/llama-server.1.en.html).
- Expert-page hinting when RAM < model: a patched llama.cpp issuing `madvise(MADV_WILLNEED)` on the experts the router just selected reportedly moved an 8 GB MacBook Air from 0 tok/s (thrashing) to 0.57 tok/s; the author notes it only helps when RAM is smaller than the model and layers run on CPU — [Expert Sniper (HF)](https://huggingface.co/waltgrace/llama-cpp-expert-sniper) **[secondary, anecdotal]**.
- Blocking and packing on Apple M1 AMX: three-level Goto/BLIS cache blocking, explicit B-panel packing, K-blocking with partial-accumulator carry, 4-way ILP across four Z banks; weights pre-packed once at load; panel width Nc=64 (vs 512) exposed enough parallelism for both AMX blocks and "mis-tuning this single width costs nearly 2x". Negative results: operand streaming, paired loads, software prefetch, thread pinning and 2-D tiling did not help — [Above the Inner Loop](https://arxiv.org/html/2606.25426) **[paper]**.
- SME2 micro-kernel packing parameters (512-bit SVL): mr=16, nr=64, kr=4, sr=2; packed RHS loaded into Z registers with sequential access "which improves cache locality"; packing runs once at load through `ggml_backend_cpu_kleidiai_buffer_set_tensor → tensor_traits::repack` — [Arm learning path](https://learn.arm.com/learning-paths/mobile-graphics-and-gaming/kai_sme2_matmul_ukernel_explained/explain_with_an_example_p1/).
- x86 interleaved layouts: `block_q4_Kx8` (8 blocks, 8-byte quant interleave, 96-byte scale array) and `block_q8_Kx4` — [PR #12332](https://github.com/ggml-org/llama.cpp/pull/12332); 8x4 (ymm) and 16x4 (zmm) VNNI layouts — [PR #30036](https://github.com/ggml-org/llama.cpp/pull/30036); permute tables built lazily in a function-local static because `GGML_BACKEND_DL` dlopens every CPU variant — [PR #29397](https://github.com/ggml-org/llama.cpp/pull/29397).
- Layout sensitivity measured: naive packing tripled decode GEMV latency (0.52 → 1.71 ms) on M4 Pro — [SMEPilot](https://arxiv.org/html/2606.16332) **[paper]**.
- Avoiding copies: llama.cpp keeps the user-visible tensor type (Q4_0) and stores converted layouts via the buffer type (`tensor->extra`) so `get_tensor` still returns the original format — [PR #9921](https://github.com/ggml-org/llama.cpp/pull/9921); a KleidiAI weight cache PR is open to avoid repeat conversions — [GitHub API listing](https://api.github.com/search/issues?q=repo:ggml-org/llama.cpp+is:pr+kleidiai+in:title); AMX prepacks weights in `set_tensor` and the AMX buffer is not host-accessible (`is_host=false`, `buffer_from_host_ptr` disabled) — [PR #8998](https://github.com/ggml-org/llama.cpp/pull/8998).
- Load-time cost of repacking: Phi-4 Q4_K_M 17 → 77 s, Command-A 109 → 1221 s on a dual Xeon — [PR #12332](https://github.com/ggml-org/llama.cpp/pull/12332); +40 ms for a 9-layer model on M5 — [gradium xn #102](https://github.com/gradium-ai/xn/pull/102).
- AVX-512 frequency/power: ~10% clock reduction under heavy AVX-512 on Ryzen 9000 — [Tom's Hardware](https://www.tomshardware.com/pc-components/cpus/ryzen-9000-cpus-drop-10-frequency-executing-avx-512-instructions-intel-cpus-typically-suffer-from-more-substantial-clock-speed-drops) **[secondary]**.

### Inferences
- For LLMario's memory predictability goal, the engine should mmap the GGUF and compute directly on mapped quantised blocks for decode (page-cache shared, evictable), and only materialise a packed copy for the prefill GEMM path when the model is small enough that the extra copy is affordable — or persist the packed layout as a sidecar file so it too can be mmapped. Mixed strategy: packed copies for the attention/FFN weights touched by prefill, mapped originals for everything else.
- Tile sizes should be derived from register count (16 ymm / 32 zmm / 32 NEON v-regs / ZA 512-bit tiles) rather than cache sizes; cache blocking matters only in prefill GEMM (K-blocking to L2, N-panels sized to share across threads). Software prefetch is not worth engineering effort on modern cores (measured no gain on M1; hardware prefetchers handle sequential weight streams).
- Transparent huge pages (`madvise(MADV_HUGEPAGE)` on anonymous packed buffers) are cheap to add and likely a few percent; explicit hugetlbfs is operationally unsuitable for a desktop app.

### Gaps
- No controlled measurement of THP on/off for CPU decode on consumer hardware beyond the (unfetched) Phoronix article.
- The Apple 16 KB page size and its effect on mmap/`madvise` granularity were not verified against an Apple page in this session.
- No source on the resident-memory overhead (mapped + packed copies) of llama.cpp's repack path was found; this should be measured directly.

## Key question 6 — CPU-side MoE and sparsity

### Takeaway
On consumer machines, MoE inference splits experts to CPU RAM and attention/dense parts to the GPU (`--n-cpu-moe`, `-ot`), which makes gpt-oss-120b usable on 8–32 GB GPUs and runs at ~49 tok/s on a 128 GB Strix Halo; but llama.cpp's CPU expert path reads 3–4x more than the active-parameter roofline, and the research systems that close the gap (KTransformers' AMX/NUMA expert kernels, PowerInfer's hot/cold neuron split, ProMoE/HOBBIT/FineMoE expert prefetching) either need Xeon-class hardware or special ReLU-sparse models.

### Cited Findings

**llama.cpp expert offload (flags, memory, measured)**
- Flags: `--n-cpu-moe N` ("keep the MoE weights of the first N layers in the CPU"), `--cpu-moe` (all), `-ot "<regex>=CPU"` tensor overrides — [llama-server(1)](https://manpages.debian.org/testing/llama.cpp-tools/llama-server.1.en.html). The gpt-oss guide (2025-08-18): weights 12.0 GB (20B) / 61.0 GB (120B) in MXFP4 (treated as "roughly equivalent to Q4_0", always use the original MXFP4 files); KV 0.2–0.3 GB per 8K tokens; 120B needs ~8 GB VRAM minimum when offloading experts; Apple users should stay under ~70% of unified memory; `-ub 2048 -b 2048` recommended with enough memory; examples: RTX 2060 8 GB → 120B at 32k context with `--n-cpu-moe 35`; V100 16 GB → `--n-cpu-moe 32`; RTX 5090 32 GB `--n-cpu-moe 21` ≈ 30 tok/s at zero context — [llama.cpp discussion #15396](https://github.com/ggml-org/llama.cpp/discussions/15396) **[measured where stated]**.
- Community numbers in the same thread: RX 7900 XT 20 GB + Ryzen 9 5900X, dual-channel DDR4-3200, gpt-oss-20b: ~94 tok/s full GPU → ~60 (4 layers on CPU), 38 (8), 25–27 (16), ~20 (all experts on CPU); RTX 3060 12 GB + Ryzen 7 5700X: ~64 tok/s with `-ncmoe 2` (16k context), 53–56 at 32k; `-ot "\.([2-9][0-9])\.ffn_up_exps.=CPU"` ≈ `-ncmoe 2` — [discussion #15396](https://github.com/ggml-org/llama.cpp/discussions/15396) **[measured]**. Metal unified memory: M2 Ultra 192 GB gpt-oss-120b 79.7 tok/s; M4 Max 36 GB gpt-oss-20b 92.4 — same thread **[measured]**.
- Strix Halo gpt-oss-120b: 49.0 tok/s tg, 165.9 pp (ROCm, b10440) — [seehiong](https://seehiong.github.io/posts/2026/08/running-llama.cpp-on-amd-strix-halo/); ~48 (Vulkan) — [agledger](https://agledger.ai/blog/local-llm-strix-halo-ubuntu-26-04/) **[secondary]**.
- CPU-only MoE: EPYC 9454P gpt-oss-120b 35.75, Qwen3-30B-A3B 63.1, Qwen3-Next-80B 11.76 tok/s; Ryzen AI 9 HX 370 Qwen3-Next-80B-A3B 7.74 tok/s (vs 20–30 roofline) — [issue #19480](https://github.com/ggml-org/llama.cpp/issues/19480); EPYC 9554 Qwen3-30B-A3B ~43 tok/s — [ahelpme](https://ahelpme.com/ai/llamacpp-ai/llama-bench-the-qwen3-coder-30b-a3b-and-amd-epyc-9554-cpu/) **[secondary]**; Radxa Orion O6 (7 threads) Qwen3-30B-A3B Q4_K_M ~16 tok/s — [Radxa forum](https://forum.radxa.com/t/llama-cpp-benchmarks/27813) **[secondary]**.
- `--n-cpu-moe` TG path improvements (open PR #20596): fused gated activation for single-token, per-thread activation quantisation, work stealing; +4–14% on x86 hosts, regressions on Apple — [PR #20596](https://github.com/ggml-org/llama.cpp/pull/20596) **[measured]**. Expert-cache RFCs for `--n-cpu-moe` (persistent expert cache #21614, dedup #21620, CUDA adaptive VRAM caching of CPU-resident experts #24524) were all closed unmerged in 2026 — [GitHub API listing](https://api.github.com/search/issues?q=repo:ggml-org/llama.cpp+is:pr+cpu-moe+in:title).

**KTransformers (Apache-2.0)**
- DeepSeek-V3 Q4_K_M on 2× Xeon Gold 6454S (32c each, 1 TB DDR5-4800, 8 channels/socket) + RTX 4090D 24 GB (Feb 2025): V0.2 dual-socket 6-expert prefill 97.3 / decode 13.69 tok/s vs llama.cpp 10.31 / 4.51 on the same 64 cores (9.44x / 3.03x); V0.2.1 at 8K prompt 101 / 13.9; V0.3-preview AMX kernel prefill 255–287 tok/s (1K–8K prompts; 27.8x llama.cpp), decode unchanged; minimum 14 GB VRAM and 382 GB (1 socket) / 644 GB (V0.3) RAM — [KTransformers DeepSeek tutorial](https://github.com/kvcache-ai/ktransformers/blob/main/doc/en/DeepseekR1_V3_tutorial.md) **[vendor-measured]**. SOSP'25 "Expert Deferral" (overlapping CPU expert compute with GPU attention) raised DeepSeek-V3 decode utilisation 74%/28% → 100%/37% and throughput +33% (up to 45%), accuracy loss < 0.5% — [SOSP'25 paper](https://madsys.cs.tsinghua.edu.cn/publication/ktransformers-unleashing-the-full-potential-of-cpu/gpu-hybrid-inference-for-moe-models/SOSP25-chen.pdf) **[paper, secondary]**; SGLang integration (Oct 2025): single-GPU + dual Xeon 8452Y, prefill up to 20x and decode up to 4x over baselines; DeepSeek-R1-0528 ShareGPT 227.85 total tok/s on 8× L20 — [LMSYS](https://www.lmsys.org/blog/2025-10-22-KTransformers/) **[vendor]**. Aug 2026: LoRA fine-tuning on AVX-512 CPUs without AMX — [KTransformers README](https://github.com/kvcache-ai/ktransformers) **[secondary]**.

**Activation sparsity (hot/cold neurons, ReLU-fied models)**
- PowerInfer (MIT; background 2023): neuron activations follow a power law; hot neurons preloaded on GPU, cold computed on CPU with adaptive predictors (distributed as separate "-Predictor" repos); RTX 4090: 13.20 tok/s average, 29.08 peak, up to 11.69x llama.cpp (incl. OPT-175B); only ReLU/ReGLU/squared-ReLU models (ReLU-Llama-2, Falcon-ReLU-40B, ProSparse, Bamboo); latest news: SmallThinker-21BA3B/4BA0.6B (2025-07-27) and a "Tiiny AI Pocket Lab" device claiming gpt-oss-120b int4 at 20 tok/s (CES 2026, vendor claim) — [SJTU-IPADS/PowerInfer](https://github.com/SJTU-IPADS/PowerInfer).
- PowerInfer-2 (paper only; no source release shown): TurboSparse-Mixtral-47B at 11.68 tok/s on a 24 GB OnePlus 12 with 50% of FFN weights on flash, 21.2x llama.cpp; hot clusters on NPU, cold on CPU; up to 29x in aggregate — [arXiv 2406.06282](https://arxiv.org/abs/2406.06282v1) **[paper, background]**. TurboSparse (dReLU): ~2.5B active params for the Mistral-7B variant and 4.3B for Mixtral-47B, 2–5x decode speedup — [arXiv 2406.05955](https://arxiv.org/abs/2406.05955) **[paper, background]**. Deja Vu contextual sparsity (ICML 2023): >2x latency vs FasterTransformer on OPT-175B with per-layer predictors — [arXiv 2310.17157](https://arxiv.org/abs/2310.17157) **[paper, background]**. CoreInfer (Oct 2024) challenges assumptions behind these methods — [arXiv 2410.18311](https://arxiv.org/pdf/2410.18311) **[secondary]**.
- SparAMX: unstructured sparsity + AMX for decode, 1.42x on linear layers — [arXiv 2502.12444](https://arxiv.org/abs/2502.12444) **[paper]**.

**Expert prefetching / caching systems**
- ProMoE (v3 2025-09-01): predicts upcoming experts from intermediate results and prefetches to GPU; prefill 2.20x avg (up to 3.21x), decode 2.07x avg (up to 5.02x) over reactive offloading baselines — [arXiv 2410.22134](https://arxiv.org/abs/2410.22134) **[paper]**.
- HOBBIT (Nov 2024, built on llama.cpp): replaces cache-miss experts with low-precision versions; token-level dynamic loading, layer-level prefetching, sequence-level caching; up to 9.93x decode over prior offloading systems on edge devices — [arXiv 2411.01433](https://arxiv.org/abs/2411.01433) **[paper, background]**.
- FineMoE/fMoE (v2 2025-10-04): fine-grained expert selection patterns + prompt semantic hints for prefetch/cache; −47% latency and +39% expert hit rate vs SOTA on a six-GPU testbed — [arXiv 2502.05370](https://arxiv.org/abs/2502.05370) **[paper]**.
- CoX-MoE (arXiv 2605.17889, 2026): coalesced expert execution with AMX CPU-GPU co-execution; numbers not retrieved — [arXiv](https://arxiv.org/pdf/2605.17889) **[unverified]**.

### Inferences
- The decisive CPU-side MoE optimisation for consumer boxes is not kernel speed but bytes touched per token: a correct implementation of `mul_mat_id` should stream only the k selected experts' rows per token with one activation-quantisation pass shared across experts, parallelise across (expert, row-chunk) pairs rather than per-expert, and avoid rebuilding token→expert row maps for single-token decode. The 3–4x shortfall in issue #19480 and the 30% barrier share in PR #20596 locate the loss in scheduling/overheads, not in DRAM.
- Expert prefetch across layers (ProMoE-style, using the next layer's router inputs or simple frequency priors) and `madvise(MADV_WILLNEED)` on expert pages are cheap to add in an mmap-based engine and matter most when the model exceeds RAM (LLMario's 8–16 GB machines running 20–30B-A3B models).
- Hot/cold neuron systems require ReLU-sparse checkpoints that mainstream 2025–2026 open models (Qwen3, gpt-oss, Llama 4, DeepSeek) do not ship; they are not a near-term lever for LLMario beyond MoE expert routing itself.

### Gaps
- No reliable Llama 4 Scout CPU or CPU+GPU-offload numbers on consumer hardware were found (one hosting-vendor page gives 5.1 tok/s on an M4 Pro with inconsistent model metadata — [nordicsilicon](https://nordicsilicon.io/blog/mac-mini-m6-m5-pro-llm-benchmarks) **[unreliable]**).
- DeepSeek-R1/V3 on consumer boxes: Unsloth's dynamic-quant blog returned 403; the only community guide (ubergarm, KTransformers) reports ~15 tok/s TG without clear hardware — [ubergarm guide](https://github.com/ubergarm/r1-ktransformers-guide) **[unverified]**.
- Qwen3-235B-A22B on consumer hardware, and expert-prefetch accuracy numbers for ProMoE, were not retrieved.
- PowerInfer-2 source availability could not be confirmed (likely unreleased).

## Key question 7 — Prefill acceleration on CPU

### Takeaway
CPU prefill is compute-bound and has the widest kernel-dependent spread: int8 VNNI/interleaved kernels give 1.5–3.9x on Zen 5 and 1.7–2.8x on Intel client, SME2 via KleidiAI gives 1.2–8x on M4 Pro depending on quant and thread count, Apple's matrix unit reaches ~1.1–1.5 TFLOPS per block (M1 AMX) and ~4.1–4.4 TFLOP/s on M4 Pro (SME), and Intel AMX makes DeepSeek-class prefill 25x faster than AVX-512 ggml on Xeons; attention cost makes throughput fall with prompt length, so long prompts need a flash-attention CPU kernel and large micro-batches.

### Cited Findings
- Batching knobs: logical batch `-b` default 2048, physical micro-batch `-ub` default 512; BLAS backends help prompt processing only at batch > 32 and do not affect generation — [llama-server(1)](https://manpages.debian.org/testing/llama.cpp-tools/llama-server.1.en.html), [docs/build.md](https://github.com/ggml-org/llama.cpp/blob/master/docs/build.md). The gpt-oss guide uses `-ub 2048 -b 2048` on large-memory machines — [discussion #15396](https://github.com/ggml-org/llama.cpp/discussions/15396).
- x86 measured prefill (Oct 2026, llama.cpp master vs PR): 9950X Llama-3.1-8B Q8_0 pp2048 176.8 → 572.0 tok/s, pp4096 168.9 → 496.8 (16 thr); Q4_0 pp2048 305.8 → 580.2; Qwen3-4B Q8_0 pp2048 307 → 811; Core Ultra 7 155H (4 thr) Qwen3-4B Q8_0 pp2048 33.0 → 91.9 — [PR #30036](https://github.com/ggml-org/llama.cpp/pull/30036) **[measured]**; Ryzen AI MAX+ 395 Qwen3-4B Q4_K_M pp512 380.5 → 568.1 (16 thr) — [PR #29397](https://github.com/ggml-org/llama.cpp/pull/29397) **[measured]**; 9950X 8B Q8_0 pp512 ≈ 87–93 on b4397 (Dec 2024) — [OpenBenchmarking](https://openbenchmarking.org/performance/test/pts/llama-cpp/29a6facf82fc79d735d24c7b90ffc1d46f4c1a9b) **[secondary]** (suggestive of a roughly 2x master-to-master improvement in under two years, but the two runs differ in prompt length (pp512 vs pp2048), RAM speed and thread count, so this is indicative only).

### Inferences
- A Rust engine's prefill path should be a proper GEMM with int8-quantised activations tiled to the register file (VNNI `vpdpbusd` on x86; `smmla` on NEON i8mm; `mopa` on SME2), micro-batches of 512–2048 tokens, a fused QKV projection, and a CPU flash-attention kernel; the attention kernel is what keeps pp4096 from collapsing relative to pp512.
- On M4/M5 Macs the CPU can deliver 1–4 TFLOP/s of prefill (SME) which approaches the base/Pro iGPU; for LLMario this means CPU-only prefill is viable on M-series base/Pro laptops for ≤8B models, while on Max/Ultra the GPU remains 2–5x faster for prefill.
- Mixed SME+NEON execution needs a dynamic work queue; static splits lose up to 2x at low thread counts.

### Gaps
- No CPU-only prefill numbers for 7B+ models on M4 Max/M5 Max with KleidiAI on vs off were found; the measured SME2 tables are for 1B models.
- Intel Core Ultra 200V/300 (Lunar/Panther Lake, AVX-VNNI only) prefill numbers were not found.
- The chunked-prefill (micro-batch size) sweep on CPU — how pp throughput varies with `-ub` — was not found in the fetched sources.

## Key question 8 — What a Rust engine must implement to match or beat llama.cpp on CPU (synthesis)

### Takeaway
Matching llama.cpp on CPU means reproducing its int8-dot kernel matrix plus its 2025–2026 additions (interleaved repack GEMMs, VNNI, KleidiAI SME2, AMX), and beating it means fixing the parts the project's own PRs show are weak: MoE expert paths that read 3–4x too much, barrier-heavy scheduling, 100 ms spin-waits, cache-blind repack at every load, and missing thread-count/QoS awareness on Apple hybrid cores.

### Cited Findings
- llama.cpp (MIT; 130k stars; pushed 2026-10-09) is the baseline; ik_llama.cpp (MIT) shows 1.5–3.5x prefill and 1.1–2x decode gains over mainline were available from layout and kernel work alone in late 2024 — [GitHub API](https://api.github.com/repos/ggml-org/llama.cpp), [#164](https://github.com/ikawrakow/ik_llama.cpp/discussions/164).
- Reusable Apache-2.0/MIT building blocks: KleidiAI (Apache-2.0, SME2/i8mm/dotprod micro-kernels as C/asm) — [README](https://raw.githubusercontent.com/ARM-software/kleidiai/main/README.md); oneDNN (Apache-2.0) — [README](https://raw.githubusercontent.com/uxlfoundation/oneDNN/main/README.md); llamafile/tinyBLAS (Apache-2.0) — [README](https://raw.githubusercontent.com/mozilla-ai/llamafile/main/README.md); T-MAC and bitnet.cpp (MIT); KTransformers (Apache-2.0); PowerInfer (MIT); corsix/amx (MIT); candle (Apache-2.0, Rust) — [GitHub API license fields](https://api.github.com/repos/huggingface/candle). No GPL/AGPL/non-commercial licenses were encountered among the CPU-inference projects surveyed; SparAMX/SMEPilot/Vec-LUT code licenses are unknown.
- Rust: AVX2/AVX-512/NEON intrinsics stable; SVE nightly; SME absent; AMX nightly; portable SIMD unstable — see Key question 2.

### Inferences (engineering checklist, ordered by measured payoff)
1. **Decode GEMV kernels** on native GGUF blocks for Q4_0/Q4_K/Q5_K/Q6_K/Q8_0/IQ4_XS/MXFP4 with Q8 activation quantisation, per ISA (AVX2, AVX-512-VNNI, AVX-VNNI, NEON dotprod/i8mm). Target: bytes/token × 0.7 × peak bandwidth (7–8B Q4 ≈ 11 tok/s on dual-channel DDR5-6000; ≈ 25–45 on M-series Pro/Max CPU).
2. **MoE expert path** that touches only selected experts' rows, shares one activation quantisation across experts, parallelises over (expert, chunk) with work stealing, and prefetches next-layer experts; goal is the 20–30 tok/s roofline for A3B models on laptops where llama.cpp gets ~8.
3. **Prefill GEMM** on interleaved/packed weights (8x8 AVX2, 8x4/16x4 VNNI, 4x4/4x8 NEON, SME2 mopa via KleidiAI FFI or `asm!`), fused QKV, CPU flash attention; expect 1.5–4x over naive dot loops as measured in PRs #12332/#29397/#30036/#29219.
4. **Packed-weight cache** on disk (sidecar keyed by model hash/layout), mmapped, so repack cost is paid once and resident memory stays predictable.
5. **Scheduler**: physical-core pools (all performance-class clusters on Apple; P-cores on Intel hybrid), bounded spin then park, one parallel region per fused op, static row partition for decode, work stealing for prefill, no spinning when a GPU owns the step.
6. **Responsiveness controls**: QoS utility/background on macOS, nice/SCHED_BATCH on Linux, below-normal/EcoQoS on Windows, user-settable thread cap, and `--poll 0` semantics by default for background generation.
7. **NUMA/CCD awareness** on multi-node machines: first-touch per node, per-node thread groups, no interleaved repack across nodes.
8. **Optional accelerators**: Accelerate cblas/BNNS for fp32/fp16 prefill on macOS (what MLX does), AMX via asm on Xeon workstations, T-MAC/bitnet LUT kernels only for ≤2-bit or ternary models.

### Gaps
- No single source compares a Rust CPU engine (candle, mistral.rs, etc.) against llama.cpp on the same machine in 2026; such a baseline should be measured by LLMario itself.
