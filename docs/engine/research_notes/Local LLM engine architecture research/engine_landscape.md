## KQ1. Engine-by-engine profiles: language, backends, formats, memory model, scheduler, quantization

### Takeaway
Every mainstream local engine is one of three lineages: ggml/llama.cpp (C/C++, static worst-case preallocation, slot-based continuous batching, now with router/multi-process model management and automatic memory fitting), MLX (lazy array framework with unified-memory design, buffer cache with a soft memory limit, mlx-lm doing continuous batching in Python), or datacenter Python stacks (vLLM/SGLang/TensorRT-LLM: fixed KV pools sized by a per-process fraction, paged attention, prefix caching, heavy Python+PyTorch runtime). The Rust engines (mistral.rs on candle) are the closest existing analogue to the LLMario plan: PagedAttention on CUDA, prefix caching, ISQ, MCP/agent loop, multi-model-per-process, but Metal/CPU paths still run a simpler FCFS scheduler without paged attention, and performance claims are published only for datacenter GPUs.

#### llama.cpp / ggml / llama-server

**Language, license, design goals**
- Plain C/C++ with no dependencies, Apple Silicon "treated as a first-class target", 1.5- to 8-bit integer quantization, custom CUDA kernels plus Vulkan and SYCL, and "CPU+GPU hybrid inference to partly accelerate models larger than the GPU's VRAM"; MIT license; 11,515 commits on the README page as fetched — [Source](https://github.com/ggml-org/llama.cpp).
- ggml (the tensor library underneath) is MIT, "Plain C/C++ implementation without any dependencies", offers "2- to 8-bit integer quantization, plus MXFP4 and NVFP4 microscaling formats", and advertises "zero memory allocations at runtime"; 4,864 commits — [Source](https://github.com/ggml-org/ggml).

**Backends (README table, fetched 2026-10-08)**: BLAS (all), BLIS (all), CANN (Ascend NPU), CUDA (NVIDIA), HIP (AMD), Hexagon (Snapdragon), IBM zDNN, MUSA (Moore Threads), Metal (Apple Silicon), OpenCL (Adreno GPU), OpenVINO (Intel CPU/GPU/NPU, marked "In Progress"), RPC (all), SYCL (Intel GPU), VirtGPU, Vulkan (GPU), WebGPU (all), ZenDNN (AMD CPU); CPU paths cover ARM NEON, x86 AVX/AVX2/AVX-512/AMX and RISC-V — [Source](https://github.com/ggml-org/llama.cpp).

**GGUF format**: v3 (big-endian support), header + typed metadata KV + tensor infos + aligned data section (`general.alignment` default 32), tensor types F32/F16/BF16/F64, Q4_0/Q4_1/Q5_0/Q5_1/Q8_0/Q8_1, K-quants Q2_K..Q8_K, IQ1_S/IQ1_M/IQ2_XXS/IQ2_XS/IQ2_S/IQ3_XXS/IQ3_S/IQ4_NL/IQ4_XS, integer types, TQ1_0/TQ2_0 and MXFP4; mmap-compatibility is a stated design goal; tokenizer and chat template are embedded (`tokenizer.ggml.*`, `tokenizer.chat_template`) — [Source](https://github.com/ggml-org/ggml/blob/master/docs/gguf.md).

**ggml backend architecture (memory and device model)**
- Device types: CPU, GPU, integrated GPU, ACCEL ("accelerator devices intended to be used together with the CPU backend (e.g. BLAS or AMX)") and META (tensor parallelism); backends are registered and can be dynamically loaded (`ggml_backend_load`, `ggml_backend_load_all`); buffer types carry host-vs-device identity (`ggml_backend_buft_is_host`) and usage hints ANY/WEIGHTS/COMPUTE — [Source](https://github.com/ggml-org/ggml/blob/master/include/ggml-backend.h).
- The scheduler `ggml_backend_sched` "Handles compute buffer allocation, assignment of tensors to backends, and copying of tensors between backends"; placement follows which backend supports an op and where pre-allocated tensors (weights) live; "backends with low index are given priority"; buffers are initialised from a max-size (measure) graph via `ggml_backend_sched_reserve`; graphs are "single-use in terms of allocation, multi-use in terms of computation" — [Source](https://github.com/ggml-org/ggml/blob/master/include/ggml-backend.h).
- The graph allocator `ggml_gallocr` pre-allocates buffers from a measure graph ("pre-allocate buffers from a measure graph - does not allocate or modify the graph"); passing a worst-case graph avoids later reallocations; with a single buffer it reallocates automatically when topology changes, with multiple buffer types it returns false and requires `ggml_gallocr_reserve_n` first; inputs are placed at non-overlapping addresses and outputs are never freed — [Source](https://github.com/ggml-org/ggml/blob/master/include/ggml-alloc.h).

**KV cache and compute-buffer allocation (source-level)**
- `llama_kv_cache` allocates K and V tensors per layer in its constructor sized `n_embd_k_gqa x kv_size x n_stream`, with `n_stream = unified ? 1 : n_seq_max`, so memory for the whole context is allocated up front whether or not cells are used; buffers are cleared after allocation "to avoid NaNs in the padding"; with `hparams.no_alloc` a zero-size dummy buffer is used and the true size is computed with `ggml_backend_alloc_ctx_tensors_from_buft_size` for `memory_breakdown()`; `find_slot` searches from a head pointer and wraps; there is no defragmentation routine in this file (K-shift rewrites RoPE positions but does not compact) — [Source](https://github.com/ggml-org/llama.cpp/blob/master/src/llama-kv-cache.cpp).
- `llama_context` pads `n_ctx` to a multiple of 256; with `kv_unified` off, `n_ctx_seq = n_ctx / n_seq_max` (padded to 256); compute buffers are reserved from a worst-case graph with `n_tokens = min(n_ctx, n_ubatch)` and `n_seqs = n_seq_max`, reserving the prompt-processing graph first "so that buffers are only allocated once", then a token-generation graph, then the pp graph again "to avoid ggml-alloc reallocations during inference"; each backend logs `"%10s compute buffer size = %8.2f MiB"`; the previous graph is reused when `res->can_reuse(gparams)` holds (env `LLAMA_GRAPH_REUSE_DISABLE`); `memory_breakdown()` returns per-buffer-type `{model, context, compute}` where context includes the KV memory and the MoE expert cache, exposed as `llama_get_memory_breakdown(ctx)` — [Source](https://github.com/ggml-org/llama.cpp/blob/master/src/llama-context.cpp).
- `llama.h` context params: `n_ctx` "text context, 0 = from model"; `n_seq_max`; `n_rs_seq` (recurrent-state snapshots per sequence, experimental); `type_k`/`type_v`; `flash_attn_type`; `moe_cache_size` "device cache in bytes for the experts kept in host memory" (experimental); `offload_kqv`; `op_offload`; `swa_full` ("setting to false when n_seq_max > 1 can cause bad performance in some cases"); `kv_unified` ("try to disable when n_seq_max > 1 for improved performance when the sequences do not share a large prefix"). Model params: `devices`, `tensor_buft_overrides`, `n_gpu_layers`, `split_mode` (none/layer/row/tensor), `tensor_split`, `load_mode` (auto/none/mmap/mlock/mmap+mlock/direct I/O), `lazy_mode` (OFF "always read the whole tensor up front"; AUTO "lazy only for marked tensors larger than 4 GiB (requires mmap)"; ON "read the rows of tensors marked by the arch on demand"), `use_extra_bufts` (weight repacking), `no_host`, `no_alloc` "only load metadata and simulate memory allocations". Sequence state can be saved/loaded with `LLAMA_STATE_SEQ_FLAGS_ON_DEVICE` ("Keeps the tensor data on device buffers ... faster save/load") and `PARTIAL_ONLY` for SWA/recurrent partial states. Backend sampling: `llama_set_sampler` (experimental) and `llama_get_sampled_token_ith` — [Source](https://github.com/ggml-org/llama.cpp/blob/master/include/llama.h).

**llama-server flags and defaults (tools/server/README.md, fetched 2026-10-08)**
- Context/batch: `-c/--ctx-size` default 0 = from model; `-b` 2048 logical, `-ub` 512 physical; `-fit/--fit` default **on** ("Adjusts unset arguments to fit device memory"); `--fit-target` per-device margin default 1024 MiB; `--fit-ctx` minimum context `--fit` may set, default 4096; `-ngl` default `auto` — [Source](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md).
- Placement: `--device`, `--split-mode {none,layer,row,tensor}` (tensor experimental), `--tensor-split`, `--override-tensor/-ot <pattern>=<buffer type>`, `--cpu-moe`, `--n-cpu-moe N`, `--n-cpu-ffn N`, `--moe-cache-mib N` (GPU cache for CPU-resident experts, default 0), `--load-mode` (auto/none/mmap/mlock/mmap+mlock/dio) — [Source](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md).
- KV: `-ctk/-ctv` default f16 (f32, bf16, q8_0, q4_0, q5_1 allowed); `-fa` auto; `--kv-offload` default on; `--swa-full` default false; `-np/--parallel` default -1 (auto); `--kv-unified` default enabled when slots are auto; `--kv-unified-per-slot N` sizes the shared pool to `n_parallel x N` if `-c` is unset; `--cont-batching` default on; `--context-shift` default disabled — [Source](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md).
- Prompt cache: `--cache-ram` "Maximum prompt-cache size in MiB. Default 8192. -1 means no limit, and 0 disables it"; `--cache-idle-slots` default on (saves idle slot KV to the RAM cache when a new task arrives); `--cache-reuse N` (KV shifting); `--cache-prompt` default on; `--slot-prompt-similarity` 0.10; `--slot-save-path` (disk save/restore via `/slots/{id}?action=save|restore`); `--ctx-checkpoints` 32 per slot; `--checkpoint-min-step` 8192 — [Source](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md).
- Server lifecycle and multi-model: `--sleep-idle-seconds` default -1 (disabled); router mode flags `--models-dir`, `--models-preset`, `--models-max` default 4 (0 = unlimited), `--models-autoload` default on; `--metrics` (Prometheus) default off; `--slots` default on — [Source](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md).

**Router mode (model management), published 2025-12-11 by ngxson and Victor Mustar**: start `llama-server` without a model; each model runs in its own process ("if one model crashes, the others are unaffected"); the request `model` field routes and auto-loads; models are discovered from `LLAMA_CACHE`/`~/.cache/llama.cpp` or `--models-dir`; `--models-preset` INI gives per-model settings (`ctx-size`, `temp`, ...); LRU eviction when `--models-max` (default 4) is reached; endpoints `GET /models`, `POST /models/load`, `POST /models/unload`; flags passed to the router are inherited by all instances; no memory-usage figures or cross-model memory budget are described — [Source](https://huggingface.co/blog/ggml-org/model-management-in-llamacpp). Follow-ups: "server: (router) move model downloading to dedicated process" merged 2026-06-22 (#24834) and "split child commands from logs in router mode" merged 2026-10-04 (#29895) — [Source](https://github.com/ggml-org/llama.cpp/pulls?q=is%3Apr+is%3Amerged+%22fit%22+%22device+memory%22).

**Hybrid/recurrent memory (2025)**: PR #13979 "Hybrid recurrent cache" (gabe-l-hart, IBM; merged 2025-06-19) adds `llama_kv_cache_hybrid_recurrent` holding two child caches (attention and recurrent) following the iSWA-cache pattern, routes each layer to one of them from an hparam listing attention layers, renames `kv` terminology to a neutral `mem_` prefix, and chose two explicit child caches over the more generic #13276 design that reviewers "judged too abstract"; related: #13834 Mamba2 (merged 2025-06-10), #13550 Granite 4, #7531 Jamba — [Source](https://github.com/ggml-org/llama.cpp/pull/13979).

**Graph reuse (2025)**: PR #14482 "llama : reuse compute graphs" (ggerganov, merged 2025-07-17) reuses the previous ubatch's graph when shapes match (requires `ggml_set_rows`); the scheduler is no longer reset after each batch so buffers stay allocated; measured on Apple M2 Ultra (Metal, tg32) gains were 1.02-1.04x (e.g. qwen2 1.5B Q4_0 206.63 -> 215.55 t/s); CUDA results from a contributor were mixed (hardware unstated) — [Source](https://github.com/ggml-org/llama.cpp/pull/14482).

**Backend (GPU) sampling (2026)**: PR #17004 "sampling : add support for backend sampling" (danbev, merged 2026-01-04) moves sampler chains into the compute graph so only the sampled token (or filtered logits) moves to host; sampler tensors use the same buffer type as the output logits to avoid graph splits; limitations: no grammar sampling, one output per sequence per batch, no save/load of sampling state; `-bs/--backend-sampling` flag; end-to-end gpt-oss-20b llama-cli eval throughput rose ~278 -> ~373 t/s (hardware not stated; measured by author) — [Source](https://github.com/ggml-org/llama.cpp/pull/17004).

**Metal 4 tensor API for M5 (2025)**: PR #16634 "metal : initial Metal4 tensor API support" (ggerganov, opened 2025-10-17, merged 2025-11-06) reworks Metal matmul to use MetalPerformancePrimitives matmul when supported; used only on M5 and later because on M2 Ultra it was slightly slower than the simdgroup kernels; measured on M5 (llama-bench): Llama 7B Q4_0 pp512 252.82 -> 608.05 t/s, tg128 27.55 -> 26.59; gpt-oss 20B MXFP4 pp512 415.45 -> 846.69, tg128 32.53 -> 42.63; Llama 3.1 8B Q4_0 on an M5 MacBook Pro 32 GB pp512 257.25 -> 609.26, pp2048 247.79 -> 540.15, tg128 22.56 -> 22.88 — [Source](https://github.com/ggml-org/llama.cpp/pull/16634).

**Hexagon NPU backend (Snapdragon)**: official docs: builds Hexagon v73/v75/v79/v81 libraries; "A single NPU session provides ~3.5GB of available virtual address space", so larger models either map/unmap weight buffers dynamically during graph execution or are split: layer-split across virtual sessions (`HTP0:0,HTP0:1`, partitioned at load time, which "eliminates runtime buffer re-mapping overhead"), tensor-split across physical NPUs (`--split-mode tensor`), or row-split via device grouping (`HTP0[0-1]`); the backend logs itself as experimental; sample logs (single runs, version not stated): Llama-3.2-1B Q4_0 on Hexagon v79 pp128 169.42 t/s, tg64 51.54 t/s; Gemma-2-2B Q4_0 on Android prompt eval 3200 t/s, eval 47.62 t/s; GPT-OSS-20B on four virtual sessions on one NPU prompt eval 51.25 t/s, eval 18.39 t/s; builds use Qualcomm's `snapdragon-toolchain` Docker images with the Hexagon SDK 6.6.0.0 and NDK r28b; SDK licensing is not discussed — [Source](https://github.com/ggml-org/llama.cpp/blob/master/docs/backend/snapdragon/README.md). A search summary attributes the backend to PR #16547, lists Snapdragon 8 Gen 3 / 8 Elite / 8 Elite Gen 5 and Q4_0/Q8_0/MXFP4/FP32 support, and one documented run of gpt-oss-20B Q4_0 across four Hexagon devices on a 16 GB device — unverified (seen only in fork mirrors of `docs/backend/snapdragon/developer.md`) — [Source](https://huggingface.co/OpenTransformer/llama.cpp-prismml/blob/main/docs/backend/snapdragon/developer.md).

**MoE expert GPU cache (2026)**: PR #29887 "llama : add a GPU cache for MoE experts kept in host memory" (am17an, merged 2026-10-07): MUL_MAT_ID ops on host-resident experts run on the GPU from an LRU cache of experts, only misses are uploaded, applies to batches <= 32 tokens, enabled with `--moe-cache-mib N` (author suggests ~10 % of total expert size); with `--fit` the cache counts against the VRAM budget; single-device at launch, multi-GPU in #30112 (merged 2026-10-08). Community: AMD R9700 32 GB (ROCm, Windows) IQ1_M `-cmoe` tg 11.0 -> 27.6 t/s with a 16000 MiB cache; with MTP enabled on dual RTX 3090 the cache was 25-34 % slower — [Source](https://github.com/ggml-org/llama.cpp/pull/29887).

**Design lessons from llama.cpp (inference unless cited)**
- Good: a single tensor library with a backend registry, buffer types that encode host-vs-device, a scheduler that splits a graph by where weights live, and a graph allocator that reserves from a worst-case graph once — this is what makes "hybrid CPU+GPU" nearly free to express — [Source](https://github.com/ggml-org/ggml/blob/master/include/ggml-backend.h).
- Good: a simulated-allocation mode (`no_alloc`) plus an explicit memory breakdown API; `--fit` was only possible because allocation sizes can be computed without allocating — [Source](https://github.com/ggml-org/llama.cpp/blob/master/include/llama.h), [Source](https://github.com/ggml-org/llama.cpp/blob/master/src/llama-kv-cache.cpp).
- Good: per-process model isolation in router mode (crash containment) and a capped, bounded prompt cache (`--cache-ram` default 8192 MiB) — [Source](https://huggingface.co/blog/ggml-org/model-management-in-llamacpp), [Source](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md).
- Bad/costly: the KV cache is allocated for the full `n_ctx` x streams at context creation and compute buffers for the worst-case ubatch; `n_ctx` defaults to the model's training context (0 = from model), so the memory footprint of "just run it" depended on the model card until `--fit` landed and then needed ~20 follow-up fixes over two months — [Source](https://github.com/ggml-org/llama.cpp/blob/master/src/llama-kv-cache.cpp), [Source](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md), [Source](https://github.com/ggml-org/llama.cpp/pulls?q=is%3Apr+is%3Amerged+author%3AJohannesGaessler+fit).
- Bad/costly: non-unified multi-sequence mode divides `n_ctx` by `n_seq_max` (each slot gets `n_ctx/n_seq_max`), which surprises users; the unified buffer fixes sharing but the header warns to disable it when sequences share little prefix — [Source](https://github.com/ggml-org/llama.cpp/blob/master/src/llama-context.cpp), [Source](https://github.com/ggml-org/llama.cpp/blob/master/include/llama.h).
- Bad/costly: no in-file defragmentation; `find_slot` requires contiguous runs for some paths, so fragmentation shows up as "no slot" failures rather than compaction — [Source](https://github.com/ggml-org/llama.cpp/blob/master/src/llama-kv-cache.cpp).
- Ecosystem risk: prebuilt engine bundles can silently lose hardware features (LM Studio's Metal runtime 2.21.0 failed the Metal 4 tensor-API check and lost 2-2.4x prefill on M5 Max; upstream b9592 passed on the same machine) — [Source](https://github.com/lmstudio-ai/lmstudio-bug-tracker/issues/2040).

#### MLX and mlx-lm (Apple)

**Language, license, platforms**: MLX is MIT; "Familiar APIs" (Python/C++/C/Swift), composable function transformations, lazy computation ("Arrays are materialized only when needed"), dynamic graph construction, multi-device (CPU or GPU), unified memory ("Arrays live in shared memory, so operations on any supported device need no data transfer"); install targets macOS (`pip install mlx`), Linux CUDA (`pip install mlx[cuda]`), Linux CPU (`mlx[cpu]`); 28.7k stars, 2,399 commits — [Source](https://github.com/ml-explore/mlx).

**Unified memory and streams**: arrays are created without a device; the device is specified per operation (`mx.add(a, b, stream=mx.cpu)` vs `stream=mx.gpu`); the scheduler inserts cross-stream dependencies automatically; the docs' example splits a matmul (GPU) from a 500-step `exp` loop (CPU) and reports ~2.8 ms all-GPU vs ~1.4 ms split on an M1 Max (background, pre-2025 example) — [Source](https://ml-explore.github.io/mlx/build/html/usage/unified_memory.html).

**Lazy evaluation and memory**: nothing is computed until `eval()`; creating a model "allocates nothing until evaluation", and loading weights as float16 instead of float32 halves peak memory relative to eager execution; graphs of tens to thousands of ops per eval "generally work well"; MLX "doesn't currently compile and rerun graphs; they're generated dynamically" — [Source](https://ml-explore.github.io/mlx/build/html/usage/lazy_evaluation.html).

**Memory limits and caches**: `set_memory_limit(bytes)` is "a guideline for the maximum amount of memory to use during graph evaluation"; default when Metal is available is "1.5 times the device's maximum recommended working set size"; if exceeded and no RAM (incl. swap) remains, allocations raise an exception — [Source](https://ml-explore.github.io/mlx/build/html/python/_autosummary/mlx.core.set_memory_limit.html). `set_cache_limit(bytes)` caps the free-buffer cache, "defaults to the memory limit", excess is reclaimed on the next allocation, 0 disables the cache — [Source](https://ml-explore.github.io/mlx/build/html/python/_autosummary/mlx.core.set_cache_limit.html). `set_wired_limit(bytes)` keeps memory resident (default 0; must stay below total memory; values above the system wired limit are an error; the system limit is `device_info()["max_recommended_working_set_size"]` and can be raised with `sudo sysctl iogpu.wired_limit_mb=<MB>`; macOS 15.0+) — [Source](https://ml-explore.github.io/mlx/build/html/python/_autosummary/mlx.core.set_wired_limit.html).

**Quantization modes**: `affine` (group 32/64*/128, bits 2/3/4*/5/6/8, scales+biases), `mxfp4` (group 32, e8m0 scales), `mxfp8` (group 32, e8m0), `nvfp4` (group 16, e4m3 scales, optional `global_scale`); fp modes have no bias — [Source](https://ml-explore.github.io/mlx/build/html/python/_autosummary/mlx.core.quantize.html).

**M5 Neural Accelerators (Metal 4)**: Apple ML Research (2025-11-19): MLX uses Metal 4 TensorOps / Metal Performance Primitives; requires macOS 26.2+; on a 14-inch MacBook Pro M5 24 GB vs an M4 model with `mlx_lm.generate`, 4096-token prompt, 128 generated tokens: TTFT speedups 3.57x (Qwen3-1.7B bf16, 4.40 GB), 3.62x (Qwen3-8B bf16, 17.46 GB), 3.97x (Qwen3-8B 4-bit, 5.61 GB), 4.06x (Qwen3-14B 4-bit, 9.16 GB), 3.33x (gpt-oss-20b MXFP4, 12.08 GB), 3.52x (Qwen3-30B-A3B 4-bit, 17.31 GB); generation speedups 1.19-1.27x, attributed to bandwidth 153 GB/s vs 120 GB/s; absolute tokens/s only in a figure (vendor-measured) — [Source](https://machinelearning.apple.com/research/exploring-llms-mlx-m5).

**CUDA backend**: announced 2025-07-25 (`pip install "mlx[cuda]"`, CUDA Toolkit 12.0+, driver 550.54.14+); at launch missing quantized matmul/matvec, gather mm (MoE), FFT and LAPACK ops, and "MLX will crash for missing ops" (CPU fallback by passing `mx.cpu` as stream); a commenter notes it is Linux-only and does not add CUDA to macOS — [Source](https://github.com/ml-explore/mlx/discussions/2422). Later releases filled gaps: v0.31.2 (Apr 22) "Wider CUDA quantized matmul support" (pipelined QMM, int4/fp quants for `qmm_sm80`, 3/5/6-bit in `qmm_naive`, GatherQMM); v0.32.0 (Jul 7) JIT-compiled `qmm_naive`, cached JIT CUDA kernels, buffer caching for the no-GPU CPU allocator, Windows JIT support; v0.32.1 (Aug 18) "zero-copy CPU import on unified memory", nvfp4 fixes; v0.32.2 (Aug 25) fused NAX attention for head_dim 256, bounded winograd conv working set; v0.32.3 (Sep 29) NAX fixes above 32K rows, M5 Ultra tunings, "Lower Metal memory use for SDPA at D256 and D512", DXGI-based WDDM VRAM budget on Windows (release years not printed on the page; sequence places them in 2026) — [Source](https://github.com/ml-explore/mlx/releases).

**mlx-lm (MIT)**: README: `mlx_lm.generate`/`chat`/`server`, prompt caching to file (`mlx_lm.cache_prompt`), batch generation, distributed inference via `mx.distributed`; "mlx-lm tries to wire the model and cache memory, which requires macOS 15.0 or higher" and advises raising `iogpu.wired_limit_mb`; `--max-kv-size` (rotating cache) and `--prefill-step-size` (default 2048; smaller lowers peak memory) are the memory levers — [Source](https://github.com/ml-explore/mlx-lm).
- Server internals (`server.py`): a `ResponseGenerator` thread drains a request queue; batchable requests (no draft model, all caches support `merge`, no `seed`, `kv_bits` unset) go into a `BatchGenerator` (continuous batching), others run one at a time; a `TimeBudget` limits each batch step to ~0.5 s; defaults `--decode-concurrency 32`, `--prompt-concurrency 8`, `--prefill-step-size 2048`, `--prompt-cache-size 10` entries, `--prompt-cache-bytes` None (unlimited unless set), `--kv-bits` None (quantized KV "disables batching"), `--kv-group-size 64`, `--max-tokens 512`, `--num-draft-tokens 3`; only one model is held at a time (a different `model` field triggers `reset()`, `gc.collect()`, `mx.clear_cache()` and reload after draining the batch) — [Source](https://github.com/ml-explore/mlx-lm/blob/main/mlx_lm/server.py). SERVER.md: "The MLX LM server is not recommended for production as it only implements basic security checks"; with a quantized KV cache attention is not fused and keeps a `prefill_step_size x context_length` score matrix that "can exceed the memory the quantized cache saves" — [Source](https://github.com/ml-explore/mlx-lm/blob/main/mlx_lm/SERVER.md).
- Cache internals (`models/cache.py`): `KVCache`, `BatchKVCache`, `QuantizedKVCache` grow in `step = 256` token chunks by concatenation; `trim(n)` lowers the offset "without freeing memory", so `nbytes` reflects allocated, not logical, size; `QuantizedKVCache` default bits 8 / group 64; `RotatingKVCache` is a bounded ring buffer; `LRUPromptCache(max_size=10, max_bytes=1<<63)` keys a trie by model then token prefix, keeps per-type (`system`/`user`/`assistant`) queues, evicts oldest-inserted first (fetch does not refresh recency), returns deep copies and trims longer matches; `trim_to(n_sequences, n_bytes)`; no locking — [Source](https://github.com/ml-explore/mlx-lm/blob/main/mlx_lm/models/cache.py).
- Loading (`utils.py`): `mx.load()` per safetensors shard then `mx.eval(model.parameters())` unless `lazy=True`; quantized layers are instantiated from per-layer config or inferred from `.scales` tensors (affine, nvfp4, mxfp4, mxfp8); AWQ/GPTQ weights are repacked; `maybe_set_recommended_wired_limit()` sets the wired limit to `max_recommended_working_set_size` — [Source](https://github.com/ml-explore/mlx-lm/blob/main/mlx_lm/utils.py).
- Releases (2025-12 to 2026-04): v0.30.0 (Dec 18) model-parallel generation, idle-server busy-wait fix; v0.30.1 (Jan 6) GIL starvation fix; v0.30.4 (Jan 19) cache-list batching and a continuous-batching server benchmark; v0.30.6 (Feb 4) distributed inference in the server; v0.31.0 (Mar 7) "Cache size limit improvements", `mx.clear_cache()` in server prompt processing, cached-token counts in usage; v0.31.2 (Apr 7) caching of system prompts and user messages in non-trimmable caches, batch generator refactor, Gemma 4, GatedDeltaNet shared-buffer leak fix; v0.31.3 (Apr 22) batch KV `extend()` dimension fix — [Source](https://github.com/ml-explore/mlx-lm/releases). A proposed `--prompt-cache-dir` (persist LRU prompt cache to disk, PR #1405) is shown closed, i.e. the server cache is in-memory only — unverified detail from a search summary — [Source](https://github.com/ml-explore/mlx-lm/pull/1405).

**Design lessons from MLX (inference unless cited)**
- Good: a soft memory limit expressed against the OS "recommended working set" plus a separately capped buffer cache, both queryable (`get_active_memory`, `get_peak_memory`, `get_cache_memory`) — simple, predictable knobs a desktop supervisor can set per model — [Source](https://ml-explore.github.io/mlx/build/html/python/_autosummary/mlx.core.set_memory_limit.html).
- Good: lazy loading means quantized weights are never materialised in fp32; unified memory removes host<->device copies entirely on Apple Silicon — [Source](https://ml-explore.github.io/mlx/build/html/usage/lazy_evaluation.html), [Source](https://ml-explore.github.io/mlx/build/html/usage/unified_memory.html).
- Bad/costly: the default memory limit is 1.5x the recommended working set, i.e. MLX will happily overshoot physical GPU budget into swap before failing; the cache limit "defaults to the memory limit", so freed buffers are retained up to that limit unless the app lowers it — [Source](https://ml-explore.github.io/mlx/build/html/python/_autosummary/mlx.core.set_memory_limit.html), [Source](https://ml-explore.github.io/mlx/build/html/python/_autosummary/mlx.core.set_cache_limit.html).
- Bad/costly: KV caches grow by concatenation in 256-token steps and never shrink on trim; the prompt cache byte limit is unbounded by default and the LRU is insertion-ordered; the Python server serialises when KV quantization is on — [Source](https://github.com/ml-explore/mlx-lm/blob/main/mlx_lm/models/cache.py), [Source](https://github.com/ml-explore/mlx-lm/blob/main/mlx_lm/server.py).
- Bad/costly: CUDA backend "crashes for missing ops" rather than falling back — a lesson for op-coverage gating in a new backend — [Source](https://github.com/ml-explore/mlx/discussions/2422).

#### Ollama

**Language, license, architecture**: Go with CGO-compiled native code; MIT; 182k stars; repository contains `runner`, `mlxrunner`, `MLX_VERSION`, `MLX_C_VERSION` (i.e. MLX is consumed through the MLX C API) — [Source](https://github.com/ollama/ollama). `llm/server.go` states "All GGUF models are served via the upstream llama-server subprocess" and exposes `Pid()`/`GetPort()` per loaded model; `Load(..., requireFull bool)` returns `ErrLoadRequiredFull` ("unable to load full model on GPU") when a model cannot be fully placed; requested `NumCtx` above the training context is clamped with a warning — [Source](https://github.com/ollama/ollama/blob/main/llm/server.go). Build docs: MLX is enabled by default on macOS arm64; other platforms select llama.cpp backends with `-DOLLAMA_LLAMA_BACKENDS` (`cuda_v12`, `cuda_v13`, `rocm_v7_1`, `rocm_v7_2`, `vulkan`, Jetpack) and MLX backends with `OLLAMA_MLX_BACKENDS` (e.g. `cuda_v13`) — [Source](https://docs.ollama.com/development).

**New engine (2025)**: blog 2025-05-15: Ollama moved from relying on llama.cpp for model support to "access GGML directly from Go" to build per-model inference graphs; stated goals: model modularity, accuracy for large images/batches, memory management ("image caching, memory estimation, and KV cache optimizations"), chunked attention for Llama 4; hardware-partner-validated memory metadata; Gemma 3 sliding-window attention lets Ollama "allocate part of the context length" — [Source](https://ollama.com/blog/multimodal-models). Issue #11060 (2025-06-13, RTX 3090 Ti, `qwen3:30b-a3b`) reported the new engine at 12-60 tok/s vs >100 on the old engine ("10x slower"); closed as not planned, no root cause confirmed — [Source](https://github.com/ollama/ollama/issues/11060).

**New model scheduling (2025-09-23)**: the scheduler "now measures the exact memory a model needs before loading it, instead of relying on the earlier estimate", for models on the new engine; vendor-measured: gemma3:12b at 128k context on one RTX 4090 went 52.02 -> 85.54 tok/s with VRAM 19.9 -> 21.4 GiB and layers 48/49 -> 49/49; mistral-small3.2 at 32k on 2x RTX 4090 prompt eval 127.84 -> 1380.24 tok/s — [Source](https://ollama.com/blog/new-model-scheduling).

**Scheduler (`server/sched.go`)**: when other models are resident a new load runs with `requireFull=true`; VRAM is predicted (`llm.PredictServerVRAM`) and the fit test is `predictedForLoad > freeMemory*80/100` -> "needs eviction"; placement prefers one GPU that fits at 80 % of available memory unless `SchedSpread`; eviction picks runners with `refCount == 0` ordered by shortest `sessionDuration`; `keep_alive` timers expire runners; `OLLAMA_MAX_LOADED_MODELS` defaults to `defaultModelsPerGPU` (3) x GPU count; `OLLAMA_NUM_PARALLEL` multiplies the predicted context (embedding and several VLM architectures forced to 1); the pending channel is buffered to `OLLAMA_MAX_QUEUE` ("server busy, please try again. maximum pending requests exceeded"); after unloading, `waitForVRAMRecovery` polls every 250 ms up to 5 s because "Free memory reporting on GPUs can lag"; on OOM it first retries with context reduced to 4096 or 32768, then evicts all other models and retries once; a comment notes "llama-server auto-detects layers based on available VRAM" — [Source](https://github.com/ollama/ollama/blob/main/server/sched.go). FAQ defaults: `OLLAMA_MAX_LOADED_MODELS` = 3 x GPUs; `OLLAMA_NUM_PARALLEL` = 1 ("Required RAM scales with NUM_PARALLEL times CONTEXT_LENGTH"); `OLLAMA_MAX_QUEUE` = 512; `OLLAMA_CONTEXT_LENGTH` = 4096; `OLLAMA_KEEP_ALIVE` = 5 min; `OLLAMA_FLASH_ATTENTION` auto; `OLLAMA_KV_CACHE_TYPE` f16 (q8_0 ~half, q4_0 ~quarter; requires flash attention; global); a new model must fully fit in VRAM to load concurrently — [Source](https://docs.ollama.com/faq). GPU docs: Vulkan "Enabled by default once the backend is installed", disable with `OLLAMA_VULKAN=0`; Vulkan needs root or `cap_perfmon` to expose VRAM data, otherwise Ollama falls back to estimates; CUDA needs compute capability 5.0+ and driver 550+; ROCm v7 — [Source](https://docs.ollama.com/gpu).

**MLX on Apple Silicon (2026)**: PR #13648 "Add experimental MLX backend and engine with imagegen support" (dhiltgen, merged 2026-01-09; `go build -tags mlx`, CMake `MLX` preset, macOS and a Linux CUDA build, imagegen first, text/embeddings later; ~28,000 lines added per a commenter) — [Source](https://github.com/ollama/ollama/pull/13648). Blog 2026-03-30 (Ollama 0.19 preview): "Ollama on Apple silicon is now built on top of Apple's machine learning framework, MLX, to take advantage of its unified memory architecture"; M5/M5 Pro/M5 Max use the GPU Neural Accelerators; preview accelerates Qwen3.5-35B-A3B (NVFP4 tag `qwen3.5:35b-a3b-coding-nvfp4`), requires >32 GB unified memory; vendor-measured on 2026-03-29 (hardware unspecified): prefill 1154 -> 1810 tok/s, decode 58 -> 112 tok/s (Ollama 0.18 Q4_K_M vs 0.19 NVFP4; int4 reaches 1851/134); KV cache is reused across conversations with snapshots "at intelligent locations" and prefix-preserving eviction — [Source](https://ollama.com/blog/mlx). Release v0.19.0 (Mar 27) also fixed "a KV cache snapshot memory leak in the MLX runner" and added periodic snapshots during prompt processing — [Source](https://github.com/ollama/ollama/releases/tag/v0.19.0). Later: v0.34.2 (Sep 15, 2026) "Fixes excessive memory growth during long generations with MLX speculative decoding"; v0.40.0 (Sep 25, 2026) "On Apple Silicon, MLX-supported architectures run on MLX by default" (gemma4, qwen3.6, qwen3.5, decision models, embeddinggemma-2); v0.40.1 (Oct 7) "Drops a Metal residency patch now upstream in MLX"; v0.40.2 (Oct 8) models from earlier versions are upgraded in the background "for llama.cpp compatibility" — [Source](https://github.com/ollama/ollama/releases).

**Overhead evidence**: issue #14861 (2026-03-15, Ollama 0.18.0, Apple chip unspecified, `qwen3.5:35b-a3b-q8_0`): Ollama vs raw llama.cpp prompt processing 640.08 vs 1001.39 tok/s and generation 32.54 vs 53.53 tok/s at 471 prompt tokens; 627.12 vs 924.02 and 28.81 vs 42.66 at 33,057 tokens; gpt-oss:20b generation 73.84 vs 93.66; open with no maintainer response — [Source](https://github.com/ollama/ollama/issues/14861). (A third-party article attributes a ~2x gap to "Ollama's Go wrapper" — opinion, unverified — [Source](https://yage.ai/share/mlx-apple-silicon-en-20260331.html).)

**Design lessons from Ollama (inference unless cited)**
- Good: process-per-model runners, idle eviction with keep-alive, a queue with an explicit overload error, and a VRAM-recovery wait after unload (GPU free-memory reporting lags) — [Source](https://github.com/ollama/ollama/blob/main/server/sched.go).
- Good: replacing estimates with measured allocations (Sep 2025) removed a class of OOM crashes and raised offload — [Source](https://ollama.com/blog/new-model-scheduling).
- Bad/costly: a Go re-implementation of the inference graph on top of ggml opened a window of large regressions (10x slowdown reports) and, by 2026, GGUF serving is delegated back to "the upstream llama-server subprocess" — [Source](https://github.com/ollama/ollama/issues/11060), [Source](https://github.com/ollama/ollama/blob/main/llm/server.go).
- Bad/costly: default context 4096 and global `OLLAMA_KV_CACHE_TYPE` (no per-model KV policy); `NUM_PARALLEL` multiplies the whole context per slot — [Source](https://docs.ollama.com/faq).
- Bad/costly: MLX adoption was gated on >32 GB machines and one model, and brought its own leaks (KV snapshot leak, speculative-decoding memory growth) — [Source](https://ollama.com/blog/mlx), [Source](https://github.com/ollama/ollama/releases/tag/v0.19.0), [Source](https://github.com/ollama/ollama/releases).

#### mistral.rs (Rust)

- MIT (copyright Eric Buehler, 2024) — [Source](https://github.com/EricLBuehler/mistral.rs/blob/master/LICENSE). Rust crate `mistralrs` and Python package `mistralrs`; backends: CUDA (FlashAttention V2/V3, optional cuTile acceleration requiring NVIDIA's `tileiras` tool), Metal, CPU (Linux and Windows; MKL/Accelerate wheel variants), multi-GPU/distributed (NCCL tensor parallelism, P2P layer mapping, multi-node, ring); formats: Hugging Face checkpoints, GGUF, UQFF; quantization: ISQ, GGUF 2-8 bit, GPTQ, AWQ, HQQ, FP8, BNB, per-layer topology, auto-selection of the fastest method for the hardware; PagedAttention "for high-throughput continuous batching on CUDA or Apple Silicon"; prefix caching incl. multimodal; continuous batching on by default; models can be loaded/unloaded at runtime; MCP client (process/HTTP/WebSocket), tool calling with grammar enforcement, server-side agentic loop, tool dispatch URL, web search with embedding ranking, sandboxed persistent Python/shell execution, Skills and file inputs; `mistralrs tune` recommends quantization and device mapping. Performance claims in README (v0.8.2, datacenter GPUs only, vendor-measured): Gemma 4 E4B Q8 prefill 26,220.6 tok/s (mistral.rs) vs 11,702.1 (llama.cpp) on H100 SXM; Q8 decode on B200 241.4 vs 194.4; BF16 Gemma 4 26B-A4B prefill 2,766.0 (mistral.rs) vs 26,295.9 (vLLM) on H100; BF16 decode on B200 159.6 vs 220.2 — [Source](https://github.com/EricLBuehler/mistral.rs/blob/master/README.md).
- PagedAttention guide: `--paged-attn auto` "enables paged attention on CUDA and disables it on Metal and CPU"; pool sized by one of `--pa-memory-mb`, `--pa-memory-fraction`, `--pa-context-len`; default on a dedicated CUDA GPU: model + KV get 90 % of total VRAM after runtime reservations; on unified-memory CUDA devices (DGX Spark, Jetson) the budget is system RAM minus 1 GiB capped at the model context, overridable via `MISTRALRS_IGPU_MEMORY_FRACTION`; `--pa-block-size` default 32 (8/16/32 allowed); `--pa-cache-type f8e4m3` halves K/V storage (not for MLA); prefix caching = reference-counted shared blocks; freed CUDA scratch allocations are kept for reuse and trimmed on idle/memory pressure; `--max-num-batched-tokens` 4096, `--max-prefill-chunk-tokens` 512 (CUDA only), `--max-decode-steps-before-prefill` 8; CUDA graphs apply to decode only — [Source](https://docs.mistralrs.dev/guides/perf/paged-attention/).
- Throughput tuning: `--max-seqs` 32 (Python 16); when the block pool runs out mid-generation the scheduler preempts a running sequence, frees its blocks and requeues it (recomputation); without paged attention (Metal, CPU, or off) scheduling is first-come-first-served with sequences "batched by equal length"; `--prefix-cache-n` 16 cached prefixes on device; auto device mapping reserves worst case for `--max-seq-len` 4096 and `--max-batch-size` 1; CPU worker count defaults to high-capacity cores on heterogeneous Linux (`RAYON_NUM_THREADS`, `CANDLE_CPU_MASK`, `CANDLE_CPU_AFFINITY`); FlashInfer paged kernels and CUDA decode graphs on by default; no throughput figures given — [Source](https://docs.mistralrs.dev/guides/perf/throughput-tuning/).
- Serve CLI (defaults): `--paged-attn auto`; `--pa-block-size` 32; `--pa-cache-type auto`; `--no-kv-cache` false; `--encoder-cache-memory-mb` cap for multimodal encoder cache; `--lora-max-bytes` 8 GiB; `--sb-max-memory-mb` 2048 per sandboxed session; `-n/--device-layers "0:10;1:20"` (omit for automatic mapping); `--topology` YAML; `--cpu`; `--max-seq-len` 4096; `--max-batch-size` 1; `--prefix-cache-n` 16; `--max-seqs` 32; `--isq` levels 2/3/4/5/6/8 or names like `q4k`/`q8_0`; `--mcp-config` (or `MCP_CONFIG_PATH`); `--enable-search` with `--search-embedding-model embedding-gemma` — [Source](https://ericlbuehler.github.io/mistral.rs/reference/cli/serve/).
- Multiple models per process: TOML `[[models]]` with `model_id` and optional `[models.quantization]`; each entry is "one loaded model, running on its own engine" (no shared scheduler); request `model` field selects; `POST /v1/models/unload|reload|status`, `GET /v1/models` with `loaded`/`unloaded`/`reloading`; multi-model is server-only in Python and `MultiModelBuilder` in Rust; no cross-model memory budget described — [Source](https://docs.mistralrs.dev/guides/serve/multiple-models/).
- Releases (2026): v0.8.23 (Jun 25) ISQ executor/planning, PagedAttention FCFS preemption-priority fix, CUDA 13.3; v0.9.0 (Jul 7) multi-model loading planning, UQFF per model ID, improved Metal runtime and AOT compilation, aarch64 CPU repacking kernels, x86/aarch64 decode/prefill optimizations; v0.9.1 (Aug 14) "Major scheduler and concurrent-serving improvements", true LoRA kernels, LM-head/embedding quantization, GGUF loading for all supported models, Metal kernel warmup; v0.9.2 (Aug 20) Qwen3.5 MTP with CUDA graphs and quantized drafter, DFlash/DFlash 2 block-diffusion drafters, CUDA graph batch buckets, hybrid-model auto device map, new scheduler and TTFT/ITL metrics; v0.9.3 (Sep 7) first-class FP8 (tensor-core gemv/gemm, ModelOpt/compressed-tensors checkpoints via cuTile), NVFP4 loading with Blackwell acceleration, fused FP8 MoE kernel, load-time kernel autotuner, Anthropic Messages API; v0.9.4 (Sep 24) candle and cutile bumps, server hardening, wheels for CUDA 12.8 (sm80-sm120), 12.9 (sm121), 13.0 (sm100) — [Source](https://github.com/EricLBuehler/mistral.rs/releases).

**Design lessons from mistral.rs (inference unless cited)**
- Good: Rust proves out ISQ (quantize at load from any HF checkpoint), per-layer topology files, auto device mapping with an explicit worst-case reservation, independent engines per model with unload/reload endpoints, and a built-in MCP/agent loop — all items on LLMario's wish list — [Source](https://github.com/EricLBuehler/mistral.rs/blob/master/README.md), [Source](https://docs.mistralrs.dev/guides/serve/multiple-models/).
- Bad/costly: the memory story is still "90 % of VRAM" per process with manual fractions; Metal/CPU lack paged attention and fall back to FCFS equal-length batching; released performance is only for H100/B200; wheels and features are CUDA-first — [Source](https://docs.mistralrs.dev/guides/perf/paged-attention/), [Source](https://docs.mistralrs.dev/guides/perf/throughput-tuning/), [Source](https://github.com/EricLBuehler/mistral.rs/blob/master/README.md).

#### candle (Rust tensor library, Hugging Face)

- Dual Apache-2.0 / MIT; "Optimized CPU backend with optional MKL support for x86 and Accelerate for macs", CUDA with NCCL multi-GPU, optional cuDNN and an opt-in `cutile` JIT feature, WASM; `candle-metal-kernels` directory (Metal not described in README text); formats safetensors, npz, ggml, PyTorch; "Quantization support using the llama.cpp quantized types"; `candle-flash-attn` (v2) and a `candle-flash-attn-v3` directory; stated goal "make serverless inference possible" and remove Python from production; ~21.2k stars, 2,725 commits, 534 open issues, 383 open PRs, no GitHub releases — [Source](https://github.com/huggingface/candle). crates.io: `candle-core` latest 0.11.0 (2026-06-26), 0.10.2/0.10.1 (2026-04-01), 0.10.0 (2026-03-31), 0.9.2 (2026-01-24); 37 versions; license "MIT OR Apache-2.0" — [Source](https://crates.io/crates/candle-core).

#### ExLlamaV2 (archived) and ExLlamaV3

- ExLlamaV2 page says "This project is archived for now" and "Development continues on ExLlamaV3"; MIT; EXL2 is GPTQ-method based with 2/3/4/5/6/8-bit levels mixed within a model for "any average bitrate between 2 and 8 bits per weight"; dynamic generator with paged attention via Flash Attention 2.5.7+, dynamic batching, prompt caching and K/V cache deduplication; CUDA builds (ROCm not mentioned) (background, pre-2025 features) — [Source](https://github.com/turboderp-org/exllamav2).
- ExLlamaV3: MIT; Python with a C++/CUDA extension compiled at first import, plus Triton kernels for attention, cache and recurrent ops; targets "modern consumer-class GPUs"; requires PyTorch >= 2.6 with CUDA 12.4+, `triton-windows` on Windows; no ROCm/AMD/Apple mention; EXL3 is "a streamlined variant of QTIP" (Cornell RelaxML) with a fused Viterbi kernel and on-the-fly Hessians; conversion "a couple of minutes for smaller models, up to a few hours for larger ones (70B+) on a single high-end consumer GPU"; 2-8-bit KV cache quantization; "Flexible tensor-parallel and expert-parallel inference for consumer hardware setups"; CPU expert offloading (AVX2/AVX-512) for large MoE; continuous dynamic batching, speculative decoding, multimodal; README benchmarks are images only (Llama 3.1 8B bpw and KLD charts); wheel example v0.0.6, 1,996 commits — [Source](https://github.com/turboderp-org/exllamav3). Conversion options: fractional `-b` targets (e.g. 3.75), separate head/MTP/vision/embedding/n-gram bits, per-tensor recipe YAML, `-hq` raises attention/shared-expert bits ("typically adds 0.05-0.10 bpw" on MoE), codebooks `mul1` (default; required by int8 GEMV and CPU expert offload paths), `mcg`, `3inst`; trellis encoding with one-sided LDLQ rounding (two-sided when output Hessians exist), Hessians from `util/yaqa_hessians.py`, default calibration 250 rows x 2048 columns, checkpoint every 120 s — [Source](https://github.com/turboderp-org/exllamav3/blob/master/doc/convert.md).
- Independent measurement (2026-09-14, RTX 5090 32 GB on RunPod, Ubuntu 24.04, driver 570.195.03, CUDA 12.8, ExLlamaV3 1.4.9 via TabbyAPI, llama.cpp commit 8172e6577, Gemma 4 12B, batch 1, 16k FP16 cache, no speculative decoding, prefix caching off, 5 runs): EXL3 4.00 bpw file 7.79 GiB, PPL 1.2908, mean KLD 0.02479, prefill 4,077 t/s @2k / 5,199 @8k, decode 113.1 / 108.4 t/s, loaded VRAM 8.71 GiB, peak 9.60 GiB; GGUF Q4_K_M (4.798 bpw) file 6.63 GiB, PPL 1.3064, KLD 0.03985, prefill 1,762 / 4,097 t/s, decode 139.4 / 136.4 t/s, loaded 8.04 GiB, peak 8.54 GiB; GGUF IQ4_XS KLD 0.05435, decode 154.6 t/s; Q5_K_M KLD 0.01719, decode 130.1; EXL3 5.00 bpw KLD 0.00946, decode 98.8; EXL3 3.00 bpw KLD 0.09399, decode 119.2; matched-size prefill ratios 2.21-2.27x at 2k and 1.27-1.39x at 8k in favour of EXL3; llama.cpp decoded 15-21 % faster in size-matched pairs — [Source](https://atomic.chat/blog/guides/exl3-vs-gguf).

**Design lessons**: EXL3 shows that a QTIP-class trellis format gives markedly better KLD per byte than K-quants at 4 bpw, at the cost of a GPU-hours conversion step, CUDA-only kernels and slower decode than llama.cpp; a new engine should treat weight format as pluggable (GGUF for reach, a trellis/vector-quant format for VRAM-bound users) rather than inventing one (inference from the cited measurements).

#### vLLM (V1) and vllm-metal (sub-researcher findings)

- **Language**: Python engine/scheduler/API server with C++/CUDA and Triton kernels; V1 isolates the scheduler + model executor in a separate `EngineCore` process talking ZeroMQ to the API server, so tokenization/detokenization/streaming overlap the GPU loop — [Source](https://vllm.ai/blog/2025-01-27-v1-alpha-release) (2025-01-27). vllm-metal executes through MLX/Metal and reuses `mlx_lm` model code — [Source](https://vllm.ai/blog/2026-09-22-vllm-metal-v0-28-0) (2026-09-22).
- **License**: Apache-2.0 (widely documented; LICENSE file not re-fetched). vllm-metal's license is not stated in its announcement — unverified.
- **Backends**: CUDA/ROCm/TPU etc. CPU backend: x86 Linux (`avx512f` recommended, `avx2` "Limited features"; FP32/FP16/BF16), ARM aarch64 Linux (NEON), **Apple Silicon "Experimental", source build only, FP32 and FP16 only**, s390x; prebuilt x86 wheels since v0.17.0, ARM since v0.11.2, none for Apple — [Source](https://docs.vllm.ai/en/stable/getting_started/installation/cpu/). Apple GPU only through the vllm-metal plugin (macOS 15+) — [Source](https://vllm.ai/blog/2026-09-22-vllm-metal-v0-28-0).
- **Model formats**: `--load-format` auto/pt/safetensors/tensorizer/runai_streamer/sharded_state/mistral (no GGUF listed on that page) — [Source](https://docs.vllm.ai/en/stable/cli/serve/).
- **Memory model**: `--gpu-memory-utilization` default **0.92**, "a per-instance limit"; for two instances on one GPU "set ... to 0.5 for each instance" — [Source](https://docs.vllm.ai/en/stable/cli/serve/). "vLLM pre-allocates GPU cache using this percentage of memory"; startup profiles weights+activations then sizes a fixed KV cache; `--kv-cache-memory` pins the KV size and "ignores gpu_memory_utilization"; vLLM logs the exact value to reproduce the allocation; preemption default `RECOMPUTE`; multimodal processor cache `mm_processor_cache_gb` default 4 GiB — [Source](https://docs.vllm.ai/en/stable/configuration/optimization/). KV dtypes include fp8 variants, nvfp4, `int4_per_token_head`, `int8_per_token_head`, `turboquant_3bit_nc`/`turboquant_4bit_nc` — [Source](https://docs.vllm.ai/en/stable/cli/serve/). CPU backend: `VLLM_CPU_KVCACHE_SPACE` in GiB, documented as both default 0 and 4 GB in different sections; worker exits with code 9 if weights+KV exceed a NUMA node — [Source](https://docs.vllm.ai/en/stable/getting_started/installation/cpu/); doc/code mismatch reported in issue #60048 — unverified — [Source](https://github.com/vllm-project/vllm/issues/60048). vllm-metal: budget = `--gpu-memory-utilization` (0.92) of device memory; a warmup pass accounts weights/activations/temp buffers, the remainder becomes a fixed KV cache; the MLX buffer cache is capped; requests that do not fit wait — [Source](https://vllm.ai/blog/2026-09-22-vllm-metal-v0-28-0).
- **Scheduler**: token-budget scheduler that "does not distinguish prefill from decode"; chunked prefill inside the budget; hash-based prefix caching with LRU eviction, enabled by default, "<1% throughput loss at 0% hit rate" (vendor-claimed); piecewise CUDA graphs + torch.compile — [Source](https://vllm.ai/blog/2025-01-27-v1-alpha-release). "In V1, chunked prefill is enabled by default whenever possible" — [Source](https://docs.vllm.ai/en/stable/configuration/optimization/). One model per instance. vllm-metal packs mixed prefill+decode into one forward (`[total_q, H, D]` + `cu_seqlens`) over paged KV with per-request block tables — [Source](https://vllm.ai/blog/2026-09-22-vllm-metal-v0-28-0).
- **Quantization (CPU backend)**: AWQ, GPTQ (x86/s390x), compressed-tensors INT8 W8A8; no FP8 listed — [Source](https://docs.vllm.ai/en/stable/getting_started/installation/cpu/).
- **Performance**: Apple Silicon, vendor-run measured, vllm-metal v0.28.0.dev / vLLM 0.28.0, M5 Pro 64 GB, Qwen3.6-35B-A3B 4-bit, batch of 8 requests (~6,000 prompt tokens, 20 output each): even batch (750x8) mlx_lm 4.52 s / oMLX 7.32 / llama.cpp 5.29 / vllm-metal 3.87; uneven batch (3,000 + 430x7) mlx_lm 10.99 s (+143 %) / oMLX 7.22 / llama.cpp 5.33 / vllm-metal 3.64 — [Source](https://vllm.ai/blog/2026-09-22-vllm-metal-v0-28-0). PR author measured on M5 Pro 64 GB, Qwen3.5-0.8B: hot shared-prefix TTFT 26.6 ms vs 126 ms cache-off; all-cold throughput 2,764 tok/s (c=1) / 5,528 (c=8) — [Source](https://github.com/vllm-project/vllm-metal/pull/584) (merged 2026-08-10). Independent SiliconBench (arXiv 2609.19169, 2026-09-12, nine Apple Silicon engines): vllm-metal "alone more than doubles throughput" on Qwen3-0.6B from concurrency 1 to 16; "explicit memory budgets do not guarantee headroom"; two of its authors also wrote the vllm-metal post — [Source](https://arxiv.org/abs/2609.19169). V1 vs V0 "up to 1.7x higher throughput" (vendor-claimed) — [Source](https://vllm.ai/blog/2025-01-27-v1-alpha-release). Consumer NVIDIA / plain CPU 2025-26 numbers: not found in primary sources.
- **Memory-waste evidence**: eager per-block state preallocation "wired about 10 GB for Qwen3.5-0.8B at memory fraction 0.5" and "degraded every TTFT by 2-3x"; fixed by lazy geometric growth by high-water block ID while still charging worst case in the admission plan (per-block state 19.5 MB -> 6.5 MB; planned block count 3,162 -> 1,585) — [Source](https://github.com/vllm-project/vllm-metal/pull/584). Prefix caching initially cost 0.38x cold throughput at c=1 (decode 446 ms -> 1,188 ms for a 32-token request) until PR #634 (merged 2026-08-21) brought it to 0.98x — [Source](https://github.com/vllm-project/vllm-metal/pull/584). Python/CPU overhead was the stated V1 motivation: Llama-8B on H100 "GPU execution can take about 5 ms", so scheduling/input prep/detokenization dominate — [Source](https://vllm.ai/blog/2025-01-27-v1-alpha-release).
- **2025-2026 changes**: V1 (process isolation, unified scheduler, default prefix caching, piecewise CUDA graphs); vllm-metal first official release v0.28.0 (2026-09-22) with a paged varlen Metal attention kernel ported from vLLM's Triton kernel, batched MTP (Gemma 4 only), experimental hybrid (GDN) prefix caching via `align` mode; sub-byte KV dtypes in the CLI. Latest PyPI 0.31.0 (2026-10-05) — unverified — [Source](https://pypi.org/project/vllm/).
- **Weaknesses for consumer/multi-model**: Apple CPU path experimental/source-build/FP16-FP32 only; vllm-metal depends on Python + MLX + Homebrew-managed deps; one model per process; static per-instance budget; 4 GiB multimodal cache default; CPU KV default documented inconsistently.
- **Legally reusable (Apache-2.0)**: paged-KV + block-table design, token-budget scheduler, hash/LRU prefix-cache scheme, Triton/CUDA attention kernels; vllm-metal's Metal paged-varlen kernel if its repo is Apache-2.0 (unverified); the lazy-growth-with-worst-case-charging allocator pattern.

Apple Silicon, consumer NVIDIA and plain-CPU numbers: not found.

- Legally reusable (Apache-2.0): unified radix tree design, session-aware eviction policy, the Rust radix core, sgl-kernel CUDA kernels, lpm scheduling policy.

#### bitnet.cpp (sub-researcher findings)

- 2025-2026 changes: system paper (2025-02-18); official 2B4T model (2025-04-14); GPU kernel (2025-05-20); CPU parallel kernels + tunable tiling + quantized embeddings (2026-01-15); I2_S embedding models (2026-07); no 2026 GPU kernel release — [Source](https://github.com/microsoft/BitNet).

### Inferences
- The two engine families that matter for LLMario's targets are ggml (reach: every backend, GGUF, CPU+GPU hybrid, now NPU) and MLX (Apple: unified memory, M5 accelerators, best Apple numbers). Everything else on consumer hardware is either a wrapper around them (Ollama, LM Studio, llamafile, bitnet.cpp, PowerInfer, vllm-metal) or a CUDA-only specialist (ExLlamaV3, TensorRT-LLM, ktransformers' real numbers).
- mistral.rs demonstrates that a Rust engine on candle can reach feature parity on CUDA (paged attention, prefix cache, FP8/NVFP4, MTP, MCP) but shows the cost: Metal and CPU remain second-class (no paged attention, FCFS batching), and the memory policy is the datacenter "fraction of VRAM" model, not a desktop budget.
- The one capability no engine delivers end-to-end is cross-model, cross-process memory arbitration on one machine: llama.cpp's router evicts by LRU count, Ollama by an 80 % free-VRAM heuristic plus polling, vLLM/SGLang/TRT-LLM by per-process fractions, mistral.rs by independent engines, LM Studio by guardrails whose behaviour is not documented; oMLX (Apple-only, Python) is the only project with a total-memory budget plus LRU/pin/TTL.
- NPUs in October 2026 are a prefill accelerator for 1-8B models behind static-shape, per-SoC, single-tenant runtimes (OpenVINO GenAI, QNN/Genie, LiteRT-LM, FastFlowLM, llama.cpp Hexagon); the practical integration shape for a Rust engine is FFI to a vendor C API (OpenVINO, QAIRT, LiteRT-LM C ABI) or a sidecar server (Lemonade/FLM, GenieX), with the engine owning the CPU/GPU path and treating the NPU as an optional, budgeted, one-model-at-a-time device; Apple's ANE is not addressable outside Core ML.

### Gaps
- No per-engine peak-RSS/VRAM measurements across the same model and hardware were found in primary sources except the RTX 5090 EXL3-vs-GGUF article and Apple's M5 memory table.
- Nexa SDK's current state (repositories redirect to Qualcomm GenieX), the Foundry Local core-library license, QAIRT redistribution terms and Apple's Core ML LLM state (stateful KV models) were not verified.
- The llama.cpp `--fit` algorithm's exact search procedure (which parameters it varies and in what order) was not read from source; only the PR titles, flags and the `no_alloc` simulation hook are confirmed.
- The llama.cpp Hexagon backend's original PR number, supported quant list and SoC list are unverified (fork mirrors only).
- LM Studio "guardrail" levels and KV-cache quantization settings were not found in the fetched docs; the proprietary core's memory policy is undocumented.
- ExLlamaV3's own bpw/KLD numbers exist only as images; no ROCm/Apple support statement either way.
- candle's Metal backend maturity and quant-kernel coverage are not described in the README; mistral.rs is the only large consumer.
- Ollama's MLX runner: whether it is a separate process (like the GGUF llama-server subprocess) was not confirmed; `runner/README.md` returned 404.

## KQ1b. Performance numbers on consumer hardware (compiled, with provenance)

### Takeaway
Decode is bandwidth-bound everywhere (7B Q4_0 decode reaches ~58-79 % of peak bandwidth on Apple GPUs and ~64-72 % on RTX cards), prefill is compute-bound (M5 tensor ops give 2-4x prefill, ~1.2x decode; power caps hit prefill, not decode); Vulkan has become a credible single GPU backend (within ~79 % prefill / ~91 % decode of CUDA on an RTX 5090); on CPUs weight layout (row-interleaved repacking) matters more than bit-width; MoE decode is gather/launch-bound rather than bandwidth-bound; and benchmark numbers rot within months (+27 % prefill between two llama.cpp builds ~90 builds apart), so every number below carries a version.

### Inferences
- Target efficiency envelope for a new engine on consumer hardware, from the measured tables: decode at >=70 % of peak bandwidth on both Apple GPUs (M5-class) and RTX; prefill through tensor cores (Metal 4 on M5+, cooperative-matrix on Vulkan/CUDA); CPU prefill at ~250+ tok/s for 8B Q4 on a Zen 4 desktop requires repacked interleaved weights.
- The biggest unclaimed wins are structural, not kernel-level: MoE expert residency (30B-A3B decodes only 1.26x faster than 8B dense; 80B-A3B runs 3-4x under the CPU bandwidth ceiling), fewer host round-trips for sub-4B models (1.9x engine gaps at 0.6B collapse to 1.2x at 8B), and KV-cache quantization for 8-16 GB machines.

### Gaps
- vLLM/SGLang throughput on RTX 3090/4090/5090 with versions and concurrency; MLC-LLM/WebLLM/wllama tok/s on named GPUs/browsers; Modular MAX on Apple GPU; absolute tok/s for Apple's M5 post and BaseRT; gpt-oss-120b and 70B-class dense on M-series with 2025-2026 builds (only unverified community numbers); EXL3 vs GGUF on a 70B; NVFP4 vs Q4_K_M quality.

## KQ1c. Notable new or newly matured engines (2025-2026) (sub-researcher findings)

### Takeaway
The new entrants split into Rust rewrites of datacenter designs (rvLLM, candle-vllm), small-footprint Rust GGUF engines (Frink, cera), WebGPU/Zig toolchains (ratchet, ZML, WebLLM), Apple-specific servers with the best multi-model memory discipline seen anywhere (oMLX: total-memory budget with LRU/pin/TTL and tiered RAM/SSD KV), and NPU-vendor servers (Lemonade/FastFlowLM, GenieX); none combines a desktop memory arbiter with CPU+GPU+NPU scheduling, and several carry license hazards (koboldcpp and forge-ml AGPL-3.0, gmlx BUSL-1.1, FastFlowLM binary kernels).

### Cited Findings
- **Frink (formerly Ferrox), Rust:** Apache-2.0; CPU + Metal + CUDA (CUDA "builds and runs, not benchmarked"); GGUF dense+MoE; weights stay quantised and mmap'd, dequant inside matmul; Metal prefill uses simdgroup-MMA flash attention, batched GEMM and one fused command encoder per layer; refuses models that do not fit and unverified architectures (~12 of 150 catalog families verified); self-reported v0.12.0 on M2 Pro, Metal tg128 vs llama.cpp (version unstated): Llama-3.2-3B Q4_K_M 62.7 vs 64.7; 1B 149.4 vs 149.7; Mistral-7B Q4_K_M 32.9 vs 32.4; Qwen2.5-0.5B Q8_0 212.9 vs 131.2; CPU 1.41-5.06x slower; 19 MB static binary (post 2026-08-05) — [Source](https://www.fratepietro.com/2026/frink-rust-gguf-inference-engine/); HN criticism: repo four days old at ~92K lines/day of AI-generated code — [Source](https://news.ycombinator.com/item?id=49180302).
- **cera, Rust:** Apache-2.0 OR MIT; v0.6.3 (2026-09-25); CPU SIMD (AVX2/AVX-512, NEON dotprod/i8mm), wgpu, native Metal; no CUDA; GGUF (Q4_0/Q4_1/Q5_K/Q8_0); prompt-lookup speculative decoding; "TurboQuant" KV compression ~12x claimed; prefix caching, LoRA hot-swap, WASM + FFI; one live session per model on GPU (vendor-claimed, pre-1.0) — [Source](https://docs.rs/crate/cera/latest).
- **rvLLM, Rust + CUDA:** Apache-2.0; vLLM rewrite with PagedAttention block tables, continuous batching with preemption, CUDA graphs, 15 kernels (FlashAttention-2, FP8 KV), prefix caching; safetensors; sm_70-sm_122; v0.1.0, single developer — [Source](https://github.com/arm64be/rvllm).
- **candle-vllm, Rust (candle):** MIT; CUDA + Metal; safetensors/GGUF/GPTQ/AWQ/Marlin/MXFP4/NVFP4/FP8; PagedAttention, continuous batching, prefix caching, chunked prefill (8K), CUDA graphs, FlashInfer, multi-process TP, MTP + DFlash2, TurboQuant/FP8 KV, ISQ; Hopper-80G single-stream LLaMA-8B 119 BF16 / 171 Marlin tok/s; Qwen3-30B MoE 102 BF16 / 124 Q4K (vendor-claimed); M4 16 GB demo without numbers — [Source](https://github.com/EricLBuehler/candle-vllm).
- **ratchet (Hugging Face), Rust/WebGPU:** lazy graph, `Tensor = Arc<Inner>` with `Arc<RwLock<Cpu|Gpu>>` storage, greedy buffer-reuse pool for intermediates (WebGPU buffer creation/first-bind is expensive), in-place unary ops, custom block-wise quant so `.matmul()` works on quantised tensors; Whisper reference model; activity slowed (last commit ~8 months earlier; crate/CLI "not released") — [Source](https://github.com/huggingface/ratchet/blob/master/ARCHITECTURE.md).
- **Other Rust (search snippets only, unverified):** forge-ml (wgpu, AGPL-3.0), web-rwkv (WebGPU/WASM, RWKV only), Onyxia (ONNX -> WGSL via wgpu), ruvllm (Apple-Silicon-focused), pegainfer (CUDA-only); paddler is a Rust load balancer over llama.cpp, not an engine (v4.0.1, 2026-07-07) — [Source](https://github.com/distantmagic/paddler); a primary "vllm.rs" repo was not found.
- **ZML, Zig:** Apache-2.0; Zig + MLIR + Bazel, compiles models per target via OpenXLA/PJRT; CUDA, ROCm, Intel OneAPI, TPU, Trainium/Inferentia, CPU; no Metal; Llama 3.x, Qwen 3.5, LFM 2.5 examples; no published numbers; 4.2k stars — [Source](https://github.com/zml/zml).
- **WebLLM / MLC-LLM, TypeScript + TVM, WebGPU:** Apache-2.0; q4f16_1 / q4f32_1 artifacts; OpenAI API, JSON mode, service workers, Cache API/IndexedDB/OPFS; v0.2.85; no tok/s on README — [Source](https://github.com/mlc-ai/web-llm).
- **Modular MAX (Mojo):** latest stable 26.6 (2026-09-17), nightly 26.7.0.dev2026100805; Apple Silicon GPU status, consumer RTX support and license split not found — [Source](https://max.modular.com/changelog).
- **ik_llama.cpp, C/C++ fork:** CPU and CPU/CUDA hybrid focus with repacked row-interleaved quants (`-rtr`, `*_R4/R8`), IQK quants, MLA/FlashMLA for DeepSeek, `llama-sweep-bench`; no release tags; downstream notes say only AVX2+/NEON CPUs and Turing+ CUDA are fully supported (no ROCm/Vulkan/Metal bug reports); mainline added MTP (May 2026) that ik lacks; "ik is sometimes slower than mainline — benchmark first" — [Source](https://github.com/ikawrakow/ik_llama.cpp/discussions/164), [Source](https://gittrend.io/repo/Thireus/ik_llama.cpp), [Source](https://huggingface.co/blog/Doctor-Shotgun/llamacpp-moe-offload-guide).

- **vllm-mlx, Python on MLX:** continuous batching, content-hash prefix cache for images/video; numbers in KQ1b; license not stated — [Source](https://arxiv.org/html/2601.19139v1), [Source](https://github.com/waybarrios/vllm-mlx).
- **Osaurus, Swift:** MIT; "native Swift, no Electron"; MLX runtime + Apple Foundation Models (macOS 26+) + cloud providers; OpenAI, Anthropic and Ollama-compatible endpoints; MCP server and client; "single-residency handoff" (unload chat model, run sub-agent model, reload); no GGUF; macOS 15.5+; no benchmarks; ~8k stars — [Source](https://github.com/osaurus-ai/osaurus).
- **exo, Python + Rust + Swift:** Apache-2.0; MLX backend (mlx-cuda12/13 and mlx-cpu extras); topology-aware auto-parallel (pipeline and tensor); RDMA over Thunderbolt 5 ("99% latency reduction", full-mesh TB5); claims TP 1.8x on 2 and 3.2x on 4 devices (charts only); macOS 26.2+; Linux CPU-only; 47.8k stars (vendor-claimed) — [Source](https://github.com/exo-explore/exo).

- **koboldcpp, C/C++ + Python:** **AGPL-3.0** (bundled ggml/llama.cpp/sd.cpp stay MIT) — flag for an Apache-2.0 project; CUDA/Vulkan/ROCm/Metal/CPU; single portable binary; GGUF text + SD/Flux/WAN + Whisper + TTS; KoboldAI/OpenAI/Ollama/Anthropic APIs; MCP — [Source](https://github.com/LostRuins/koboldcpp).

### Inferences
- oMLX's memory contract (total process limit = RAM minus a reserve, LRU with pin and TTL, tiered KV to SSD, copy-on-write prefix blocks) is the closest existing specification of what LLMario's engine should guarantee, but it is Python-on-MLX and Apple-only; llama-swap's process-level swap with TTL is the minimal cross-platform contract; Osaurus's single-residency handoff is the pattern for agent sub-models on small machines.
- Frink's reported M2 Pro parity with llama.cpp on Metal decode suggests a from-scratch Rust Metal path can match ggml kernels for dense Q4 decode, but its CPU path lags 1.4-5x and the claims are single-author and unreproduced; cera shows wgpu + native Metal in one crate is practical for small models.
- Zig/MLIR (ZML) and TVM (WebLLM) toolchains trade portability for per-target compilation steps that conflict with a "download GGUF and run" desktop UX.

### Gaps
- No independent reproduction of Frink, cera, rvLLM, candle-vllm, oMLX or exo numbers; BaseRT and vllm-mlx licenses unknown; Modular MAX Apple GPU status unknown; Jan/Cortex current engine not verified.

## KQ2. Which design decisions drive memory overhead or waste (with evidence)

### Takeaway
The recurring memory sinks are: (1) allocate-for-the-worst-case at load (llama.cpp KV for full `n_ctx` x streams and worst-case compute buffers; vLLM/TRT-LLM/mistral.rs 90-92 % VRAM pools; vllm-metal's early 10 GB wired per-block state), (2) caches that are unbounded or bounded only by the memory limit (MLX buffer cache, mlx-lm prompt cache bytes, llama.cpp prompt cache before `--cache-ram`), (3) runtime overhead that is not model memory at all (Python+PyTorch+CUDA-graph pools, separate engines per model), and (4) defaults inherited from the model card or a global env var (training-context `n_ctx`, global KV type, `NUM_PARALLEL x ctx`).

### Cited Findings
- llama.cpp allocates K/V for `kv_size x n_stream` per layer in the cache constructor regardless of use, and reserves compute buffers for `n_tokens = min(n_ctx, n_ubatch)` x `n_seq_max` from a worst-case graph; `n_ctx` defaults to the model's training context — [Source](https://github.com/ggml-org/llama.cpp/blob/master/src/llama-kv-cache.cpp), [Source](https://github.com/ggml-org/llama.cpp/blob/master/src/llama-context.cpp), [Source](https://github.com/ggml-org/llama.cpp/blob/master/include/llama.h).
- llama.cpp needed `--fit` (Dec 2025) plus ~20 follow-up fixes through Apr 2026 to make "fits in memory" automatic, including "fix underflow for dense models", "fix Gemma 3 calculation", "fix last devices with low VRAM", "fit ctx size for CPU only" — [Source](https://github.com/ggml-org/llama.cpp/pulls?q=is%3Apr+is%3Amerged+author%3AJohannesGaessler+fit).
- llama-server's prompt cache is capped at 8192 MiB by default (`--cache-ram`), with -1 meaning unlimited, and idle slots are pushed into it by default — [Source](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md).
- MLX's default memory limit is 1.5x the recommended working set and the buffer cache limit defaults to the memory limit; exceeding both raises only when RAM including swap is exhausted — [Source](https://ml-explore.github.io/mlx/build/html/python/_autosummary/mlx.core.set_memory_limit.html), [Source](https://ml-explore.github.io/mlx/build/html/python/_autosummary/mlx.core.set_cache_limit.html).
- mlx-lm KV caches grow by 256-token concatenation and never free on trim (`nbytes` = allocated); prompt cache bytes default unlimited (`1<<63`) with insertion-order eviction; quantized-KV attention keeps a `prefill_step_size x context` score matrix that "can exceed the memory the quantized cache saves" — [Source](https://github.com/ml-explore/mlx-lm/blob/main/mlx_lm/models/cache.py), [Source](https://github.com/ml-explore/mlx-lm/blob/main/mlx_lm/SERVER.md).
- mlx-lm had to add `mx.clear_cache()` into server prompt processing and fix a GatedDeltaNet shared-buffer leak (v0.31.0/v0.31.2, 2026) — [Source](https://github.com/ml-explore/mlx-lm/releases); Ollama's MLX runner had a KV-snapshot leak (v0.19.0) and "excessive memory growth during long generations with MLX speculative decoding" (v0.34.2) — [Source](https://github.com/ollama/ollama/releases/tag/v0.19.0), [Source](https://github.com/ollama/ollama/releases).
- Ollama's pre-Sep-2025 estimation under-offloaded (48/49 layers) and cost 1.5 GiB less VRAM but 39 % lower throughput than exact measurement — [Source](https://ollama.com/blog/new-model-scheduling); Vulkan without `cap_perfmon` forces estimates — [Source](https://docs.ollama.com/gpu); required RAM "scales with NUM_PARALLEL times CONTEXT_LENGTH" — [Source](https://docs.ollama.com/faq).
- vLLM: fixed KV pool at 0.92 of GPU memory per instance; multi-instance guidance is "set 0.5 each"; 4 GiB multimodal processor cache by default — [Source](https://docs.vllm.ai/en/stable/cli/serve/), [Source](https://docs.vllm.ai/en/stable/configuration/optimization/). vllm-metal's eager per-block state "wired about 10 GB for Qwen3.5-0.8B at memory fraction 0.5" and slowed TTFT 2-3x until lazy growth landed — [Source](https://github.com/vllm-project/vllm-metal/pull/584).
- SGLang: "Total memory usage = model weights + KV cache pool + CUDA graph buffers + activations"; sizing is manual trial-until-OOM; CUDA-graph pool needed warmup-measured sizing; expert padding wasted 47 GB on an MI355X FP4 MoE — [Source](https://docs.sglang.io/advanced_features/hyperparameter_tuning.html), [Source](https://github.com/sgl-project/sglang/releases).
- TensorRT-LLM: 0.9 free-memory default; static per-layer-group pool split in KV manager V1; hybrid Mamba fallback "can produce a suboptimal pool split"; PyTorch 2.9 container runtime — [Source](https://nvidia.github.io/TensorRT-LLM/features/kvcache.html), [Source](https://nvidia.github.io/TensorRT-LLM/release-notes.html).
- mistral.rs: 90 % VRAM block pool by default on dedicated GPUs; freed CUDA scratch kept until idle/pressure trimming; auto device map reserves a worst case for `--max-seq-len`/`--max-batch-size` — [Source](https://docs.mistralrs.dev/guides/perf/paged-attention/), [Source](https://docs.mistralrs.dev/guides/perf/throughput-tuning/).
- ktransformers AMX re-lays-out expert weights at load (full copy, no mmap sharing) and needs 382 GB-1 TB DRAM for DeepSeek-V3 — [Source](https://github.com/kvcache-ai/ktransformers/blob/main/doc/en/AMX.md), [Source](https://github.com/kvcache-ai/ktransformers/blob/main/doc/en/DeepseekR1_V3_tutorial.md).
- Python control-plane overhead was the stated motivation for vLLM V1 ("GPU execution can take about 5 ms" for Llama-8B on H100) — [Source](https://vllm.ai/blog/2025-01-27-v1-alpha-release); SGLang moved its radix tree to Rust for 5-38 % TTFT — [Source](https://www.lmsys.org/blog/2026-08-11-unified-radix-cache/).
- Wrapper overhead: Ollama 0.18 vs raw llama.cpp on the same Apple machine: decode 32.54 vs 53.53 tok/s (qwen3.5 35B-A3B q8_0) — [Source](https://github.com/ollama/ollama/issues/14861).
- Unified-memory reality: SiliconBench finds "explicit memory budgets do not guarantee headroom" across nine Apple engines — [Source](https://arxiv.org/abs/2609.19169).
- Vendor/NPU runtimes: ONNX Runtime GenAI allocates the KV cache for `max_length` (default = model `context_length`) up front unless the paged path is used — [Source](https://onnxruntime.ai/docs/genai/reference/config.html); OpenVINO NPU graphs are static (`MAX_PROMPT_LEN` + `MIN_RESPONSE_LEN`), need ">16 GB of RAM ... for prompts over 1024 tokens with models above 7B", and silently corrupt output past the budget (#3255) or crash at `generate()` on the wrong precision (#35641) — [Source](https://raw.githubusercontent.com/openvinotoolkit/openvino/master/docs/articles_en/openvino-workflow-generative/inference-with-genai/inference-with-genai-on-npu.rst), [Source](https://github.com/openvinotoolkit/openvino.genai/issues/3255), [Source](https://github.com/openvinotoolkit/openvino/issues/35641); FastFlowLM: "The NPU can access only under 50% of system DRAM" and 3B/8B models OOM at 128k/64k context — [Source](https://fastflowlm.com/docs/benchmarks/llama3_results/); Foundry Local NPU models fail under parallel fan-out — [Source](https://github.com/microsoft/Foundry-Local/issues/506).
- Counter-examples that reduce memory: MNN keeps embeddings in flash (~2.18 GB saved on Qwen-7B bf16) and stores values as fp8 so old KV entries never need re-quantizing — [Source](https://arxiv.org/html/2506.10443); LiteRT-LM runs Gemma 4 E2B text-only in "as low as 0.8 GB" with 1.12 GB of embeddings mmapped — [Source](https://huggingface.co/litert-community/gemma-4-E2B-it-litert-lm); Apple's on-device model shares block-2 KV with block 1 ("reducing KV cache memory usage by 37.5%") and quantizes KV to 8-bit — [Source](https://arxiv.org/html/2507.13575); oMLX enforces a total process memory limit (default RAM - 8 GB) with LRU/pin/TTL and tiers cold KV to SSD — [Source](https://github.com/jundot/omlx).

### Inferences
- A new engine should separate three budgets explicitly — weights (mmap/wired), KV (paged, grown lazily, charged at admission at worst case), and scratch (reserved once from a measured worst-case graph, never allowed to grow silently) — and print the plan before allocating, as vLLM logs `--kv-cache-memory` and llama.cpp prints compute-buffer sizes.
- The "fraction of device memory" model is wrong for desktops where the engine coexists with the user's apps and other models; a per-machine arbiter with per-model hard caps is the gap.
- Lazy-growing data structures must still be accounted at worst case for admission (vllm-metal PR #584 pattern) or they become unpredictable.

### Gaps
- No primary measurement was found that isolates Python-runtime RSS vs model memory on consumer hardware for vLLM/SGLang; the overhead is documented qualitatively only.
- No llama.cpp issue quantifying compute-buffer size growth at long contexts was retrieved in this pass (search budget exhausted).

## KQ3. Major architectural changes that landed in 2025-2026 and why

### Takeaway
2025-2026 was the period in which the local engines converged on: automatic memory fitting and measured (not estimated) allocation; multi-model management by process isolation; first-class hybrid/recurrent memory; GPU-side sampling and graph reuse to cut per-token host work; Apple M5 Metal-4 tensor paths; NPU backends (Hexagon) with hard per-session address-space limits; MoE-specific host/device expert caching; and, on the datacenter side, V1-style process-split schedulers, unified radix caches (now in Rust), and the removal of AOT engine builds.

## KQ4. What is missing or weak in all of them (gaps a new engine could fill)

### Takeaway
No engine offers a machine-level memory arbiter with hard per-model caps, deterministic (printable, testable) memory plans, lazy-but-admission-charged KV growth, and crash-isolated multi-model serving on CPU+GPU+NPU at once; Apple-first engines lack paged attention on Metal, CUDA-first engines lack Apple/NPU, and every NPU path is boxed by static shapes or per-session address-space limits.

### Cited Findings
- Per-process fractions with "set 0.5 each" as the multi-instance answer (vLLM), heuristic fractions (SGLang), 0.9 default (TRT-LLM), 90 % (mistral.rs) — [Source](https://docs.vllm.ai/en/stable/cli/serve/), [Source](https://docs.sglang.io/advanced_features/hyperparameter_tuning.html), [Source](https://nvidia.github.io/TensorRT-LLM/features/kvcache.html), [Source](https://docs.mistralrs.dev/guides/perf/paged-attention/).
- Router mode evicts by model count (`--models-max 4`) with no cross-model memory budget described — [Source](https://huggingface.co/blog/ggml-org/model-management-in-llamacpp); Ollama's fit test is 80 % of free VRAM plus polling after unload — [Source](https://github.com/ollama/ollama/blob/main/server/sched.go).
- Paged attention is off on Metal/CPU in mistral.rs (FCFS equal-length batching instead) — [Source](https://docs.mistralrs.dev/guides/perf/throughput-tuning/); mlx-lm serialises when KV is quantized and holds one model — [Source](https://github.com/ml-explore/mlx-lm/blob/main/mlx_lm/server.py); vLLM's Apple CPU path is experimental FP16/FP32 — [Source](https://docs.vllm.ai/en/stable/getting_started/installation/cpu/).
- NPU: Hexagon sessions provide ~3.5 GB of virtual address space, forcing dynamic remapping or multi-session splits — [Source](https://github.com/ggml-org/llama.cpp/blob/master/docs/backend/snapdragon/README.md).
- CUDA-only specialists: ExLlamaV3 (CUDA 12.4+, no ROCm/Apple statement) — [Source](https://github.com/turboderp-org/exllamav3); TensorRT-LLM Linux-only, consumer RTX "community support" — [Source](https://nvidia.github.io/TensorRT-LLM/reference/support-matrix.html).
- Unified memory: "explicit memory budgets do not guarantee headroom" — [Source](https://arxiv.org/abs/2609.19169).
- Wrapper/runtime tax: Ollama vs raw llama.cpp decode gap — [Source](https://github.com/ollama/ollama/issues/14861); LM Studio runtime missing the M5 tensor path — [Source](https://github.com/lmstudio-ai/lmstudio-bug-tracker/issues/2040).
- Tool use: only mistral.rs (MCP client, agentic loop, sandboxed shell/python, web search) and LM Studio (MCP via stateful chat) ship built-in tool execution; llama-server exposes tool-call parsing but no execution loop (no execution loop found in the server README) — [Source](https://github.com/EricLBuehler/mistral.rs/blob/master/README.md), [Source](https://lmstudio.ai/blog/0.4.0), [Source](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md). Osaurus adds MCP server/client and a "single-residency handoff" between chat and sub-agent models — [Source](https://github.com/osaurus-ai/osaurus).
- NPU paths are single-tenant and static: Foundry NPU models fail under parallel requests — [Source](https://github.com/microsoft/Foundry-Local/issues/506); OpenVINO NPU ignores prefix caching/cache-size/batch settings (snippet, unverified) — [Source](https://docs.openvino.ai/2025/model-server/ovms_demos_llm_npu.html); per-SoC, per-context-length bundles with runtime-version coupling (LiteRT-LM, Genie) — [Source](https://github.com/google-ai-edge/LiteRT-LM/issues/2226), [Source](https://raw.githubusercontent.com/quic/ai-hub-apps/main/tutorials/llm_on_genie/README.md); EP downloads failing cause silent CPU fallback — [Source](https://github.com/microsoft/foundry-local/issues/792); NPU decode is often slower than CPU for sub-1B models (MNN: CPU 94.3 vs NPU 68.5 tok/s) — [Source](https://github.com/alibaba/MNN/releases). No heterogeneous CPU+GPU+NPU scheduler with published numbers was found by any of the three sub-researchers.
- Existing partial answers to multi-model memory: oMLX (total process limit, LRU/pin/TTL, tiered KV) — [Source](https://github.com/jundot/omlx); llama-swap (process-level swap with `ttl`) — [Source](https://github.com/mostlygeek/llama-swap); llama.cpp router (count-based LRU) — [Source](https://huggingface.co/blog/ggml-org/model-management-in-llamacpp); Ollama (80 % free-VRAM fit + idle eviction) — [Source](https://github.com/ollama/ollama/blob/main/server/sched.go). None of them budgets RAM, VRAM and NPU memory jointly or exposes per-model hard caps across heterogeneous devices.

### Inferences
- The defensible niche for LLMario's engine is "predictable memory on consumer machines with several models": a global budget per device (RAM, VRAM, NPU session), per-model hard caps, measured worst-case plans printed before load, lazy KV with admission charging, process isolation per model, and one scheduler that works identically on Metal, CUDA, Vulkan and CPU.
- Built-in tool use is a product-level differentiator today found only in mistral.rs and LM Studio; implementing the agent loop in the engine (not the UI) with sandboxing is feasible in Rust.

### Gaps
- No source quantifies how often router-mode LRU eviction thrashes on 24 GB cards or how much memory a sleeping llama-server retains; both would be useful baselines.
- Whether Windows ML / Foundry Local arbitrate NPU memory across apps is covered in the NPU section appended below (sub-researcher 2).

## KQ5. Licensing: what an Apache-2.0 Rust engine can reuse or interoperate with

### Takeaway
Everything in the ggml/MLX/mistral.rs/candle/ExLlama lineage is MIT or Apache/MIT and reusable (kernels, formats, specs, designs); vLLM/SGLang/TensorRT-LLM/ktransformers/LiteRT are Apache-2.0; proprietary pieces are the LM Studio core, TensorRT/TensorRT-RTX binaries, Apple's Foundation Models framework and vendor NPU SDKs (Hexagon SDK terms not stated in llama.cpp docs); no GPL/AGPL code was found in the engines surveyed here (see appended sections for others).

### Cited Findings
- llama.cpp MIT — [Source](https://github.com/ggml-org/llama.cpp); ggml MIT (GGUF spec lives in the ggml repo) — [Source](https://github.com/ggml-org/ggml), [Source](https://github.com/ggml-org/ggml/blob/master/docs/gguf.md).
- MLX MIT — [Source](https://github.com/ml-explore/mlx); mlx-lm MIT — [Source](https://github.com/ml-explore/mlx-lm); LM Studio mlx-engine MIT, Outlines Apache-2.0, mlx-vlm MIT — [Source](https://github.com/lmstudio-ai/mlx-engine); lms CLI MIT — [Source](https://github.com/lmstudio-ai/lms); LM Studio app proprietary but free for commercial use — [Source](https://lmstudio.ai/blog/free-for-work).
- Ollama MIT — [Source](https://github.com/ollama/ollama).
- mistral.rs MIT — [Source](https://github.com/EricLBuehler/mistral.rs/blob/master/LICENSE); candle Apache-2.0 OR MIT — [Source](https://github.com/huggingface/candle), [Source](https://crates.io/crates/candle-core).
- ExLlamaV2 MIT, ExLlamaV3 MIT (EXL3 derives from Cornell RelaxML QTIP; QTIP's own license not verified) — [Source](https://github.com/turboderp-org/exllamav2), [Source](https://github.com/turboderp-org/exllamav3).
- vLLM Apache-2.0 (vllm-metal license unverified); SGLang Apache-2.0; TensorRT-LLM Apache-2.0 with proprietary TensorRT-RTX; ktransformers Apache-2.0; PowerInfer MIT; bitnet.cpp MIT; llamafile Apache-2.0 with MIT patches to llama.cpp — see the respective subsections above for sources.
- Apple's M5 accelerator path is reachable only through Metal 4 TensorOps / Metal Performance Primitives (system frameworks, usable from any Metal client) — [Source](https://machinelearning.apple.com/research/exploring-llms-mlx-m5); llama.cpp's Hexagon build depends on Qualcomm's Hexagon SDK via `snapdragon-toolchain` images whose licensing the docs do not state — [Source](https://github.com/ggml-org/llama.cpp/blob/master/docs/backend/snapdragon/README.md).
- Vendor runtimes: ONNX Runtime GenAI MIT — [Source](https://github.com/microsoft/onnxruntime-genai); OpenVINO GenAI Apache-2.0 — [Source](https://github.com/openvinotoolkit/openvino.genai); LiteRT-LM Apache-2.0 (NPU dispatch libraries are prebuilt vendor binaries) — [Source](https://github.com/google-ai-edge/LiteRT-LM), [Source](https://developers.google.com/edge/litert/next/litert_lm_npu); MNN Apache-2.0 (MNN Kit SDKs under separate ToS) — [Source](https://github.com/alibaba/MNN); Foundry Local SDK MIT but CLI under "Microsoft Software License Terms" and the core library license unstated — [Source](https://github.com/microsoft/Foundry-Local); Apple Foundation Models framework is a closed OS component reachable only from Swift — [Source](https://afm-tutorial.netlify.app/), [Source](https://arxiv.org/abs/2606.22283); GenieX BSD-3-Clause plus "Qualcomm's Terms of Use", bundling QAIRT binaries whose redistribution terms were not found — [Source](https://github.com/qualcomm/nexa-sdk); Nexa's OmniNeural-4B model is CC BY-NC 4.0 (non-commercial) — [Source](https://huggingface.co/NexaAI/OmniNeural-4B); FastFlowLM orchestration MIT but NPU kernels are closed binaries — [Source](https://github.com/ROCm/FastFlowLM); Lemonade Apache-2.0 — [Source](https://github.com/lemonade-sdk/lemonade); AMD mlir-aie/IRON "Apache 2.0 with LLVM exception" with an open single-core compiler (only `xchesscc` needs an AMD license) — [Source](https://github.com/Xilinx/mlir-aie); Intel Linux NPU user-mode driver MIT — [Source](https://github.com/intel/linux-npu-driver).
- New engines: koboldcpp **AGPL-3.0** — [Source](https://github.com/LostRuins/koboldcpp); forge-ml AGPL-3.0 (snippet, unverified); gmlx/mlx-kquant **BUSL-1.1** (not open source until the 4-year conversion) — [Source](https://pypi.org/project/gmlx/); Frink Apache-2.0 — [Source](https://www.fratepietro.com/2026/frink-rust-gguf-inference-engine/); cera Apache-2.0 OR MIT — [Source](https://docs.rs/crate/cera/latest); rvLLM Apache-2.0 — [Source](https://github.com/arm64be/rvllm); candle-vllm MIT — [Source](https://github.com/EricLBuehler/candle-vllm); ZML Apache-2.0 — [Source](https://github.com/zml/zml); WebLLM Apache-2.0 — [Source](https://github.com/mlc-ai/web-llm); oMLX Apache-2.0 — [Source](https://github.com/jundot/omlx); Osaurus MIT — [Source](https://github.com/osaurus-ai/osaurus); exo Apache-2.0 — [Source](https://github.com/exo-explore/exo); llama-swap MIT — [Source](https://github.com/mostlygeek/llama-swap); ratchet, BaseRT, vllm-mlx, vllm-metal licenses not confirmed.

### Inferences
- A Rust engine can legally: read/write GGUF (spec MIT), port ggml quant kernels (MIT), port MLX Metal kernels and the NAX/Metal 4 approach (MIT), port vLLM/SGLang paged-attention and radix-cache designs (Apache-2.0), consume EXL3 checkpoints with ported MIT kernels, and link candle (Apache/MIT). It must treat LM Studio, TensorRT-RTX, Apple Foundation Models and vendor NPU runtimes as external services or system frameworks, not code to vendor.
- Patent/attribution hygiene: MIT requires preserving copyright notices in ported kernels; Apache-2.0 sources require NOTICE propagation — straightforward for an Apache-2.0 project.

### Gaps
- QTIP (RelaxML) license, vllm-metal LICENSE, Cosmopolitan Libc (ISC claimed) and CUTLASS (BSD-3 claimed) were not re-verified in this pass.
- Whether Qualcomm Hexagon SDK / QNN redistribution terms permit shipping NPU binaries in an Apache-2.0 desktop app was not checked (see NPU section below).
