# GPU and NPU execution for local LLM inference on consumer devices (state as of October 2026)

Scope: Apple Metal, NVIDIA CUDA, Vulkan, AMD ROCm/HIP, Intel oneAPI/SYCL/OpenVINO, WebGPU/wgpu, DirectML/Windows ML, NPUs (Apple ANE, Intel NPU, AMD XDNA2, Qualcomm Hexagon), heterogeneous CPU+GPU+NPU scheduling, and kernel-authoring options from Rust. Written for the design of a from-scratch Rust (Apache-2.0) local inference engine for LLMario (0.5B–70B dense, MoE up to ~120B total, 8–128 GB machines).

Labeling conventions used below:
- **MEASURED** = a third party ran a benchmark and published hardware + software versions.
- **SELF-REPORTED** = measured by the authors of the thing being measured (PR authors, paper authors of their own runtime).
- **VENDOR** = vendor marketing/spec claim, not independently measured.
- **COMMUNITY** = forum/Reddit/blog numbers with partial methodology.
- **UNVERIFIED** = seen only in a search snippet or a secondary summary; the primary page could not be fetched.
- **BACKGROUND** = older than 2025.

## KQ1. Apple Metal: unified memory semantics, limits, Metal 4, M5 Neural Accelerators, backend structure, measured performance, and Rust access

### Takeaway
On Apple silicon the winning design is already visible in both llama.cpp and MLX: `MTLResourceStorageModeShared` buffers (zero-copy over mmap'd weights), per-buffer `MTLResidencySet`s kept warm with a keep-alive thread (macOS 15+), a budget derived from `recommendedMaxWorkingSetSize` (≈75% of RAM by community observation; raisable with the undocumented `iogpu.wired_limit_mb` sysctl), simdgroup-matrix kernels for M1–M4, and Metal 4 `MetalPerformancePrimitives` tensor ops (macOS 26) gated to M5/A19+ where they give 2–4× prefill but ~0–25% decode gains because decode is memory-bandwidth-bound.

### Cited Findings

**Memory model, limits and wired memory**
- Apple documents `recommendedMaxWorkingSetSize` as "An approximation of how much memory, in bytes, this GPU device can allocate without affecting its runtime performance… keeping the total memory footprint of its resources and heaps less than this threshold value"; available macOS 10.12+, iOS 16+. — [Apple docs: recommendedMaxWorkingSetSize](https://developer.apple.com/documentation/metal/mtldevice/recommendedmaxworkingsetsize)
- Community observation (not Apple-documented): the default equals about 75% of unified RAM (e.g., ~96 GB on a 128 GB Mac); on Sonoma 14+ `sudo sysctl iogpu.wired_limit_mb=<MB>` raises it immediately without reboot (`0` restores default); Ventura/Monterey use `debug.iogpu.wired_limit` in bytes; persistence via `/etc/sysctl.conf` may require disabling SIP; the note calls it "unsupported/undocumented", advises leaving 8–16 GB for macOS, and warns that over-wiring leads to swapping/instability. — [devnote-override-macos-metal-vram-cap](https://github.com/ivanopcode/devnote-override-macos-metal-vram-cap) (COMMUNITY)
- BACKGROUND: a June 2023 Apple developer-forum thread asked whether `recommendedMaxWorkingSetSize` is a hard cap or advisory; one commenter believed the 75% figure is hard-coded, with no Apple answer in the thread. — [Apple forums thread 732035](https://developer.apple.com/forums/thread/732035)
- An iPhone Air with 12 GB reported an 8,192 MB Metal ceiling and could not finish loading a 7.3 GB Llama-2-13B Q4_K GGUF, while 7B/8B models loaded; no sysctl route exists on iOS. — [Apple forums thread 805161](https://developer.apple.com/forums/thread/805161) (COMMUNITY)
- llama.cpp's Metal device layer reads `maxBufferLength`, `maxThreadgroupMemoryLength` and `recommendedMaxWorkingSetSize`; `ggml_metal_device_get_memory` reports total = `recommendedMaxWorkingSetSize` and free = total − `currentAllocatedSize`. — [ggml-metal-device.m](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-metal/ggml-metal-device.m)
- MLX's Metal allocator sets its memory limit (`block_limit_`) to min(1.5 × `recommendedMaxWorkingSetSize`, 0.95 × physical memory), a GC threshold (`gc_limit_`) at 0.95 × `recommendedMaxWorkingSetSize`, and a free-buffer cache limit defaulting to `block_limit_`; `set_wired_limit` throws `std::invalid_argument` if the request exceeds `recommendedMaxWorkingSetSize`. — [mlx/backend/metal/allocator.cpp](https://github.com/ml-explore/mlx/blob/main/mlx/backend/metal/allocator.cpp)
- MLX exposes `set_memory_limit`, `set_cache_limit`, `set_wired_limit`, `clear_cache`, `get_active_memory`, `get_peak_memory`, `get_cache_memory` (one-line docs, no defaults stated). — [MLX memory management docs](https://ml-explore.github.io/mlx/build/html/python/memory_management.html)

**Storage modes, heaps, zero-copy and buffer splitting (how llama.cpp and MLX allocate)**
- llama.cpp: `use_shared_buffers` follows `hasUnifiedMemory` (with an eGPU exception on x86). Shared buffers are host memory from `vm_allocate` (macOS) wrapped with `newBufferWithBytesNoCopy` + `MTLResourceStorageModeShared`, accessed directly with `memcpy`; private buffers use `newBufferWithLength` + `MTLResourceStorageModePrivate` and blit encoders. `ggml_metal_buffer_map` wraps an existing page-aligned pointer (typically the mmap'd model file) with `newBufferWithBytesNoCopy` in shared mode without owning it; data larger than `max_buffer_size` is split into overlapping views (overlap sized from `max_tensor_size` so any tensor fits one view), capped at `GGML_METAL_MAX_BUFFERS` = 64. llama.cpp does **not** use `MTLHeap`; each allocation is a separate `MTLBuffer`. Env overrides: `GGML_METAL_SHARED_BUFFERS_ENABLE/DISABLE`. — [ggml-metal-device.m](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-metal/ggml-metal-device.m)
- MLX: buffers use `ResourceStorageModeShared` + `ResourceHazardTrackingModeUntracked`; unless the device is an "Apple Paravirtual device", MLX creates an `MTLHeap` and sub-allocates requests smaller than `small_size_` from it, falling back to `device->newBuffer`; requests > `vm_page_size` are rounded to page multiples; freed buffers go to a `BufferCache` keyed at page granularity; when active + cached + requested ≥ `gc_limit_` the cache is reclaimed; requests > `maxBufferLength` throw. — [mlx allocator.cpp](https://github.com/ml-explore/mlx/blob/main/mlx/backend/metal/allocator.cpp)

**Residency sets (macOS 15 / iOS 18)**
- Apple: `MTLResidencySet` is "A collection of resource allocations that can move in and out of resident memory"; "Adding allocations to a residency set requires less overhead than the equivalent methods of a command encoder… residency sets don't track hazards"; methods `addAllocation`, `commit`, `requestResidency` ("do as much preparatory work as it can… to make the set's resource allocations resident"), `endResidency`; introduced macOS 15.0 / iOS 18.0. — [Apple docs: MTLResidencySet](https://developer.apple.com/documentation/metal/mtlresidencyset)
- llama.cpp PR #11427 ("metal : use residency sets", merged 2025-01-26) creates one residency set per buffer, commits and requests residency; it fixed GPU idle-throttling overhead (issue #10119) and made requests ~250 ms faster on an M2 Ultra with a 7B Q8_0 model while pp512/tg128 were unchanged (~1.00×); `GGML_METAL_NO_RESIDENCY` disables it (then GPU memory is reclaimed after ~1 s idle). A keep-alive heartbeat PR (#17766) merged 2025-12-04. — [llama.cpp PR 11427](https://github.com/ggml-org/llama.cpp/pull/11427) (SELF-REPORTED by maintainer)
- Current ggml code: residency sets are compiled in only for macOS 15 / iOS 18+ SDKs and guarded with `@available`; a background thread calls `requestResidency` on all sets every 5 ms while a keep-alive counter is positive (default 3 minutes, `GGML_METAL_RESIDENCY_KEEP_ALIVE_S`); `ggml_metal_dummy_work` submits a tiny blit to avoid a memory-retention issue on idle devices. — [ggml-metal-device.m](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-metal/ggml-metal-device.m)
- MLX adds non-heap buffers to residency sets on allocation (removes on free); heap-backed buffers are covered by inserting the heap once. — [mlx allocator.cpp](https://github.com/ml-explore/mlx/blob/main/mlx/backend/metal/allocator.cpp)
- WWDC25: residency sets attached to an `MTL4CommandQueue` make every committed command buffer include those resources; updates are cheap and can run on a background thread; Apple calls them "an easy win". — [WWDC25 205 "Discover Metal 4"](https://developer.apple.com/videos/play/wwdc2025/205)

**Metal 4 (WWDC 2025) and MTLTensor**
- Metal 4 is supported on Apple M1 and later and A14 Bionic and later; new objects: `MTL4CommandQueue` (decoupled from command buffers), `MTL4CommandBuffer` (independent, parallel-encodable), `MTL4CommandAllocator` (app-controlled command memory), unified compute encoder (dispatch + blit + acceleration structures), `MTL4ArgumentTable` bindings, `MTL4Compiler` (explicit, QoS-inheriting, separate from the device), placement sparse resources (pages from a placement heap; mapping needs an `MTL4CommandQueue`), stage-to-stage barriers; Metal 4 coexists with Metal 3 on the same `MTLDevice`, synchronized via `MTLEvent`. — [WWDC25 205](https://developer.apple.com/videos/play/wwdc2025/205)
- `MTL4CommandBuffer` and `MTLTensor` are introduced in macOS 26.0 / iOS 26.0 (all Apple platforms 26.0). `MTLTensor` is "A resource representing a multi-dimensional array that you can use with machine learning workloads", a `MTLResource` with `dataType`, `dimensions`, `strides`, `usage`, optional backing `buffer`/`bufferOffset`, and a `gpuResourceID` for argument buffers. — [Apple docs: MTL4CommandBuffer](https://developer.apple.com/documentation/metal/mtl4commandbuffer), [Apple docs: MTLTensor](https://developer.apple.com/documentation/metal/mtltensor)
- WWDC25 262: `MTLTensor` has any rank (textures are limited to 4 channels); usages `MachineLearning`, `Compute`, `Render`; device-created tensors get an opaque optimized layout, buffer-backed tensors need explicit strides (innermost stride 1). `MTL4MachineLearningCommandEncoder` runs whole networks (CoreML `mlprogram` → `metal-package-builder` → `.mtlpackage`) on the GPU timeline with an intermediates heap (`MTLHeapTypePlacement`, sized from `pipeline.intermediatesHeapSize`) and `MTLStageMachineLearning` barriers. "Shader ML" lets shaders bind weights as `tensor<device half, dextents<int,2>>` and run `MetalPerformancePrimitives` `tensor_ops::matmul2d<desc, execution_scope>` (scopes: thread / simdgroup / threadgroup) inside compute, vertex or fragment shaders. — [WWDC25 262](https://developer.apple.com/videos/play/wwdc2025/262)
- A WWDC26 session "Optimize custom machine learning operations with Metal tensors" (session 330) exists; its content was not fetched. — [WWDC26 330](https://developer.apple.com/videos/play/wwdc2026/330/) (UNVERIFIED content)

**simdgroup matrix ops and feature detection in llama.cpp**
- Capability flags come from `supportsFamily:`: `has_simdgroup_mm` requires `MTLGPUFamilyApple7` (M1 class), `has_simdgroup_reduction` also accepts the custom `MTLGPUFamilyMetal3_GGML` (5001), `has_bfloat` checks Metal 3 or Apple6, `has_tensor` checks the custom `MTLGPUFamilyMetal4_GGML` (5002) and is enabled by default only when the device name contains "M5", "M6", "A19" or "A20". — [ggml-metal-device.m](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-metal/ggml-metal-device.m)

**How llama.cpp's Metal backend is structured**
- One `MTLDevice` + one command queue shared by all Metal backends; ~35 per-kind shader libraries (`fa_*`, `mul_mv`, `mul_mm`, `rope`, `misc`, …) compiled in parallel with `dispatch_group_async`; three source modes: embedded source (`GGML_METAL_EMBED_LIBRARY`, compiled with `newLibraryWithSource`), precompiled `default.metallib` (+ `ggml-tensor.metallib` for tensor overrides; tensor disabled if missing), or reading `kernels/<name>.metal` from `GGML_METAL_PATH_RESOURCES`; pipelines cached with function constants; preprocessor macros `GGML_METAL_HAS_BF16`, `GGML_METAL_HAS_TENSOR`. — [ggml-metal-device.m](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-metal/ggml-metal-device.m)
- Backend glue: default `n_cb` = 1 command buffer; `graph_optimize` adds allocation dependencies so fused MoE weighted-reduction inputs stay alive and calls `ggml_metal_graph_optimize`; `get_alloc_size` reserves scratch for `MUL_MAT_ID` (tpe/ids/amax), `FLASH_ATTN_EXT` (pad/blk/tmp/kv_f16/idx), `CUMSUM`, `ARGSORT`, `TOP_K`; async set/get tensor and events supported; `offload_op` accepts `MUL_MAT`/`MUL_MAT_ID` only when batch ≥ `op_offload_min_batch_size` (`GGML_OP_OFFLOAD_MIN_BATCH`, default 32). — [ggml-metal.cpp](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-metal/ggml-metal.cpp)
- Kernel selection in `ggml_metal_op_mul_mat`: FWHT → MMA path (if `has_simdgroup_mm` and `use_mma`) → small-batch "mat-vec-ext" path when src1 is F32, `ne00 % 128 == 0` and `ne11 ∈ [2,8]` (Q*_K: `[4,8]`) → `mul_mm` (`use_mm`) → `mul_mv` fallback; fusions visible include soft_max+top-k MoE, SSM conv+SiLU, gated-delta-net cache copy, and `mul_mat + add` (residual stored by the MMA kernel); fusion controlled by `GGML_METAL_FUSION_DISABLE/DEBUG`. — [ggml-metal-ops.cpp](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-metal/ggml-metal-ops.cpp)

**How MLX is structured (lazy evaluation, compile, fused ops, allocator)**
- MLX operations record a graph; computation happens at `mx.eval()` or implicitly (print, NumPy conversion, `.item()`, save). Benefits listed: transformations, skipping unused outputs, lower peak memory (loading fp16 weights lazily roughly halves peak vs eager fp32). Guidance: evaluate once per outer-loop iteration; tens to thousands of ops per eval is fine. — [MLX lazy evaluation](https://ml-explore.github.io/mlx/build/html/usage/lazy_evaluation.html)
- `mx.compile` merges common work and fuses element-wise chains into single kernels; example `gelu` on M1 Max 15.5 ms → 3.1 ms; first call traces, optimizes, generates and compiles code (slow, cached); recompiles on shape/rank/dtype/argument-count change; `shapeless=True` avoids shape recompiles with caveats. — [MLX compile](https://ml-explore.github.io/mlx/build/html/usage/compile.html)
- `mlx.core.fast` provides fused `rms_norm`, `layer_norm`, `rope`, `scaled_dot_product_attention`, and `metal_kernel` (custom MSL JIT-compiled from a source string; `cuda_kernel` and `precompiled_cuda_kernel` for the CUDA backend). — [MLX fast ops](https://ml-explore.github.io/mlx/build/html/python/fast.html)
- Allocator/buffer-cache behavior: see "Storage modes…" above. — [mlx allocator.cpp](https://github.com/ml-explore/mlx/blob/main/mlx/backend/metal/allocator.cpp)
- COMMUNITY/secondary (yage.ai, 2026-03-31): claims Ollama v0.19.0 routes safetensors to an MLX runner and GGUF to llama.cpp, and quotes Reddit/blog decode numbers such as Qwen3-Coder-30B-A3B at ~130 t/s on MLX vs 43 t/s via Ollama (M4 Pro 64 GB, quant unstated) and MLX using ~13% less memory for that model (34.7 vs 40 GB); the article's own estimate is MLX 1.4–1.8× over raw llama.cpp, but an mlx-lm issue it cites reports MLX ~50% slower than llama.cpp with flash attention at 30K+ context on an M3 Ultra. ### Inferences
- Decode on Apple silicon is bandwidth-bound: from the 4167 table, M4 Max (546 GB/s) decoding 7B Q4_0 (~3.8 GB of weights) at 83 t/s implies ~315 GB/s effective (~58% of peak); M5 Max (614 GB/s) at 120 t/s implies ~455 GB/s (~74%); M5 Ultra (1,228 GB/s) at 179 t/s implies ~680 GB/s (~55%). A new engine's decode kernels should be judged by effective bandwidth, not FLOPs.
- A 70B dense model at ~4.8 bits/weight (Q4_K_M = 4.798 bpw per the EXL3 comparison in KQ2) is ~42 GB; the bandwidth bound gives ≤ ~13 t/s on M4 Max, ≤ ~19 t/s on M3 Ultra, ≤ ~29 t/s on M5 Ultra, and realistically 55–75% of those. No primary 70B measurement on M-series was found (see Gaps).
- The tensor-API path pays off for prefill, batched/multi-user decode, speculative-decoding verification batches, and MoE expert GEMMs; single-stream decode should stay on bandwidth-tuned SIMD GEMV kernels (both llama.cpp's `mul_mv` and BaseRT do this). Runtime gating must test-compile (llama.cpp's approach) rather than trust family checks, given the silent-inert bug history.
- For predictable memory the llama.cpp pattern (shared buffers wrapping mmap, per-buffer residency sets, no heap) is simpler; MLX's heap + page-granular cache is better for many transient allocations (activations/KV growth). An engine can combine them: mmap-backed shared buffers for weights, a small placement/`MTLHeap` arena for activations, and residency sets with a keep-alive thread.
- Budgeting against `recommendedMaxWorkingSetSize` (≈75% RAM) and exposing an explicit opt-in to raise `iogpu.wired_limit_mb` (with a warning) matches what users already do with llama.cpp/Ollama.

### Gaps
- No Apple-published absolute tokens/s for M5 (only ratios) and no independent 70B 4-bit measurement on M4/M5 Macs was retrieved (the 4167 table is 7B only).
- The WWDC26 session 330 content (newer tensor-op guidance, possibly register-loaded cooperative tensors mentioned in PR 16634) was not fetched.
- Whether `recommendedMaxWorkingSetSize` is strictly enforced by Metal (vs advisory) is not documented by Apple; evidence is community-only.
- Apple does not document `iogpu.wired_limit_mb`; behavior across macOS 26.x was not verified.

## KQ2. NVIDIA CUDA on consumer RTX cards

### Takeaway
RTX 50-series adds FP4 tensor ops and GDDR7 (5090: 32 GB, 1,792 GB/s), but single-stream decode on consumer cards is still bandwidth-bound (measured ~186 t/s for Qwen3-8B Q4_K_XL on a 5090 at 4K context); the proven engine patterns are a VMM-backed growable pool (`cuMemCreate`/`cuMemMap`), CUDA graphs for batch-1 decode (~1.2× in NVIDIA's 2024 llama.cpp study), custom quantized GEMV/int8-MMQ kernels for decode with cuBLAS only for large dense GEMMs, and awareness that Windows WDDM silently spills VRAM to system RAM.

**CUDA graphs for decode**
- NVIDIA/llama.cpp (2024-08-07, BACKGROUND): capturing each token's kernel stream into a CUDA graph removed GPU-side launch gaps; up to 1.2× over stream execution at batch size 1 (largest on Llama 7B, measured on H100; profiling on A100); graphs are inspected and recaptured only when the GGML graph structure changes (context growth), `cudaGraphExecUpdate` used for infrequent structural changes, kernel parameters patched manually for per-token KV pointer changes; enabled by default for batch size 1. — [NVIDIA blog: Optimizing llama.cpp AI Inference with CUDA Graphs](https://developer.nvidia.com/blog/optimizing-llama-cpp-ai-inference-with-cuda-graphs)
- Current ggml-cuda: graphs disabled below Volta; disabled when a `MUL_MAT_ID` node needs a stream sync; a graph is reused if its `uid` matches, else per-node properties (tensor struct, src pointers, `ne`, `nb`) are compared with `memcmp`; capture requires a second consecutive call with unchanged properties ("warmup"); capture uses `cudaStreamBeginCapture` (relaxed) → `cudaStreamEndCapture` → instantiate, `cudaGraphExecUpdate` on change with destroy/re-instantiate on `cudaErrorGraphExecUpdateFailure`, launch via `cudaGraphLaunch`. Op fusion (`ggml_cuda_try_fuse`, disable with `GGML_CUDA_DISABLE_FUSION`) covers rms_norm+mul/add/RoPE/set-rows, add/mul chains (≤8), mul_mat+scale/bias/add, gate/up GLU for mul_mat and mul_mat_id, unary+mul, top-k MoE routing (softmax/sigmoid gating + argsort + get_rows), SSM conv+SiLU, MoE weighted reduction, gated-delta-net cache copy; a memory-range check blocks fusions that would overwrite live inputs. — [ggml-cuda.cu](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-cuda/ggml-cuda.cu)
- The original PR (#6766) disabled graphs for multi-GPU and batch size > 1 and old architectures and added a capture-failure fallback; the build flag is `GGML_CUDA_USE_GRAPHS` with runtime `GGML_CUDA_DISABLE_GRAPHS`. — [llama.cpp PR 6766 (via semanticdiff mirror)](https://app.semanticdiff.com/gh/ggml-org/llama.cpp/pull/6766/overview) (BACKGROUND)

**cuBLAS vs custom kernels in ggml-cuda**
- `ggml_cuda_mul_mat` order: FWHT → cuBLAS if src0 is a padded view or src1/dst not F32 → MMVF (batch gate on `ne11`) → MMVF for transposed vectors → MMF → MMVQ (quantized GEMV) → MMQ (quantized GEMM) → cuBLAS default; cuBLAS calls are `cublasSgemm`, `cublasGemmEx`, `cublasGemmStridedBatchedEx`, `cublasGemmBatchedEx` with `GGML_CUDA_CUBLAS_COMPUTE_TYPE` override; large F16/BF16 src0 converted in ≤512 MiB chunks; `GGML_CUDA_FORCE_MMQ` is suggested in a log message for Turing GPUs without tensor cores; cuBLASLt is not used; `GGML_TYPE_NVFP4` appears as a weight type in the scale helpers (the only FP4 reference found; no FP8 kernels seen). — [ggml-cuda.cu](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-cuda/ggml-cuda.cu)

**VRAM over-subscription: Windows WDDM vs Linux**
- NVIDIA developer forum (2025-10-15): on Windows WDDM, `cudaMalloc` asks the Microsoft WDDM driver, which "manages device memory with system memory as a fallback", so allocations beyond VRAM succeed and page over PCIe; the responder calls this "expected functionality and not a bug" that has existed for at least five years and says the NVIDIA driver cannot return OOM for it; alternatives: switch to Linux, or TCC mode (no display). The user notes customers are told to change the driver's sysmem fallback setting. — [NVIDIA forum: cudaMalloc with sysmem fallback](https://forums.developer.nvidia.com/t/cudamalloc-with-sysmem-fallback/347791)
- COMMUNITY guides: the "CUDA – Sysmem Fallback Policy" control-panel option ("Prefer No Sysmem Fallback", global or per executable) makes the app fail with CUDA OOM instead of running slowly; Task Manager "Shared GPU memory" > 0 during generation is the symptom; WSL2 does not honor the setting; one guide dates the behavior to driver 536.40 (June 2023), which conflicts with the forum's "at least five years". — [runaihome guide (2026)](https://runaihome.com/blog/shared-gpu-memory-slow-local-ai-sysmem-fallback-fix-2026/), [llmconfigurator guide](https://llmconfigurator.com/en/guides/troubleshooting/windows-shared-gpu-memory-slow)
- Linux: no automatic fallback; llama.cpp offers `GGML_CUDA_ENABLE_UNIFIED_MEMORY=1` → `cudaMallocManaged` (docs: suits integrated GPUs, hurts discrete). On DGX Spark (unified memory), `GGML_CUDA_ENABLE_UNIFIED_MEMORY=1` lowered gpt-oss-120B tg32 from 45.9 to 40.6 t/s and pp2048 from 1,737 to 1,672 (build 6816), i.e., managed memory was slower than plain `cudaMalloc` even on a unified-memory system; slow model loads were traced to DGX OS kernel 6.17 (`NO_PAGE_MAPCOUNT`). — [build.md](https://github.com/ggml-org/llama.cpp/blob/master/docs/build.md), [discussion 16578](https://github.com/ggml-org/llama.cpp/discussions/16578) (COMMUNITY)

**CUDA virtual memory for growable allocations**
- BACKGROUND (2020-04-15): CUDA 10.2 VMM APIs `cuMemAddressReserve`, `cuMemCreate` (granularity-aligned sizes via `cuMemGetAllocationGranularity`), `cuMemMap`, `cuMemSetAccess`, `cuMemUnmap`, `cuMemRelease`, `cuMemAddressFree` let a buffer grow by mapping new physical chunks at the end of a reserved VA range with no copy and no over-commit; cudaMalloc-based growth needs old+new buffers so cannot exceed ~half of VRAM; `cuMemUnmap`/`cuMemSetAccess` may synchronize on older GPUs. — [NVIDIA blog: low-level GPU virtual memory management](https://developer.nvidia.com/blog/introducing-low-level-gpu-virtual-memory-management/)
- ggml-cuda's `ggml_cuda_pool_vmm` reserves a 32 GB VA range and grows it in granularity-sized physical chunks with access set per device (and peers with `GGML_CUDA_P2P`/NCCL builds); allocations are 128-byte aligned, carved sequentially and must be freed in reverse order; the legacy pool caches ≤256 buffers with ~5% slack and frees everything on OOM then retries. — [ggml-cuda.cu](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-cuda/ggml-cuda.cu)

### Inferences
- 5090 decode of Qwen3-8B Q4_K_XL at 185.9 t/s with ~4.8 GiB of weights implies ~890 GB/s effective, about half of the 1,792 GB/s peak, so there is headroom in decode kernels (or the KV/attention share is larger than it looks at 4K context). The 7B Q4_0 Vulkan figure (263.6 t/s ≈ 1,000 GB/s effective) shows a leaner model/quant reaching ~56% of peak.
- FP4/FP8 tensor cores matter for prefill/batched GEMMs and for NVFP4/MXFP4 weight formats, not for single-stream decode; ggml-cuda already recognizes `GGML_TYPE_NVFP4`, so a new engine should plan MXFP4/NVFP4 weight support on Blackwell but not depend on FP4 tensor math for decode.
- A VMM-backed arena (reserve large VA, map on growth, free in reverse) is the simplest way to get "predictable memory" for KV-cache growth on CUDA; combine it with an explicit VRAM budget check (`cudaMemGetInfo`) and, on Windows, a documented recommendation to set "Prefer No Sysmem Fallback" (the engine cannot detect spill through `cudaMalloc` return codes).
- `cudarc` with dynamic loading + NVRTC is the lowest-friction Rust path (no CUDA toolkit at build time for users, PTX compiled at first run and cacheable); candle's build-time PTX via `cudaforge` is the alternative when a toolkit is acceptable at build time. cuda-oxide/cutile-rs are too early for a production kernel set in 2026.

## KQ3. Vulkan as a cross-vendor GPU path

### Takeaway
Vulkan is now a credible single cross-vendor path: llama.cpp's Vulkan backend runs on NVIDIA, AMD, Intel, Apple (via MoltenVK or the new Metal-4-based KosmicKrisp in Mesa) and iGPUs, uses KHR cooperative matrix on all vendors and NV coopmat2 on NVIDIA (≈85% of tensor-core peak in NVIDIA's own GEMM demo), and in 2026 reaches or beats ROCm for decode on AMD Strix Halo; but it still trails CUDA on NVIDIA prefill, has recurring driver/coopmat correctness bugs, and its flash-attention coverage per vendor changed repeatedly through 2025–2026.

### Cited Findings
- Design (Vulkanised 2025, Feb 2025, Jeff Bolz/NVIDIA): KHR_cooperative_matrix (coopmat1, "released summer 2023, widely supported"), NV_cooperative_matrix2 ("October 2024, currently NVIDIA-only"); precisions A=B=fp16 with fp16/fp32 accumulate, or int8 with int32 accumulate; llama.cpp's Vulkan backend "works everywhere (needs basic vk1.2 support)"; mat-mat mul has scalar, KHR_coopmat and NV_coopmat2 paths; flash attention had an NV_coopmat2 path at that time; quantization formats supported in all paths via a per-format dequantization callback ("Mat-vec mul is bandwidth-limited, so this [fitting in VRAM] is good for perf, too"); MoE handled by indirected B-row loads; an optimized coopmat1 GEMM reached ~98 TFLOPS and a coopmat2 GEMM ~97 TFLOPS on an RTX 4070 (peak ~116 TFLOPS fp16 tensor) vs ~8 TFLOPS for a naive coopmat1 kernel; coopmat2 shipped in the Vulkan 1.4.304 SDK and NVIDIA R575 drivers. — [Vulkanised 2025 T47 (PDF)](https://www.vulkan.org/user/pages/09.events/vulkanised-2025/T47-Jeff-Bolz-NVIDIA.pdf), [llama.cpp PR 10206 (coopmat2 mul_mat + FA2)](https://github.com/ggml-org/llama.cpp/pull/10206)
- Scoreboard (Llama-2 7B Q4_0, pp512/tg128, no FA unless noted): RTX 5090 10,382/263.6 (coopmat2); RTX 4090 9,452/188.0; RX 7900 XTX 3,727/182.6; RTX 3090 4,666/164.1; RX 9070 XT 5,036/137.1; RX 6800 XT 1,753/100.3; Arc A770 1,074/52.6; Apple M4 Max via Vulkan 724.8/75.0 (driver not stated; MoltenVK or Asahi); same-GPU comparisons: RTX 3080 (Dec 2024, BACKGROUND) Vulkan 1,706/62.2 vs CUDA 4,499/131.0; Radeon Pro VII Vulkan 330/75.2 vs ROCm 1,065/87.5; RX 5700 XT Vulkan 439/70.1 vs HIP 354/67.6; a 2026 RX 470 (Polaris) run showed FA improving tg 34.4 → 37.3 (Feb 2026) and 40.1 → 43.4 (Jul 2026). A March-2025 maintainer comment ("no Vulkan flash attention support except with coopmat2 on very new nvidia drivers") is outdated per the 2026 entries. — [llama.cpp discussion 10879](https://github.com/ggml-org/llama.cpp/discussions/10879) (COMMUNITY)
- Cross-API on the same Mac: M4 Max 40-core Llama-2 7B Q4_0 via Vulkan 724.8/75.0 vs Metal 885.7/83.1 (different builds/dates). — [discussion 10879](https://github.com/ggml-org/llama.cpp/discussions/10879), [discussion 4167](https://github.com/ggml-org/llama.cpp/discussions/4167)
- AMD Strix Halo, Vulkan vs ROCm, 2026: see KQ4 (Vulkan wins decode, ROCm wins prefill in most 2026 runs). — [Soothill 2026-08-03](https://www.soothill.io/blog/2026/08/03/llamacpp-vulkan-vs-rocm-strix-halo/), [slb350](https://slb350.github.io/strix-benchmarks/)
- Correctness/stability issues in 2025–2026: coopmat2 FA produced incoherent output on an RTX 3090 (early 2025) — [issue 11268](https://github.com/ggml-org/llama.cpp/issues/11268); KHR coopmat caused GPU timeouts/driver resets on Intel Arc 140V driver 101.8509, closed "not planned" — [issue 20554](https://github.com/ggml-org/llama.cpp/issues/20554); Vulkan FA let stale K/V in freed cells affect output on a Radeon 8060S (disappears with coopmat disabled or on CPU) — [issue 26744](https://github.com/ggml-org/llama.cpp/issues/26744); a build break when glslc lacks `GL_KHR_cooperative_matrix` after PR #24406 (Intel Xe FA kernels; "fa_decode shaders built as coopmat unconditionally") — [issue 29373](https://github.com/ggml-org/llama.cpp/issues/29373); an open request to group heads in FA when a model's 20 query heads per KV head exceed coopmat1's limit of 16 (author measured +46% tg at 32K on a Radeon 780M) — [issue 29965](https://github.com/ggml-org/llama.cpp/issues/29965); a 2025 report of "extreme performance degradation" with Vulkan + AMD + FA — [discussion 12629](https://github.com/ggml-org/llama.cpp/discussions/12629). `GGML_VK_DISABLE_COOPMAT=1` is the standard diagnostic. (COMMUNITY/issue tracker)
- macOS: llama.cpp's build docs say MoltenVK is the default Vulkan driver on macOS, with KosmicKrisp as an alternative (`-DGGML_METAL=OFF`). — [build.md](https://github.com/ggml-org/llama.cpp/blob/master/docs/build.md)
- MoltenVK: Apache-2.0, "a layered implementation of Vulkan 1.4 graphics and compute functionality", "not fully compliant with the Vulkan specification" (limitations listed in its user guide, not fetched); some features need private Metal APIs (App Store-ineligible). — [KhronosGroup/MoltenVK](https://github.com/KhronosGroup/MoltenVK)

- Rust: `ash` is "A very lightweight wrapper around Vulkan" generated from `vk.xml`, Vulkan 1.1–1.4, "everything is unsafe", extensions loaded explicitly by namespace (`ash::khr`, `ash::ext`), Apache-2.0/MIT, MSRV 1.69. — [ash-rs/ash](https://github.com/ash-rs/ash)
- `wgpu` v30 (Apache-2.0/MIT) runs natively on Vulkan, Metal, D3D12 and OpenGL and on WebGL2/WebGPU in wasm; Vulkan on macOS/iOS requires MoltenVK; Naga translates WGSL to each platform's shading language; the README does not mention cooperative/subgroup-matrix or f16 features. — [gfx-rs/wgpu](https://github.com/gfx-rs/wgpu)
- Shader compilation: llama.cpp's Vulkan shaders are GLSL (`types.comp`, `mul_mm.comp`) compiled to SPIR-V with glslc; the build requires the Vulkan SDK (or system packages) plus SPIRV-Headers on Linux. — [Bolz slides](https://www.vulkan.org/user/pages/09.events/vulkanised-2025/T47-Jeff-Bolz-NVIDIA.pdf), [build.md](https://github.com/ggml-org/llama.cpp/blob/master/docs/build.md)
- Intel Vulkan: PR #24406 added Intel Xe FA kernels (Xe-LPG+, Xe2, Xe3) in 2026 (secondary write-up claims gains at 16K context; not verified). — [freenode article](https://freenode.net/article/llama-cpp-vulkan-backend-adds-intel-xe-flash-attention-kernels) (UNVERIFIED)

### Inferences
- On NVIDIA, Vulkan decode is within ~0–10% of CUDA in the 2026 7B figures (5090 Vulkan 263.6 t/s on 7B Q4_0 vs 185.9 CUDA on the heavier 8B Q4_K_XL — not directly comparable, but the Dec-2024 2× CUDA advantage has clearly narrowed), while prefill still favors CUDA/cuBLAS for large batches.
- A Rust engine can ship one GLSL (or Slang) → SPIR-V kernel set compiled at build time, probe `VK_KHR_cooperative_matrix` + `VK_NV_cooperative_matrix2` + subgroup sizes at runtime, and fall back to scalar kernels, exactly as llama.cpp does; `ash` is the right binding (wgpu's WebGPU abstraction hides coopmat and f16/int8 dot features).
- Because the recurring Vulkan bugs are driver/coopmat specific, the engine needs a per-device feature allow/deny list and an env/CLI switch to disable coopmat and FA, plus a numerical self-test at startup.
- On macOS, Vulkan via MoltenVK/KosmicKrisp is a fallback for testing portability only; Metal is ~10–20% faster on the one cross-API data point and gets the M5 tensor path.

### Gaps
- No primary source was retrieved on llama.cpp's use of `VK_KHR_shader_integer_dot_product` for quantized matmul (int-dot MMQ path); treat as unverified.
- No 2026 same-GPU Vulkan-vs-CUDA llama-bench pair on a 40/50-series card was found; the only same-GPU pair is from Dec 2024 (RTX 3080).
- Slang support in llama.cpp Vulkan and wgpu/naga cooperative-matrix status were not confirmed.

## KQ4. AMD ROCm/HIP and Intel (consumer)

### Takeaway
AMD consumer support is real but fragmented: ROCm 7.x Linux lists RX 7000/9000 and Radeon AI PRO; the Windows HIP SDK 7.2 lists RX 7000/9000 and Ryzen AI Max (gfx1151) iGPUs; on Strix Halo (128 GB unified, ~215 GB/s measured) llama.cpp Vulkan beats ROCm on decode (e.g., 97.7 vs 73.7 t/s on Qwen3-Coder-30B-A3B Q4_K_S) while ROCm leads prefill (1,345 vs 1,115 t/s), and dense 70B/128B models decode at ~3–5 t/s. Intel Arc/Core Ultra GPUs are served by llama.cpp's SYCL backend (oneAPI 2026.1 verified; Arc B580 listed; NVIDIA/AMD-via-SYCL dropped) and a newer OpenVINO backend; Vulkan is the lowest-friction path on Intel but has had coopmat driver resets.

### Cited Findings

### Inferences
- On Strix Halo the bandwidth bound (215 GB/s measured) explains the numbers: 30B-A3B MoE (~3B active) decodes at 70–100 t/s while dense 70B Q4_K_M lands at ~5 t/s; the box is a MoE machine. A new engine's default for Strix Halo should be Vulkan (RADV) for decode with an optional HIP path only if prefill at long context matters, and it should expose unified-memory zero-copy (Vulkan host-visible, device-local heaps) rather than copying weights.
- Backend-specific behavior flips with builds (Vulkan vs ROCm leadership swapped between 2025 and 2026 runs), so the engine should keep per-device benchmark-based backend selection (autotune at first run, cached) rather than a static preference.
- For Intel discrete GPUs a Vulkan-first strategy covers Arc A/B with one kernel set; SYCL would be a second kernel language (DPC++) solely for Intel prefill gains and is hard to justify for a Rust engine.

### Gaps
- No Intel Arc B580 llama.cpp numbers with model and version were retrieved (only B570 pp without model, and A770 on Vulkan).
- AMD's vendor claims for Strix Halo (LM Studio blog) were not retrievable; no Windows ROCm llama.cpp measurements on Strix Halo were found.
- ROCm on Windows beyond the HIP SDK (which libraries ship, PyTorch status) not verified.

## KQ5. WebGPU/wgpu and DirectML/Windows ML as fallback paths

### Takeaway
WebGPU is viable as a last-resort portable path (llama.cpp now has a Dawn-based WebGPU backend, and the LlamaWeb paper reports it competitive with vendor backends on some devices), but per-dispatch overhead of ~24–71 µs (native Vulkan/Metal via Dawn or wgpu) and the lack of f16/int8/int4 native types and tensor-core access in WGSL make it a poor primary engine; DirectML is in "sustained engineering" and Microsoft's successor, Windows ML (ONNX Runtime with vendor execution providers delivered via Windows Update), is a model-level runtime rather than a kernel API.

### Cited Findings
- LlamaWeb (arXiv 2605.20706, submitted 2026-05-20): an open-source WebGPU backend for llama.cpp using static memory planning, efficient loading, a tunable kernel library and templated quantization kernels; tested on 16 devices from 8 vendors, 10 models, 4 weight formats; 29–33% less memory than existing browser frameworks; 45–69% higher decode throughput across four GPUs from different vendors; "competitive with vendor-specific backends and sometimes faster on some devices"; software license not stated. — [arXiv 2605.20706](https://arxiv.org/abs/2605.20706) (SELF-REPORTED)
- Dispatch overhead study (arXiv 2604.02344, 2026-02-09, independent): per-dispatch ~24 µs (Dawn/Vulkan, RTX 5090), ~36 µs (wgpu/Vulkan, 5090), ~24.5 µs (wgpu/Vulkan, AMD iGPU), ~33 µs (Chrome/Vulkan), ~32 µs (Safari/Metal, M2), ~71 µs (wgpu/Metal, M2), ~59–67 µs (Chrome/D3D12), ~1,040 µs (Firefox); kernel fusion +53% throughput on Vulkan (312 fewer dispatches) but no gain on Metal/CUDA; per-token argmax readback ~11 ms; Qwen2.5-0.5B decode: torch-webgpu fused fp32 21.0 t/s vs CUDA fp16 185.5 t/s on the same 5090; WebLLM q4f16 in-browser decode 41.7–51.1 t/s (Chrome/Safari) vs ~9 t/s Firefox; conclusion: practical for latency-tolerant/portability/privacy cases, not for latency-critical serving where CUDA exists. — [arXiv 2604.02344](https://arxiv.org/html/2604.02344v1) (MEASURED)
- llama.cpp build docs: `-DGGML_WEBGPU=ON` requires a locally installed Dawn; browser builds use Emscripten (`EMDAWNWEBGPU_DIR`). — [build.md](https://github.com/ggml-org/llama.cpp/blob/master/docs/build.md)
- Chrome 134 (2025-02-26) shipped WebGPU subgroups after ~a year of trials; subgroup-based matrix-vector shaders ran 2.3–2.9× faster than packed-integer versions in Google Meet's origin trial. — [Chrome: New in WebGPU 134](https://developer.chrome.com/blog/new-in-webgpu-134) (VENDOR)
- BACKGROUND: WebLLM (2024) reported ~80% of native MLC-LLM decode speed. — [MLC blog 2024](https://blog.mlc.ai/2024/06/13/webllm-a-high-performance-in-browser-llm-inference-engine); a 2026 engineering blog cites ~41 t/s for Llama-3.1-8B 4-bit on an M3 Max in WebLLM and a practical ceiling of 7–8B at 4-bit. — [tianpan.co](https://tianpan.co/blog/2026-04-17-browser-native-llm-inference-webgpu) (COMMUNITY)
- wgpu v30: native on Vulkan/Metal/D3D12/OpenGL; Naga WGSL translation; no mention of cooperative/subgroup matrix or f16 features in the README. — [gfx-rs/wgpu](https://github.com/gfx-rs/wgpu)
- DirectML: "DirectML is in sustained engineering. DirectML continues to be supported, but new feature development has moved to Windows ML"; DX12-only low-level operator API (page dated 2025-02-10, updated 2026-01). — [Microsoft Learn: DirectML](https://learn.microsoft.com/en-us/windows/ai/directml/dml)
- Windows ML (doc dated 2026-09-01): "unified and high-performance local AI inferencing framework for Windows, powered by ONNX Runtime"; execution providers for NPUs/GPUs/CPUs installed and updated by Windows; CPU and GPU-via-DirectML on all supported Windows versions, hardware-optimized NPU/GPU EPs require Windows 11 24H2 (build 26100)+; claims performance "on par with dedicated SDKs like TensorRT for RTX or Qualcomm's AI Engine Direct" (vendor claim); foundation for Foundry Local. — [Microsoft Learn: What is Windows ML](https://learn.microsoft.com/en-us/windows/ai/new-windows-ml/overview)

### Inferences
- For a Rust engine, `wgpu` is attractive only as a portability/testing backend (one WGSL kernel set, runs on every OS). Its measured per-dispatch cost (24–71 µs) multiplied by hundreds of ops per token caps batch-1 decode unless the engine aggressively fuses (which the overhead paper shows helps on Vulkan), and WGSL's missing f16/int8/int4 types force packed-integer tricks.
- Windows ML/DirectML are not kernel-level targets for a custom engine; they are alternatives to the engine (ONNX models). They matter only if LLMario wants an NPU path on Windows without writing vendor code (see KQ6).

### Gaps
- No 2025–2026 benchmark of any wgpu-native Rust LLM engine (Ratchet, crabml, web-rwkv) against llama.cpp was found.
- The LlamaWeb software license and whether it is merged upstream (vs the in-tree Dawn backend) were not confirmed.
- WebGPU "subgroup matrix" (tensor-core) extension status in Chrome/Dawn/wgpu in 2026 not verified.

## KQ6. NPUs: Apple ANE, Intel NPU, AMD XDNA2, Qualcomm Hexagon

### Takeaway
In 2026 NPUs are worth targeting only for small models (≤4B), prefill/TTFT, embeddings/speech, and battery efficiency; measured decode on 8B-class models is 3–12 t/s on Intel/AMD/Qualcomm NPUs versus 2–4× that on the same machine's iGPU, every NPU imposes static shapes, narrow quantization menus and address-space or SRAM limits, and Apple's ANE has no public SDK beyond Core ML (community tooling reaches ~34 t/s for Gemma-4-E2B on an iPhone 17 Pro and ~15 t/s for 3–4B models).

### Cited Findings

**Apple Neural Engine**
- Apple publishes no ANE SDK; Core ML is the only official route; some projects use reverse-engineered private interfaces (`_ANEClient`) that can break with a macOS update. — [insiderllm guide](https://insiderllm.com/guides/apple-neural-engine-llm-inference/) (COMMUNITY)
- Direct-ANE microbenchmarks on an M4 Mac mini (16-core ANE, macOS 15, `_ANEClient`, 2026-02-28): peak 19 TFLOPS FP16 claimed (16 × ~1.2); measured 5.7 TFLOPS at 2048², 4.0 at 4096² (working set 96 MB overflows ~32 MB on-chip SRAM); ~0.095 ms dispatch overhead; INT8 no faster than FP16 (dequantized to FP16 before compute; "38 TOPS" ≈ 19 TFLOPS × 2); Core ML adds 2–4× overhead for small ops; ~6.6 TFLOPS/W; author recommends prefill on ANE and decode on CPU (SME)/GPU because the KV cache does not fit SRAM. — [maderix: Inside the M4 ANE, Part 2](https://maderix.substack.com/p/inside-the-m4-apple-neural-engine-615) (MEASURED, individual)
- CoreML-LLM (ANE-only, iPhone 17 Pro, 2048 context): Gemma 4 E2B ~34 t/s, Gemma 4 E4B ~15.7 t/s, Qwen3-VL 2B ~7.5 t/s; Granite 4.1 3B 14 t/s (Mac). — [john-rocky/CoreML-LLM](https://github.com/john-rocky/CoreML-LLM) (SELF-REPORTED)
- ANEMLL 0.3.5 (MIT): converts Llama 3.1/3.2 (1B, 8B), Qwen3 (0.6–8B), Qwen2.5, Gemma 3 (270M–4B QAT), DeepSeek-R1-8B to Core ML; recommended LUT4 FFN + LUT6 LM head ("LUT4 quality is fairly low due to the lack of block quantization on the ANE"); context ≤ 2048 (LLaMA; 512–1024 recommended), ≤ 4096 (Qwen3, Gemma 3); automatic weight chunking; 16 GB min (32 GB for 8B); no tokens/s published. — [Anemll/Anemll](https://github.com/Anemll/Anemll)
- ANEForge (private-API runtime compiling the whole decoder into one ANE program with KV cache on-accelerator): ~62 t/s TinyLlama-1.1B fp16 on M5 Pro, ~75 t/s Qwen3-0.6B — page returned HTTP 401; numbers are from search snippets only. — [aneforge/llm-text-generation](https://huggingface.co/aneforge/llm-text-generation) (UNVERIFIED)
- Apple's on-device foundation model is ~3B parameters with KV-cache sharing (block 2 shares block 1's K/V, −37.5% KV memory and ~−37.5% TTFT) and 2-bit quantization-aware training; the 2025 report page states no latency, tokens/s or execution unit. — [Apple Foundation Models Tech Report 2025](https://machinelearning.apple.com/research/apple-foundation-models-tech-report-2025), [arXiv 2507.13575](https://huggingface.co/papers/2507.13575); BACKGROUND (2024): ~0.6 ms TTFT per prompt token and 30 t/s on iPhone 15 Pro at ~3.7 bpw before speculative decoding, with "efficient KV cache update on our neural engines". — [Apple 2024 post](https://machinelearning.apple.com/research/introducing-apple-foundation-models) (VENDOR)
- Core ML stateful KV (`MLState`) requires macOS 15 / iOS 18; typical ANE context ceilings 512–2,048 (some 4,096). — [insiderllm guide](https://insiderllm.com/guides/apple-neural-engine-llm-inference/) (COMMUNITY)

**Intel NPU (Core Ultra, via OpenVINO)**
- OpenVINO GenAI on NPU requires symmetric 4-bit weights (INT4 or NF4, ratio 1.0), channel-wise (group size −1) or group-wise (128; better for ≤4–5B models); NF4 only on Core Ultra Series 2 (Lunar Lake)+ with channel-wise; static shapes with `MAX_PROMPT_LEN` default 1,024 and `MIN_RESPONSE_LEN` default 128 (context = sum); prefill chunking `NPUW_LLM_PREFILL_CHUNK_SIZE` default 1,024 since 2025.3 (dynamic prompts auto when prompt > chunk); `GENERATE_HINT` FAST_COMPILE vs BEST_PERF; more than 16 GB RAM may be needed for prompts > 1,024 with > 7B models on Series 2; driver ≥ 32.0.100.3104 for failures; weightless blob cache/AoT export; Whisper and VLMs supported. — [OpenVINO docs: GenAI on NPU (rst)](https://raw.githubusercontent.com/openvinotoolkit/openvino/master/docs/articles_en/openvino-workflow-generative/inference-with-genai/inference-with-genai-on-npu.rst) ([rendered page](https://docs.openvino.ai/2025/openvino-workflow-generative/inference-with-genai/inference-with-genai-on-npu.html))
- BACKGROUND (NITRO, Dec 2024, Meteor Lake, OpenVINO 2024.4, Linux NPU driver 1.10): decode derived from ms/token — Llama3-8B NPU ~2.9 t/s vs iGPU ~3.7 vs CPU ~1.6; Llama3.2-1B NPU ~12.5 vs iGPU ~16.6 vs CPU ~9.7; workaround was fixed-length KV with −inf masks, stateful ReadValue/Assign, model chunking; INT4 symmetric failed to compile on the NPU at that time. — [arXiv 2412.11053](https://arxiv.org/html/2412.11053v1) (MEASURED, dated)
- Intel (measurements "as of May 2026", LiteRT-LM OpenVINO backend, Gemma 4 E2B): Core Ultra 7 355 NPU ≈1.3× prefill and 1.2× decode vs its GPU with 2.8× perf/W; Core Ultra X7 358H NPU decode "roughly on par" with the LiteRT-LM WebGPU GPU path at ~3× the power efficiency; relative numbers only. — [Intel developer article](https://www.intel.com/content/www/us/en/developer/articles/community/litert-unlocks-core-ultra-npu-performance-for-aipc.html) (VENDOR)
- ExecuTorch OpenVINO backend PR on a Core Ultra 7 258V: a contributor reported ~50 t/s after channel-wise quantization (model unnamed; INT4 initially slower on NPU than CPU). — [pytorch/executorch PR 14022](https://github.com/pytorch/executorch/pull/14022) (UNVERIFIED)
- Memory sharing: OpenVINO offers `DISABLE_OPENVINO_GENAI_NPU_L0` to stop Level Zero memory allocation when OOM; llama.cpp's OpenVINO backend runs the NPU from the same GGUF with a static prefill chunk of 256. — [OpenVINO NPU rst](https://raw.githubusercontent.com/openvinotoolkit/openvino/master/docs/articles_en/openvino-workflow-generative/inference-with-genai/inference-with-genai-on-npu.rst), [OPENVINO.md](https://github.com/ggml-org/llama.cpp/blob/master/docs/backend/OPENVINO.md)

**Qualcomm Hexagon (Snapdragon 8 Gen 3 / 8 Elite / X Elite / X2 Elite)**
- llama.cpp Hexagon backend merged as PR #16547 (commit 63d2fc46, late October 2025; co-authored by Qualcomm engineers), labeled experimental; launch support Hexagon v73/v75/v79/v81 (Snapdragon 8 Gen 3, 8 Elite, 8 Elite Gen 5); Q4_0, Q8_0, MXFP4, FP32 tensors; matmul, RMS norm, RoPE, SwiGLU, softmax on the NPU; a community report adds IQ4_NL and says KV-cache quantization is unsupported. — [PR 16547 (semanticdiff mirror)](https://app.semanticdiff.com/gh/ggml-org/llama.cpp/pull/16547/overview), [Reddit snapshot](https://reddit.sentinel-team.org/posts/1t0k6fj/snapshots/2026-05-02T03%3A06%3A21.60641Z) (COMMUNITY)
- Backend docs: each NPU session has a 32-bit VA window of ~3.5 GB; larger models use dynamic mapping of inactive weight buffers during batch preparation (pinned KV/compute buffers stay mapped) or layer-split across sessions (`GGML_HEXAGON_DEVICES`, replacing `GGML_HEXAGON_NDEV`); buffers live in shared DDR (RPCMEM) mapped through FastRPC FDs; `GGML_HEXAGON_OPFILTER` excludes ops; numbers in the README: Llama-3.2-1B Q4_0 pp128 ~169 t/s / tg64 ~52 t/s; Gemma-2-2B ~3,200 pp / ~48 tg; GPT-OSS-20B across four sessions ~51 pp / ~18 tg (device not named); kernel-authoring guidance (DDR → DMA → VTCM pipeline, multi-buffering, avoid scalar VTCM access). — [snapdragon/README.md](https://github.com/ggml-org/llama.cpp/blob/master/docs/backend/snapdragon/README.md), [snapdragon/developer.md](https://github.com/ggml-org/llama.cpp/blob/master/docs/backend/snapdragon/developer.md) (SELF-REPORTED)
- Windows on Snapdragon: native arm64 build with Hexagon SDK Community Edition 6.6+, OpenCL SDK 2.3+, VS 2026; the Hexagon NPU library must be catalog-signed with a trusted certificate — requires `bcdedit /set TESTSIGNING ON` (Secure Boot may need disabling) and a self-signed cert in Trusted Root/Publishers; the Adreno OpenCL backend needs no test signing. — [snapdragon/windows.md](https://github.com/ggml-org/llama.cpp/blob/master/docs/backend/snapdragon/windows.md)
- Qualcomm Genie (QAIRT) LLM tutorial: Android (8 Elite Gen 5, 8 Elite), Windows (X2 Elite, X Elite), Hexagon v73+ (v81 = 8 Elite Gen 5/X2 Elite); 16 GB+ for 7B+ or 4,096 context, 12 GB+ for 3B+; SDK license and performance not stated. — [quic/ai-hub-apps llm_on_genie](https://github.com/quic/ai-hub-apps/blob/main/tutorials/llm_on_genie/README.md)
- Vendor: Snapdragon X2 Elite NPU 80 TOPS (85 on one SKU) vs 45 TOPS on X Elite; product pages cite "30 tokens per second" generative AI without model/quant. — [Qualcomm X series](https://www.qualcomm.com/products/mobile/snapdragon/x-series) (VENDOR)
- Phone: OnePlus 12 (8 Gen 3), Gemma 3 12B QAT Q4_0 on the Hexagon backend ~8 t/s pp, ~4.5 t/s tg, "roughly matched the CPU while staying much cooler". — [Reddit snapshot](https://reddit.sentinel-team.org/posts/1t0k6fj/snapshots/2026-05-02T03%3A06%3A21.60641Z) (COMMUNITY)

### Inferences
- Memory sharing is uniform in principle (all four NPUs read system/unified DRAM: ANE via unified memory, Intel via Level Zero host allocations, XDNA via system RAM, Hexagon via RPCMEM shared DDR) but every NPU adds a mapping/address-space constraint (Hexagon 3.5 GB VA window, ANE ~32 MB SRAM working set, OpenVINO static prompt windows), so an engine cannot treat NPU memory as a free extension of the GPU budget.
- Decode on NPUs is dispatch/SRAM-bound, not DRAM-bound; the consistent pattern (maderix, Intel, AMD hybrid mode, Apple's own prefill-on-ANE history) is prefill/TTFT and small-model work on the NPU, decode on GPU/CPU. For LLMario the realistic NPU uses in priority order: (1) embeddings and speech (fixed shapes, small), (2) draft models for speculative decoding (≤2B, fixed context), (3) prefill offload for 4B–8B models on laptops, (4) full decode only for ≤2B assistants in battery mode.
- A from-scratch Rust engine should not write NPU kernels: Apple exposes none, Intel/AMD/Qualcomm paths are vendor runtimes (OpenVINO, OGA/FLM, QNN/Hexagon SDK with signing). The practical route is an optional "NPU runner" boundary that delegates to those runtimes (or to llama.cpp's Hexagon/OpenVINO backends) behind the same API.

### Gaps
- No power measurements (watts) for NPU vs GPU decode were found beyond vendor ratios (Intel 2.8–3×, FastFlowLM ">10×" claim) and AMD's qualitative statement.
- No llama.cpp Hexagon numbers on Snapdragon X Elite/X2 Elite laptops were found; Qualcomm's "30 t/s" has no model attached.
- Apple's 2025 on-device model tokens/s and whether it runs on ANE vs GPU were not stated on the pages fetched.
- ANEForge numbers are unverified (page requires authentication).

## KQ7. Heterogeneous execution: GPU/CPU splits, MoE expert offload, unified memory, overlap

### Takeaway
The measured win in heterogeneous execution comes from keeping attention, KV cache, router/shared experts and norms on the GPU while streaming routed-expert weights from system RAM (llama.cpp `--n-cpu-moe`/`-ot`; KTransformers "hot experts on GPU, cold on CPU"): on gpt-oss-120B a 24 GB RTX 3090 goes from 0.9 t/s (layer split) to 1.6–1.8 t/s, and a 5090 from ~3.4 to ~9.6 t/s, with decode then bounded by system-RAM bandwidth; unified-memory machines (Strix Halo, DGX Spark, Apple) make the split moot for fit but remain bandwidth-bound (~215–273 GB/s), and CUDA managed memory on DGX Spark measured slower than explicit allocation.

### Cited Findings
- llama-server options (current README): `--fit on|off` (default on) adjusts unset arguments so the model fits device memory, with `--fit-target` (default 1,024 MiB per device margin) and `--fit-ctx` (minimum context 4,096); `-ngl` accepts a number, `auto` (default) or `all`; `--cpu-moe` keeps all MoE weights on CPU; `--n-cpu-moe N` keeps the first N layers' experts on CPU; `--moe-cache-mib N` sets a GPU cache for CPU-resident experts (default 0 = off); `--n-cpu-ffn N` does the same for dense FFNs; `-ot PATTERN=BUFTYPE` overrides any tensor's buffer; `--device`, `--tensor-split`, `--split-mode none|layer|row|tensor` (tensor experimental), `--main-gpu`; `--load-mode auto|none|mmap|mlock|mmap+mlock|dio`; KV cache types f32/bf16/f16/q8_0/q4_0/q5_1 and `-nkvo` to keep KV on CPU; `--cache-ram` prompt cache (default 8,192 MiB). — [llama-server README](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)
- gpt-oss-120B (Nov 2025): RTX 3090 24 GB + EPYC 7343 + 64 GB DDR4-3200: standard layer split (13/32 layers on GPU) tg 0.90 t/s; `--n-gpu-layers 99 --n-cpu-moe 27` (VRAM just under 24 GB) tg 1.81 at 85-token context, 1.41 at 5,500; pp 48 → 246 t/s as context grows; RTX 5090: `--n-cpu-moe 21` tg 9.60 (short) / 8.14 at 5,650 context, pp 448; the 5090 "standard split" row (tg 3.40) also had `--n-cpu-moe 21` in its command, so that comparison is muddled; author: "RAM bandwidth directly affects token generation speed". — [Hardware Corner MoE offload guide](https://www.hardware-corner.net/guides/gpt-oss-offloading-moe-layers/) (MEASURED, single source)
- COMMUNITY (secondary summaries): on a 12 GB card, Qwen3-35B-A3B generation rose from 17 to 34 t/s when `--n-cpu-moe` went from 8 to 30 layers (freeing VRAM) — [aiweekly summary](https://aiweekly.co/alerts/qwen3-moe-cpu-expert-offload-doubles-decode-speed-on-12gb-vram); an 8 GB RTX 3070 Ti went from ~8.7 to >40 t/s on Qwen3.6-35B with `-ncmoe` — [Medium post](https://medium.com/coding-nexus/one-flag-tripled-my-tokens-per-second-on-an-8gb-gpu-238f55d1e3bd) (UNVERIFIED)
- KTransformers (Apache-2.0): CPU kernels with Intel AMX/AVX512/AVX2 for INT4/INT8, NUMA-aware MoE, "hot experts on GPU and cold experts on CPU"; DeepSeek-R1/V3 on a single 24 GB GPU with 382 GB DRAM (Feb 2025) and 139K context in 24 GB (Mar 2025); v0.7.0 (2026-08-17) adds AVX2-only CPUs, Ascend NPU, Intel Arc, ROCm; the only inference throughput on the README is 8×L20 + Xeon (227.85 t/s total at 8-way concurrency). — [kvcache-ai/ktransformers](https://github.com/kvcache-ai/ktransformers) (SELF-REPORTED)
- Unified memory, DGX Spark (GB10, ~273 GB/s per thread commenters), llama.cpp build 7941 (2026-02-05), pp2048/tg32 at depth 0 → 32K: gpt-oss-120b 2,444 / 58.7 → 1,567 / 42.8; gpt-oss-20b 4,506 / 83.4 → 2,689 / 61.7; Qwen3-Coder-30B-A3B Q8_0 2,987 / 61.1 → 1,348 / 30.2; Qwen2.5-Coder-7B Q8_0 2,250 / 29.4; Gemma-3-4B QAT 5,949 / 81.1; batched gpt-oss-120b aggregate 541.5 t/s (B=1, PP512) → 1,832 (B=32); `GGML_CUDA_ENABLE_UNIFIED_MEMORY=1` was slower (tg32 45.9 → 40.6 on build 6816). — [benches/dgx-spark.md](https://github.com/ggml-org/llama.cpp/blob/master/benches/dgx-spark/dgx-spark.md), [discussion 16578](https://github.com/ggml-org/llama.cpp/discussions/16578) (SELF-REPORTED by maintainer / COMMUNITY)
- Unified memory, Strix Halo: see KQ4 (measured 215 GB/s; 122B-A10B MoE at 21–23 t/s; dense 70B/128B at 3–5 t/s). — [Framework thread](https://community.frame.work/t/amd-strix-halo-ryzen-ai-max-395-gpu-llm-performance-tests/72521), [Soothill](https://www.soothill.io/blog/2026/08/03/llamacpp-vulkan-vs-rocm-strix-halo/)
- Unified memory, Apple: llama.cpp wraps mmap'd model memory in shared-mode `MTLBuffer`s with no copy (KQ1); Hexagon shares DDR via RPCMEM (KQ6). — [ggml-metal-device.m](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-metal/ggml-metal-device.m), [snapdragon/developer.md](https://github.com/ggml-org/llama.cpp/blob/master/docs/backend/snapdragon/developer.md)
- Metal backend offload heuristic: ops are offloaded to the GPU for CPU-resident weights only when batch ≥ 32 (`GGML_OP_OFFLOAD_MIN_BATCH`), i.e., CPU-resident tensors are computed on CPU during decode and on GPU during prefill. — [ggml-metal.cpp](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-metal/ggml-metal.cpp)
- NPU + GPU concurrency on Strix Halo (Lemonade): running an 8B on the NPU and a 9B on the GPU simultaneously cost the NPU 5.8% and the GPU 14.1% decode speed for a 1.42× total wall-time gain. — [sleepingrobots](https://sleepingrobots.com/dreams/lemonade-server-npu-strix-halo/) (MEASURED)
- A 2026 arXiv paper (DALI) states llama.cpp does not support expert caching on the GPU, i.e., the split is fixed at load time (llama.cpp has since added `--moe-cache-mib`). — [DALI, arXiv 2602.03495](https://arxiv.org/pdf/2602.03495), [llama-server README](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)

### Inferences
- The expert-offload ceiling is system-RAM bandwidth divided by active-expert bytes per token: taking gpt-oss-120B's roughly 5B active parameters at ~4.25 bpw for MXFP4 (both figures from general knowledge of the model card and format, not re-fetched here) ≈ 2.7 GB/token of expert reads, dual-channel DDR5 (~60–80 GB/s theoretical) caps at ~20–30 t/s before overheads, and dual-channel DDR4-3200 (~50 GB/s theoretical) at ~18 t/s; the observed 1.5–1.8 t/s on the 3090 host is far below that bound, so other overheads (per-layer CPU GEMM efficiency, synchronization, only 27 of 36 MoE layers on CPU) dominate there. The engine should compute this bound at load time and report it, and treat the gap to the bound as the optimization target.
- Overlap: the 5090 numbers (pp 448 t/s with experts on CPU) show prefill still benefits from GPU attention + CPU experts if the CPU GEMM is batched; decode gains need (a) prefetching the next token's likely experts (hot-expert caching like `--moe-cache-mib`/KTransformers) and (b) pinned host memory with async copies. No source measured transfer/compute overlap in isolation (Gap).
- On unified-memory machines the engine should never copy weights; it should place every tensor once and choose kernels by bandwidth, with `cudaMallocManaged`/UM avoided on DGX Spark per the measurements.

### Gaps
- No controlled experiment isolating "attention on GPU vs attention on CPU" was found; all comparisons are layer-split vs expert-offload.
- No measurement of PCIe transfer/compute overlap for streamed experts (pinned memory, double-buffering) on consumer PCs.
- No KTransformers single-4090 decode tokens/s on the current README (older claims from 2025 announcements not fetched).

## KQ8. Kernel authoring from Rust: options, maturity, license, performance

### Takeaway
In 2026 the only production-proven way to get vendor-class kernels from a Rust engine is still hand-written kernel source per API (MSL, CUDA C/PTX, GLSL/SPIR-V) compiled at build time (or JIT via NVRTC/`newLibraryWithSource`) and launched through thin bindings (`objc2-metal`, `cudarc`, `ash`); the Rust-native kernel languages (CubeCL — alpha but used by Burn with tensor-core matmul on NVIDIA; cuda-oxide/cutile-rs — early research; rust-gpu — early, SPIR-V only; Rust-CUDA — rebooting) are promising but none is mature on all three target APIs.

### Cited Findings
- Hand-written per-API (reference implementations): llama.cpp embeds MSL sources and compiles them at runtime or ships `.metallib`, uses GLSL → SPIR-V for Vulkan, and `.cu` for CUDA (KQ1–3). candle (Apache-2.0/MIT) compiles `.cu` to PTX at build time via `cudaforge`, ships MoE/MMQ as a static lib, and its Metal kernels are MSL driven through `metal`/`objc2_metal`. — [candle](https://github.com/huggingface/candle), [candle-kernels build.rs](https://github.com/huggingface/candle/blob/main/candle-kernels/build.rs), [candle-metal-kernels](https://github.com/huggingface/candle/blob/main/candle-metal-kernels/src/lib.rs)
- `cudarc` 0.19.10 (Apache-2.0/MIT): driver API + NVRTC + cuBLAS/cuBLASLt/cuDNN/NCCL wrappers, dynamic loading by default, PTX load/launch at runtime. — [docs.rs cudarc](https://docs.rs/crate/cudarc/latest)
- `objc2-metal` 0.3.2 (Zlib/Apache/MIT): Metal 4 and tensor/residency types bound; unsafe at the resource/sync boundary. — [docs.rs objc2-metal](https://docs.rs/objc2-metal/latest/objc2_metal/)
- `ash` (Apache-2.0/MIT): Vulkan 1.1–1.4 raw bindings, all unsafe, extensions by namespace. — [ash](https://github.com/ash-rs/ash)
- `wgpu` v30 (Apache-2.0/MIT): WebGPU abstraction over Vulkan/Metal/D3D12/GL; Naga WGSL translation; no coopmat/f16 features documented. — [wgpu](https://github.com/gfx-rs/wgpu)
- CubeCL (MIT/Apache-2.0): "currently in alpha", used in production by Burn, breaking changes between minors; runtimes: NVIDIA (LLVM → PTX, CUDA), AMD (LLVM → AMDGPU, HIP), Apple (MSL via wgpu, plus `metal-native`), Vulkan (SPIR-V via wgpu), WebGPU (WGSL), CPU (LLVM native); tensor cores unavailable with the WGSL compiler and on CPU; CUDA thread-block clusters on Hopper+ with `cuda-cpp`; autotune benchmarks kernels/comptime specializations and caches results per device (`cubecl::environment::bundle()` to pre-warm). — [tracel-ai/cubecl](https://github.com/tracel-ai/cubecl), [docs.rs cubecl 0.10.0](https://docs.rs/crate/cubecl)
- Burn 0.20 (2026-01-15): CubeK kernel architecture minimizing CPU launch latency; NVIDIA matmul engine with TMA + warp specialization and tensor-core batched vec@mat, "low-level tuning for full tensor core saturation is still in progress"; CPU backend conv/matmul "need more work" before production; quantized `QuantStore` packing (`PackedNative`, e2m1x2 FP4); benchmarks vs LibTorch on RTX 5090-class hardware: matmul 4096² 639 µs vs 627 µs (LibTorch faster), batched vec@mat 638 µs vs 628 µs (was 58.8 ms in 0.19.1). — [Burn 0.20 release](https://tracel.ai/blog/release-0.20.0) (SELF-REPORTED)
- cuda-oxide / cutile-rs (Apache-2.0): Rust → PTX via custom rustc codegen (pinned nightly), SIMT model with shared memory/TMA/cluster ops; "early-stage research project… expect bugs… API breakage"; cutile-rs reportedly needs stable Rust 1.89+ and CUDA 13.3 (secondary). — [NVlabs/cuda-oxide](https://github.com/NVlabs/cuda-oxide), [DevX](https://www.devx.com/artificial-intelligence-ai/what-is-cuda-rust-nvidia-gpu-kernels/)
- rust-gpu (Apache-2.0/MIT): "still heavily in development and is at an early stage… not yet production-ready"; SPIR-V (Vulkan) only ("Currently only SPIR-V support is planned"); plugs in via `-Z codegen-backend` (implies nightly). — [Rust-GPU/rust-gpu](https://github.com/Rust-GPU/rust-gpu); the Embark repository reportedly went read-only on 2025-10-31 with the project moved to the Rust-GPU org (seen only in a search summary). — [embarkstudios/rust-gpu](https://github.com/embarkstudios/rust-gpu) (UNVERIFIED)
- Rust-CUDA (Apache-2.0/MIT): rebooted, early, "Expect bugs, safety issues". — [Rust-GPU/Rust-CUDA](https://github.com/Rust-GPU/Rust-CUDA)
- Licenses of reference kernels that could be ported: llama.cpp/ggml (MIT), MLX (MIT), candle (Apache-2.0/MIT), ExLlamaV3 (MIT), KTransformers (Apache-2.0), MoltenVK (Apache-2.0), Lemonade (Apache-2.0), ANEMLL (MIT), FastFlowLM (MIT wrapper + proprietary free binary kernels), Hexagon SDK and QAIRT (license not stated on the pages fetched). — see repo links above. (ggml/MLX licenses are from general knowledge of those repositories and were not re-fetched in this session.)

### Inferences
- A pragmatic kernel strategy for an Apache-2.0 Rust engine: (1) write kernels in each API's native language (MSL, CUDA C++, GLSL) under `kernels/`, (2) compile at build time into embedded artifacts (`.metallib`, PTX/cubin per arch, SPIR-V) with a runtime JIT fallback (`newLibraryWithSource`, NVRTC, glslang at runtime is avoidable), (3) bind through `objc2-metal`, `cudarc` (dynamic loading), `ash`, (4) keep a `wgpu`/WGSL subset only for portability testing. Porting algorithms (not code) from MIT/Apache references is license-clean; verbatim MIT code requires attribution notices.
- CubeCL is the one Rust-native option worth tracking for a shared quantized-GEMV/GEMM kernel across CUDA/HIP/Metal/Vulkan, but its own benchmarks still trail LibTorch on dense matmul and its Metal/Vulkan tensor-core status is undocumented; adopting it in v1 would couple the engine to an alpha API.
- Because decode is bandwidth-bound, the highest-value hand-written kernels are: quantized GEMV (per quant type), fused RMSNorm/RoPE/residual, flash-decode attention with quantized KV, and MoE router+gather; prefill GEMMs can initially lean on vendor libraries (cuBLAS via cudarc, MPP tensor ops on Metal, coopmat GLSL on Vulkan).

### Gaps
- No head-to-head benchmark of CubeCL-generated kernels vs llama.cpp/MLX kernels on Metal or Vulkan was found.
- rust-gpu release cadence in 2026 and cuda-oxide's exact release timeline (May vs September 2026) are inconsistent across sources and unverified.
- Slang as a cross-API shading language for a Rust engine was not evaluated (no sources fetched).

## KQ9. What a new engine should implement first (synthesis)

### Takeaway
Implement Metal first (largest share of LLMario's user base per the existing MLX/llama.cpp supervision and the richest, most stable unified-memory story), CUDA second (largest discrete-GPU installed base; decode-bound patterns well understood), Vulkan third as the universal fallback covering AMD/Intel/iGPUs and Linux, and defer NPUs to an optional delegate; the core engine design should be decode-bandwidth-centric with explicit memory budgets.

### Cited Findings
- Decode is memory-bandwidth-bound across every platform examined: Apple (Apple's M5 post), NVIDIA (bandwidth-matched throughput ratios), Strix Halo (~215 GB/s), DGX Spark (~273 GB/s). — [Apple M5 post](https://machinelearning.apple.com/research/exploring-llms-mlx-m5), [Framework thread](https://community.frame.work/t/amd-strix-halo-ryzen-ai-max-395-gpu-llm-performance-tests/72521), [discussion 16578](https://github.com/ggml-org/llama.cpp/discussions/16578)
- Prefill is compute-bound and benefits 2–4× from tensor units (M5 tensor API, coopmat on Vulkan, FP8/FP4 on Blackwell). — [lmstudio #2040](https://github.com/lmstudio-ai/lmstudio-bug-tracker/issues/2040), [Bolz slides](https://www.vulkan.org/user/pages/09.events/vulkanised-2025/T47-Jeff-Bolz-NVIDIA.pdf), [Blackwell whitepaper](https://images.nvidia.com/aem-dam/Solutions/geforce/blackwell/nvidia-rtx-blackwell-gpu-architecture.pdf)
- Memory-predictability mechanisms with primary documentation: Metal residency sets + `recommendedMaxWorkingSetSize` budget (KQ1); CUDA VMM reserve/map pools (KQ2); llama.cpp `--fit` (KQ7); MLX page-granular cache limits (KQ1).
- Vulkan already covers NVIDIA/AMD/Intel/Apple/iGPUs in one backend with measured results on all (KQ3), and in 2026 wins decode on AMD APUs (KQ4).
- NPU paths are vendor-runtime-only with static shapes and ≤8B practical limits (KQ6).

### Inferences
- Phase 1 (Metal): shared-mode buffers over mmap, residency sets with keep-alive, budget from `recommendedMaxWorkingSetSize` with an opt-in wired-limit override, simdgroup-matrix GEMM + bandwidth-tuned quantized GEMV + fused norm/rope/attention kernels, runtime-probed Metal 4 `matmul2d` tensor path for prefill and MoE on M5/A19+, MSL compiled to `.metallib` at build time with runtime fallback.
- Phase 2 (CUDA): `cudarc` dynamic loading + NVRTC/PTX cache, VMM arena for KV growth, CUDA graphs for batch-1 decode with llama.cpp's "warm-up then capture, compare node properties" strategy, int8/FP8 tensor-core GEMM for prefill (cuBLAS via cudarc first), NVFP4/MXFP4 weight decode on Blackwell, Windows guidance on sysmem fallback.
- Phase 3 (Vulkan via `ash`): GLSL → SPIR-V at build time, KHR coopmat + NV coopmat2 probing, scalar fallback, per-device deny list and self-test; this is also the macOS test path through KosmicKrisp/MoltenVK.
- Later/optional: NPU delegate boundary (OpenVINO, FLM/OGA, Hexagon via llama.cpp) for ≤4B models, embeddings and draft models; `wgpu` only for portability tests.

### Gaps
- The phase ordering assumes LLMario's user distribution (Mac-heavy); no usage data was examined in this research task.
