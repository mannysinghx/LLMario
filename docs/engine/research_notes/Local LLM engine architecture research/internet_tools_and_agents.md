## Key Question 1 — Tool-call formats per model family, chat templates, and how engines parse them

### Takeaway
There is no single open-model tool format in 2026: at least six wire families coexist (Hermes-style `<tool_call>{json}</tool_call>`; Qwen3-Coder/Qwen3.5/Nemotron XML `<function=…><parameter=…>`; GLM `<arg_key>/<arg_value>` XML; Llama 3.x JSON after `<|python_tag|>` and Llama 4 pythonic lists; Mistral `[TOOL_CALLS]name[ARGS]{json}` control tokens; Gemma 4 `<|tool_call>call:name{…}<tool_call|>`; gpt-oss Harmony channels; LFM2 pythonic `<|tool_call_start|>[f(a='b')]<|tool_call_end|>`). Every serious engine (llama.cpp, vLLM, SGLang, Ollama, mlx-lm) therefore ships a per-family parser table plus an incremental (streaming) parser; llama.cpp additionally infers a parser automatically from the Jinja template by differential rendering. Small-model reliability on the only broad public benchmark (BFCL v4) is middling and the benchmark itself was rated "flawed" by Epoch AI in Sept 2026, so the engine must assume malformed calls and validate/repair them.

### Cited Findings

**Formats (from the models' own chat templates / prompt-format docs)**

- Qwen3 (2025): the Qwen docs recommend "Hermes-style tool use" for Qwen3; tools are OpenAI-style `{"type":"function","function":{...}}` objects, calls come back as name + JSON-string `arguments`; thinking mode (`enable_thinking`, default True) makes the model "first generate a thought (returned as `reasoning_content`) and then generate the tool call(s)"; vLLM ≥ 0.8.5 is run with `--enable-auto-tool-choice --tool-call-parser hermes --reasoning-parser deepseek_r1`; the docs warn that "generated tool calls can be malformed, so production code should parse and validate them independently" and that stopword-based ReAct templates break with reasoning models because stopwords may appear inside the thought — [Qwen function-calling docs](https://qwen.readthedocs.io/en/latest/framework/function_call.html)
- Qwen3.5 (repos `Qwen/Qwen3.5-0.8B/2B/4B/9B/27B/35B-A3B/122B-A10B/397B-A17B`, HF repos updated 2026-03-02 to 2026-04-24, task `image-text-to-text`): the canonical `chat_template.jinja` for Qwen3.5-9B switches from Hermes JSON to the XML format: system block `# Tools\n\nYou have access to the following functions:\n\n<tools>` + one `tool | tojson` per line + `</tools>`, then the instruction "If you choose to call a function ONLY reply in the following format with NO suffix: `<tool_call>\n<function=example_function_name>\n<parameter=example_parameter_1>\nvalue_1\n</parameter>\n</function>\n</tool_call>`"; tool results are rendered inside a **user** turn as `<tool_response>\n…\n</tool_response>`; the generation prompt ends with `<think>\n` (or `<think>\n\n</think>\n\n` when `enable_thinking` is false); prior-turn reasoning is re-rendered only for assistant messages after the last user query (`ns.last_query_index`), i.e. thinking is dropped from older history; non-string argument values are serialised with `tojson` inside `<parameter>` tags — [Qwen/Qwen3.5-9B chat_template.jinja](https://huggingface.co/Qwen/Qwen3.5-9B/blob/main/chat_template.jinja); repo list from the HF Hub search (this session).
- Qwen3-Coder-30B-A3B-Instruct (2025): same `<tool_call><function=…><parameter=…>` output format but tool *definitions* are rendered as nested XML (`<function><name>…</name><description>…</description><parameters><parameter><name>…</name><type>…</type>…`) rather than JSON — [Qwen3-Coder chat_template.jinja](https://huggingface.co/Qwen/Qwen3-Coder-30B-A3B-Instruct/blob/main/chat_template.jinja)
- NVIDIA Nemotron 3 Nano 30B-A3B (BF16 repo updated 2026-08-24; 4B variant repos March 2026): template is ChatML (`<|im_start|>`) with the Qwen3-Coder-style XML tool declaration and the identical `<tool_call><function=…><parameter=…>` call format; `enable_thinking` defaults to True; `truncate_history_thinking` (default True) strips `<think>` blocks from assistant turns before the last user message; the template injects `<think></think>` into assistant history that lacks a think block — [nvidia/NVIDIA-Nemotron-3-Nano-30B-A3B-BF16 chat_template.jinja](https://huggingface.co/nvidia/NVIDIA-Nemotron-3-Nano-30B-A3B-BF16/blob/main/chat_template.jinja)
- GLM-4.7-Flash (zai-org, repo updated 2026-01-29; GLM-4.7 / GLM-4.7-FP8 Dec 2025–Jan 2026): prompt starts `[gMASK]<sop>`; tools go in `<|system|>\n# Tools … <tools>{json}</tools>`; call format is `<tool_call>{function-name}<arg_key>{k}</arg_key><arg_value>{v}</arg_value>…</tool_call>` (non-string values `tojson`); results are `<|observation|>` followed by `<tool_response>…</tool_response>` blocks; the generation prompt emits `<think>` unless `enable_thinking` is false (then `</think>`); historic reasoning is kept only after the last user index unless `clear_thinking` is false — [zai-org/GLM-4.7-Flash chat_template.jinja](https://huggingface.co/zai-org/GLM-4.7-Flash/blob/main/chat_template.jinja)
- Gemma 4 (google/gemma-4-E2B-it, E4B-it, 12B-it, 31B-it, 26B-A4B-it; HF repos updated 2026-07-20; QAT q4_0 GGUF variants exist): native special-token format — declarations `<|tool>declaration:name{description:<|"|>…<|"|>,parameters:{…}}<tool|>`, calls `<|tool_call>call:name{key:<|"|>value<|"|>}<tool_call|>`, responses `<|tool_response>…<tool_response|>`, string delimiter `<|"|>`, turns `<|turn>model … <turn|>`, thinking channel `<|channel>thought\n…<channel|>`; the canonical template header reads "Published: 2026-07-09 … Fixed tool-calling loops, turn closures, and thinking content-ordering"; the template raises if `arguments` is a JSON string instead of a mapping; `preserve_thinking` keeps thinking on assistant messages that carry tool calls — [google/gemma-4-E4B-it chat_template.jinja](https://huggingface.co/google/gemma-4-E4B-it/blob/main/chat_template.jinja); Google's function-calling page (updated 2026-06-04) documents the same tokens, says `enable_thinking=True` "improves call accuracy", that `processor.parse_response` separates thinking/content/tool calls, and that "A Gemma model cannot execute code on its own" so developers must validate calls — [ai.google.dev Gemma function calling](https://ai.google.dev/gemma/docs/capabilities/function-calling)
- Llama 3.1/3.3 (2024, background for format; still widely used): roles `system/user/assistant/ipython`; `<|python_tag|>` marks a tool call, `<|eom_id|>` means "expects a tool result before continuing", `<|eot_id|>` ends the turn; built-ins `brave_search`, `wolfram_alpha`, `code_interpreter` via `Environment: ipython` + `Tools:`; custom JSON calls are `<|python_tag|>{"type":"function","name":…,"parameters":{…}}<|eom_id|>`; "only single tool calls are supported for the JSON format"; a zero-shot `<function=name>{json}</function>` variant also exists — [meta-llama/llama-models prompt_format.md](https://github.com/meta-llama/llama-models/blob/main/models/llama3_1/prompt_format.md)
- Llama 4 (2025): headers `<|header_start|>role<|header_end|>`, `<|eot|>`; tool definitions as a JSON list in the system message; pythonic output `[get_weather(city="San Francisco", metric="celsius"), get_weather(city="Seattle", metric="celsius")]` and a JSON-list alternative; results returned under the `ipython` role as a JSON list; the reference system prompt says to "never mix text and function calls in one response" — [Meta Llama 4 prompt format](https://dev.meta.ai/llama/docs/model-cards-and-prompt-formats/llama4/)
- Mistral family incl. Devstral Small 2 (24B, Apache-2.0, 256k context, "light enough to run on a single RTX 4090 or a Mac with 32GB RAM" [vendor-claimed]; SWE-bench Verified 68.0% [vendor-claimed]): template tokens `[SYSTEM_PROMPT]…[/SYSTEM_PROMPT]`, `[AVAILABLE_TOOLS]{json list}[/AVAILABLE_TOOLS]` emitted once before the first user message, `[INST]…[/INST]`, calls `[TOOL_CALLS]name[ARGS]{json}` (one `[TOOL_CALLS]` per call), results `[TOOL_RESULTS]…[/TOOL_RESULTS]`; consecutive same-role messages are merged; the template ships a Mistral Vibe system prompt by default; llama.cpp support required PR #17945 and vLLM uses `--tool-call-parser mistral` with `mistral_common >= 1.8.6` — [Devstral-Small-2 chat_template.jinja](https://huggingface.co/mistralai/Devstral-Small-2-24B-Instruct-2512/blob/main/chat_template.jinja), [Devstral-Small-2 README](https://huggingface.co/mistralai/Devstral-Small-2-24B-Instruct-2512). Mistral's API docs: `tool_choice` ∈ `auto|any|none`, `parallel_tool_calls` default true, example call id `D681PevKs` (9 alphanumerics; vLLM's docs separately say the Transformers backend "needs 9-digit call IDs") — [Mistral function calling](https://docs.mistral.ai/capabilities/function_calling/), [vLLM tool calling](https://docs.vllm.ai/en/latest/features/tool_calling.html)
- gpt-oss (Harmony, Aug 2025): tokens `<|start|>`(200006) `<|channel|>`(200005) `<|message|>`(200008) `<|constrain|>`(200003) `<|end|>`(200007) `<|call|>`(200012, stop token for tool call) `<|return|>`(200002, stop token for final); roles `system > developer > user > assistant > tool`; channels `analysis` (CoT, "not safety-tuned, so don't show it to end users"), `commentary` (function calls + preambles), `final`; tools declared in the developer message as TypeScript-like `namespace functions { … }`; a call is an assistant message on `commentary` with header `to=functions.get_current_weather` + `<|constrain|>json` + args + `<|call|>`; a result is `<|start|>{toolname} to=assistant<|channel|>commentary<|message|>{output}<|end|>`; prior `analysis` content must be passed back while a tool loop is in progress and dropped once the turn ends in `final`; `Reasoning: low|medium|high` in the system message; built-in `browser.search/open/find` and `python` are declared in the system message and called on the `analysis` channel; schema enforcement "requires a grammar applied during sampling" — [OpenAI Harmony guide](https://developers.openai.com/cookbook/articles/openai-harmony). Library: `openai-harmony` is a Rust core with pyo3 bindings, Apache-2.0, crates.io 0.0.8 (updated 2025-11-05, ~2.05M downloads), provides `StreamableParser` for incremental decoding — [openai/harmony](https://github.com/openai/harmony), [crates.io API](https://crates.io/api/v1/crates/openai-harmony)
- LFM2 / LFM2.5 (Liquid AI; LFM2.5 230M–8B-A1B repos updated Aug–Sep 2026): ChatML framing; tools listed as `List of tools: <|tool_list_start|>[json, json]<|tool_list_end|>` in the system prompt; calls are pythonic `<|tool_call_start|>[name(arg='v', n=1)]<|tool_call_end|>` (strings single-quoted, mappings `tojson`); results `<|tool_response_start|>…<|tool_response_end|>`; the template raises if `arguments` is a JSON-encoded string — [LiquidAI/LFM2-1.2B chat_template.jinja](https://huggingface.co/LiquidAI/LFM2-1.2B/blob/main/chat_template.jinja). llama.cpp's PEG builder has `python_style_tool_calls()` "Used by LFM2 and similar templates" — [chat-peg-parser.h](https://github.com/ggml-org/llama.cpp/blob/master/common/chat-peg-parser.h)
- SmolLM3-3B (HF, 2025): ChatML; Hermes-style `<tools>{json}</tools>` + `<tool_call>{json}</tool_call>`; reasoning toggled by `/think` / `/no_think` in the system prompt or `enable_thinking`; supports `xml_tools` and `python_tools` template variables — [SmolLM3-3B chat_template.jinja](https://huggingface.co/HuggingFaceTB/SmolLM3-3B/blob/main/chat_template.jinja)
- IBM Granite 4.0 (h-small): Hermes-style — system text "You are provided with function signatures within <tools></tools> XML tags" and "return a json object with function name and arguments within <tool_call></tool_call> XML tags: `<tool_call>\n{"name": <function-name>, "arguments": <args-json-object>}\n</tool_call>`", plus a `<documents>` RAG block — [granite-4.0-h-small chat_template.jinja](https://huggingface.co/ibm-granite/granite-4.0-h-small/blob/main/chat_template.jinja). Granite 4.2 (3B/8B/30B; MLX/NVFP4 repos dated 2026-09-02) has thinking on by default per vLLM (`granite_thinking_parser`, `enable_thinking=false` to disable) — [vLLM reasoning outputs](https://docs.vllm.ai/en/latest/features/reasoning_outputs.html)
- DeepSeek-V3.2 (MIT): README states the `DeepSeek-V3.2-Speciale` variant "does not support the tool-calling functionality", introduces a `developer` role "dedicated exclusively to search agent scenarios", and warns a provided parser "is not suitable for production use without robust error handling" — [deepseek-ai/DeepSeek-V3.2 README](https://huggingface.co/deepseek-ai/DeepSeek-V3.2). XGrammar-2 adds a `deepseek_xml` option "for DeepSeek's XML-style parameter format" — [XGrammar-2 post](https://blog.mlc.ai/2026/05/04/xgrammar-2-fast-customizable-structured-generation)
- Phi-4-mini-instruct: 3.8B dense, 200K vocab, 128K context, MIT license, released February 2025, post-trained for "instruction following, function calling" — [microsoft/Phi-4-mini-instruct](https://huggingface.co/microsoft/Phi-4-mini-instruct) (exact tool token format not captured; see Gaps)
- FunctionGemma-270M: vLLM ships a `functiongemma` parser and says the model is "intended to be fine-tuned for your task" — [vLLM tool calling](https://docs.vllm.ai/en/latest/features/tool_calling.html)

### Inferences
- An engine written in 2026 should treat the *template* as the source of truth and implement (a) a Jinja renderer (minijinja in Rust is the obvious candidate, unverified here) with `tools`, `enable_thinking`, `reasoning_content`, `tool_responses`, `preserve_thinking`, `truncate_history_thinking`, `clear_thinking` variables, (b) a small set of hand-written incremental parsers for the ~8 wire families above, and (c) an auto-parser modelled on llama.cpp's differential template analysis as the fallback. llama.cpp's four `tool_format` kinds plus pythonic cover every template examined here.
- Argument values must be kept as JSON objects internally: Gemma 4, LFM2 and Qwen3.5 templates all raise or mis-render when `arguments` is a JSON-encoded string, while the OpenAI API requires a string on the wire — convert at the API boundary only.
- Tool results are rendered under different roles (`ipython` for Llama, a `user` turn with `<tool_response>` for Qwen3.5, `<|observation|>` for GLM, `tool` role named after the tool for Harmony); the internal message model must carry `tool_call_id → name` so templates like Gemma 4's can resolve names.
- Streaming tool calls needs the partial-parse state machine (llama.cpp `NEED_MORE_INPUT`, Ollama `Add(chunk, done)`, Harmony `StreamableParser`); the buffering of arguments "until tool name is known" is a recurring design point.
- Reliability below ~4B is poor on multi-turn tool use by every source found; the engine should default small models to single-call mode with grammar enforcement and validation/repair, and reserve parallel calls for models whose templates/parsers advertise them.

## Key Question 2 — Constrained (grammar-guided) decoding

### Takeaway
For a Rust engine the natural embed is **llguidance** (MIT, native Rust crate `llguidance` 1.9.1, no precomputation, ~50 µs/token measured, already the backend inside llama.cpp, vLLM, SGLang, mistral.rs and OpenAI); **XGrammar-2** (Apache-2.0, C++ with a community Rust binding) is the alternative with the richest "structural tag" DSL for tool calls and reasoning-then-JSON. Outlines-core (Apache-2.0, Rust) is regex/DFA-only, lm-format-enforcer is Python, and llama.cpp's own GBNF engine has documented performance problems. Lazy/triggered grammars (start enforcing only after `<tool_call>` or `</think>`) are how every engine reconciles free-form thinking with constrained tool JSON.

### Cited Findings
- llguidance: "Super-fast Structured Outputs"; MIT; Rust (build needs Rust ≥1.87; Python and C/C++ bindings); grammars = large JSON-Schema subset, regex, Lark-like CFG that can embed schemas/regex; "about 50μs of CPU time per token for a 128k tokenizer, with negligible startup cost"; full mask for a typical JSON schema ≈1.5 ms, with the slicer the JSON-Schema-Bench average (2.5M tokens, 10k schemas) is <50 µs, <1% of masks >1 ms, 0.001% >10 ms; integrations: Guidance, OpenAI (JSON Schema, 2025-05-20), llama.cpp (`-DLLAMA_LLGUIDANCE=ON`, merged b4613 2025-02-01), Chromium (2025-04-11), SGLang (v0.4.4, 2025-02-26), vLLM (v0.8.2, 2025-03-25), LLGTRT, mistral.rs, onnxruntime-genai; v1.0.0 declared 2025-06-23 — [guidance-ai/llguidance](https://github.com/guidance-ai/llguidance). crates.io: `llguidance` max stable 1.9.1, MIT, updated 2026-09-30, ~1.93M downloads — [crates.io API](https://crates.io/api/v1/crates/llguidance)
- llguidance internals and measurements (Microsoft blog, 2025-06-11): regex-derivative lexer (`derivre`, Brzozowski derivatives, lazily built) handles most checks, Earley parser only "about 0.1-1% of checks"; token trie with depth-first layout (~13 cycles per node at ~4.2 IPC on AMD EPYC 7V13); "slicer" precomputed masks for regex-defined token slices; MaskBench (~2M masks) average ≈50 µs, startup ≈2 ms; sparse masks ≈28 µs, sliced ≈61 µs, dense-unsliced (0.5%) ≈1,577 µs; other libraries "10-1000x slower on masks, and about 1000x slower at startup"; XGrammar "pre-computation often takes seconds and sometimes minutes" though masks can be <8 µs in about half of cases; llama.cpp grammars slower due to "a lack of a lexer and use of a backtracking parser" [measured, by the llguidance authors] — [Making structured outputs go brrr](https://guidance-ai.github.io/llguidance/llg-go-brrr)
- XGrammar: Apache-2.0; APIs in Python, C++, JavaScript, Swift; JSON, regex, custom CFG; "near-zero overhead" [vendor-claimed]; default backend for vLLM, SGLang, TensorRT-LLM, MLC-LLM; third-party Rust binding `xgrammar-rs` (trymirai) — [mlc-ai/xgrammar](https://github.com/mlc-ai/xgrammar). `xgrammar-rs`: Apache-2.0, crate `xgrammar-rs` 0.1, builds the C++ core via a git submodule/`build.rs`, supports JSON Schema/EBNF/regex/CFG, `GrammarCompiler`/`GrammarMatcher`, optional HF tokenizers feature, wasm32-wasi builds — [trymirai/xgrammar-rs](https://github.com/trymirai/xgrammar-rs)
- XGrammar-2 (2026-05-04): "Structural Tag" composable JSON DSL describing formats such as OpenAI Harmony and model-specific tool-call protocols, exposed through engines' `response_format`; `triggered_tags` enforce a tool-call format once a trigger string appears after a free-text reasoning segment ending at `</think>`; built-in tags for DeepSeek V4, Qwen 3.6, GPT-OSS; JSON Schema, regex, literal strings and token IDs as atomic types; cross-grammar cache with hierarchical hashing ("nearly 50%" structure reuse at 50 tools); bounded-repetition fix 534 ms → 5.37 ms (~100×); "up to an 80× compilation speedup over XGrammar" scaling 10→500 tools; batch mask APIs and `traverse_draft_tree` for speculative decoding; APIs in Python, C++, Rust and JS via TVM-FFI; adopters xAI, Databricks, DeepSeek [vendor-claimed numbers] — [XGrammar-2 blog](https://blog.mlc.ai/2026/05/04/xgrammar-2-fast-customizable-structured-generation)
- Outlines-core: Rust, Apache-2.0, crate `outlines-core`; pipeline = JSON schema → regex (`regex_from_str`) → `Vocabulary` → `Index` (token→DFA transitions); no CFG support shown; Python bindings — [dottxt-ai/outlines-core](https://github.com/dottxt-ai/outlines-core). (The llguidance blog attributes Outlines' "significant startup cost and memory overhead" to precomputing automaton states/masks.)
- lm-format-enforcer: Python, MIT; JSON Schema + regex; lets the model choose whitespace and field order (default whitespace cap 12, default max array length 20); integrations incl. llama.cpp (python), vLLM, TRT-LLM; regex parser limited to characters present in the vocabulary — [noamgat/lm-format-enforcer](https://github.com/noamgat/lm-format-enforcer)
- llama.cpp GBNF: syntax incl. token matchers `<[id]>` and `<text>` (single-vocab-token strings) and `!` negation; JSON-schema conversion limits: `additionalProperties` defaults to false, "Unsupported features are skipped silently", `prefixItems` broken, `minimum/maximum` only for integers, nested/remote `$ref` broken, `pattern` must be `^…$`, no `uri/email` formats, no `patternProperties`, `not`/conditionals "unlikely to be implemented"; "Grammars have known performance problems, tracked in issue #4218"; `x? x? … x?` patterns are "extremely slow" (use `x{0,N}`) — [llama.cpp grammars/README.md](https://github.com/ggml-org/llama.cpp/blob/master/grammars/README.md)
- llama.cpp lazy grammars: the PEG builder's `build_grammar(builder, lazy)` emits "only trigger rules and their descendants", i.e. generation is unconstrained until a trigger (e.g. a tool-call opener) is seen — [peg-parser.h](https://github.com/ggml-org/llama.cpp/blob/master/common/peg-parser.h)
- vLLM structured outputs: backends xgrammar, guidance (llguidance), outlines, lm-format-enforcer with `--structured-outputs-config.backend auto` default; request fields `structured_outputs.{choice,regex,json,grammar,structural_tag}` and `response_format: json_schema`; legacy `guided_*` fields removed in v0.12.0; reasoning + structured outputs: reasoning in `message.reasoning`, structured result in `message.content`; Qwen3-Coder with unparsed reasoning may disable structured outputs unless `--structured-outputs-config.enable_in_reasoning=True` (v0.11.2+); advice: "state the JSON schema and how fields should be populated in the prompt" — [vLLM structured outputs](https://docs.vllm.ai/en/latest/features/structured_outputs.html)
- OpenAI exposes the same idea as "custom tools" with `format: {type: "grammar", syntax: "lark"|"regex"}` returning `custom_tool_call` plain-text `input` — [OpenAI function calling guide](https://developers.openai.com/api/docs/guides/function-calling)
- JSONSchemaBench (arXiv 2501.10868, v3 2025-02-27; authors incl. Geng, Moskal, Nori): 10K real-world JSON schemas plus the official JSON Schema Test Suite; compares Guidance, Outlines, llama.cpp, XGrammar, OpenAI, Gemini on efficiency, coverage, and output quality (results not in the abstract) — [arXiv 2501.10868](https://arxiv.org/abs/2501.10868)
- Harmony note: a `# Response Formats` JSON schema in the developer prompt "only influences output. Enforcing the schema requires a grammar applied during sampling" — [OpenAI Harmony guide](https://developers.openai.com/cookbook/articles/openai-harmony)

### Inferences
- Token-mask cost is now small relative to a forward pass on consumer hardware (tens of µs per token vs. tens of ms per token for a 7B model on a laptop), so the engine can afford to run a mask on every step; the real engineering risk is *startup* (schema compile) latency, which favours llguidance's no-precompute design for interactive desktop use with many MCP tools whose schemas change per session. Caching compiled grammars keyed by (tool-set hash, tokenizer hash) is still worthwhile given XGrammar-2's reported 80× gains from exactly that.
- "Thinking then JSON" is solved uniformly by *trigger-based* enforcement: unconstrained until `</think>` (or a tool-call opener) then constrained; the engine's sampler needs a hook that switches the mask provider on at a trigger string, and the chat parser must tell the sampler which trigger strings exist for the active template.
- Streaming is compatible with constrained decoding because masks are per-token; the complication is that incremental *parsing* of the constrained output into OpenAI deltas needs the partial-parse machinery from Q1.
- Licenses are all permissive (MIT/Apache-2.0) for the candidates; the only GPL-adjacent item in this area is none. Embedding llguidance as a crate avoids a C++ toolchain dependency, which matters for a Rust desktop build matrix.

### Gaps
- No independent head-to-head of llguidance vs XGrammar-2 (post-May-2026) was found; the only cross-library numbers are from the llguidance authors (June 2025) and XGrammar-2's self-comparison against XGrammar-1.
- JSONSchemaBench's quantitative results (coverage %, compliance, per-engine overhead) were not extracted (abstract only).
- Whether llguidance exposes a first-class "structural tag"/trigger API in Rust comparable to XGrammar-2's `triggered_tags`, versus relying on the host (as llama.cpp does with lazy GBNF), was not confirmed from the repo page.
- Memory footprint of mask caches for 150k–260k-token vocabularies on consumer machines: no figures found.

## Key Question 3 — Model Context Protocol (MCP)

### Takeaway
The current MCP revision is **2026-07-28** (previous: 2025-11-25, 2025-06-18, 2025-03-26, 2024-11-05). The 2026-07-28 revision made MCP *stateless* (no `initialize` handshake, no `Mcp-Session-Id`, every request carries protocol version + client capabilities in `_meta`, new `server/discover`), replaced server-initiated requests with the Multi Round-Trip Request pattern (`resultType: "input_required"`), moved Tasks into an official extension, deprecated Roots/Sampling/Logging and HTTP+SSE, and deprecated Dynamic Client Registration in favour of Client ID Metadata Documents. The official Rust SDK `rmcp` (Apache-2.0, 3.5.1, 2026-10-05) already implements 2026-07-28 with stdio and Streamable HTTP client/server, OAuth, elicitation and tasks. For a local host the spec's normative duties are: human-in-the-loop with the ability to deny every tool call, show tool inputs before calling, treat tool annotations as untrusted, show the exact command before launching a local (stdio) server, sandbox it, and log tool usage.

### Cited Findings
- Spec landing page: schema is `schema/2026-07-28/schema.ts`; hosts/clients/servers over JSON-RPC 2.0; server features Resources/Prompts/Tools; client feature Elicitation; extensions: Tasks, Skills over MCP, MCP Apps; security principles: "Hosts must obtain explicit user consent before invoking any tool", "descriptions of tool behavior such as annotations should be considered untrusted, unless obtained from a trusted server" — [MCP specification (latest)](https://modelcontextprotocol.io/specification/latest)
- 2026-07-28 changes vs 2025-11-25: remove protocol sessions and `Mcp-Session-Id` (SEP-2567); remove `initialize`/`notifications/initialized`, carry `io.modelcontextprotocol/protocolVersion` and `clientCapabilities` in `_meta` on every request (SEP-2575); add `server/discover` (MUST implement); replace GET stream and resource subscriptions with `subscriptions/listen`; remove `ping`, `logging/setLevel`; tasks moved to extension `io.modelcontextprotocol/tasks` with `tasks/get` polling and `tasks/update` (SEP-2663); Multi Round-Trip Requests replace `roots/list`, `sampling/createMessage`, `elicitation/create` server-initiated calls (SEP-2322); all results carry `resultType` (`complete`/`input_required`); SSE resumability (`Last-Event-ID`) removed; minor: `extensions` capability field, OpenTelemetry `traceparent/tracestate/baggage` in `_meta` (SEP-414), deterministic `tools/list` ordering for prompt-cache hits, required `Mcp-Method`/`Mcp-Name` headers and `x-mcp-header` (SEP-2243), `ttlMs`/`cacheScope` on list results (SEP-2549), `iss` validation (SEP-2468), `inputSchema`/`outputSchema` may use any JSON Schema 2020-12 keywords (SEP-2106); deprecated: Roots, Sampling, Logging (SEP-2577), HTTP+SSE transport, `includeContext` values, RFC 7591 Dynamic Client Registration (in favour of Client ID Metadata Documents, PR #2858); a 12-month minimum deprecation window policy (SEP-2596) — [2026-07-28 changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog)
- 2025-11-25 changes vs 2025-06-18: OpenID Connect Discovery for AS discovery (PR #797); icons on tools/resources/prompts (SEP-973); incremental scope consent via `WWW-Authenticate` (SEP-835); tool-name guidance (SEP-986); URL-mode elicitation (SEP-1036); tool calling in sampling (`tools`, `toolChoice`, SEP-1577); OAuth Client ID Metadata Documents (SEP-991); experimental tasks (SEP-1686); stdio servers may log to stderr; 403 for invalid `Origin`; input-validation errors as Tool Execution Errors "to enable model self-correction" (SEP-1303); SSE polling (SEP-1699); JSON Schema 2020-12 default (SEP-1613); SDK tiering (SEP-1730) — [2025-11-25 changelog](https://modelcontextprotocol.io/specification/2025-11-25/changelog)
- Tools (2026-07-28): "there SHOULD always be a human in the loop with the ability to deny tool invocations"; applications SHOULD show which tools are exposed, insert visual indicators on invocation, and present confirmation prompts; `tools/list` MUST NOT vary per connection but MAY vary by authorization; deterministic ordering SHOULD be used; tool fields `name/title/description/icons/inputSchema/outputSchema/annotations`; "clients MUST consider tool annotations to be untrusted unless they come from trusted servers"; names SHOULD be 1–128 chars of `[A-Za-z0-9_.-]`, unique per server, and aggregators SHOULD prefix with a server identifier; results: `content[]` of `text|image|audio|resource_link|resource` plus `structuredContent` validated against `outputSchema` (clients SHOULD validate); `isError: true` tool-execution errors SHOULD be passed to the model; stateful tools use explicit handles as arguments; security: servers MUST validate inputs, access-control, rate limit, sanitize outputs; clients SHOULD prompt for confirmation on sensitive operations, "Show tool inputs to the user before calling the server, to avoid malicious or accidental data exfiltration", validate results before passing to the LLM, implement timeouts, and "Log tool usage for audit purposes"; `x-mcp-header` must not carry secrets — [MCP Tools spec](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)
- Security best practices (2026-07-28): confused-deputy mitigations for OAuth proxies (per-client consent, exact `redirect_uri` match, single-use `state`); "MCP servers MUST NOT accept any tokens that were not explicitly issued for the MCP server" (token passthrough forbidden); SSRF section for clients fetching OAuth metadata URLs: require HTTPS (loopback exception), block `10/8, 172.16/12, 192.168/16, 127/8, ::1, 169.254/16 (cloud metadata), fc00::/7, fe80::/10`, "Avoid implementing IP validation manually. Attackers exploit encoding tricks (octal, hex, IPv4-mapped IPv6)", validate redirect targets / consider disabling auto-redirect, use egress proxies "like Smokescreen", pin DNS between check and use; state-handle hijacking (bind handles to the authenticated user, random non-sequential, expiring); local MCP server compromise: a client with one-click local config "MUST … Show the exact command that will be executed, without truncation", require explicit approval, SHOULD highlight dangerous patterns (`sudo`, `rm -rf`, network ops, SSH keys), "Warn that MCP servers run with the same privileges as the client", "Execute MCP server commands in a sandboxed environment with minimal default privileges", restrict FS/network with explicit grants; local servers SHOULD prefer stdio or require a token/unix socket over HTTP; OAuth URLs: only `http(s)`, reject `javascript:/data:/file:/vbscript:`, "MUST NOT use shell commands … to open URLs"; scope minimization guidance — [MCP security best practices](https://modelcontextprotocol.io/specification/2026-07-28/basic/security_best_practices)
- Tasks extension: id `io.modelcontextprotocol/tasks`; server returns `CreateTaskResult` (`resultType: "task"`, `taskId`, status, `ttlMs`, `pollIntervalMs`); statuses `working | input_required | completed | failed | cancelled`; `tasks/get` polling, `tasks/update` for input responses, `tasks/cancel` (cooperative); optional `notifications/tasks` via `subscriptions/listen`; clients declare support in per-request `_meta` capabilities and servers in `server/discover`; "Never return a task to a client that did not declare support" — [MCP Tasks overview](https://modelcontextprotocol.io/extensions/tasks/overview)
- rmcp (official Rust SDK): crate `rmcp` (+ `rmcp-macros`), max stable 3.5.1, Apache-2.0, created 2025-03-16, updated 2026-10-05, ~33.7M downloads; "Implements the stable MCP 2026-07-28 spec and stays compatible with 2025-11-25 and earlier"; transports: stdio (client/server), child process (client), Streamable HTTP server and client (reqwest), in-process; the standalone 2024-11-05 HTTP+SSE transport is explicitly not provided; features: `#[tool]`, `#[tool_router]`, `#[prompt]` macros, OAuth, elicitation (form and URL), tasks (SEP-2663), sampling/roots/logging/completions/subscriptions/MRTR/caching/pagination; dependents include goose (Block), apollo-mcp-server, hyper-mcp; client example: `().serve(TokioChildProcess::new(...)).await?` then `client.list_all_tools()` / `client.call_tool(CallToolRequestParams::new("add"))` — [modelcontextprotocol/rust-sdk](https://github.com/modelcontextprotocol/rust-sdk), [crates.io API](https://crates.io/api/v1/crates/rmcp)
- Claude Desktop: local servers configured in `claude_desktop_config.json` under `mcpServers` with `command/args/env`; "All actions require your explicit approval before execution"; the filesystem server is scoped to the directories passed as args; "The server runs with your user account permissions"; stderr of each server is logged to `mcp-server-NAME.log` — [Connect to local MCP servers](https://modelcontextprotocol.io/docs/develop/connect-local-servers)
- LM Studio: "Starting LM Studio 0.3.17, LM Studio acts as an Model Context Protocol (MCP) Host" (local and remote servers, 0.3.17 b10); config via `mcp.json` in Cursor notation; remote servers use `url` + `headers`; "Never install MCPs from untrusted sources"; warns some servers "use excessive tokens and cause context overflows"; deeplink "Add to LM Studio" installs; no built-in web search mentioned — [LM Studio MCP docs](https://lmstudio.ai/docs/app/plugins/mcp)
- Jan: MCP servers added in Settings > MCP Servers (Command/Arguments/Environment Variables, i.e. local processes); approval is per tool call with the arguments shown inline, or globally bypassed with "Allow All MCP Tool Permissions"; local models need tool calling enabled in Model Capabilities; Browser MCP example with advice to use private windows "so it doesn't access logged-in sessions" — [Jan MCP docs](https://www.jan.ai/docs/desktop/mcp)
- Open WebUI v0.6.31 (2025-09-25): "MCP (streamable HTTP) server support was added alongside existing OpenAPI server integration"; OAuth 2.1 dynamic client registration for MCP auth; tools can return HTML/iframes rendered in chat — [Open WebUI v0.6.31 release](https://github.com/open-webui/open-webui/releases/tag/v0.6.31)
- llama.cpp server as MCP client: `--mcp-servers-config PATH` / `--mcp-servers-json` take Cursor-compatible definitions, "Only the stdio transport is supported", keys `command` (required), `args`, `env`, `cwd`, `timeout_ms` (default 30000); servers are spawned at startup to list tools, then "stopped and respawned on demand"; tools appear as `<server>_<tool>` (collisions skipped); "runs with the same privileges as the server, so only declare commands you trust"; no approval mechanism described; separate `--ui-mcp-proxy` for browser-side remote MCP — [llama.cpp server README](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)
- Ollama ships a Python MCP server (`web-search-mcp.py`) so "any MCP client" (Cline, Codex, Goose shown) can use its hosted web search — [Ollama web search docs](https://docs.ollama.com/capabilities/web-search)
- AnythingLLM (v1.17.0 banner): built-in agent skills RAG Search, Web Browsing, Web Scraping, Save Files, List/Summarize Documents, Chart Generation, SQL Agent, File System Agent, Document Generation, Gmail/Calendar/Outlook agents, Scheduled Jobs; "AnythingLLM will automatically determine if your LLM can use tools"; MIT — [AnythingLLM agent docs](https://docs.anythingllm.com/agent/overview)

### Inferences
- Because 2026-07-28 removed sessions and the initialize handshake, a Rust host should design its connection layer around per-request `_meta` (protocol version, client capabilities, client info) and `server/discover`, with a compatibility shim for 2025-11-25 servers (rmcp already does this). Supporting the deprecated Roots/Sampling/Logging is optional and arguably undesirable for a new host; "integrate directly with LLM provider APIs instead of Sampling" is the spec's own migration advice.
- The spec's normative duties map directly to engine features: per-server permission profiles (allow/ask/deny per tool), mandatory argument display before execution, treatment of `annotations.readOnlyHint`/`destructiveHint` as hints only (they are untrusted), `outputSchema` validation, timeouts, and an audit log of tool invocations.
- A desktop engine that spawns stdio servers should run them under the same sandbox used for its own web fetcher (see Q7); the spec explicitly recommends platform sandboxing and explicit grants for directories/network.
- Tasks (polling with `input_required`) fit the agent loop well for long web research or human-approval gates; since Tasks is an extension, the host must opt in per request and handle polymorphic results.

### Gaps
- The 2025-06-18 changelog (structured tool output, elicitation, resource links, OAuth resource-server classification, removal of JSON-RPC batching) was not fetched; those attributions are [unverified] here.
- Open WebUI's doc page for MCP returned 404; only the release note was used. Whether Ollama's own desktop app hosts MCP servers was not determined.
- The MCP "client matrix" for extension support and LM Studio's tool-approval UX (allow once/always) were not captured.
- rmcp's MSRV and whether it supports the new `subscriptions/listen` stream were not stated on the pages read.

## Key Question 4 — Built-in internet tools: search providers, fetching, extraction, robots, caching, Markdown conversion

### Takeaway
A local engine has three viable search back-ends: self-hosted SearXNG (free, JSON must be enabled, engines rate-limit), metered APIs with monthly free credit (Brave $5/1k with $5/month free; Exa $4/1k instant search + $1/1k page contents with $10/month free), and Ollama's hosted `web_search`/`web_fetch` (free account, max 10 results, recommends ≥32k context). For fetching and compaction the reference designs are gpt-oss's `simple_browser` (numbered lines, 80-column wrap, 1,024-token view windows, `【id†title】` links and `【cursor†Lx-Ly】` citations) and safewebfetch (SSRF + hidden-text + injection stripping). Permissively licensed Rust building blocks exist for every step: `dom_smoothie` (Readability port, MIT, Markdown output), `htmd` (HTML→Markdown, Apache-2.0), `texting_robots` (robots.txt, MIT/Apache), `chromiumoxide` (CDP, MIT/Apache); trafilatura is Apache-2.0 only from v1.8.0 and is Python.

### Cited Findings
- Ollama web search (launched 2025-09-24): `POST https://ollama.com/api/web_search` with `query` and `max_results` (default 5, max 10) → `results[{title,url,content}]`; `POST https://ollama.com/api/web_fetch` with `url` → `{title, content, links[]}`; auth via `OLLAMA_API_KEY`; "Web search is included with a free Ollama account" with "much higher rate limits available by upgrading your Ollama subscription" (no numeric limits published); "increase the context length of the model to ~32000 tokens"; the reference agent loop truncates each tool result to `2000 * 4` characters; Python SDK `ollama>=0.6.0`; recommended `qwen3` and `gpt-oss` — [Ollama web search blog](https://ollama.com/blog/web-search), [Ollama web search docs](https://docs.ollama.com/capabilities/web-search)

- Harmony browser instructs ≤10-word direct quotes; Brave's terms restrict storage of results — see above (both affect caching design)

### Inferences
- A provider abstraction with three adapters (SearXNG JSON, Brave/Exa/Tavily REST, Ollama hosted) covers the free-local, paid-API and zero-config cases; each adapter should surface `title/url/snippet(/content)` and a provenance tag so the agent loop and the security layer can treat results as untrusted data.
- The gpt-oss browser's line-numbered, windowed page model is the proven way to fit web pages into 8k–32k-token local contexts and gives small models stable citation anchors; an engine can reproduce it with `dom_smoothie` → `htmd` → 80-column wrap → numbered lines, with a 1k-token default window and `find`.
- Caching should be per-URL within a session (as gpt-oss does) and should respect Brave's storage-rights clause and robots.txt (via `texting_robots`); long-term caching of third-party page text is a licensing risk the engine should make opt-in.
- Headless-browser fetching (chromiumoxide) is a heavyweight optional path; for SPAs it is the only way to get content, but it also enlarges the SSRF/injection surface (JS execution), so it should run with the same egress policy as plain fetch.

### Gaps
- DuckDuckGo has no official search API; the `ddgs`/`duckduckgo-search` scraping library's status and terms were not verified [unverified].
- SearXNG's license (believed AGPL-3.0, which matters only if the engine bundled/modified it rather than calling an instance) was not confirmed from a primary source [unverified].
- Tavily pricing/free credits and the Open WebUI providers/loaders lists (Playwright, Firecrawl, Jina, external loader) were not retrievable (404 / not on page).
- LM Studio's and Jan's built-in web search status beyond MCP servers was not documented on the pages fetched.
- No measured numbers for Readability/trafilatura extraction accuracy on 2025–2026 web pages were found beyond trafilatura's self-cited benchmarks.

## Key Question 5 — Agent loop design and the OpenAI-compatible API surface

### Takeaway
OpenAI's own direction is clear: the Responses API (typed items `message | reasoning | function_call | function_call_output`, flattened tool definitions, `tool_choice` incl. `allowed_tools`, strict mode by default, hosted tools) is "recommended for all new projects", Chat Completions "remains supported" but newer OpenAI models restrict tool calling on it, and an industry "Open Responses" spec (backed by vLLM, Ollama, LM Studio, HF, NVIDIA, AWS, …) standardises the shape for other providers. Local servers already expose `/v1/responses` (llama.cpp by converting to chat completions; vLLM natively with cancel). The engine should implement both, keep reasoning items in history during a tool loop (Harmony, Qwen3.5, Gemma 4 and Nemotron templates all encode rules for this), expose thinking-budget controls (llama.cpp `--reasoning-budget`, vLLM `thinking_token_budget`), and truncate tool results aggressively (Ollama's reference uses 8,000 characters; gpt-oss uses 1,024-token windows).

### Cited Findings
- OpenAI function calling (current): Responses tool = `{type:"function", name, description, parameters, strict}`; tools may be grouped as `type: "namespace"` and functions may set `defer_loading`; output items `function_call {call_id, name, arguments}`; results as `function_call_output {call_id, output}` where output may include image/file objects; "Reasoning items from the model's output must be passed back with the tool outputs"; `tool_choice`: `auto` (default) | `required` | `none` | `{type:"function", name}` | `allowed_tools {mode, tools}` ("helps preserve prompt caching"); `parallel_tool_calls: false` limits to ≤1 call; built-in tools cannot be in a parallel batch; `strict: true` requires `additionalProperties: false` and all properties `required` (optional → `null` type); Responses tries strict and falls back, "Chat Completions requests remain non-strict by default"; streaming events `response.output_item.added` → `response.function_call_arguments.delta` → `response.function_call_arguments.done` → `response.output_item.done`, accumulated by `output_index`; custom tools with `format: {type:"grammar", syntax:"lark"|"regex"}`; `tool_search` needs gpt-5.4+; "GPT-6 Astra and GPT-6.1 Sol require the Responses API for tool calling" — [OpenAI function calling](https://developers.openai.com/api/docs/guides/function-calling)
- Migration guide: Responses uses typed items vs `messages`; preserves reasoning across turns (or replays encrypted reasoning with `store: false`); hosted tools (web search, file search, code interpreter, computer use, remote MCP, image generation); `previous_response_id` / Conversations API; `response_format` → `text.format`; function definitions flattened (no nested `function` key); top-level `instructions` not carried by `previous_response_id`; stated benefits: "3% SWE-bench improvement" and "40% to 80% better cache utilization" [vendor-claimed]; "Chat Completions remains supported … Responses is recommended for all new projects"; "Starting with GPT-5.4, Chat Completions does not support tool calling with `reasoning_effort` values other than `none`"; Assistants API sunset 2026-08-26 — [Migrate to Responses](https://developers.openai.com/api/docs/guides/migrate-to-responses)
- OpenAI built-in tools list: function calling, web search, remote MCP servers, Skills (hosted shell), Shell (hosted or local runtime), computer use, image generation, file search, tool search (gpt-5.4+), Programmatic Tool Calling (model-written JavaScript orchestrating tools), apply_patch harness — [OpenAI tools guide](https://developers.openai.com/api/docs/guides/tools)
- Open Responses: "open-source specification and ecosystem" for multi-provider interoperable LLM interfaces "based on the OpenAI Responses API", with a reference OpenAPI spec, acceptance tests and a technical charter; community logos NVIDIA, Vercel, OpenRouter, Hugging Face, LM Studio, Databricks, Red Hat, AWS, Ollama, OpenAI, vLLM, Llama Stack (shown as backers, not confirmed implementations); launch date/licence not stated on the page — [openresponses.org](https://www.openresponses.org/)
- llama.cpp server: `POST /v1/responses` "works by converting Responses request into Chat Completions request"; `/v1/embeddings` requires pooling ≠ none, Euclidean-normalised, supports multimodal `content` parts with `--mmproj` (non-standard extension); `/v1/rerank` (`--rerank`, e.g. bge-reranker-v2-m3); built-in agent tools `--tools read_file,file_glob_search,grep_search,exec_shell_command,write_file,edit_file,get_info` ("do not enable in untrusted environments"), `--tools-runtime docker:|podman:|docker-container:|ssh:`, `-ag/--agent` enables CORS proxy + all tools — [llama.cpp server README](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)
- vLLM endpoints (developer preview, 2026-10-08): `/v1/completions`, `/v1/chat/completions` (+`/batch`), `/v1/responses`, `/v1/responses/{id}`, `/v1/responses/{id}/cancel`, `/v1/embeddings`, `/v2/embed`, `/pooling`, `/classify`, `/score`, `/v1/score`, `/rerank`, `/v1/rerank`, `/v2/rerank`, `/tokenize`, `/detokenize`, `/tokenizer_info`, `/v1/audio/transcriptions|translations`, `/v1/realtime`, Anthropic-style `/v1/messages` (+`count_tokens`) — [vLLM online serving](https://docs.vllm.ai/en/latest/serving/online_serving/)
- Reasoning in the loop: Harmony — pass prior `analysis` content back "when continuing after a tool call. Otherwise, drop it once the turn ends in `final`", and "Replace the trailing `<|return|>` with `<|end|>` when saving a reply to history" — [Harmony guide](https://developers.openai.com/cookbook/articles/openai-harmony); Qwen3.5 template re-emits `<think>` only after the last user query; GLM-4.7 `clear_thinking`; Nemotron `truncate_history_thinking`; Gemma 4 `preserve_thinking` for messages with tool calls (templates cited in Q1); vLLM: `include_reasoning=false` omits reasoning from the API but "Reasoning is still generated"; thinking budget via `thinking_token_budget`; llama.cpp `--reasoning-budget N`, `--reasoning-budget-message`, `--reasoning-preserve`, `reasoning_control` endpoint — [vLLM reasoning](https://docs.vllm.ai/en/latest/features/reasoning_outputs.html), [llama.cpp server README](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)
- Parallel calls: Llama 3.1 JSON format single-call only; Llama 4 and Mistral support lists/multiple; vLLM notes small Llama models unreliable and no parallel on Llama 3; vLLM `mimo`/`step3p5` parsers support `parallel_tool_calls=False`; SGLang shows parallel only for pythonic; OpenAI: built-in tools excluded from parallel batches (sources in Q1/above)
- Tool-result truncation: Ollama reference loop truncates each result to `2000 * 4` characters "to fit limited context windows" and recommends ~32k context — [Ollama web search docs](https://docs.ollama.com/capabilities/web-search); gpt-oss browser windows of 1,024 `o200k_base` tokens with explicit scrolling — [simple_browser_tool.py](https://github.com/openai/gpt-oss/blob/main/gpt_oss/tools/simple_browser/simple_browser_tool.py)
- MCP error semantics for the loop: tool-execution errors (`isError: true`) SHOULD be fed back to the model for self-correction; protocol errors MAY be — [MCP Tools spec](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)
- Ollama's example loop: `while` model returns `tool_calls`: execute, append `role: "tool"` messages, call `chat()` again with `think=True`; break when no tool calls — [Ollama web search blog](https://ollama.com/blog/web-search)

### Inferences
- The engine's canonical internal transcript should be the Responses item model (message/reasoning/function_call/function_call_output with ids), with Chat Completions as a lossy projection; this matches llama.cpp's "convert Responses → chat completions" shortcut but keeps reasoning items first-class so templates that require re-feeding thinking (Harmony, Gemma 4 with tool calls) work.
- The loop should be: render (template, with per-family thinking-history policy) → generate with lazy grammar → incrementally parse → validate args against JSON Schema (repair/retry once on failure) → policy check (Q7) → execute tools (MCP/built-in, with timeouts, concurrency for independent calls) → truncate/window results → append → repeat until no calls or a step/token budget is hit. Budget controls (max steps, max tool tokens, reasoning budget) should be API parameters because small models loop.
- Hosted tool types (`web_search`, `file_search`, `mcp`) can be mapped onto the engine's built-in search/fetch/retrieval and MCP layers and reported as Responses items (`web_search_call` + `url_citation` annotations) so clients written for OpenAI work unchanged; Open Responses' acceptance tests would be the conformance target.

### Gaps
- The exact `web_search_call`/`url_citation` item schemas, `search_context_size`, and `allowed_domains` filters were not captured from OpenAI's tools page; only the tool list was.
- Open Responses' launch date, governance members, and licence are not on its landing page.
- vLLM's Responses API feature list (background mode, built-in tools for gpt-oss) was not documented on the endpoints page.
- No primary source was found for recommended default step/token budgets in local agent loops beyond Ollama's 8,000-character truncation and 32k-context advice.

## Key Question 6 — Retrieval: local embeddings, rerankers, embeddable vector stores, chunking

### Takeaway
Two embedding families dominate the small-footprint space in Oct 2026: Qwen3-Embedding 0.6B/4B/8B (Apache-2.0, 32k context, matching rerankers) and the brand-new EmbeddingGemma 2 (Apache-2.0, 270M text-only path, 768-d with Matryoshka down to 128, 8k context, GGUF/MLX/Ollama builds). Rerankers are the latency hot spot (cross-encoder cost scales with candidates). For a Rust binary, `fastembed-rs` (ONNX, Apache-2.0) covers embeddings + rerankers, and `lancedb` (Apache-2.0, vector + full-text + SQL), `usearch` (Apache-2.0 HNSW, f16/i8/b1), `sqlite-vec` (MIT/Apache, pre-v1) and `arroy` (MIT, LMDB) are all embeddable; `text-splitter` (MIT) provides Markdown-aware chunking.

### Cited Findings

- arroy: Annoy-like ANN in Rust on LMDB (multi-process shared, memory-mapped); MIT; Euclidean/Manhattan/cosine/dot; incremental updates, filtered queries, multiple indexes, rayon builds, on-disk builds; "generally slower than alternatives" per its own README — [meilisearch/arroy](https://github.com/meilisearch/arroy)
- text-splitter: Rust (Python bindings `semantic-text-splitter`); MIT; sizes by characters, HF `tokenizers` or `tiktoken-rs`; `TextSplitter` (char/grapheme/word/sentence/newline boundaries), `MarkdownSplitter` (CommonMark elements), `CodeSplitter` (tree-sitter); chunk capacity ranges; overlap not mentioned — [benbrandt/text-splitter](https://github.com/benbrandt/text-splitter)
- Chunking/retrieval practice (background, 2024-09-19): chunks of a few hundred tokens (800 in the cost example) + 50–100 tokens of chunk context; hybrid embeddings + BM25 and reranking top-150 → top-20 cut retrieval failure from 5.7% to 1.9% [vendor-measured]; skip RAG below ~200k tokens of knowledge — [Anthropic contextual retrieval](https://www.anthropic.com/news/contextual-retrieval)
- MCP spec note: `structuredContent` "is unrelated to LLM 'structured outputs'" — relevant when storing tool outputs for retrieval — [MCP Tools spec](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)

### Inferences
- For a desktop engine the pragmatic default is a 270M–600M embedder (EmbeddingGemma 2 text-only or Qwen3-Embedding-0.6B) run through the engine's own GGUF path or `fastembed-rs`, with a reranker only on GPU-capable machines or for ≤20 candidates on CPU; Matryoshka truncation to 256 d keeps on-disk indexes small for web-page caches.
- `sqlite-vec` is the lowest-friction store for a single-binary app that already uses SQLite (one file, metadata filters, brute-force is fine for tens of thousands of web chunks); `lancedb` is the step up if hybrid full-text + vector search over larger corpora is wanted; `usearch` is the best pure-ANN crate.
- Web-page chunking should be Markdown-aware (`MarkdownSplitter`) over the Readability→Markdown output, ~300–800 tokens per chunk, with URL/title/heading-path prepended as "contextual" metadata, mirroring both the gpt-oss line-window approach and Anthropic's contextual-retrieval result.

- EmbeddingGemma 2's full MTEB/MMTEB text scores are only in the model card (not fetched).

## Key Question 7 — Security for a local model that can browse and call tools

### Takeaway
The consensus 2025–2026 position is that prompt injection via fetched content is unsolved, so the engine must be designed so an injected instruction *cannot* complete an attack: avoid the "lethal trifecta" (private data + untrusted content + external communication) / Meta's "Rule of Two" in any single session without human approval; adopt the design patterns formalised by Beurer-Kellner et al. (Plan-Then-Execute, Dual LLM, Map-Reduce, Code-Then-Execute, Context-Minimization) and CaMeL (capability tracking; 77% vs 84% utility on AgentDojo); apply OWASP LLM01 controls (constrain behaviour, validate output formats, least privilege, human approval for high-risk actions, "segregate and identify external content"); enforce SSRF/egress rules below the model (block private/metadata ranges, revalidate redirects, pin DNS, egress proxy, OS sandbox such as Seatbelt/bubblewrap with a domain-allowlisting proxy); treat MCP tool descriptions/annotations as untrusted and show arguments before execution; and log tool usage with content capture opt-in only (OpenTelemetry GenAI conventions mark message content Opt-In with PII warnings).

### Cited Findings
- OWASP Top 10 for LLM Applications 2025: LLM01 Prompt Injection, LLM02 Sensitive Information Disclosure, LLM03 Supply Chain, LLM04 Data and Model Poisoning, LLM05 Improper Output Handling, LLM06 Excessive Agency, LLM07 System Prompt Leakage, LLM08 Vector and Embedding Weaknesses, LLM09 Misinformation, LLM10 Unbounded Consumption — [OWASP LLM Top 10](https://genai.owasp.org/llm-top-10/). LLM01 mitigations (headings verbatim): "Constrain model behavior", "Define and validate expected output formats", "Implement input and output filtering", "Enforce privilege control and least privilege access", "Require human approval for high-risk actions", "Segregate and identify external content", "Conduct adversarial testing and attack simulations"; types: direct, indirect (websites/files), multimodal; scenarios include payload splitting and multilingual/obfuscated attacks — [OWASP LLM01:2025](https://genai.owasp.org/llmrisk/llm01-prompt-injection/)
- OWASP Top 10 for Agentic Applications 2026 published 2025-12-09 (entries not extractable from the landing page) — [OWASP agentic top 10](https://genai.owasp.org/resource/owasp-top-10-for-agentic-applications-for-2026/)
- CaMeL (Google DeepMind et al., arXiv 2503.18813, v2 2025-06-24, CC BY 4.0): a protective system layer that "explicitly extracts control and data flows from the trusted user query" so untrusted data "can never impact the program flow", with capabilities to stop private-data exfiltration enforced at tool calls; on AgentDojo "solves 77% of tasks with provable security, compared with 84% for an undefended system" [measured] — [arXiv 2503.18813](https://arxiv.org/abs/2503.18813)
- Design patterns paper (arXiv 2506.08837, v3 2025-06-27; authors from Invariant Labs, IBM, EPFL, ETH Zurich, Swisscom, Google, Microsoft, Kyutai/Lakera…): core principle — once an agent has ingested untrusted input "it is impossible for that input to trigger any consequential actions"; patterns: Action-Selector (LLM picks from predefined actions, results never fed back), Plan-Then-Execute (fix the tool plan before reading untrusted data), LLM Map-Reduce (isolated instances per untrusted item, constrained reduce), Dual LLM (privileged planner never sees untrusted data; quarantined LLM has no tools), Code-Then-Execute (LLM writes a program that calls tools and spawns unprivileged LLMs), Context-Minimization (drop the user prompt from context once it has informed the action) — [arXiv 2506.08837 (HTML)](https://arxiv.org/html/2506.08837v3)
- Lethal trifecta (Willison, 2025-06-16): private data access + exposure to untrusted content + external communication; "LLMs follow instructions wherever they appear in their input"; MCP "encourages users to mix tools from different sources"; GitHub MCP exploit combined public issues (attacker-controlled), private repos and PR creation; for users "the only reliable way to stay safe is to avoid combining all three"; guardrail products with ~95% detection are "a failing grade in web application security" — [simonwillison.net](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)
- Meta "Agents Rule of Two" (2025-10-31): an agent should satisfy no more than two of [A] process untrustworthy inputs, [B] access sensitive systems/private data, [C] change state or communicate externally "within a single session"; if all three are required it "should not run autonomously" — needs human approval or a fresh session/context — [Meta AI blog](https://ai.meta.com/blog/practical-ai-agent-security/)
- MCP security best practices: SSRF mitigations (HTTPS, block private/loopback/link-local/metadata ranges, don't hand-roll IP validation, validate redirect targets, egress proxy e.g. Smokescreen, DNS pinning/TOCTOU), local-server consent (show exact command untruncated, sandbox with minimal privileges, explicit grants for directories/network), token-passthrough forbidden, state-handle binding, OAuth URL scheme allowlist and no shell-based URL opening — [MCP security best practices](https://modelcontextprotocol.io/specification/2026-07-28/basic/security_best_practices); tools: annotations untrusted, show inputs before calling, validate results before passing to the LLM, timeouts, audit logging — [MCP Tools spec](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)
- Anthropic Claude Code sandboxing (2025-10-20): filesystem isolation (read/write only the working directory) via Linux bubblewrap and macOS Seatbelt applied to all subprocesses; network isolation by routing all traffic through a Unix domain socket to a proxy outside the sandbox that enforces a domain allowlist and "prompts the user to confirm newly requested domains"; both layers needed ("Without network isolation, a compromised agent could exfiltrate sensitive files such as SSH keys. Without filesystem isolation, it could escape the sandbox"); "sandboxing safely reduces permission prompts by 84%" [vendor-measured]; runtime open-sourced as a research preview and "can sandbox arbitrary processes, agents, and MCP servers" — [Anthropic engineering blog](https://www.anthropic.com/engineering/claude-code-sandboxing)
- safewebfetch controls (SSRF, content-type/size limits, hidden-text and injection stripping, random-suffix wrapper tags, recommendation to disable the agent's native fetch) — see Q4 — [Hwanhui02/safewebfetch](https://github.com/Hwanhui02/safewebfetch)

### Inferences
- Concrete engine policy that follows from the sources: (1) classify every tool as read-only/open-world/destructive from engine-owned metadata (not server-supplied annotations); (2) default profile for a browsing session = web search + fetch + read-only retrieval only; any state-changing or exfiltration-capable tool (shell, file write, email/HTTP POST, MCP tools marked destructive) requires per-call human approval once untrusted web content has entered the context (Rule of Two / design-pattern principle); (3) provenance-tag every tool result (`source=web, url=…, trust=untrusted`) in the transcript and wrap it in delimiters with a random nonce (safewebfetch) so the model can be told, and the policy layer can know, which spans are data; (4) run the fetcher with an engine-level SSRF guard (allow http/https only, resolve-then-connect to a validated public IP, revalidate redirects, size/time caps, strip hidden text) *and* an OS-level sandbox/egress proxy with a domain allowlist so an injected instruction cannot talk its way past; (5) keep API keys in the OS keychain/env and never in prompts or logs; (6) emit OTel-style tool spans (names, ids, durations, token counts, URLs/hosts) with prompt/result bodies off by default.
- Pattern-matching filters (safewebfetch's ~60 rules) are a cheap first pass but every source treats them as speed bumps; the architectural controls above are what provide the guarantee.
- Because LLMario binds to loopback, DNS-rebinding and CSRF-style access from a browser tab to the local API is a real vector (the MCP spec lists "DNS rebinding" against local servers); the OpenAI-compatible server should require a token even on loopback and validate `Origin`/`Host` like the MCP Streamable HTTP transport (403 on invalid Origin).
