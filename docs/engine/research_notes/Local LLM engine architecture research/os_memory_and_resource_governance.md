## Key question 1 — Weight residency: mmap + page cache vs read() into process memory vs wired/pinned memory; madvise/mlock/MAP_POPULATE/prefault; how each OS accounts for file-backed vs anonymous memory; what llama.cpp, MLX, Ollama and LM Studio actually do

### Takeaway
Every mainstream local engine still defaults to a read-only `MAP_SHARED` mmap of the weight file (llama.cpp, and Ollama via llama.cpp), because file-backed clean pages cost nothing in overcommit accounting, are shared across processes, and can be dropped by the OS instead of swapped; the price is that under pressure the OS silently drops them and the next token re-reads from SSD (page-fault storms, "swap death spiral" reports). The alternatives each trade one failure mode for another: `read()`/direct I/O into anonymous memory makes residency predictable but turns the weights into swappable/compressible anonymous memory (macOS compresses it, Linux swaps it, Windows pages it); `mlock`/`VirtualLock`/Metal residency sets make them truly resident but push the pressure onto every other process and are rate-limited by OS lock limits. Activity Monitor, Task Manager and RSS all mix file-backed, shared and anonymous pages differently, so an engine must do its own accounting (bytes it mapped, bytes it wired, bytes it allocated privately) rather than trusting the OS process counter.

### Cited Findings

**What llama.cpp does today (source on `master`, read 2026-10-08)**
- `llama_mmap` maps the file read-only and shared: `mmap(NULL, size, PROT_READ, MAP_SHARED, fd, 0)`; `MAP_POPULATE` is added only on Linux and only when prefetch is requested and there are no "lazy" ranges (comment: "MAP_POPULATE would fault in the lazy ranges too"); it calls `posix_fadvise(fd, 0, 0, POSIX_FADV_SEQUENTIAL)` (warning only on failure); applies `POSIX_MADV_WILLNEED` to the prefetch range and `POSIX_MADV_RANDOM` to lazy ranges and (when NUMA) to the whole mapping; `unmap_fragment` `munmap`s page-aligned sub-ranges so weights not needed on the host (e.g. layers copied to a discrete GPU) are released from the address space. — [llama-mmap.cpp](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/src/llama-mmap.cpp)
- Windows path: `CreateFileMappingA(... PAGE_READONLY ...)` + `MapViewOfFile(FILE_MAP_READ)`; `PrefetchVirtualMemory` (looked up at runtime, needs `_WIN32_WINNT >= 0x602`) is called once for the non-lazy prefetch range; `unmap_fragment` is a no-op on Windows. — [llama-mmap.cpp](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/src/llama-mmap.cpp)
- `llama_mlock` locks in page-granular increments (`grow_to` locks only the increment, stops after the first failure); on POSIX failure with `ENOMEM` it prints the `RLIMIT_MEMLOCK` hint; on Apple the hint names `vm.user_wire_limit`, `vm.global_user_wire_limit`, `vm.global_no_user_wire_amount` and `ulimit -l`; on Windows it tries `VirtualLock`, and on failure raises the working set by `len + 1 MiB` via `SetProcessWorkingSetSize` and retries once. — [llama-mmap.cpp](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/src/llama-mmap.cpp)
- Direct I/O (Linux only in this file): opens `O_RDONLY | O_DIRECT`, alignment from `st_blksize`, stages through a `posix_memalign` buffer capped at `LLAMA_DIRECT_IO_BUFFER_SIZE`, falls back to buffered `fopen` if the open fails and to `fread` on `EFAULT`/`EINVAL`; on Windows `has_direct_io()` returns true but reads are plain `ReadFile` in 64 MiB chunks with no `FILE_FLAG_NO_BUFFERING` in this file; macOS has no `F_NOCACHE`/`F_RDADVISE` here and uses the generic buffered path. — [llama-mmap.cpp](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/src/llama-mmap.cpp)
- The user-facing switch is now `-lm, --load-mode` with values `none | mmap | mlock | mmap+mlock | dio`, default `auto` ("mmap is used unless a device doesn't support it"); `--mlock`/`--no-mmap`/`--direct-io` are not separate flags in the server README any more. — [llama.cpp server README](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/tools/server/README.md)
- Origin of `--mlock` **(background, PR #453, March 2023 per search summary; commit page shows no date)**: the author reported that "macOS is quite eager to compress llama.cpp's memory" and decompression "froze the program for a few seconds, even with a model using about 25 GB of 32 GB of RAM"; the commit warns that locking "forces the system to swap or compress other processes' memory instead" and "should not be enabled by default". **user-reported** — [commit 563cdc3](https://github.com/ggml-org/llama.cpp/commit/563cdc391dde140f1084d1012234e8e6f57f881f)
- Direct-I/O PR #18012 (merged 2025-12-18, Linux `O_DIRECT`; maintainer refused to make `use_mmap=false` the macOS default because a macOS load went from ~4.6 s on master to ~18.0 s with the PR). **measured (PR author / testers)**: DGX Spark, GPT-OSS-120B-MXFP4: mmap ~110 s first load, ~67 s later loads, direct I/O ~10.5 s consistently; Strix Halo (Ryzen AI Max+ 395, 2× WD SN850X RAID-0, btrfs, Vulkan): mmap ~6 GB/s, master ~3 GB/s, PR ~2 GB/s, with some OOM runs; M4 Pro, GPT-OSS-20B cold load: `--no-mmap` 4.168 s vs `--mmap` 6.3 s; warm: `--mmap` 2.1 s vs `--no-mmap` ~4.1 s. PR #19109 "disable Direct IO by default" merged 2026-01-27. — [PR #18012](https://github.com/ggml-org/llama.cpp/pull/18012)
- Discrepancy to flag: the PR text says Windows "already had async uncached I/O from an earlier PR" (search summary of PR #7896 claimed >3× load-time gain on a Gen5 NVMe for non-mapped CUDA loading, **user-reported**), but the current `llama-mmap.cpp` shows plain `ReadFile`; the async path, if still present, lives elsewhere. **unverified** — [PR #18012](https://github.com/ggml-org/llama.cpp/pull/18012); [llama-mmap.cpp](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/src/llama-mmap.cpp)

**What Ollama does**
- Scheduler (`server/sched.go`, `main` read 2026-10-08): on Linux with discrete GPUs it disables mmap when free system RAM is below *model size + already-mmapped size + headroom*, with headroom = max(8 GB, 10% of total RAM); loads are not otherwise refused on free system RAM; if the runner reports `ErrLoadRequiredFull` with no other models loaded the request fails as "too large for system memory". — [sched.go](https://raw.githubusercontent.com/ollama/ollama/main/server/sched.go)
- `envconfig/config.go` exposes no mmap/mlock env var; `OLLAMA_GPU_OVERHEAD` default 0 bytes; `OLLAMA_KEEP_ALIVE` default 5m; `OLLAMA_MAX_LOADED_MODELS` default 0 (code) = "3 × GPUs or 3 for CPU" (FAQ); `OLLAMA_NUM_PARALLEL` default 1; `OLLAMA_MAX_QUEUE` 512; `OLLAMA_CONTEXT_LENGTH` default 0 meaning "4k, 32k or 256k depending on VRAM"; `OLLAMA_LOAD_TIMEOUT` 5m. — [config.go](https://raw.githubusercontent.com/ollama/ollama/main/envconfig/config.go); [Ollama FAQ](https://docs.ollama.com/faq)
- New engine (post 2025-09-23) "measures the exact amount of memory required" before running instead of estimating; claims fewer OOM crashes and that `nvidia-smi` now matches `ollama ps`. **vendor-claimed with examples**: RTX 4090, gemma3:12b at 128k context: old 19.9 GiB VRAM / 48 of 49 layers / 52.02 tok/s → new 21.4 GiB / 49 of 49 / 85.54 tok/s; 2× RTX 4090, mistral-small3.2 32k: prompt eval 127.84 → 1380.24 tok/s, generation 43.15 → 55.61 tok/s. — [Ollama blog, 2025-09-23](https://ollama.com/blog/new-model-scheduling)

**What MLX / mlx-lm do**
- MLX's Metal allocator wraps host memory into Metal buffers with a no-copy `newBuffer(ptr, size, ...)` path (`make_buffer`), uses shared storage with hazard tracking untracked, rounds requests > `vm_page_size` to page multiples, keeps a small-buffer `MTLHeap`, and caches freed buffers (see Q5). — [allocator.cpp](https://raw.githubusercontent.com/ml-explore/mlx/main/mlx/backend/metal/allocator.cpp)
- `mlx-lm` "tries to speed up models that are large relative to system RAM by wiring the memory used by the model and cache" (macOS 15+), warns "[WARNING] Generating with a model that requires ..." when it cannot, and tells users to run `sudo sysctl iogpu.wired_limit_mb=N` with N above the model size and below total RAM. — [mlx-lm README](https://raw.githubusercontent.com/ml-explore/mlx-lm/main/README.md)
- **measured (single user, April 2026)**: M1 Max 64 GB, MLX, Qwen 3.6 35B-A3B Q8 (MoE): after ~8 h uptime, 60.74 GB "Memory Used", 19.69 GB Compressed, swap 1.57 GB and climbing, Python "Memory" column 44 GB; after `mx.set_wired_limit(45 GB)`, `mx.set_cache_limit(512 MB)`, `mx.set_memory_limit(48 GB)` and periodic `clear_cache()`: Compressed 1.7 GB (−91%), Python ~40 GB, ~30 GB free+reclaimable; no tokens/s reported; the author labels thresholds as guesses. — [dev.to, SleepyQuant](https://dev.to/sleepyquant/what-19-gb-of-memory-compression-taught-me-about-mlx-on-m1-max-3eha)

**OS mechanisms — Linux**
- `madvise(2)`: `MADV_WILLNEED` is a pure hint (read-ahead; `EIO` if paging in would exceed the RSS limit); `MADV_SEQUENTIAL` = aggressive read-ahead and free soon after; `MADV_RANDOM` = less read-ahead; `MADV_DONTNEED` on shared file mappings drops pages and later access reloads from the file (RSS drops immediately); `MADV_FREE` (4.5) private anonymous only; `MADV_HUGEPAGE` (2.6.38; file-backed since 5.4 but "for non-tmpfs file-backed memory, the file must not be open for writing and the mapping must be executable" — i.e. a read-only data mapping of a weight file is **not** eligible); `MADV_COLLAPSE` (6.1) synchronous best-effort collapse that ignores the sysfs setting; `MADV_POPULATE_READ` (5.14) prefaults page tables readable without touching memory and reports errors instead of `SIGBUS`; `MADV_COLD`/`MADV_PAGEOUT` (5.4) deactivate / reclaim now. — [madvise(2)](https://man7.org/linux/man-pages/man2/madvise.2.html)
- `mmap(2)`: `MAP_POPULATE` prefaults page tables and triggers read-ahead for file mappings, never fails the `mmap` if population fails (private mappings since 2.6.23); `MAP_LOCKED` (2.5.37) is weaker than `mlock(2)` — population failure is not reported, so major faults may still occur; `MAP_NORESERVE` skips swap reservation; `MAP_HUGETLB` needs `CAP_IPC_LOCK` or membership in `hugetlb_shm_group`, with `MAP_HUGE_2MB`/`MAP_HUGE_1GB` since 3.8. — [mmap(2)](https://man7.org/linux/man-pages/man2/mmap.2.html)
- `mlock(2)`: since 2.6.9 a `CAP_IPC_LOCK` process has no lock limit and `RLIMIT_MEMLOCK` applies only to unprivileged processes (soft-limit overrun → `ENOMEM`); `MLOCK_ONFAULT`/`MCL_ONFAULT` (4.4) lock pages as they fault in, which the man page recommends for large mappings where only part is touched; locks are not inherited across `fork()` and are dropped on `execve()`; `mlockall()` covers memory-mapped files. — [mlock(2)](https://man7.org/linux/man-pages/man2/mlock.2.html)
- Overcommit accounting: in all modes "shared or read-only [file] mappings cost nothing, because the file itself serves as the backing store", while private writable mappings are charged in full; default `vm.overcommit_memory=0` (heuristic), mode 2 = strict with `overcommit_ratio` default 50. — [overcommit-accounting](https://docs.kernel.org/mm/overcommit-accounting.html)
- `/proc/meminfo`: `MemAvailable` (since 3.14) is "an estimate of how much memory is available for starting new applications, without swapping"; `Cached` is the page cache; `Committed_AS` counts allocated-but-untouched memory; `CommitLimit` is enforced only in overcommit mode 2. — [proc_meminfo(5)](https://man7.org/linux/man-pages/man5/proc_meminfo.5.html)
- `PrefetchVirtualMemory` (Windows 8+): brings discontiguous ranges in "using large, concurrent I/O requests"; "the prefetched memory is not added to the target process' working set; it is cached in physical memory"; it is "a strong hint" that "can completely or partially fail under low-memory conditions" and "can also create memory pressure if called with large address ranges". — [PrefetchVirtualMemory](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-prefetchvirtualmemory)

**OS mechanisms — Windows locking and working sets**
- `VirtualLock`: all pages must be committed; "Each version of Windows has a limit on the maximum number of pages a process can lock. This limit is intentionally small"; the maximum "is equal to the number of pages in its minimum working set minus a small overhead", so callers must first raise the working set with `SetProcessWorkingSetSize`; locked pages "are guaranteed not to be written to the pagefile while they are locked"; no lock count. — [VirtualLock](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-virtuallock)
- Raymond Chen's counterpoint **(background)**: `VirtualLock` historically "locks the memory into your process's working set" and only protects pages "as long as there is a thread executing in your process"; older MSDN text said this more clearly before the wording changed, and he warns against assuming it keeps data out of the pagefile. — [Old New Thing](https://devblogs.microsoft.com/oldnewthing/?p=24573)
- `SetProcessWorkingSetSizeEx`: default minimum 50 pages (204,800 B at 4 KiB), default maximum 345 pages (1,413,120 B); `(SIZE_T)-1` for both empties the working set; `QUOTA_LIMITS_HARDWS_MIN_ENABLE`/`MAX_ENABLE` make the limits hard; raising sizes needs `SE_INC_WORKING_SET_NAME`; sizes are granted "first-come, first-served" and raising them "is taking away physical memory from the rest of the system ... can also lead to failures of operations that require physical memory". — [SetProcessWorkingSetSizeEx](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-setprocessworkingsetsizeex)
- Working set = pages resident in RAM; "nonpageable memory allocations such as AWE or large page allocations are not included in the working set"; hard faults read from the paging file or the mapped file; the memory manager trims working sets to create available memory; transition pages stay cached until repurposed. — [Working Set](https://learn.microsoft.com/en-us/windows/win32/memory/working-set)
- Large pages: require `SeLockMemoryPrivilege` ("Lock pages in memory", disabled for all users by default, granted via Group Policy), `MEM_LARGE_PAGES` with sizes a multiple of `GetLargePageMinimum()`; the memory "is always read/write and nonpageable", "part of the process private bytes but not part of the working set", "not subject to job limits", and "may be difficult to obtain after the system has been running for a long time" so apps "should ... allocate all large pages one time, at startup". — [Large-Page Support](https://learn.microsoft.com/en-us/windows/win32/memory/large-page-support)
- y-cruncher's field notes **(unverified, third party)**: large/locked pages need the privilege, an elevated process and enough contiguous physical memory; Windows "does not appear to be able to defragment the memory on the fly", so a reboot is the only remedy; support is "very flaky". — [y-cruncher guide](https://numberworld.org/y-cruncher/guides/pages.html)
- Process memory counters: `GetProcessMemoryInfo` reports working set, paged/nonpaged pool and pagefile usage; the working set "is the amount of memory physically mapped to the process context", which includes shared file-mapped pages. — [Process Memory Usage Information](https://learn.microsoft.com/en-us/windows/win32/psapi/process-memory-usage-information)

**OS mechanisms — macOS accounting (what Activity Monitor shows)**
- Apple's definitions: *Memory Pressure* "is determined by free memory, swap rate, wired memory, and file cached memory"; *Wired Memory* is "memory required by the system to operate ... can't be cached ... isn't available to other apps"; *Compressed*: "as the Mac nears its memory limit, inactive apps are compressed"; *Cached Files* "stay cached until overwritten"; *Swap Used* is startup-disk space used to move unused files to and from RAM; a per-process *VM Compressed* column exists. The page does not define the per-process "Memory" vs "Real Memory" columns. — [Activity Monitor User Guide](https://support.apple.com/guide/activity-monitor/view-memory-usage-actmntr1004/mac)
- `os_proc_available_memory()` is listed for iOS 13+, tvOS, watchOS, visionOS and Mac Catalyst 13.1 but **not macOS** ("macOS: -" in availability); it returns "current memory limit minus the memory footprint", is advisory, and Apple warns not to maximise usage against it. — [os_proc_available_memory](https://developer.apple.com/documentation/os/os_proc_available_memory.md)
- Metal host buffers: `ggml` page-aligns the host pointer, rounds the length up to whole pages and calls `newBufferWithBytesNoCopy:` with `MTLResourceStorageModeShared` and a nil deallocator; regions larger than `maxBufferLength` are split into overlapping views (overlap = max tensor size rounded to pages + 1 page) so every tensor fits in one view; "owned" shared buffers come from `vm_allocate` on macOS; `use_shared_buffers = hasUnifiedMemory`. — [ggml-metal-device.m](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/ggml/src/ggml-metal/ggml-metal-device.m)
- Apple's `makeBuffer(bytesNoCopy:...)` requires a page-aligned start address, whole-page length and a single VM region. — [Apple doc](https://developer.apple.com/documentation/metal/mtldevice/makebuffer(bytesnocopy:length:options:deallocator:).md)

### Inferences
- For a Rust engine the practical default is: read-only shared mmap of the weight file (zero overcommit charge on Linux, OS-managed sharing between the app and a CLI/daemon), plus explicit, bounded prefaulting of exactly the tensors the first forward pass needs (`MADV_WILLNEED`/`MADV_POPULATE_READ` on Linux, `PrefetchVirtualMemory` on Windows, touching pages in a background thread on macOS), rather than `MAP_POPULATE` of the whole file (which llama.cpp itself avoids when lazy ranges exist).
- The three failure reports (#19825 kernel-panic/thrash on 24 GB, #13361 swap cycles while loading 98 GiB on 128 GB, the 2023 compression stalls) share one cause: the engine let the OS decide residency instead of refusing or shrinking the load. Governance (Q6) must happen before the mapping is touched, and a model that does not fit must be streamed deliberately (Q7) or rejected.
- Locking is a scalpel, not a default: on Linux it needs `CAP_IPC_LOCK` or a raised `RLIMIT_MEMLOCK`; on Windows it needs working-set changes that other processes will contend for; on macOS it competes with the GPU wired limit (Q2). `MLOCK_ONFAULT` is the cheapest safe variant because it never prefaults pages the model never touches (e.g. unused vocab rows, MoE experts).
- Because Linux RSS and the Windows working set both count shared file-backed pages, and macOS reports mapped weights under "Cached Files" rather than "App Memory", an engine's own ledger (mapped bytes, resident-estimate via `mincore`/`QueryWorkingSetEx`, wired bytes, private anonymous bytes, GPU-private bytes) is the only figure that can be compared against a budget. Reporting that ledger in the API will also stop users from filing "it uses 44 GB" issues based on the Activity Monitor column.

### Gaps
- No controlled, same-machine measurement comparing resident/wired memory and tokens/s across `--load-mode mmap|mlock|none|dio` for llama.cpp was found; the only numbers are load-time comparisons from PR #18012.
- The Linux default `RLIMIT_MEMLOCK` value (recollection: raised from 64 KiB to 8 MiB in 5.16; distros vary) is **unverified** — the mlock(2) page does not state it.
- Apple does not document how Activity Monitor's per-process "Memory" column treats mmapped file pages vs anonymous Metal buffers; XNU's `task_vm_info.phys_footprint` field has no explanatory comment in `task_info.h`. Treat any statement that "Memory = phys_footprint = dirty + compressed + IOKit" as unverified.
- The Apple-silicon 16 KiB page size is a recollection, not sourced here; ggml's code queries the page size at runtime, which is the right approach.
- LM Studio's mmap/mlock defaults and its guardrail thresholds are undocumented (only the settings keys from issue #499 are known).

## Key question 2 — Apple Silicon specifics: unified memory, Metal shared buffers, wired limits (`iogpu.wired_limit_mb`, `recommendedMaxWorkingSetSize`), residency sets, compression/swap, memory-pressure notifications, termination, App Sandbox, QoS

### Takeaway
On Apple silicon the GPU can only wire a fraction of unified memory — `recommendedMaxWorkingSetSize`, by convention about 2/3 of RAM on small machines and 3/4 above 32 GB, raisable with `sudo sysctl iogpu.wired_limit_mb` (not persistent, root only) — and since macOS 15 both llama.cpp and MLX keep weights wired via `MTLResidencySet` because the OS otherwise unwires GPU memory after ~1 s of idle, costing 100–450 ms on the next token. Memory not wired is subject to compression and swap, and there is no `os_proc_available_memory` on macOS; the only pressure signal is the dispatch memory-pressure source (normal/warning/critical). Keep inference threads at utility QoS or lower when the user is not waiting, so the UI thread and P-cores stay responsive.

### Cited Findings

**Working-set limit and the wired sysctl**
- `MTLDevice.recommendedMaxWorkingSetSize` (macOS 10.12+): "An approximation of how much memory, in bytes, this GPU device can allocate without affecting its runtime performance ... keep the total memory footprint of its resources and heaps less than this threshold value." — [Apple doc](https://developer.apple.com/documentation/metal/mtldevice/recommendedmaxworkingsetsize.md)
- ggml reports this value as the device's "total" memory and `total − currentAllocatedSize` as "free", warns (debug builds) when `currentAllocatedSize` exceeds it, and logs it at init. — [ggml-metal-device.m](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/ggml/src/ggml-metal/ggml-metal-device.m)
- llama.cpp discussion #2182 (comments 2023–2025): default usable fraction "2/3 or 3/4" of unified memory (Jul 2023); a code snippet in a comment shows a default 33.333 % system reserve, dropping to 25 % when memory exceeds 32 GB (`gpu-sysmem-reserve-percent`); the command is `sudo sysctl iogpu.wired_limit_mb=<MB>`; the setting "is not sticky" and must be re-applied every boot (Nov 2023) or placed in `/etc/sysctl.conf` on Sonoma (Apr 2024); verification is the `recommendedMaxWorkingSetSize` line in `ggml_metal_init` output (Aug 2024); kdyke warns against 100 % because "things will start to go seriously wrong"; Azirine (May 2025) reports that going slightly above 96 GiB (¾ of 128 GB) made models load much slower with long swap/unswap cycles (issue #13361). **user-reported** — [discussion #2182](https://github.com/ggml-org/llama.cpp/discussions/2182)
- MLX: `set_wired_limit` default 0, "only useful on macOS 15.0 or higher", must stay strictly below total memory, raising above the system wired limit is an error, and `device_info()` exposes `max_recommended_working_set_size` and `memory_size`. — [mlx.core.set_wired_limit](https://ml-explore.github.io/mlx/build/html/python/_autosummary/mlx.core.set_wired_limit.html)
- MLX's allocator rejects wired limits above `max_recommended_working_set_size` and derives its memory limit from the same value: `block_limit = min(1.5 × recommendedMaxWorkingSetSize, 0.95 × memory_size)` and `gc_limit = min(0.95 × recommendedMaxWorkingSetSize, block_limit)`. — [allocator.cpp](https://raw.githubusercontent.com/ml-explore/mlx/main/mlx/backend/metal/allocator.cpp)
- MLX issue (mirror) notes `resource_limit` is read once at startup from `iogpu.rsrc_limit` with a hard-coded fallback of 499000 and has no setter. **unverified mirror** — [mlx issue #3849 mirror](https://upd.dev/ml-explore/mlx/issues/3849)

**Residency sets and the idle "wired collector"**
- `MTLResidencySet` (macOS 15+, iOS 18+): "A collection of resource allocations that can move in and out of resident memory"; Metal "makes the union of all residency sets' allocations resident"; `requestResidency()` asks Metal to prepare residency, `endResidency()` lets it reuse the memory; adding a heap-sourced resource makes the whole heap resident; methods are not thread-safe. — [MTLResidencySet](https://developer.apple.com/documentation/metal/mtlresidencyset.md)
- Idle throttling **measured** (llama.cpp PR #10119, Nov 2024–Jan 2025, M2 Ultra, Llama-3.1-8B-Instruct, single-token decode after `sleep(t)`): F16 26.34 ms at 0 ms idle → 29.53 ms at 1000 ms → 226.81 ms at 1200 ms → 472.38 ms at ~2200 ms; Q8_0 16.13 → 268.24 ms; Q4_0 11.04 → 215.77 ms. M4 Pro 20-core GPU 48 GB, macOS 15.1.1, Llama-2-7B F16: 56.37 ms → ~315–338 ms after 1.2–2 s idle. Cause (2025-01-24, citing Awni Hannun): the GPU wired-memory collector unwires memory after inactivity; `sudo sysctl iogpu.disable_wired_collector=1` fixed it; not seen on CUDA; overhead scales with model size. — [PR #10119](https://github.com/ggml-org/llama.cpp/pull/10119)
- Fix: PR #11427 "metal : use residency sets" merged 2025-01-26: one `MTLResidencySet` per Metal buffer, committed with `requestResidency`; env `GGML_METAL_NO_RESIDENCY` disables it ("the OS can reclaim GPU memory after about one second of inactivity", hurts performance); M2 Ultra 7B Q8_0 requests ~250 ms faster; pp512/tg128 throughput unchanged (ratios ≈1.00). — [PR #11427](https://github.com/ggml-org/llama.cpp/pull/11427)
- Current ggml behaviour: residency sets gated on `@available(macOS 15.0, iOS 18.0, tvOS 18.0, visionOS 2.0)`; a background thread re-calls `requestResidency` on every set about every 5 ms while a countdown is positive; each graph compute resets the countdown; default keep-alive "keep the memory wired for 3 minutes" (`GGML_METAL_RESIDENCY_KEEP_ALIVE_S` overrides); a 1-byte private fill is submitted at init as a workaround so residency memory is released when no GPU work occurs. PR #17766 (keep-alive heartbeat) merged 2025-12-04. — [ggml-metal-device.m](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/ggml/src/ggml-metal/ggml-metal-device.m); [PR #10119](https://github.com/ggml-org/llama.cpp/pull/10119)
- MLX's `ResidencySets` spreads allocations across several size-capped `MTL::ResidencySet`s (cap via `MLX_RESIDENCY_SET_MAX_PCT`, at most 32 sets) "so that when one set loses residency under memory pressure, only its allocations need to be made resident again"; allocations that do not fit within the wired limit get `kNoSet`; "nothing is wired unless asked for"; every set is attached to every command queue, and new sets are committed before every command-buffer commit because Metal locks residency at commit time. — [resident.h](https://raw.githubusercontent.com/ml-explore/mlx/main/mlx/backend/metal/resident.h)

**QoS / cores**
- Apple's QoS guide **(background, archived)**: user-interactive (instant), user-initiated ("a few seconds or less"), utility ("a few seconds to a few minutes", progress bar), background ("minutes or hours"); recommendation: "When user activity is not occurring, run the app at utility or lower at least 90% of the time"; set per thread with `pthread_attr_set_qos_class_np` / `pthread_set_qos_class_self_np`, per queue at creation; priority inversion is resolved only for `dispatch_sync`, `pthread_mutex_lock` and serial queues; check with `sudo powermetrics --show-process-qos --samplers tasks`. — [Prioritize Work at the Task Level](https://developer.apple.com/library/archive/documentation/Performance/Conceptual/power_efficiency_guidelines_osx/PrioritizeWorkAtTheTaskLevel.html)

- Low Power Mode is queryable on macOS 12+ via `ProcessInfo.isLowPowerModeEnabled` with `NSProcessInfoPowerStateDidChange` notifications; the system "reduces CPU and GPU performance" in that mode. — [isLowPowerModeEnabled](https://developer.apple.com/documentation/foundation/processinfo/islowpowermodeenabled.md)

### Inferences
- Treat `recommendedMaxWorkingSetSize` as the GPU budget ceiling and `0.95 ×` it (MLX's `gc_limit`) as the practical trigger for reclaiming caches; do not plan weights + KV + scratch above it without the user explicitly raising `iogpu.wired_limit_mb` — and a sandboxed/notarized app cannot raise it (root `sysctl`), so the UI should explain the command rather than attempt it.
- Residency sets are mandatory for a Metal backend on macOS 15+ to avoid the ~1 s-idle penalty; the engine should keep a keep-alive similar to ggml's (re-request residency while a request could arrive, release after an idle window) and must count wired bytes toward the same budget as the wired-limit sysctl.
- Memory the engine does not wire is subject to compression; an engine that sizes a model "to fit" but leaves KV/scratch unwired will see exactly the April-2026 MLX pattern (compression and swap growing over hours). Either wire everything the forward pass touches or keep the total under a budget that leaves the OS room to avoid compressing.
- Because there is no byte-count pressure API on macOS, admission must be computed from `recommendedMaxWorkingSetSize`, `host_statistics64`-style free/inactive counts (not sourced here) and the engine's own ledger, with the dispatch pressure source used only as an emergency back-pressure signal (drop caches, shrink batch, unload idle models at warning; stop admitting at critical).
- Run generation workers at utility QoS (or user-initiated only while a user-visible request is streaming), keep the thread count at the P-core count, and never pin to E-cores — the OS does the placement.

### Gaps
- `iogpu.wired_lwm_mb` (low-water mark) appeared in no fetched source; its semantics are unverified.
- Exact `recommendedMaxWorkingSetSize` values per Mac configuration (e.g. 16/24/32/48/64/128 GB) were not fetched; the 2/3–3/4 split is from a code snippet quoted in a discussion comment.
- macOS termination behaviour for memory-hungry user apps (whether `memorystatus`/jetsam kills a GUI app, the "Your system has run out of application memory" dialog) was not sourced; search budget ended before this could be checked.
- Apple's official explanation of the idle wired-memory collector (`iogpu.disable_wired_collector`) is only via a maintainer comment; no Apple document was found.
- Whether App Sandbox restricts `mlock`/`vm_wire` or `MTLResidencySet` was not found in any source; Apple's sandbox pages do not mention memory.

## Key question 3 — Windows specifics: working-set limits, large pages, VirtualLock, WDDM and the CUDA sysmem fallback, job objects, memory-resource notifications, process priority / EcoQoS

### Takeaway
Windows gives an engine four levers that macOS/Linux lack: a per-process OS-provided GPU budget (`IDXGIAdapter3::QueryVideoMemoryInfo`, with stutter if `CurrentUsage > Budget`), a system-wide low/high memory event (`CreateMemoryResourceNotification`), job objects that cap a child process's committed memory, and a documented EcoQoS opt-in/opt-out. The trap is WDDM: the GPU may use up to half of system RAM as "shared GPU memory", and since driver 536.40 (June 2023) NVIDIA's default "sysmem fallback" lets `cudaMalloc` silently succeed into system RAM, so VRAM-overcommit shows up as 5–10× slowdowns rather than OOM errors unless the engine measures `Budget`/`CurrentUsage` itself.

### Cited Findings
- Low/high memory notification: `CreateMemoryResourceNotification(LowMemoryResourceNotification | HighMemoryResourceNotification)` (Windows XP+) returns a handle usable with `QueryMemoryResourceNotification` or the wait functions; "This is a system-wide event, so all applications receive notification"; "there is a range of memory availability where neither ... object is signaled. In this case, applications should attempt to keep the memory use constant." — [CreateMemoryResourceNotification](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-creatememoryresourcenotification)
- Firefox's Windows watcher reacts to the low-memory callback and then polls on a timer until pressure clears; Raymond Chen (Dec 2025) notes an AI-generated answer invented a `WM_LOWMEMORY` message that does not exist. — [Firefox AvailableMemoryWatcherWin.cpp](https://searchfox.org/firefox-main/source/xpcom/base/AvailableMemoryWatcherWin.cpp); [Old New Thing 2025-12-29](https://devblogs.microsoft.com/oldnewthing/20251229-00?p=111927)
- Working set, `VirtualLock`, `SetProcessWorkingSetSizeEx` and large pages: see Q1 findings (defaults 50/345 pages; lock limit tied to minimum working set; large pages nonpageable, outside working set and job limits, allocate once at startup). — [VirtualLock](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-virtuallock); [SetProcessWorkingSetSizeEx](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-setprocessworkingsetsizeex); [Large-Page Support](https://learn.microsoft.com/en-us/windows/win32/memory/large-page-support)
- Job objects: `JOB_OBJECT_LIMIT_PROCESS_MEMORY` (0x100) makes a commit that would exceed `ProcessMemoryLimit` fail; `JOB_OBJECT_LIMIT_JOB_MEMORY` caps the whole job independently (e.g. 100 MB job / 10 MB per process); the system tracks `PeakProcessMemoryUsed`/`PeakJobMemoryUsed` continuously "to establish a memory limit"; limits are on committed virtual memory, not physical RAM; large-page allocations are exempt. — [JOBOBJECT_EXTENDED_LIMIT_INFORMATION](https://learn.microsoft.com/en-us/windows/desktop/api/winnt/ns-winnt-jobobject_extended_limit_information); [Large-Page Support](https://learn.microsoft.com/en-us/windows/win32/memory/large-page-support)
- WDDM shared memory **(background, 2017 DirectX blog)**: dedicated memory is VRAM managed by VidMm; shared GPU memory is "normal system memory that can be used by either the GPU or the CPU"; "the GPU is only allowed to use half of physical memory at any given instant" (8 GB on a 16 GB system); apps may allocate more than that because video memory is virtualized up to the system commit limit; VidMm "locks and releases DRAM pages dynamically" and releases unused surfaces' pages back to Mm over time; per-process Task Manager GPU columns double-count shared surfaces. — [GPUs in the Task Manager](https://devblogs.microsoft.com/directx/gpus-in-the-task-manager/)
- DXGI budget: `IDXGIAdapter3::QueryVideoMemoryInfo(NodeIndex, DXGI_MEMORY_SEGMENT_GROUP_LOCAL|NON_LOCAL)` returns `Budget` ("the OS-provided video memory budget ... If CurrentUsage is greater than Budget, the application may incur stuttering or performance penalties"), `CurrentUsage`, `AvailableForReservation` and `CurrentReservation` (a hint for the app's minimum working set); "Processes that cannot keep their usage within their assigned budgets will likely experience stuttering, as they are intermittently frozen and paged-out". — [QueryVideoMemoryInfo](https://learn.microsoft.com/en-us/windows/win32/api/dxgi1_4/nf-dxgi1_4-idxgiadapter3-queryvideomemoryinfo); [DXGI_QUERY_VIDEO_MEMORY_INFO](https://learn.microsoft.com/en-us/windows/win32/api/dxgi1_4/ns-dxgi1_4-dxgi_query_video_memory_info)
- Vulkan equivalent (cross-platform, incl. Windows/Linux): `VK_EXT_memory_budget` (revision 1, 2018-10-08, NVIDIA authors) exposes per-heap `heapBudget` ("estimate of how much total memory from each heap the current process can use before allocations may start failing or performance may degrade") and `heapUsage`; budgets change with other activity, so apps should re-query "once per frame or every few seconds" and free/move resources when over budget. — [VK_EXT_memory_budget](https://docs.vulkan.org/refpages/latest/refpages/source/VK_EXT_memory_budget.html)
- NVIDIA sysmem fallback: introduced in driver 536.40 so apps near the GPU memory limit "can use system memory (shared memory) instead" and keep running "but more slowly"; the "CUDA - Sysmem Fallback Policy" control-panel setting (`Prefer No Sysmem Fallback` vs `Driver Default`) arrived in 546.01; with fallback off an over-size allocation makes the app crash with CUDA OOM; changes require an app restart. (Article updated 2023-10-31, background.) — [NVIDIA support article 5490](https://nvidia.custhelp.com/app/answers/detail/a_id/5490)
- NVIDIA forum (developer thread, 2025): `cudaMalloc` under WDDM can report success while the allocation lands in shared (system) memory; a reply calls this intended WDDM behaviour and notes TCC mode bypasses it on supported cards; the poster asks for an explicit status code. **user-reported** — [NVIDIA forum 347791](https://forums.developer.nvidia.com/t/cudamalloc-with-sysmem-fallback/347791)
- A third-party guide claims spill-over "can make workloads 5–10× slower". **unverified** — [runaihome.com](https://runaihome.com/blog/shared-gpu-memory-slow-local-ai-sysmem-fallback-fix-2026/)
- Process power throttling / EcoQoS: `SetProcessInformation(ProcessPowerThrottling)` with `ControlMask = StateMask = PROCESS_POWER_THROTTLING_EXECUTION_SPEED` opts the process into EcoQoS ("reducing CPU frequency or using more power efficient cores ... should not be used for performance critical or foreground user experiences"; before Windows 11 it was labelled LowQoS); `ControlMask` set and `StateMask = 0` forces HighQoS (opt out of throttling); `ControlMask = 0` returns to system heuristics, which otherwise "infer a Quality of Service level" automatically; `PROCESS_POWER_THROTTLING_IGNORE_TIMER_RESOLUTION` and Windows 11's automatic timer-resolution coarsening for occluded/minimized windows are documented on the same page; `ProcessMemoryPriority` (`MEMORY_PRIORITY_LOW` etc.) sets the default page priority used when the memory manager trims working sets. Minimum Windows 8. — [SetProcessInformation](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-setprocessinformation); [PROCESS_POWER_THROTTLING_STATE](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/ns-processthreadsapi-process_power_throttling_state)
- EcoQoS launch post **(background, 2021-05-21, vendor-claimed)**: Insider build 21359; initial hardware 10th/11th-gen Intel mobile, Ryzen 5000 mobile, Qualcomm; "up to a 90% reduction in CPU power consumption" and "less than half the CPU energy" in initial assessments; intended for background services/updaters/indexers. — [Introducing EcoQoS](https://devblogs.microsoft.com/sustainable-software/introducing-ecoqos/)
- Power-state signals: `GUID_ACDC_POWER_SOURCE` (AC/DC/UPS), `GUID_BATTERY_PERCENTAGE_REMAINING`, `GUID_POWER_SAVING_STATUS` (battery saver on/off: "Save energy where possible"), `GUID_ENERGY_SAVER_STATUS` (prerelease; OFF / STANDARD / HIGH_SAVINGS), `GUID_POWERSCHEME_PERSONALITY` (High Performance / Power Saver / Balanced), `GUID_SESSION_USER_PRESENCE`, `GUID_IDLE_BACKGROUND_TASK`; apps register for each with power-setting notifications. — [Power Setting GUIDs](https://learn.microsoft.com/en-us/windows/win32/power/power-setting-guids)
- Ollama FAQ: Windows with Radeon GPUs defaults to one loaded model because of ROCm v5.7 VRAM-reporting limits. — [Ollama FAQ](https://docs.ollama.com/faq)

### Inferences
- On Windows the engine should budget GPU memory from `QueryVideoMemoryInfo().Budget` (or `VK_EXT_memory_budget` if using Vulkan/wgpu) and treat `CurrentUsage > Budget` as a hard stop, never from "free VRAM" reported by vendor tools; it should expose a setting that prefers OOM over fallback (and, for CUDA backends, document the control-panel policy), because sysmem fallback converts a refusable load into a silent 5–10× slowdown.
- A desktop app that spawns an inference child (as LLMario does today) can put the child in a job object with `JOB_OBJECT_LIMIT_PROCESS_MEMORY` set to the admission budget: the child then fails its own commit instead of swapping the machine, and `PeakProcessMemoryUsed` gives a free measurement of the model's real peak for the next admission decision. Note that large-page allocations escape the limit and that the limit is on commit, so file-backed mmap views are not counted.
- Avoid `VirtualLock` for multi-GB weights: it requires raising the process minimum working set, which is first-come-first-served physical memory taken from everything else. If locking is needed (e.g. latency-critical KV), lock only that region.
- Register `LowMemoryResourceNotification` and treat it like macOS "warning": drop prompt caches and idle models; also register `HighMemoryResourceNotification` to re-enable caches. Opt generation threads into EcoQoS only when the app is in the background or on battery saver; explicitly opt *out* (HighQoS) while a user-visible request is streaming, because Windows 11 may otherwise infer a low QoS for a minimized window.

### Gaps
- No Microsoft documentation of the exact thresholds behind Low/HighMemoryResourceNotification was found.
- The "shared GPU memory = half of RAM" statement is from a 2017 blog; whether Windows 11 changed the fraction was not verified.
- No measured data on Windows paging behaviour of mmapped GGUF weights under pressure (e.g. working-set trim rates) was found; all Windows figures here are API semantics.
- Thread-level `SetThreadInformation(ThreadPowerThrottling)` was referenced by the EcoQoS post but its page was not fetched.

## Key question 4 — Linux specifics: THP/hugetlbfs, cgroups v2 (`memory.high` throttling), PSI, io_uring for NVMe streaming, overcommit and the OOM killer, containers/Flatpak

### Takeaway
Linux is the only OS that offers an engine both a precise pressure signal (PSI `some`/`full` with pollable triggers, per-cgroup `memory.pressure`) and an enforceable soft limit (`memory.high`, which throttles instead of killing); an engine or its supervisor can run inference in a child cgroup with `memory.high` set to the admission budget and watch `memory.events high`/`memory.pressure`. THP helps only anonymous/shmem memory (page-cache-backed weight mappings are not eligible via `MADV_HUGEPAGE` unless executable), hugetlbfs requires pre-reserved, unswappable pages copied in by the engine, and direct I/O from NVMe measured 3–10× faster cold loads than mmap on fast SSDs but is not a win on macOS or page-cache-warm systems. Flatpak sandboxes impose no memory limits and only need `--device=dri` for GPU access.

### Cited Findings
- cgroup v2 memory controller: `memory.high` is "the main mechanism to control memory usage" — exceeding it throttles the cgroup's processes and puts them under heavy reclaim, never invokes the OOM killer; `memory.max` is the hard limit that triggers the in-cgroup OOM killer; `memory.min`/`memory.low` protect from reclaim; `memory.swap.high`/`.max` throttle/cap swap; `memory.oom.group` kills the whole group atomically; `memory.events` counts `high`, `max`, `oom`, `oom_kill`; `memory.reclaim` triggers proactive reclaim (with optional `swappiness=`); page cache **is** charged to the cgroup that instantiated it and stays charged until released (`POSIX_FADV_DONTNEED` can relinquish file pages); hugetlb counts only with `memory_hugetlb_accounting`. — [cgroup-v2](https://docs.kernel.org/admin-guide/cgroup-v2.html)
- Throttling implementation **(background, 2019 patch)**: allocator delays are applied only after reclaim fails to keep up, grow exponentially with the overshoot, and are capped at `2*HZ` (~2 s) per allocation; the thread shows a system OOM "within about two to three seconds" without the patch under a 100 MB `memory.high`. — [LKML patch (Chris Down)](https://lore.kernel.org/patchwork/patch/1068885/)
- PSI: `/proc/pressure/memory` lines `some` (≥1 task stalled) and `full` (all non-idle tasks stalled — "thrashing"), `avg10/avg60/avg300` percentages and `total` µs; triggers are registered by writing `<some|full> <stall µs> <window µs>` (window 500 ms–10 s, update interval 50 ms–1 s; unprivileged users need windows that are multiples of 2 s) and waited on with `poll()`/`POLLPRI`; one fd per trigger; notifications are rate-limited to one per window; per-cgroup `memory.pressure` works the same way with cgroup2 mounted. — [PSI docs](https://docs.kernel.org/accounting/psi.html)
- systemd-oomd defaults: `SwapUsedLimit=90%`, `DefaultMemoryPressureLimit=60%` (PSI full avg10 — "the fraction of time in a 10 second window in which all tasks in the control group were delayed"), `DefaultMemoryPressureDurationSec=30s`; kill order by reclaim activity (pgscan) or swap usage; only units with `ManagedOOMMemoryPressure=`/`ManagedOOMSwap=` are candidates. — [oomd.conf(5)](https://man7.org/linux/man-pages/man5/oomd.conf.5.html)
- OOM killer tuning: `oom_score_adj` ranges −1000..+1000 and is added to a 0–1000 badness score (≈ fraction of allowed memory used; root gets a 3 % discount); −1000 "is equivalent to disabling OOM-killing entirely for that task"; lowering it needs `CAP_SYS_RESOURCE`; children inherit it. — [proc_pid_oom_score_adj(5)](https://man7.org/linux/man-pages/man5/proc_pid_oom_score_adj.5.html)
- Overcommit modes and the zero cost of read-only file mappings: see Q1. — [overcommit-accounting](https://docs.kernel.org/mm/overcommit-accounting.html)
- THP admin guide: modes `always|madvise|never` per size (`hugepages-<size>kB/enabled`, PMD size inherits by default, other sizes `never`); `MADV_HUGEPAGE` is the way to use THP in `madvise` mode "without risking extra memory use elsewhere"; `MADV_COLLAPSE` ignores `enabled`; `defrag` default `madvise` (direct reclaim/compaction only for `MADV_HUGEPAGE` regions); THP "currently works for anonymous memory and tmpfs/shmem"; khugepaged can collapse file/shmem pages; `shrink_underused` splits zero-heavy THPs under pressure; embedded systems are advised to use madvise-only because touching one byte can allocate a 2 MiB page. — [transhuge](https://docs.kernel.org/admin-guide/mm/transhuge.html)
- Read-only file THP history **(background, 2019 `READ_ONLY_THP_FOR_FS`)**: initially only executable mappings (`VM_DENYWRITE`) qualified, and the man page still says non-tmpfs file-backed THP needs a non-writable file and an executable mapping. — [LKML v4 patch](https://lkml.iu.edu/1906.2/05168.html); [madvise(2)](https://man7.org/linux/man-pages/man2/madvise.2.html)
- hugetlbfs: pages come from a pre-reserved pool (`nr_hugepages`, best set at boot; `nr_overcommit_hugepages` for surplus), "cannot be swapped out under memory pressure", can be used via a hugetlbfs mount or `MAP_HUGETLB`; syscalls must use huge-page-aligned lengths; `read` works on hugetlb files but `write` does not. — [hugetlbpage](https://docs.kernel.org/admin-guide/mm/hugetlbpage.html)
- io_uring(7): shared SQ/CQ rings; `IOSQE_CQE_SKIP_SUCCESS` and multishot change the 1:1 SQE→CQE rule; `SQPOLL` lets a kernel thread poll submissions; buffers must stay valid until completion; features gated by `IORING_FEAT_*` (e.g. `SINGLE_MMAP` needs ≥5.4). The man page does not cover registered buffers or IOPOLL. — [io_uring(7)](https://man7.org/linux/man-pages/man7/io_uring.7.html)
- A Rust io_uring + polled direct-I/O crate (`io2`) requires Linux ≥ 6.1, ext4/XFS and NVMe poll queues (`nvme.poll_queues`). — [io2 crate](https://docs.rs/crate/io2/0.0.1)
- llama.cpp's Linux direct-I/O path and its measured load times (DGX Spark 110 s→10.5 s; Strix Halo mmap faster than DIO) are in Q1; llama.cpp issue #19745 reports `-dio` fixing stalls when uploading >100 GiB models over RPC between two Strix Halo machines. **user-reported** — [PR #18012](https://github.com/ggml-org/llama.cpp/pull/18012); [issue #19745](https://github.com/ggml-org/llama.cpp/issues/19745)
- Flatpak sandbox: default denies host filesystem (except app dirs), network, device nodes, D-Bus beyond own name; `--device=dri` "Necessary for GL"; `--device=all` for everything except `shm`; the permissions page mentions no memory/CPU/cgroup limits and only ptrace/non-standard-socket seccomp restrictions. — [Flatpak sandbox permissions](https://docs.flatpak.org/en/latest/sandbox-permissions.html)
- Thermal/throttling state on Linux: `/sys/class/thermal/thermal_zoneX/{type,temp,trip_point_N_temp}` and `cooling_deviceX/{cur_state,max_state}` (cur_state vs max_state shows throttling), mirrored under `/sys/class/hwmon`. — [thermal sysfs API](https://docs.kernel.org/driver-api/thermal/sysfs-api.html)

### Inferences
- Governance on Linux should be cgroup-based when permitted: put the inference process/thread group in a child cgroup, set `memory.high` to the admitted budget and `memory.max` slightly above it, set `memory.oom.group=1` so a failure takes only the inference process, and poll `memory.pressure` (`full avg10`) with a PSI trigger (e.g. `full 100000 1000000`) as the back-pressure signal; outside a controllable cgroup fall back to system `/proc/pressure/memory`. Because page cache is charged to the cgroup, mmapped weights count toward `memory.high` — which is correct for admission but means the limit must include the mapped weights, not just anonymous memory.
- Set the engine's `oom_score_adj` positive (e.g. +500) on the inference process so the kernel kills it before the desktop session if admission was wrong, and keep the UI process at 0.
- THP is a win only for engine-owned anonymous buffers (KV cache, scratch, weights copied in via read/direct-I/O): allocate them 2 MiB-aligned and `MADV_HUGEPAGE` them in `madvise` mode; do not expect huge pages for an mmapped weight file. hugetlbfs is impractical for a consumer app (root/boot-time reservation, unswappable, copy-in).
- Direct I/O + io_uring is the right cold-load path for weights that will be copied into engine-owned memory on fast NVMe (3–10× on the DGX Spark numbers), but keep mmap as the default when the page cache is warm or the device is slow, as llama.cpp's own measurements and maintainer decision show.

### Gaps
- No measurement of PSI-trigger latency vs. actual swap onset for an LLM workload was found; the 60 %/30 s systemd-oomd defaults are the only field-tested thresholds.
- Current status of `READ_ONLY_THP_FOR_FS` and large-folio page cache in 6.x kernels (whether a read-only data mmap can become huge-folio-backed without `MADV_COLLAPSE`) was not verified.
- io_uring registered buffers and their `RLIMIT_MEMLOCK` interaction were not covered by the fetched man page.
- Container (Docker/systemd-nspawn) specifics beyond cgroup v2 semantics were not researched; Flatpak's seccomp filter contents (e.g. whether `io_uring_setup` or `mlock` are allowed) are not in the permissions doc.

## Key question 5 — Allocator design inside the engine: arenas/static plans (ggml-alloc), buffer caches (MLX), Metal heaps, CUDA pools/VMM, jemalloc/mimalloc vs system allocators, measured overheads

### Takeaway
The two reference designs are complementary: ggml plans every activation of a graph once against a worst-case graph (best-fit over ≤256 free blocks per chunk, in-place reuse for a whitelist of ops, inputs never overwritten, outputs never freed) and only reallocates when the plan grows; MLX instead runs a size-bucketed buffer cache under a memory limit (default 1.5× `recommendedMaxWorkingSetSize`, GC at 0.95×) and relies on residency sets to keep it wired. CUDA's stream-ordered pools (release threshold 0 by default — i.e. return everything at every sync unless raised) and VMM-backed expandable segments show the same lesson: fragmentation in long-running servers is solved by reserving virtual address space once and mapping physical pages on demand, not by a smarter free list. Measured overheads are scarce: PyTorch's June-2026 devlog gives concrete reserved-vs-allocated numbers (e.g. 140 MiB mapped for 128 MiB allocated with expandable segments), llama.cpp's `--fit` early versions wasted ~5 GiB per 24 GB GPU before per-tensor placement.

### Cited Findings
- ggml graph allocator (`ggml-alloc.c`, `master`): each chunk keeps ≤ `MAX_FREE_BLOCKS` (256) free blocks sorted by offset; allocation is best-fit over all non-last blocks, then the last block of each chunk by a "reuse_factor", else a new chunk; frees merge with neighbours ("a very naive implementation" assuming few free blocks); tensor lifetimes come from `n_children`/`n_views` counts; in-place reuse of a parent is allowed only for ops in `ggml_op_can_inplace` (ADD, MUL, SCALE, ROPE, RMS_NORM, …) and only if the parent is not external, not an output, same layout, single child, no views; inputs/leaves are allocated before their consumers, outputs never freed; everything padded to the buffer type's alignment; `ggml_gallocr_reserve_n` records per-node buffer/offset/size, `ggml_gallocr_alloc_graph` re-reserves automatically only for a single buffer type and reallocates only when a chunk must grow; chunk size is the backend's max buffer size, ≤ `GGML_VBUFFER_MAX_CHUNKS` (16), with the last chunk effectively unlimited; no measured overheads in the source; hash table has 25 % slack. — [ggml-alloc.c](https://raw.githubusercontent.com/ggml-org/ggml/master/src/ggml-alloc.c)
- ggml backend scheduler (unofficial doc mirror): assigns nodes to backends by priority order, copies tensors between backends automatically, allocates compute buffers per backend; `reserve` with a max-size graph avoids allocation at compute time. **secondary** — [mintlify ggml memory management](https://www.mintlify.com/ggml-org/ggml/concepts/memory-management)
- MLX Metal allocator: freed buffers go to `BufferCache` while cached ≤ `max_pool_size_` (default = memory limit); `malloc` first tries `reuse_from_cache(size)`; sizes > `vm_page_size` are rounded to page multiples (granularity = page size); when `active + cached + requested ≥ gc_limit` or the resource count hits `resource_limit_`, cached buffers are released; beyond that a "Resource limit exceeded" or "Unable to allocate" error is thrown; requests above `maxBufferLength` throw; a single `MTLHeap` serves buffers below `small_size_` (skipped on "Apple Paravirtual device"); buffers are shared-storage, hazard tracking untracked; wrapped external pointers count as active memory. — [allocator.cpp](https://raw.githubusercontent.com/ml-explore/mlx/main/mlx/backend/metal/allocator.cpp)
- MLX public semantics: `set_memory_limit` is "a guideline for the maximum amount of memory to use during graph evaluation" (exceeding it with no RAM/swap left raises), default 1.5× recommended working set; `set_cache_limit` — "When usage exceeds this limit, the next allocation reclaims memory from the cache", default = memory limit, 0 disables the cache. — [set_memory_limit](https://ml-explore.github.io/mlx/build/html/python/_autosummary/mlx.core.set_memory_limit.html); [set_cache_limit](https://ml-explore.github.io/mlx/build/html/python/_autosummary/mlx.core.set_cache_limit.html)
- mlx-lm's `--prefill-step-size` (default 2048 tokens) chunks long prompts to lower peak memory at the cost of prompt speed; `--max-kv-size` bounds the KV cache (rotating). — [mlx-lm README](https://raw.githubusercontent.com/ml-explore/mlx-lm/main/README.md)
- `MTLHeap` (macOS 10.13+): "A memory pool from which you can suballocate resources", sub-allocations can be aliasable, all share the heap's storage/cache mode, heaps (not resources) can be made purgeable. ggml-metal uses no heaps (one `MTLBuffer` per allocation). — [MTLHeap](https://developer.apple.com/documentation/metal/mtlheap.md); [ggml-metal-device.m](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/ggml/src/ggml-metal/ggml-metal-device.m)
- CUDA stream-ordered allocator **(background, 2021 NVIDIA blog, CUDA 11.2)**: "By default, the release threshold of a pool is zero" so unused pool memory returns to the OS at every synchronisation and the next `cudaMallocAsync` pays a system allocation; `cudaMemPoolAttrReleaseThreshold` caps cached memory (a hint — the driver may release early to satisfy `cudaMalloc`/`cuMemCreate`); on fragmentation "the driver remaps unused pool memory into a contiguous range of the GPU's virtual address space"; reuse policies across streams via event dependencies / opportunistic / internal dependencies. No absolute timings given. — [NVIDIA blog](https://developer.nvidia.com/blog/using-the-nvidia-cuda-stream-ordered-memory-allocator-part-1/)
- PyTorch caching allocator devlog (2026-06-01, **measured** toy examples): without expandable segments each `cudaMalloc` is its own segment (1–10 MiB requests get 20 MiB segments; ≥10 MiB rounded to 2 MiB) and "blocks in different segments can never merge": 8×16 MiB then 4×32 MiB reserves 256 MiB vs 128 MiB in the reverse order; with expandable segments (`cuMemAddressReserve` ≈1⅛ × `totalGlobalMem`, `cuMemCreate`/`cuMemMap` on demand in 2 MiB small / 20 MiB large pages) 8×16 MiB maps 140 MiB for 128 MiB and later 4×32 MiB needs no new pages; small (≤1 MiB) and large pools stay separate; live allocations still pin splits. — [PyTorch devlog](https://docs.pytorch.org/devlogs/eager/2026-06-01-cuda-caching-allocator/)
- CUDA VMM granularity: a forum poster read 2 MB from `cuMemGetAllocationGranularity` on an RTX 3090 / CUDA 12 with no official explanation; GMLake reports VMM calls are far slower than `cudaMalloc` and adds a caching pool. **user-reported / paper** — [NVIDIA forum 268699](https://forums.developer.nvidia.com/t/virtual-memory-management-minimum-granularity/268699); [GMLake](https://arxiv.org/pdf/2401.08156)
- mimalloc (MIT; README v3.4.5, 2026-08-05): claims "bounded worst-case allocation times", "~0.2% meta-data" overhead, free-list sharding that "reduces fragmentation and increases locality", eager purging for long-running programs; `MIMALLOC_PURGE_DELAY` default 1000 ms (0 = immediate, −1 = never); `MIMALLOC_ALLOW_LARGE_OS_PAGES=1` can help but such pages "can't be purged or shared"; `MIMALLOC_RESERVE_HUGE_OS_PAGES=N` reserves 1 GiB pages at startup; benchmarks (2021, 16-core 5950X, mimalloc v1.7.0 — **vendor-claimed, stale**) show it ahead of jemalloc/tcmalloc with "similar memory footprint". — [mimalloc readme](https://raw.githubusercontent.com/microsoft/mimalloc/master/readme.md); [mimalloc LICENSE](https://raw.githubusercontent.com/microsoft/mimalloc/master/LICENSE)
- llama.cpp `--fit` (PR #16653, merged 2025-12-15) sizes everything with `no_alloc` dummy loads instead of real allocations; early versions "wasted roughly 5 GiB per GPU on 24 GB cards" until per-tensor placement; the fit itself costs ~0.1 s simple case up to ~10 s for DeepSeek R1 on six GPUs; assumes uniform layer sizes. **measured by PR author/testers** — [PR #16653](https://github.com/ggml-org/llama.cpp/pull/16653)
- Ollama's older estimator (v0.11.0 `llm/memory.go`) used heuristics: if the partial-offload graph size is unknown it is estimated as `gqa × kvTotal / 6`; each GPU needs `overhead + projector + max(graph) + MinimumMemory + 2 × layerSize` to be eligible; "on metal there's no partial offload overhead"; multimodal models force ≥ 2048 context. — [memory.go v0.11.0](https://raw.githubusercontent.com/ollama/ollama/v0.11.0/llm/memory.go)

### Inferences
- A Rust engine should combine the two models: a static per-graph plan (ggml-style lifetimes, in-place whitelist, worst-case reservation at admission time so the plan's size is known *before* loading) for activations, plus a size-bucketed cache with an explicit byte limit for transient buffers (prompt-cache, batch-variable scratch), with the cache limit counted in the admission budget and purged on pressure signals (Q2–Q4).
- Reserve virtual address space once per device and grow physical backing in large fixed pages (2 MiB/20 MiB as PyTorch does; Metal heaps / `vm_allocate` regions on macOS; `VirtualAlloc(MEM_RESERVE)` + `MEM_COMMIT` on Windows) so a long-running server's footprint is bounded by the plan, not by allocation order.
- For host-side allocations use mimalloc or jemalloc only for the engine's own small-object traffic (tokenizer, request metadata); weights, KV and scratch should bypass malloc entirely (mmap/`vm_allocate`/`VirtualAlloc` with explicit alignment) so they can be huge-page-aligned, locked and accounted individually. Measure RSS drift over hours, as the MLX user did, before choosing.

### Gaps
- No published measurement of ggml-alloc's fragmentation/overhead vs. the theoretical minimum, or of MLX's cache hit rate, was found.
- No head-to-head jemalloc vs mimalloc vs glibc data for an inference server's host-side allocations was found (search budget ended); the mimalloc numbers are vendor benchmarks from 2021.
- CUDA VMM 2 MiB granularity and Metal heap allocation costs are not officially documented in the sources fetched.
- llama.cpp's measured scratch ("compute buffer") sizes as a function of batch/context were not extracted.

## Key question 6 — Admission control and degradation: estimating peak memory, headroom, refusing/shrinking requests, unloading idle models, detecting pressure from other processes; policies of LM Studio, Ollama, llama.cpp, vLLM; reported failures

### Takeaway
Every engine has converged on "size before you load, then shrink context before you spill": llama.cpp (`--fit`, default on since Dec 2025) projects memory with no-alloc dummy loads, reduces context to ≥4096 and then moves layers to system RAM keeping 1 GiB free per device; Ollama measures exact memory on its new engine, requires a new model to fit in 80 % of free VRAM alongside loaded ones, retries OOM loads at 32k/4k context and evicts idle models (5 min keep-alive, 3 per GPU); LM Studio refuses loads above a "guardrails" estimate and evicts earlier JIT models (60-min TTL); vLLM pre-allocates a fixed fraction of GPU memory and preempts-and-recomputes requests when KV runs out. The reported failures (over-estimates by 2×, under-estimates leading to kernel panics, idle unwiring, VRAM-reporting lag) all point to the same rule: measure the real allocation, keep an explicit headroom, and respond to pressure by shedding caches and idle models, never by swapping.

### Inferences — governance design a new engine should implement (grounded in the findings above)
1. **Plan with a no-alloc dry run, not a formula.** llama.cpp's `--fit` and Ollama's new engine both moved from heuristics (Ollama's old `gqa × kv / 6` graph guess) to building the graph plan without allocating and reading back exact buffer sizes. LLMario's engine should produce, per request to load: weights (by device), KV at the requested context × slots × KV dtype, the static activation plan (Q5), prompt-cache budget, and runtime overhead, and only then compare against budgets.
2. **Budgets per device, with explicit headroom.** Host budget = min(`MemAvailable`-style free+reclaimable, user cap) minus headroom; GPU budget = `recommendedMaxWorkingSetSize` (macOS) / DXGI `Budget` or `VK_EXT_memory_budget` (Windows/Linux) minus a margin. Field defaults: llama.cpp 1 GiB per device, Ollama 20 % of free VRAM and max(8 GB, 10 % RAM) host headroom before it disables mmap, MLX GC at 95 % of the working set. A margin expressed as max(1 GiB, 10 %) per device plus "keep ≥ N GB free for the OS" is defensible.
3. **Degrade in a fixed order before refusing**: (a) shrink prompt cache and buffer caches; (b) reduce context to a floor (4096, like `--fit-ctx`, or Ollama's 32k→4k steps); (c) quantize KV (q8_0 ≈ ½, q4_0 ≈ ¼ per Ollama's FAQ) if the model/attention path supports it; (d) move dense-first layers to host memory (llama.cpp prioritises dense weights over MoE experts on the GPU); (e) refuse with a structured error that names the shortfall per device. Never fall through to OS swap: the three macOS failure reports are the cost.
4. **Admission is per request, not only per model.** vLLM's preempt-and-recompute and llama.cpp's slot/`--cache-ram` limits show that concurrency (slots × context) is where KV blows up; the API should reject or queue a request whose context/batch would exceed the planned KV budget, and expose `max_num_seqs`-style caps.
5. **Idle policy**: keep-alive with a default (Ollama 5 min, LM Studio 60 min JIT, llama.cpp router 4 models) and evict least-recently-*used* (Ollama's own code admits it is not true LRU); release residency sets/wired memory after an idle window (ggml's 3-minute keep-alive) so a backgrounded app stops holding GPU memory.
6. **Back-pressure from the OS**: subscribe to macOS warning/critical, Windows low-memory + DXGI budget change, Linux PSI/cgroup events; on *warning*: drop caches, unload idle models, stop admitting new loads; on *critical*: cancel queued requests and, if the engine is a child process, let the supervisor kill it. Re-check budgets after any such event because VRAM reporting can lag seconds (Ollama polls up to 5 s).
7. **Verify after load**: record real peak (job-object peak on Windows, `memory.peak`/`memory.current` in a cgroup, `currentAllocatedSize` on Metal) and feed it back into the estimator so the next admission for the same model is exact — the same loop Ollama's blog describes.

### Gaps
- Ollama's new-engine measurement code (`ml/backend.go`) was not readable at `main` (404 at fetch time); the exact pre-load allocation protocol is known only from the blog post.
- LM Studio's guardrail levels (names, thresholds, formula) are undocumented; only the error text, the `--estimate-only` output and issue reports were found.
- No engine was found that uses cgroup `memory.high`, job objects, or the Metal residency keep-alive as an *admission* mechanism rather than a crash-avoidance patch; the design in Inferences is a synthesis, not an observed practice.
- No controlled study of estimate accuracy (predicted vs measured peak) across engines exists beyond single issue reports (LM Studio 2× over, llama.cpp `--fit` early 5 GiB waste).

## Key question 7 — Streaming weights from disk when the model does not fit: Apple "LLM in a flash", later SSD-streaming and MoE expert streaming work, measured tokens/s, SSD wear

### Takeaway
SSD streaming works only when the model is sparse enough that each token touches a small fraction of weights: Apple's 2023 work (background) hit ~1.5 tok/s on CPU and ~12 tok/s on an RTX 4090 for OPT-6.7B with 97 % FFN sparsity and ~50 % of the model in DRAM, and in March 2026 a MoE experiment ran a 397B-A17B model (209 GB on disk, ~6 GB engine resident) at 4.36 tok/s on a 48 GB M3 Max by reading 4 experts × ~6.75 MB per layer with parallel `pread()` and trusting the OS page cache (~71 % hit rate, 17.5 GB/s sequential SSD). Dense models cannot be streamed usefully (naive SSD-bound estimate ~0.16 tok/s for a 37B-active model at 3 GB/s), prefetching hides latency but not energy (modelled up to ~12× per-token energy vs HBM), and reads do not consume NAND program/erase endurance although controllers must relocate blocks after hundreds of thousands of reads.

### Cited Findings
- Apple "LLM in a flash" **(background; arXiv 2312.11514 v3, 2024-07-30; ACL 2024)**: hardware M1 Max 1 TB SSD, M2 Ultra 2 TB SSD, Linux RTX 4090 24 GB; OPT-6.7B per-token latency (256-token generation): CPU naive 3182 ms → 669 ms with predictor+windowing+bundling (~0.3 → ~1.5 tok/s, computed from the paper's ms figures); Metal M1 2389 → 565 ms; Metal M2 2270 → 305 ms; RTX 4090 2218 → 84 ms (~12 tok/s), 60 ms with speculative; Falcon-7B CPU 3095 → 706 ms (161 ms I/O, 92 ms memory management, 453 ms compute); DRAM ≈ 52 % of model (OPT-6.7B 6.5 GB vs 13.4 GB); flash throughput: 6.1 GB/s dense sequential, ~1.25 GB/s sparse random reads, ~2.25 GB/s with row-column bundling, 32 KiB random reads across 32 threads are enough; sparsity ~97 % (OPT), ~95 % (relufied Falcon), ~90 % (Llama-2 FATReLU); the paper's headline claims are 4–5× (CPU) and 20–25× (GPU) over naive loading and running models up to 2× DRAM. **measured by the authors** — [arXiv 2312.11514v3](https://arxiv.org/html/2312.11514v3); [Apple ML Research](https://machinelearning.apple.com/research/efficient-large-language)
- Dan Woods' flash-moe (March 2026, **user-reported, repo README**): Qwen3.5-397B-A17B (60 layers, 512 experts/layer, 4 active + 1 shared per token, hidden 4096) on a MacBook Pro M3 Max 16-core CPU / 40-core GPU / 48 GB (~400 GB/s), macOS 26.2; pure C/Objective-C with hand-written Metal shaders (no MLX, no Python); experts read on demand with parallel `pread()` via GCD, ~6.75 MB per expert, only the four active experts per layer; no custom expert cache ("Trust the OS") — the OS page cache (~35 GB) gives ~71 % hit rate; resident: 5.5 GB non-expert weights (mmap, read-only) + ~200 MB Metal scratch ≈ 6 GB engine, ~42 GB left for OS/page cache; 4.36 tok/s with 4-bit experts (209 GB on disk; 3.90 before an FMA kernel change), 5.74 tok/s sustained / 7.05 peak warm-cache with 2-bit experts (120 GB, breaks JSON/tool calling); ~4.28 ms per layer of which ~2.41 ms SSD reads; measured 17.5 GB/s sequential read on the 1 TB Apple SSD; SSD DMA and GPU compute share memory bandwidth so the pipeline runs serially; no license file. — [flash-moe README](https://github.com/danveloper/flash-moe); [Simon Willison, 2026-03-18](https://simonwillison.net/2026/mar/18/llm-in-a-flash/)

- Related 2025–26 MoE streaming work (abstract-level only): Edge0 (Sept 2026) predicts next-layer routing one token early so SSD reads overlap compute, and notes a 35B-class model's 4-bit weights are ~19.5 GB; OD-MoE (Dec 2025) drops expert caches and looks several layers ahead; fMoE (Feb 2025, revised Oct 2025) uses routing/semantic patterns to prefetch between GPU and CPU memory; importance-driven expert substitution (Aug 2025) reports 48 % lower decode latency and >60 % cache hit by swapping low-importance experts for resident ones. — [Edge0 (HF papers)](https://huggingface.co/papers/2609.18063); [OD-MoE](https://arxiv.org/abs/2512.03927v1); [fMoE](https://arxiv.org/abs/2502.05370v1); [arXiv 2508.18983](https://arxiv.org/abs/2508.18983v1)

- llama.cpp's current partial answer: `-cmoe/-ncmoe` keep expert weights on the CPU with `--moe-cache-mib` as a GPU-side cache; issue #19825 asks for a managed SSD→RAM pipeline and cites the ik_llama.cpp fork's `--cpu-moe` giving 35+ t/s (Qwen 30B IQ4_KSS), 25+ (Q4_K_M) and 10+ t/s (Qwen-Next 80B IQ4_KSS) on the 24 GB M4 Pro, with prompt processing still a bottleneck. **user-reported** — [server README](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/tools/server/README.md); [issue #19825](https://github.com/ggml-org/llama.cpp/issues/19825)
- SSD wear (background, encyclopedia-level): NAND wears by program/erase cycles; read disturb "can cause nearby cells in the same memory block to change over time" after "hundreds of thousands of reads" between erases, and controllers count reads per block and relocate the data before ECC limits are exceeded; the article does not say reads consume P/E endurance. — [Wikipedia: Flash memory](https://en.wikipedia.org/wiki/Flash_memory)

### Inferences
- For LLMario's "small and mid-size models on 8–128 GB" goal, streaming is relevant only for MoE models (and, speculatively, ReLU-sparse FFNs): the design should be expert-granular `pread`/`O_DIRECT`/io_uring reads of 4-bit experts in ≥32 KiB contiguous chunks (Apple's bundling finding), a resident set of hot experts governed by the same byte budget as everything else, and routing look-ahead by one layer to overlap I/O with compute; dense models that do not fit should be refused, not streamed.
- The page cache "Trust the OS" approach works on a 48 GB Mac because 42 GB stays free; it collapses on 8–24 GB machines (issue #19825). An engine-managed expert cache with an explicit limit and `O_DIRECT`/`F_NOCACHE`-style reads is the governable version.
- SSD wear from read-only streaming is a second-order concern (controller-managed read-disturb relocation); the first-order concern is energy on laptops (up to ~12× per token in the model), so streaming should be disabled on battery by default and surfaced as an explicit "slow, SSD-streaming mode".

### Gaps
- No tokens/s measurement of SSD streaming on Windows or Linux consumer laptops (as opposed to desktop PCIe 5.0 rigs) was found.
- No source quantified actual SSD read volume per token or per hour for any streaming engine, so wear/throughput sizing for consumer QLC drives is unverified.
- Edge0, OD-MoE and fMoE were seen only as abstracts; their absolute tok/s and hardware are not captured here.
- The flash-moe repository's license is missing, so none of its code can be reused without clarification; its numbers are from one machine and one author.

## Key question 8 — Power and thermal: laptop throttling, battery, macOS thermal/low-power APIs, Windows power throttling and power events, Linux thermal sysfs; how an engine should adapt threads and GPU usage

### Takeaway
All three OSes expose a coarse "the machine is hot / on battery / in saver mode" signal — macOS `ProcessInfo.thermalState` (nominal/fair/serious/critical, macOS 10.10.3+) plus `isLowPowerModeEnabled` (macOS 12+) and the QoS classes; Windows `GUID_POWER_SAVING_STATUS`/`GUID_ENERGY_SAVER_STATUS`/`GUID_ACDC_POWER_SOURCE` notifications plus EcoQoS opt-in/out; Linux `/sys/class/thermal` trip points and cooling-device states — but none of them tells an engine how many threads to run. The field practice is to size threads to performance cores (llama.cpp uses `hw.perflevel0.physicalcpu` on macOS), lower QoS/priority rather than thread count when backgrounded, and reduce batch/prefill size or GPU use at the serious/critical thermal state (Zed caps its frame rate at 60 fps at critical).

### Cited Findings
- `ProcessInfo.ThermalState` (macOS 10.10.3+): nominal "within normal limits", fair "slightly elevated", serious "high", critical "significantly impacting the performance of the system and the device needs to cool down"; change notification `NSProcessInfoThermalStateDidChangeNotification`; Xcode can simulate states ("Test under adverse device conditions"). — [ProcessInfo.ThermalState](https://developer.apple.com/documentation/foundation/processinfo/thermalstate-swift.enum.md)
- Zed's GPUI reads `thermalState` (raw 0–3 → four cases, default nominal) and limits the frame rate to 60 fps at critical. — [Zed commit 7694ea2](https://git.secluded.site/zed/commit/7694ea2687f6c9e05aeceaf062e85088389800db)
- Command-line visibility on macOS: `pmset -g therm` works without root; `powermetrics` (root) prints a thermal pressure level; a Dec-2025 blog found the two readings diverge under stress because they use different state scales. **user-reported** — [stanislas.blog, Dec 2025](https://stanislas.blog/2025/12/macos-thermal-throttling-app/)
- Low Power Mode: `isLowPowerModeEnabled` (macOS 12+) with `NSProcessInfoPowerStateDidChange`; the system "reduces CPU and GPU performance" and pauses discretionary/background activity. — [isLowPowerModeEnabled](https://developer.apple.com/documentation/foundation/processinfo/islowpowermodeenabled.md)
- QoS classes and the "utility or lower ≥90 % of the time when the user is not active" guidance, `powermetrics --show-process-qos`; see Q2. — [Prioritize Work at the Task Level](https://developer.apple.com/library/archive/documentation/Performance/Conceptual/power_efficiency_guidelines_osx/PrioritizeWorkAtTheTaskLevel.html)
- Windows: EcoQoS opt-in/out via `SetProcessInformation(ProcessPowerThrottling)` (frequency reduction / efficient cores; Windows infers QoS automatically otherwise; timer-resolution coarsening for occluded windows in Windows 11) — Q3; power notifications `GUID_ACDC_POWER_SOURCE`, `GUID_BATTERY_PERCENTAGE_REMAINING`, `GUID_POWER_SAVING_STATUS` ("Battery saver is on. Save energy where possible."), prerelease `GUID_ENERGY_SAVER_STATUS` (STANDARD "Save energy if the user experience impact is minimal" / HIGH_SAVINGS "Save energy where possible"), `GUID_POWERSCHEME_PERSONALITY`, `GUID_SESSION_USER_PRESENCE`. — [SetProcessInformation](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-setprocessinformation); [Power Setting GUIDs](https://learn.microsoft.com/en-us/windows/win32/power/power-setting-guids)
- EcoQoS vendor claim (2021): up to 90 % CPU power reduction for background work on supported mobile silicon. — [Introducing EcoQoS](https://devblogs.microsoft.com/sustainable-software/introducing-ecoqos/)
- Linux: thermal zones expose `temp` and trip points, cooling devices expose `cur_state`/`max_state` (throttling level) and `stats/time_in_state_ms`; hwmon mirrors `temp1_input`/`temp1_crit`. — [thermal sysfs API](https://docs.kernel.org/driver-api/thermal/sysfs-api.html)
- Thread sizing in practice: llama.cpp defaults to physical performance cores on macOS, distinct sibling sets on Linux (with CPUID-based E-core exclusion on x86-64 Linux hybrids), `RelationProcessorCore` counts on Windows, and `hardware_concurrency()/2` as a fallback; `--prio` changes nice/priority class, `--poll` (default 50) controls busy-waiting while idle. — [common.cpp](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/common/common.cpp); [server README](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/tools/server/README.md)
- E-core caution (Apple forum, user-reported): splitting work equally across all cores made the efficiency cores "a serious choke point"; macOS offers no thread-to-core affinity. — [Apple forum thread 674456](https://developer.apple.com/forums/thread/674456)
- GPU idle power-saving interacts with memory: the macOS wired collector unwires GPU memory after ~1 s idle (Q2), so "saving power while idle" and "fast first token" are in direct tension; ggml resolves it with a 3-minute residency keep-alive. — [PR #10119](https://github.com/ggml-org/llama.cpp/pull/10119); [ggml-metal-device.m](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/ggml/src/ggml-metal/ggml-metal-device.m)

### Inferences
- Default thread count = number of performance cores (not logical CPUs); never add E-cores to a barrier-synchronised matmul pool; lower *QoS/priority* (utility/background on macOS, EcoQoS on Windows, nice on Linux) rather than thread count when the app is backgrounded, and raise it (user-initiated / HighQoS) only while a user-visible request is streaming.
- Treat thermal state as a two-level signal: at *serious* reduce prefill chunk size and batch (less burst heat, same tokens), disable speculative/extra parallel slots; at *critical* or Low-Power/Battery-saver, additionally cap concurrent requests to 1, drop polling (`--poll 0`-style), and release residency after a short idle window; resume at *fair/nominal*. Expose these as policy, not hard-coded, because Apple/Microsoft give no numeric guidance.
- Disable busy-polling and SSD streaming (Q7) on battery; prefer the GPU over multi-threaded CPU for the same tokens/s where available because EcoQoS/P-core throttling hits CPU paths harder (inference from the EcoQoS and QoS docs; no measurement found).

### Gaps
- No measured tokens/s vs. thermal-state or vs. battery-saver data for any local engine was found; the only quantified power claim is Microsoft's 2021 EcoQoS figure for background work.
- Windows thermal state has no app-level API in the fetched sources (only power events); Linux thermal reading requires knowing which zone is the package sensor, which the kernel docs do not standardise.
- Apple's GPU-side thermal throttling behaviour (Metal performance under `serious`/`critical`) is undocumented in the sources fetched.
- The ggml residency keep-alive's effect on battery life (3 minutes of wired GPU memory per request) has not been measured in any source found.
