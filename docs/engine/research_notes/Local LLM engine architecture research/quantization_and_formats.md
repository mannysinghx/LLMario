# Weight quantization, compact model formats, and weight loading/streaming for a from-scratch local inference engine (state as of 2026-10-08)

Research notes for the LLMario engine design (Rust, Apache-2.0; 0.5B–70B dense, MoE to ~120B total; 8–128 GB machines).
Conventions used below: **[measured]** = a number produced by a benchmark run described in the source; **[vendor]** = claimed by the method's authors or the hardware vendor without an independent run; **[secondary]** = relayed by a third party (blog, forum, search summary) and not re-checked against the primary; **[unverified]** = could not be confirmed from a fetched source; **[background]** = source older than 2025. Perplexity (PPL) and KL-divergence (KLD) values are only comparable within one table (same model, dataset, context, build). "bpw" = bits per weight including scales.

## Key question 1 — Quantization schemes and their measured quality / size / speed trade-offs (with hardware kernels and licenses)

### Takeaway
On a bytes-of-weights basis, the 2025–2026 quality frontier at 2–5 bpw is held by calibrated vector/trellis codebook methods (EXL3/QTIP, AQLM+PV, VPTQ) and by llama.cpp's imatrix I-quants/K-quants with per-tensor mixes (Unsloth UD, llama.cpp defaults); plain block floats (MXFP4, NVFP4) trade a measurable quality loss (KLD roughly 1.4–2× that of an affine/K-quant at the same ~4.25–4.5 bpw) for native tensor-core speed on Blackwell and simpler kernels. FP8 (W8A8) and Q8_0/8-bit affine are effectively lossless; 4-bit weight-only recovers ≥98.7% of BF16 on Llama-3.1 8B–405B leaderboards, but the newest, longest-trained small models (≤8B, 15–40T tokens) degrade noticeably more at ≤4 bits than 2023-era models did. Only ExLlamaV3, HQQ, AQLM, VPTQ, Marlin, GemLite, safetensors, ggml/llama.cpp, MLX, T-MAC, BitNet, DFloat11, ZipNN, ParetoQ and llm-awq have permissive licenses; QTIP and QuIP# are GPL-3.0, SpinQuant and any4 are CC-BY-NC 4.0.

#### EXL3 (ExLlamaV3; MIT; CUDA only) and QTIP (GPL-3.0)
- EXL3 is "a streamlined variant of QTIP": procedural codebook + tail-biting trellis; differs in tensor regularization/packing; format doc "not yet published"; requires PyTorch + CUDA 12.4+ (cu124–cu132), "modern consumer GPUs", Windows needs triton-windows; 2–8-bit KV-cache quantization; tensor/expert parallel; CPU offload for MoE (AVX2/AVX512); GGUF i-quants "hold up well" against SOTA formats per the author — [ExLlamaV3 README](https://github.com/turboderp-org/exllamav3), [exl3.md](https://github.com/turboderp-org/exllamav3/blob/master/doc/exl3.md)
- Converter: `--bits` is a float (e.g. 3.75); lm_head default 6 bits; token embeddings default 16-bit (`-eb`), MTP 4-bit, vision 6/16; `-hq` raises attention/shared-expert bits (+0.05–0.10 bpw on MoE); per-tensor YAML recipes from `sc_optimize.py`; codebooks mul1 (default, required by optimized kernels), mcg, 3inst; output as safetensors shards (8192 MB default) — [convert.md](https://github.com/turboderp-org/exllamav3/blob/master/doc/convert.md)

#### Lossless compression
- DFloat11 (NeurIPS 2025; code Apache-2.0): entropy-codes BF16 exponents → ≈30% smaller, bit-exact outputs; custom CUDA decompression with SRAM LUTs; "at batch size 1 inference ≈2× slower than BF16, gap narrows with batch"; 2.3–46.2× faster than a CPU-offloaded uncompressed baseline; CUDA 12 required, no CPU inference; CPU-offload mode drops Qwen3-8B peak GPU memory 12.4→2.3 GB — [DFloat11 repo](https://github.com/LeanModels/DFloat11), [paper](https://arxiv.org/abs/2504.11651)

#### MLX affine group quantization (MIT) and learned variants
- `mlx.core.quantize(w, group_size, bits, mode)`: affine (default) with group_size ∈ {32, 64 (default), 128}, bits ∈ {2,3,4 (default),5,6,8}; s=(max−min)/(2^b−1), ŵ=round((w−β)/s); packed LSB-first into uint32 (eight 4-bit values per word); returns (w_q, scales, biases) with scales in the input dtype; modes mxfp4 (g32, E8M0), mxfp8 (g32, E8M0), nvfp4 (g16, E4M3, optional `global_scale`) return no biases — [MLX quantize docs](https://ml-explore.github.io/mlx/build/html/python/_autosummary/mlx.core.quantize.html)
- Affine 4-bit g64 bpw: 4 + 2×16/64 = 4.5 bpw (fp16 scale+bias per 64) **[arithmetic from the spec]**.
- mlx-lm learned quants: DWQ (distill scales/biases/non-quantized params from the 16-bit teacher; best for 2–4 bit; "distilling 16→8 or 6-bit often doesn't work well"; smaller group doubles tunable params), AWQ (`--n-grid`), GPTQ, and `dynamic_quant` (per-layer sensitivity; default 5 bits for sensitive layers, 4 for the rest, `--target-bpw`); "a few minutes to several hours" — [LEARNED_QUANTS.md](https://github.com/ml-explore/mlx-lm/blob/main/mlx_lm/LEARNED_QUANTS.md)

#### Scaling with training tokens (why 2026 models quantize worse)
- "Low-Bit Quantization Favors Undertrained LLMs" (Nov 2024, >1,500 Pythia 160M–12B checkpoints, GPTQ 2/3/4-bit): ΔqLoss ≈ 0.017·D^0.5251 / (N^0.2261·P^5.4967); 4-bit ΔqLoss reaches 0.2 at ≈1.44T tokens (1B), 4.51T (7B), 17.35T (70B), 48.49T (405B); predicts low-bit quantization "may NOT be desirable" for models trained on ≥10^14 tokens — [arXiv 2411.17691](https://arxiv.org/abs/2411.17691), [HTML](https://arxiv.org/html/2411.17691)

### Inferences
- For an Apache-2.0 Rust engine, GGUF K/I-quants, MLX affine, MXFP4/NVFP4, AWQ/GPTQ packings, HQQ, AQLM and VPTQ formats are all readable from permissively licensed references; EXL3 is MIT but its on-disk format is undocumented and must be reverse-read from the loader; QTIP/QuIP# (GPL) and SpinQuant/any4 (NC) must not be ported — only cleanroom re-implementations from the papers would be safe, which is a licensing/IP question for the user.
- Quality per byte ranking at ~4 bpw on recent models (from the Gemma 4 12B and Qwen3.5/3.6 tables): EXL3 4.0 ≈ UD-Q4_K_XL/Q4_K_M-with-imatrix > IQ4_XS ≈ MLX affine-4bit-g64 > NVFP4 > MXFP4. At ~2 bpw: EXL3/QTIP and AQLM-PV/VPTQ are clearly better than IQ2_*; llama.cpp IQ1/IQ2 KLDs (0.3–2.2 on 8B) mean 1-bit GGUF is usable only for large models and non-agentic use, which is also Unsloth's own guidance.
- Decode throughput on bandwidth-bound hardware is set almost entirely by bytes/token, not the quant scheme: Unsloth's llama.cpp table shows ≈90 t/s for everything except I-quants (≈85), and the RTX 5090 NVFP4 native path changed prefill (+68%) but not decode. Scheme choice therefore matters for prefill (LUT/codebook decode cost, tensor-core eligibility) and quality, not for tokens/s at batch 1.

## Key question 2 — Practical bit-width sweet spots in 2026 for 8 GB, 16 GB, 32 GB and 64 GB machines

### Takeaway
With the measured sizes above, the practical rule is "largest model that fits at ≥4.3–4.9 bpw (Q4_K_M / UD-Q4_K_XL / IQ4_XS / EXL3 4.0), then spend leftover memory on Q5–Q6 before stepping up a model size"; 3-bit mixes (Q3_K_XL, EXL3 3.0) are acceptable on ≥27B dense models (MMLU −0.6 pt on Gemma 3 27B) but cost 2–4× the KLD, and ≤2.5 bpw is reserved for making 70B-class or large-MoE models fit at all.

### Cited Findings
- 8 GB class: Llama-3-8B file sizes Q4_K_M 4.58 GiB (KLD 0.028 with imatrix), IQ4_XS 4.14 GiB (0.036), Q5_K_M 5.33 GiB (0.011), Q6_K 6.14 GiB (0.0055), IQ3_M 3.53 GiB (0.10), IQ2_M 2.74 GiB (0.33) — [llama.cpp perplexity README](https://github.com/ggml-org/llama.cpp/blob/master/tools/perplexity/README.md); Gemma 4 12B Q4_K_M is 6.63 GiB and used 8.04 GiB loaded / 8.54 GiB peak VRAM with a 16k FP16 cache on an RTX 5090 — [atomic.chat](https://atomic.chat/blog/guides/exl3-vs-gguf); MLX Qwen3-8B 4-bit used 5.61 GB on an M5 with a 4,096-token prompt — [Apple MLX/M5 post](https://machinelearning.apple.com/research/exploring-llms-mlx-m5)
- 16 GB class: Gemma 3 27B Q3_K_XL 12.76 GB scores MMLU 70.87 vs 71.5 BF16 and Q2_K_XL 9.95 GB scores 68.70 (IQ2_M 8.96 GB: 66.47) — [Unsloth Dynamic 2.0](https://unsloth.ai/docs/basics/unsloth-dynamic-2.0-ggufs); gpt-oss-20b MXFP4 used 12.08 GB in MLX on a 24 GB M5 and its checkpoint is 12.8 GiB ("as little as 16GB memory") — [Apple post](https://machinelearning.apple.com/research/exploring-llms-mlx-m5), [gpt-oss card](https://arxiv.org/html/2508.10925); Qwen3-14B 4-bit used 9.16 GB and Qwen3-30B-A3B 4-bit used 17.31 GB in MLX (so a 30B-A3B 4-bit does not fit 16 GB without offload) — [Apple post](https://machinelearning.apple.com/research/exploring-llms-mlx-m5); Qwen3.5-35B-A3B UD-Q3_K_XL is 16.06 GB (KLD 0.031) and UD-Q2_K_XL 12.04 GB (0.097) — [Unsloth](https://unsloth.ai/docs/models/qwen3.5/gguf-benchmarks)

- Cross-size evidence: W4A16 recovers 98.7% (8B), 99.5% (70B), 100.0% (405B) of BF16 on Open LLM v1 — bigger models tolerate 4-bit better — [arXiv 2411.02355](https://arxiv.org/html/2411.02355); the undertrained-LLM scaling law predicts 4-bit degradation becomes material (ΔqLoss 0.2) at ≈4.5T tokens for 7B and ≈17T for 70B — [arXiv 2411.17691](https://arxiv.org/html/2411.17691); Llama-3 8B q4_K_M KLD 0.031 vs Llama-2 7B 0.0127 and any4 int4 PPL +11.9% (Llama-3-8B) vs +4.9% (Llama-2-7B) show this effect on real models — [llama.cpp README](https://github.com/ggml-org/llama.cpp/blob/master/tools/perplexity/README.md), [any4](https://github.com/facebookresearch/any4)

- KLD values on hard, chat-templated, long-context (~30k) data run well above the 0.01–0.03 typical of Q4_K_M on Wikipedia-style sets — [localbench methodology, Apr 14 2026](https://localbench.substack.com/p/gguf-benchmark-methodology)

### Inferences
- 8 GB (unified or VRAM): 7–9B dense at Q4_K_M/IQ4_XS/EXL3-4.0 (≈4.1–4.6 GiB) with 2–4 GiB left for KV cache and the OS; 12B only at ≤Q4 with short context; 3–4B at Q8_0/Q6_K when the task needs fidelity.
- 16 GB: 12–14B at Q5–Q6 (7.8–9.2 GiB), gpt-oss-20b in MXFP4 (12.1–12.8 GiB, tight), or 27B at Q3_K_XL (12.8 GB, MMLU −0.6 pt) for knowledge-heavy work; 30B-A3B MoE only with expert offload or at ≤Q3.
- 32 GB: 27–32B dense at Q4_K_XL…Q6_K (15.6–20.6 GB) is the dominant choice; 35B-A3B MoE at Q4_K_XL…Q5_K_XL (20–25 GB); 70B only at ≈2 bpw (AQLM/VPTQ/EXL3-2.x, ~20–24 GB) with a measurable hit (MMLU −4 pt on Llama-3-70B AQLM).
- 64 GB: 70B dense at Q4_K_M (≈39–43 GiB; Llama-3-class slightly larger than Llama-2 because of the 128k vocab — arithmetic) up to Q5_K_M (≈45 GiB); gpt-oss-120b MXFP4 (60.8 GiB) does not comfortably fit a 64 GB unified machine without expert offload; 100–120B MoE at Q3–Q4 mixes is the natural 64 GB target but no fetched table measures it.
- 128 GB (outside the asked range but in LLMario's spec): 70B at Q8_0 (~70 GiB) or gpt-oss-120b with full headroom.

### Gaps
- No fetched source gives UD/K-quant sizes and KLD for a 70B-class *2026* model (Llama-3.3/Qwen3-72B-class); the 70B size table is Llama-2 (2023) and the quality table is Llama-3 8B.
- No measured sizes for 100–120B MoE GGUFs other than gpt-oss-120b's MXFP4 checkpoint.
- KV-cache memory (which decides the usable context at each tier) was out of scope for these notes and not collected.

## Key question 3 — Low-bit kernel techniques (LUT matmul, ARM repacking/KleidiAI/SME2, Marlin/Machete/GemLite, Metal int4, Apple M5 neural accelerators, Blackwell FP4)

### Takeaway
CPU low-bit speed now comes from (a) interleaved weight repacking done at load time so int8-dot-product/SME2 outer-product instructions can stream 4-bit blocks (llama.cpp aarch64 repack, KleidiAI ≈1.5× over i8mm on SME2), and (b) table-lookup kernels for ≤2-bit (T-MAC, bitnet.cpp, 2–6× over llama.cpp); on GPUs, weight-only 4-bit kernels (Marlin/Machete/GemLite) are near the 3.9× bandwidth bound at small batch, while Blackwell's FP4 tensor cores and Apple M5's per-core neural accelerators accelerate the compute-bound prefill 1.7–4× and leave bandwidth-bound decode nearly unchanged.

### Cited Findings
- T-MAC (MIT; EuroSys 2025): decomposes n-bit weights into bit-planes, groups 4 one-bit weights as an index into a 16-entry table of precomputed partial sums (halved with a sign bit), uses tbl/pshuf instead of FMA; supports int1/2/3/4 weights × int8/fp16/fp32 activations; Llama-2-7B W2 on Snapdragon X Elite 28.4 t/s (4 threads), W4 18.7 t/s; Jetson AGX Orin Llama-2-7B W2 12 threads: T-MAC 15.62 t/s vs llama.cpp CPU 7.08 vs llama.cpp GPU 20.03; BitNet-3B on Surface Laptop 7 ≈48 t/s on 4 cores (≈4–5× llama.cpp b2794); prefill Llama-2-7B W2 8 threads 94.4 vs 21.3 t/s **[authors' measurements]** — [T-MAC repo](https://github.com/microsoft/T-MAC); paper: up to 4× throughput and 70% lower energy vs llama.cpp; BitNet-b1.58-3B 30 t/s single core / 71 t/s 8 cores on M2 Ultra, 11 t/s on Raspberry Pi 5 — [T-MAC paper](https://arxiv.org/abs/2407.00088)
- bitnet.cpp LUT kernels TL1/TL2 and I2_S numbers: see KQ1 — [microsoft/BitNet](https://github.com/microsoft/BitNet)
- llama.cpp online repacking (PR #10446, merged Dec 7 2024): Q4_0_N_M/IQ4_0_N_M removed as file types and "allow only with dynamic repack"; repacking lives in the CPU backend's aarch64 extra buffer type (`ggml_backend_cpu_aarch64_buffer_type`), with a general extra-buffer API for "cpu-accel" (AMX, aarch64); debug logs show repacks; no load-time/memory figures given — [llama.cpp PR #10446](https://github.com/ggml-org/llama.cpp/pull/10446); server flag `--repack/--no-repack` ("whether to enable weight repacking", default on) — [llama-server README](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md); a Nov 2025 user report of Q4_K repacking with dotprod: LFM2-8B-A1B Q4_K_M prompt processing 32→85 t/s on ARM (Q4_0 ≈125) **[secondary, Reddit]** — [search result summary](https://redlib.groet-infra.nl/r/LocalLLaMA/comments/1p88mwr/comment/nr3plv5/?context=3)

## Key question 4 — File formats (GGUF, safetensors, MLX folders, ONNX, EXL3) and whether a new engine should define its own layout; tokenizer and chat-template metadata

### Takeaway
GGUF is the only format that bundles weights, quantization block layouts, tokenizer vocab/merges and the Jinja chat template in one 32-byte-aligned, mmap-friendly little-endian file with a documented split-file convention; safetensors is a simpler zero-copy container (8-byte length + JSON header + raw buffer) that carries no tokenizer or quantization semantics, so HF/MLX/EXL3/ONNX models rely on side files (config.json, tokenizer.json, tokenizer_config.json, quantization configs). A new engine should read GGUF and safetensors natively and keep any private cache (e.g. repacked tiles) derived and disposable rather than inventing a third distribution format.

### Cited Findings
- GGUF spec: magic "GGUF" (LE uint32 0x46554747); version 3 (v2 widened counts to uint64, v3 added big-endian); header = magic, version, tensor_count u64, metadata_kv_count u64, then KV pairs; value types UINT8=0 … FLOAT64=12 with ARRAY=9 (typed, nestable) and STRING=8 (u64 length + UTF-8, no terminator); keys ASCII lower_snake_case dotted, ≤65535 bytes; tensor info = name (≤64 bytes), n_dims u32 (≤4), dims u64[], ggml_type u32, offset u64 relative to tensor-data start and a multiple of ALIGNMENT; `general.alignment` u32 (multiple of 8, default 32); padding 0x00; tensor data begins at the first aligned position after the tensor-info array; alignment exists "so that tensors can be memory-mapped"; big-endian files store everything big-endian and are not self-identifying; required `general.architecture`, `general.quantization_version` (if quantized), optional `general.file_type`; tokenizer keys `tokenizer.ggml.{model,tokens,scores,token_type,merges,added_tokens,...}` and `tokenizer.chat_template` (Jinja); shards named `…-00001-of-XXXXX.gguf` — [ggml docs/gguf.md](https://github.com/ggml-org/ggml/blob/master/docs/gguf.md)
- gguf-py constants: split keys `split.no`, `split.count`, `split.tensors.count`; tokenizer keys add `tokenizer.ggml.pre`, `bos/eos/eot/eom/unknown/seperator(sic)/padding/mask_token_id`, `add_bos_token`, `add_eos_token`, `tokenizer.chat_templates` (named templates), FIM ids `fim_{pre,suf,mid,pad,rep,sep}_token_id`; general keys `general.{name,basename,size_label,license,license.name,license.link,uuid,repo_url,base_model.count,base_model.N.*,dataset.*}`; token types NORMAL=1 UNKNOWN=2 CONTROL=3 USER_DEFINED=4 UNUSED=5 BYTE=6; ggml types: F32 0, F16 1, Q4_0 2, Q4_1 3, Q5_0 6, Q5_1 7, Q8_0 8, Q8_1 9, Q2_K 10, Q3_K 11, Q4_K 12, Q5_K 13, Q6_K 14, Q8_K 15, IQ2_XXS 16, IQ2_XS 17, IQ3_XXS 18, IQ1_S 19, IQ4_NL 20, IQ3_S 21, IQ2_S 22, IQ4_XS 23, I8 24, I16 25, I32 26, I64 27, F64 28, IQ1_M 29, BF16 30, TQ1_0 34, TQ2_0 35, MXFP4 39, NVFP4 40, Q1_0 41 (block 128, 18 B = 1.125 bpw), Q2_0 42 (block 64, 18 B = 2.25 bpw); (4,5 = removed Q4_2/Q4_3; 31–33, 36–38 = removed Q4_0_N_M/IQ4_0_N_M); file types `general.file_type`: ALL_F32 0, MOSTLY_F16 1, Q4_0 2, Q4_1 3, Q8_0 7, Q5_0 8, Q5_1 9, Q2_K 10, Q3_K_S/M/L 11–13, Q4_K_S/M 14–15, Q5_K_S/M 16–17, Q6_K 18, IQ2_XXS 19, IQ2_XS 20, Q2_K_S 21, IQ3_XS 22, IQ3_XXS 23, IQ1_S 24, IQ4_NL 25, IQ3_S 26, IQ3_M 27, IQ2_S 28, IQ2_M 29, IQ4_XS 30, IQ1_M 31, BF16 32, TQ1_0 36, TQ2_0 37, MXFP4_MOE 38, NVFP4 39, Q1_0 40, Q2_0 41, GUESSED 1024; GGML_QUANT_SIZES (block, bytes) incl. IQ4_XS (256, 136 — note ggml-common.h's static_assert gives 140), MXFP4 (32, 17), NVFP4 (64, 36) — [gguf-py constants.py](https://github.com/ggml-org/llama.cpp/blob/master/gguf-py/gguf/constants.py)
- safetensors (Apache-2.0): 8-byte LE u64 header size N; N bytes of UTF-8 JSON that must start with `{` and may be space-padded; per tensor `dtype`, `shape`, `data_offsets` [begin,end) relative to the byte buffer; `__metadata__` is a string→string map only; duplicate keys forbidden; every byte of the buffer must belong to a tensor (no polyglots); LE row-major; header limit 100 MB; empty tensors and scalars allowed; sub-byte dtypes exist and unaligned reads error; "zero-copy" is partial (CPU with the file in page cache; GPU always copies; header not zero-copy); lazy loading cut BLOOM's 8-GPU load from 10 min to ≈45 s **[vendor]**; supports bf16 and FP8 — [safetensors README](https://github.com/huggingface/safetensors), [docs](https://huggingface.co/docs/safetensors/index); dtype tags seen in third-party readers include F8_E4M3, F8_E5M2, F8_E8M0 and 4/6-bit floats **[secondary, unverified list]**; sharding uses `model.safetensors.index.json` with `weight_map` {tensor → shard file} and `metadata.total_size` **[secondary: huggingface_hub docstring/search summary]**
- EXL3 on disk: safetensors shards (default 8192 MB), quantized n-gram tables as `ngram_embedding.safetensors`; tensor naming/suffix conventions and the packed trellis layout are not documented ("format description… not yet published") — [convert.md](https://github.com/turboderp-org/exllamav3/blob/master/doc/convert.md), [exl3.md](https://raw.githubusercontent.com/turboderp-org/exllamav3/v1.4.4/doc/exl3.md)

- ONNX Runtime GenAI model builder: precisions int4/int8 (weight-only → `MatMulNBits`), fp16, bf16, fp32 (WebGPU I/O); EPs cpu, cuda, webgpu, TRT-RTX; options `block_size` (example 32; 32/64/128 for QMoE, TRT-RTX also 16/256), `accuracy_level` (example 4), `algo_config` ∈ {default, rtn, k_quant} (legacy aliases rtn_last, k_quant_last, k_quant_mixed, k_quant_linear), `is_symmetric` (int4 vs uint4), `op_types_to_quantize` (MatMul/Gather), `nodes_to_exclude` (e.g. `/lm_head/MatMul`); MTP head written as `mtp.onnx` + `mtp.onnx.data` (external data); architectures include Llama, Mistral, Qwen, Gemma, Phi, DeepSeek, gpt-oss, Granite, LFM2, Nemotron, SmolLM3, Whisper — [onnxruntime-genai model builder README](https://github.com/microsoft/onnxruntime-genai/blob/main/src/python/py/models/README.md)
- Rust precedent: mistral.rs (MIT) loads HF safetensors, GGUF (2–8 bit), GPTQ, AWQ, HQQ, FP8, bitsandbytes, its own UQFF, and performs ISQ (in-situ quantization at load) with per-layer topology; CUDA/Metal/CPU; PagedAttention — [mistral.rs](https://github.com/EricLBuehler/mistral.rs)
- Quantization-quality metadata is not standardized: Unsloth publishes imatrix files and KLD tables out-of-band; localbench computes KLD over top-40 logprobs on chat-templated prompts — [Unsloth 3.0](https://unsloth.ai/docs/basics/dynamic-3.0-ggufs), [localbench](https://localbench.substack.com/p/gguf-benchmark-methodology)

### Inferences
- "Own format vs GGUF/safetensors": every quality-per-byte leader already ships in one of two containers (GGUF for K/I/TQ/MXFP4/NVFP4 quants; safetensors for AWQ/GPTQ/HQQ/EXL3/MLX/NVFP4-compressed-tensors). Defining a third distribution format would add zero quality and cost ecosystem reach; what an engine legitimately owns is a *derived* on-disk cache (repacked/interleaved tiles, precomputed LUTs, split-expert layouts) keyed by content hash, which must be regenerable and deletable.
- Tokenizer/chat-template handling splits by container: GGUF carries vocab, merges, pre-tokenizer id (`tokenizer.ggml.pre`), special-token ids and the Jinja template; safetensors-based folders need `tokenizer.json` (HF tokenizers format) plus `tokenizer_config.json` for the chat template and `config.json` for architecture hyper-parameters — the last three file roles are well known but were not fetched in this pass **[general knowledge, unverified here]**. A Rust engine therefore needs a Jinja-subset renderer in both paths.
- The IQ4_XS size discrepancy (136 bytes in gguf-py vs 140 in ggml-common.h) means an engine must compute block byte sizes from the C struct (the authoritative layout used by the writer), not from the Python table.

### Gaps
- EXL3's packed tensor layout and naming are undocumented; reading it requires studying the ExLlamaV3 loader (MIT) — not done here.
- The exact GPTQ/AWQ/compressed-tensors safetensors conventions (qweight/qzeros/scales/g_idx packing, `quantization_config` in config.json) were not fetched (search budget); they are needed for "read without re-quantizing" and are documented in the GPTQModel/llm-compressor repos.
- Where GGUF stores NVFP4's per-tensor FP32 scale (not visible in the block struct) was not determined.

## Key question 5 — Weight loading and streaming (mmap vs explicit reads, prefetch, "LLM in a flash", SSD streaming, on-demand MoE experts, measured load times and resident memory)

### Takeaway
mmap of an aligned file remains the default and cheapest way to get near-zero load latency and OS-managed residency (llama.cpp `--load-mode auto`, 4–6 s for a 6–9 GiB GGUF on NVMe), but explicit parallel/direct reads into pinned or device memory load 2.6–7.5× faster when the target is a GPU (fastsafetensors), and llama.cpp now adds direct-I/O and lazy on-demand modes; flash streaming only beats DRAM-resident weights when ≥90% of FFN neurons are inactive (ReLU-era models) or when MoE routing makes most experts cold, which is why 2025–2026 practice is "attention/dense on GPU, experts in system RAM" rather than streaming dense weights from SSD.

### Cited Findings
- llama.cpp loading controls: `--load-mode` ∈ {auto (mmap unless a device can't), none, mmap ("without mmap loading is slower but may reduce pageouts if not using mlock"), mlock ("keep model in RAM rather than swapping or compressing"), mmap+mlock, dio (DirectIO if available)}; `--lazy-mode` (default auto: tensors larger than 4 GiB are read from disk on demand instead of kept resident; requires mmap); `--fit` auto-adjusts unset args to device memory with `--fit-target` 1024 MiB margin; `--n-gpu-layers auto`; `--cpu-moe` keeps all MoE expert weights on CPU, `--n-cpu-moe N` for the first N layers, `--override-tensor <regex>=<buffer type>`; KV cache types f32/f16/bf16/q8_0/q4_0/q4_1/iq4_nl/q5_0/q5_1 — [llama-server README](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md); older flags `--mmap/--no-mmap/--mlock` are deprecated in favour of `--load-mode` — [Debian llama-server manpage](https://manpages.debian.org/unstable/llama.cpp-tools/llama-server.1.en.html)
- Measured load times (RTX 5090, Gemma 4 12B, Sep 2026): GGUF IQ4_XS 5.94 GiB 4 s, Q4_K_M 6.63 GiB 4 s, Q5_K_M 7.84 GiB 6 s, Q6_K 9.11 GiB 6 s; EXL3 6.5–9.1 GiB 8–9 s; loaded VRAM = file + ≈1.4 GiB (16k FP16 cache), peak +0.5 GiB — [atomic.chat](https://atomic.chat/blog/guides/exl3-vs-gguf)
- fastsafetensors (IEEE CLOUD 2025, Apache-2.0): 4.8–7.5× faster than the default safetensors deserializer on Llama/Falcon/Bloom; Llama-70B on 4 GPUs with GPU Direct Storage hit 26.4 GB/s NVMe reads; vLLM startup Llama-2-13B 4×L40S 12.39→4.74 s, 1×A100 16.04→6.88 s; on AMD ROCm without GDS: 6.02 GB/s vs 1.28 GB/s mmap (GPT-2 Medium), 2.62 vs 1.01 GB/s (GPT-2) **[measured, authors]** — [fastsafetensors](https://github.com/foundation-model-stack/fastsafetensors), [arXiv 2505.23072](https://arxiv.org/abs/2505.23072)

### Inferences
- For a memory-predictable engine, mmap's weakness is accounting, not speed: file-backed clean pages show up as cache, can be evicted under pressure (causing decode stalls) and are double-counted if the same file is also read into anonymous buffers; mlock (or wiring on macOS) fixes eviction at the cost of hard RSS. A sensible design is mmap+madvise(WILLNEED/SEQUENTIAL) for CPU-resident tensors, explicit direct-I/O reads straight into pinned/device buffers for GPU tensors (the fastsafetensors result), and never both for the same bytes.
- Dense-weight SSD streaming ("LLM in a flash") does not transfer to 2025–2026 SwiGLU models whose FFNs lack the 90–97% ReLU sparsity the method needs; the viable streaming unit today is the MoE expert (routing sparsity is architectural), ideally with llama.cpp-style tensor-pattern placement plus a prefetch/cache layer, and on Apple unified memory the "offload" is simply which tensors are wired vs pageable.
- llama.cpp's new `--lazy-mode` (on-demand reads of >4 GiB tensors, which in practice are stacked expert tensors) is the first mainline step toward expert streaming from disk; measured numbers were not found.

### Gaps
- No fetched source measures resident-memory or cold-load time of mmap vs read vs direct-IO on Apple Silicon for the same GGUF; the llama.cpp docs only state "slower without mmap".
- No 2025–2026 paper on streaming *dense* weights from NVMe for non-ReLU models was found before the search budget ran out; PowerInfer-2/Ripple-style smartphone work (2024) was not reviewed.
- Measured speed of llama.cpp `--lazy-mode` and of `--n-cpu-moe` across GPU sizes is only anecdotal (one Reddit-derived report).

## Key question 6 — Mixed precision: which tensors benefit from higher or lower precision (llama.cpp mixes, Unsloth dynamic quants, EXL3, MLX)

### Takeaway
Every production mix keeps the output head (and often token embeddings) at 6–8 bits, raises attention V (and K for MoE) and FFN-down projections in the first/last eighth of layers plus every third middle layer, keeps norms/1-D tensors unquantized, and quantizes MoE expert FFNs most aggressively (MXFP4 in gpt-oss, lowest I-quants in UD); Unsloth's 2026 data shows that spending +6–8% bytes on the right tensors halves worst-case (max) KLD.

### Cited Findings
- llama.cpp default rules (`llama_tensor_get_type`, master): 1-D tensors/norms are never quantized; `output.weight` → Q6_K by default (Q8_0 for MXFP4_MOE, Falcon, or rows not divisible by the block; Q5_K for IQ1/IQ2/IQ3 file types; stays Q8_0 if base is Q8_0); tied `token_embd` follows the output rule; untied `token_embd` keeps the base type except IQ2_XXS/IQ2_XS/IQ1_* → Q2_K, IQ2_S/IQ2_M/IQ3_XXS → IQ3_S, TQ1_0/TQ2_0/Q2_0 → Q4_K; `attn_v` (also attn_qkv, attn_kv_b): Q4_K_M/Q5_K_M → Q6_K where `use_more_bits(i, n) = i < n/8 || i >= 7n/8 || (i − n/8) % 3 == 2`; Q3_K_M → Q5_K for first two layers then Q4_K; Q3_K_L → Q5_K; Q4_K_S → Q5_K for first four; IQ3_* → Q4_K when n_gqa ≥ 4; IQ1/IQ2 → Q4_K when n_gqa ≥ 4 or n_expert ≥ 4 else Q2_K/IQ3_S; 70B-class → Q3_K/Q4_K attn_v promoted to Q5_K ("8 heads share attn_v"); n_expert == 8 → attn_v and attn_k Q8_0 (Q4_K for IQ types); `attn_output`: Q2_K → Q3_K, Q3_K_M → Q4_K, Q3_K_L → Q5_K, IQ3_XXS → IQ3_S, IQ3_M → Q4_K, IQ1 → IQ2_XXS, IQ2_S/M → IQ3_S, and Q5_K for most types when n_expert == 8; `ffn_down`: Q4_K_M/Q5_K_M → Q6_K where use_more_bits, Q4_K_S → Q5_K for first n/8 layers, Q3_K_M → Q5_K for first n/16 then Q4_K, Q2_K → Q3_K, IQ3_XXS without imatrix → Q4_K for first n/8, IQ1/IQ2 → first n/8 of expert-down tensors to IQ3_S/Q2_K; `ffn_gate/up`: only IQ3_XS downgrades middle layers [n/8, 7n/8) to IQ3_XXS; MXFP4_MOE: 3-D expert tensors → MXFP4, everything else → Q8_0; GLM5-NEXT attn_q_a/q_b/nextn.eh_proj floored at Q8_0; shape fallbacks IQ* → IQ4_NL, Q2_K/Q3_K/TQ → Q4_0, Q4_K → Q5_0, Q5_K → Q5_1, Q6_K → Q8_0, else F16; imatrix required for IQ3_XXS, IQ2_*, IQ1_* (never for token_embd/output); overrides `--pure`, `--output-tensor-type`, `--token-embedding-type`, `--tensor-type <regex>=<type>` — [llama-quant.cpp](https://github.com/ggml-org/llama.cpp/blob/master/src/llama-quant.cpp)
- Origin of the pattern: Q4_K_M "uses Q6_K for half of the attention.wv and feed_forward.w2 tensors"; Q2_K must use Q4_K for attention.wv/attention.wo/feed_forward.w2 or 7B PPL ≈9.0; "all variants use 6-bit quantization for output.weight" **[background 2023]** — [PR #1684](https://github.com/ggml-org/llama.cpp/pull/1684)
- Unsloth: "dynamically adjust the quantization type of every possible layer", combinations differ per layer and model; Dynamic 1.0 was MoE-only, 2.0 covers dense; Q4_K_XL vs Q4_K_M on Gemma 3 27B: +0.23 GB for KLD 0.0237 vs 0.0249 and MMLU 71.47 vs 71.23; Google's QAT Q4_0 (17.2 GB) scores 70.64 vs Unsloth Q4_K_XL (15.64 GB) 71.47 — [Unsloth 2.0](https://unsloth.ai/docs/basics/unsloth-dynamic-2.0-ggufs); Mar 2026 MoE recipe revision: +7.8% bytes → −51% max KLD (UD-Q4_K_XL), +6% → −42% (UD-Q5_K_XL) — [Unsloth Qwen3.5](https://unsloth.ai/docs/models/qwen3.5/gguf-benchmarks); Dynamic 3.0 drops the MTP head below 8.37 GB (−500 MB) — [Unsloth 3.0](https://unsloth.ai/docs/basics/dynamic-3.0-ggufs)
- gpt-oss: only MoE expert weights are MXFP4; attention, router and embeddings stay higher precision (inferred 16-bit from checkpoint size; FuriosaAI's docs state the same boundary **[secondary]**) — [gpt-oss card](https://arxiv.org/html/2508.10925), [Furiosa docs](https://developer.furiosa.ai/latest/en/furiosa_llm/models/gpt-oss.html)
- EXL3: lm_head default 6 bits; token embeddings default unquantized (16-bit, optionally 1–8 bits, rotated+trellis without calibration); `-hq` raises attention and shared-expert bitrates (+0.05–0.10 bpw on MoE); per-tensor recipes from `sc_optimize.py`; "quantizing the output layer can matter a lot, especially for smaller models" — [convert.md](https://github.com/turboderp-org/exllamav3/blob/master/doc/convert.md), [exl3.md](https://raw.githubusercontent.com/turboderp-org/exllamav3/v1.4.4/doc/exl3.md)
- MLX `dynamic_quant`: per-layer sensitivity estimate, default 5 bits for sensitive layers and 4 for the rest, `--target-bpw`; DWQ advice: smaller group size doubles tunable parameters and "can work much better" — [LEARNED_QUANTS.md](https://github.com/ml-explore/mlx-lm/blob/main/mlx_lm/LEARNED_QUANTS.md)
- Per-channel INT8 on Llama-3-70B degrades more than other families; giving <3% of layers finer scaling restores average accuracy **[secondary: search summary of arXiv 2408.15301]** — [arXiv 2408.15301](https://arxiv.org/html/2408.15301v2)
- Unsloth's warning that a text-only (Wikipedia) imatrix is ineffective for instruct models (chat templates) and overfits Wikipedia-based KLD tests — [Unsloth 2.0](https://unsloth.ai/docs/basics/unsloth-dynamic-2.0-ggufs)

### Inferences
- The consistent cross-ecosystem signal is: (1) output head and embeddings are cheap to keep at 6–8 bits (they are 1–3% of a 27B+ model but dominate token-level error); (2) attention V/K projections and FFN-down are the most error-sensitive linear layers, especially in the first and last layers; (3) gate/up projections and MoE experts tolerate the lowest bits; (4) in MoE models, attention is a tiny fraction of bytes and should be kept near 8 bits (llama.cpp's n_expert==8 Q8_0 rule, Unsloth's revised recipes) — a new engine should expose per-tensor type overrides from day one so it can consume UD/EXL3-style recipes rather than hard-code one mix.
- Because mixes are applied by the quantizer, a reader that honours the per-tensor `ggml_type` in GGUF (or per-tensor bits/scales in EXL3/MLX files) automatically gets the mixed precision; the engine only needs every block type's kernel.

### Gaps
- Unsloth does not publish which tensors Dynamic 2.0/3.0 upcasts; the only way to learn a recipe is to dump tensor types from the GGUF (llama-gguf) — not done here.
- No fetched source quantifies the KV-cache quant interaction (q8_0/q4_0 K/V cache) with weight mixes.

## Key question 7 — What a new engine must implement to read existing model files without re-quantizing

### Takeaway
To consume the installed base without re-quantizing, the engine needs (1) a GGUF reader with all 30-odd ggml block types including the I-quant codebooks and the 2025–2026 additions (MXFP4, NVFP4, Q1_0/Q2_0, TQ), (2) a safetensors reader plus the side-file conventions of HF/MLX/compressed-tensors checkpoints, (3) per-tensor type dispatch and an optional load-time repack cache, and (4) a tokenizer/chat-template layer that works from GGUF metadata or HF JSON files; ISQ (quantize at load from bf16 safetensors) is the fallback for formats not worth implementing.

### Cited Findings
- GGUF block layouts, LUTs and grids (ggml-common.h) and type IDs/sizes (constants.py) are listed under KQ1 and KQ4 — [ggml-common.h](https://github.com/ggml-org/ggml/blob/master/src/ggml-common.h), [constants.py](https://github.com/ggml-org/llama.cpp/blob/master/gguf-py/gguf/constants.py)
- Dequantization needs per type: Q4_0/Q5_0/Q8_0 (fp16 d), Q4_1/Q5_1 (d, m), K-quants (d, dmin, packed 4/6/8-bit sub-scales, split low/high bit planes `qs/qh/ql`), IQ2/IQ3 (sign bits + grid index into 256–2048-entry codebooks), IQ1_S/M (2048-entry grid, packed scale `iq1m_scale_t`), IQ4_NL/XS (16-entry non-linear LUT), TQ1_0 (base-3 packing of 5 trits per byte over 48+4 bytes), TQ2_0 (2 bits/weight), MXFP4 (E8M0 uint8 scale + E2M1 LUT), NVFP4 (four UE4M3 sub-scales per 64 + E2M1) — [ggml-common.h](https://github.com/ggml-org/ggml/blob/master/src/ggml-common.h)
- Metadata to honour: `general.alignment`, `general.architecture`, `general.file_type` only as a hint (per-tensor types are authoritative), split keys and shard naming, tokenizer keys incl. `tokenizer.ggml.pre` (pre-tokenizer regex id), `tokenizer.chat_template` / `tokenizer.chat_templates`, FIM token ids — [gguf.md](https://github.com/ggml-org/ggml/blob/master/docs/gguf.md), [constants.py](https://github.com/ggml-org/llama.cpp/blob/master/gguf-py/gguf/constants.py)
- Online repack is part of reading GGUF correctly on Arm: Q4_0 tensors are rearranged into interleaved tiles in the CPU buffer at load (PR #10446), KleidiAI packs to its own int4 layout once at load — [PR #10446](https://github.com/ggml-org/llama.cpp/pull/10446), [Arm repack page](https://learn.arm.com/learning-paths/mobile-graphics-and-gaming/kai_sme2_matmul_ukernel_explained/explain_with_an_example_p1/)
- safetensors reading rules (header, offsets, dtype tags, index.json) — [safetensors README](https://github.com/huggingface/safetensors)
- MLX affine packing contract (uint32 LSB-first, scales + biases per group) — [MLX quantize](https://ml-explore.github.io/mlx/build/html/python/_autosummary/mlx.core.quantize.html)
- NVFP4 HF checkpoints come from NVIDIA ModelOpt (e.g. `NVFP4_DEFAULT_CFG`, nvidia-modelopt 0.43.0) in compressed-tensors form; llama.cpp's converter for them (#21095) was still open, and early conversions dropped the MTP head — [insiderllm](https://insiderllm.com/guides/fp4-inference-llamacpp-nvfp4-mxfp4/)
- ISQ precedent in Rust: mistral.rs quantizes HF weights at load when no prebuilt artifact exists, with per-layer topology — [mistral.rs](https://github.com/EricLBuehler/mistral.rs)
- EXL3 should be produced from original HF weights, never from a GGUF — [atomic.chat](https://atomic.chat/blog/guides/exl3-vs-gguf)
- Validation metric guidance: Unsloth (KLD + top-1 + multi-token divergence on held-out chat data; perplexity "incorrect for this purpose") and localbench (KLD over top-40 logprobs on chat-templated 250k-token mixed corpus with a BF16 GGUF reference) — [Unsloth 3.0](https://unsloth.ai/docs/basics/dynamic-3.0-ggufs), [localbench](https://localbench.substack.com/p/gguf-benchmark-methodology)

### Inferences
- Priority order for kernels, by installed base and quality-per-byte: Q4_K/Q5_K/Q6_K/Q8_0 and Q4_0 (CPU repack path) first; IQ4_XS/IQ4_NL and IQ3_S/IQ3_XXS/IQ2_*/IQ1_* (codebook grids — needed for every UD low-bit file) second; MXFP4 (gpt-oss) and NVFP4 (Blackwell-era uploads) third; TQ1_0/TQ2_0 only if ternary models matter; MLX affine 2/3/4/5/6/8-bit g32/64/128 (Apple ecosystem) in parallel with GGUF; AWQ/GPTQ safetensors packings via ISQ-style conversion into the engine's native 4-bit tile format at load (quality is preserved because the values are already quantized — only re-packing, not re-quantizing).
- A content-hashed, versioned repack cache lets the engine keep GGUF/safetensors as the distribution format while loading as fast as a native layout on subsequent runs; it must be invalidated by kernel version because tile layouts are kernel-specific (KleidiAI vs ggml aarch64 vs AMX).
- Reading EXL3 would require a trellis decoder and Hadamard de-rotation on the fly; given MIT licensing it is legally fine but the format is undocumented and CUDA-only in practice, so it is the lowest-priority input.

### Gaps
- GPTQ/AWQ/compressed-tensors packing conventions and `quantization_config` schema were not fetched (search budget).
- The regex/pre-tokenizer variants behind `tokenizer.ggml.pre` and the Jinja feature subset needed for 2026 chat templates (tool-calling, reasoning blocks) were not researched.
- No source was found that measures the load-time cost of converting AWQ/GPTQ packings to another tile layout.
