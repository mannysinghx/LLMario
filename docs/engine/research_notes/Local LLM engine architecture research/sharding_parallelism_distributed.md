# Model sharding, parallel execution and distributed inference for a local LLM engine (state as of 2026-10-08)

Scope: parallelism strategies that pay off on consumer hardware (8–128 GB, one GPU/NPU plus CPU, or a few machines on a LAN/Thunderbolt), how existing systems implement them, measured results, failure modes, and the scheduling/memory-planning techniques that keep them safe. Written to feed the design of a from-scratch Rust, Apache-2.0 engine for LLMario.

Labelling used below:
- **[measured]** a number the cited source itself measured, with hardware/version stated by the source.
- **[vendor-claimed]** a number published by the project/vendor about itself without an independent rerun.
- **[secondary]** a number relayed by a third party (press, blog) from someone else's test.
- **[unverified]** came only from a search-result summary; the underlying page was not opened in this session.
- **[background]** published before 2025.

Method note: ~70 web fetches/searches. The shared web-search budget ran out part-way through, so some items (marked [unverified] or listed under Gaps) could not be confirmed against the primary page. No fabricated numbers; everything numeric has a URL.

## Key question 1 — Single machine, heterogeneous: TP vs pipeline (layer) vs expert parallelism between one GPU and the CPU, or an iGPU/NPU sharing one memory pool

### Takeaway
On one consumer box the splits that demonstrably pay off are (a) layer offload of dense models (pipeline-style, GPU layers first, remainder on CPU) and (b) *tensor-placement* expert offload for MoE (attention, router and dense FFN on the GPU; routed experts in system RAM), both of which llama.cpp now automates (`-ngl auto`, `-fit on`, `--n-cpu-moe`, `--moe-cache-mib`). No source shows tensor parallelism *between* a CPU and a GPU inside one machine in any mainstream system; every source that explains the MoE split names the per-token CPU↔GPU synchronisation (PCIe round trip) and host memory bandwidth, not CPU compute, as the limiter. Unified-memory parts (Apple Silicon, Strix Halo, DGX Spark) remove the copy but are then purely bandwidth-bound.

### Cited Findings

llama.cpp knobs (as of master, Oct 2026)
- llama-server exposes `-ngl, --gpu-layers` (default `auto`), `-fit, --fit [on|off]` (default `on`) with `--fit-target` (default 1024 MiB per device) and `--fit-ctx` (default 4096) — i.e. the loader itself plans a fit of weights + context into each device's memory minus a headroom target — [llama.cpp tools/server/README.md](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)
- MoE placement flags: `-cmoe, --cpu-moe` (all MoE weights on CPU), `-ncmoe, --n-cpu-moe N` (experts of the first N layers on CPU), `-ncffn, --n-cpu-ffn N` (dense FFN of first N layers on CPU), `--moe-cache-mib N` "GPU cache for CPU-resident experts (default: 0, disabled)", and the general `-ot, --override-tensor` pattern→buffer-type override — [llama.cpp tools/server/README.md](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)
- Explanation of why the split is attention/router on GPU and experts on CPU (gpt-oss-120b: 36 layers, 128 experts/layer, 4 active/token, ~5.1 B active of ~120 B): the always-on parts run every token so stay in VRAM; an offloaded expert receives the token's activation over PCIe, computes on CPU, returns the result; "the bottleneck is PCIe round-trip latency rather than CPU speed"; the right `--n-cpu-moe` must be found by trial — post dated 2025-10-13, no measurements — [SomeOddCodeGuy, DEV](https://dev.to/someoddcodeguy/understanding-moe-offloading-5co6)
- Practical guide for a 125 B MoE (IQ4_XS, ~70–75 GB) on RTX 4090 24 GB + Ryzen 9 7950X + 128 GB DDR5-5600 (2×64 GB, dual channel): `-ngl 99 --n-cpu-moe 40` with `-ot "blk\.(4[0-9])\.ffn_.*_exps\.=CUDA0"` then `-ot "\.ffn_.*_exps\.=CPU"` (rule order matters); tune `--n-cpu-moe` down until VRAM is ~22–23 GB; "RAM bandwidth matters more than CPU core count"; four DIMMs often drop the bus to ≤4800 MT/s so prefer two large sticks; set `-t` to physical cores because extra threads "compete for RAM bandwidth"; prefill is the weak point; no tok/s reported — undated, © 2026 — [viblo.asia guide](https://viblo.asia/p/running-100b-moe-models-on-a-single-rtx-4090-a-practical-guide-to-expert-offloading-with-llamacpp-yZJZlPyZVjm)
- The ggml scheduler's multi-device pipeline parallelism (PR "llama : add pipeline parallelism support", March 2024) helps *batch* work only: 7B F16 on 8×A100 80 GB, pp4096 went 6,277 → 25,504 tok/s with `-ub 256` [measured by author], while tg128 went 74 → 72 tok/s ("Token generation at batch size 1 does not benefit"); it introduced `n_ubatch`, async `llama_decode` and `llama_synchronize`, CUDA-only at first — [background] — [llama.cpp PR #6017](https://github.com/ggml-org/llama.cpp/pull/6017)

ktransformers (CPU/GPU hybrid for MoE)

TP vs PP evidence (cross-device, but the same trade-off applies to any two "devices")
- Hot Interconnects 2025 paper: tensor parallelism "incurs substantial network overhead but delivers superior response times for brief sequences"; pipeline parallelism "minimizes data transfer requirements but increases total latency" — [arXiv 2507.14392](https://arxiv.org/abs/2507.14392)
- Two DGX Sparks over 200 GbE, May 2026 [measured]: PP=2 beat TP=2 by 2.20× at batch 128 for GPT-OSS-120B (554.69 vs 252.01 tok/s) because "TP all-reduces twice per layer, while PP hands off activations once per token", but TP=2 wins at batch 1 across scenarios and in every decode-heavy test — [StorageReview](https://www.storagereview.com/review/nvidia-dgx-spark-cluster-review-distributed-inference-on-dell-gigabyte-and-hp)
- Two DGX Sparks with llama.cpp RPC, Feb 13 2026 [measured]: row split (tensor-style) 19 % faster decode than layer split for Llama 4 Maverick (13.16 vs 11.04 tg256), layer split better for Qwen3-235B (14.57 vs 14.12) — "the best mode depends on the model" — [Classmethod](https://dev.classmethod.jp/en/articles/dgx-spark-two-node-clustering/)

Overlap and sync costs
- llama.cpp CUDA: running the independent Q/K/V projections on concurrent streams (opt-in `GGML_CUDA_GRAPH_OPT=1`) plus default kernel fusion took Qwen3-30B-A3B Q4_K_M tg128 from 246.96 to 352.06 tok/s on RTX 5090 and 198.39 → 271.04 on RTX 4090 [measured, Nov 30 2025]; concurrent streams are single-GPU only and gains taper with context — [llama.cpp discussion #17621](https://github.com/ggml-org/llama.cpp/discussions/17621)
- Over a 10 GbE link the per-token round trip was put at ~0.17 ms and still cost 43–47 % of decode speed (see Q3); the same "sequential and latency-bound" argument applies to PCIe hops inside one machine — [kjaiswal/llama-cpp-distributed-benchmarks](https://github.com/kjaiswal/llama-cpp-distributed-benchmarks)
- CPU threads that spin while a non-CPU backend is busy slow things down; the llama.cpp threadpool reviewer "expected regressions with partial GPU offload" and suggested backing off/yielding after spinning — [background, Aug 2024] — [llama.cpp PR #8672](https://github.com/ggml-org/llama.cpp/pull/8672)
- PowerInfer-2 (smartphone) decomposes matrices into "neuron clusters", runs dense clusters on the NPU and sparse ones on the CPU, pipelines flash I/O with compute, and serves a 47B model at 11.68 tok/s, "up to 27.8×" faster than prior frameworks [vendor-claimed, background, Jun 2024] — [arXiv 2406.06282](https://arxiv.org/abs/2406.06282)

### Inferences
- For LLMario's engine the practical heterogeneous model is **placement, not parallelism**: decide per tensor (not per layer) which device owns it, keep the always-on dense path (embeddings, attention, router, shared experts, norms, lm_head) on the fastest device, and let routed experts and the KV cache spill in that order. llama.cpp's `-ot`/`--n-cpu-moe`/`--moe-cache-mib` and ktransformers' hot/cold expert placement are converging on exactly this.
- Expect decode to be bounded by the slower of (host memory bandwidth for CPU-resident experts) and (PCIe latency per layer hop); plan for one host↔device transfer per layer that has any CPU-resident tensor, and batch the expert activations for all active experts of a layer into one transfer.
- True CPU+GPU tensor parallelism inside one machine would require an all-reduce per layer across PCIe at batch 1 — the evidence from 200 GbE Spark pairs (TP wins only at batch 1 and only with sub-50 µs latency) suggests it is not worth building for a consumer box.
- "Fit" planning before load (llama.cpp `-fit` with a MiB headroom target and an explicit context size) is the simplest effective defence against oversubscription; the engine should compute the plan deterministically from GGUF/safetensors metadata plus the requested context and refuse or re-plan rather than discover OOM at runtime.

### Gaps
- No independently measured tok/s for `--n-cpu-moe` on a discrete-GPU + DDR5 desktop was found (both guides describe the method but report no numbers); the only hard MoE-offload numbers are on unified-memory machines (Strix Halo, DGX Spark).
- No documentation beyond the flag text was found for what `--moe-cache-mib` caches (LRU of hot experts? per-layer?) or how much it helps.
- No source measured CPU/GPU *overlap* during decode in llama.cpp (whether the CPU expert work overlaps the GPU attention of the next layer); ktransformers' "asynchronous CPU-GPU task scheduling" is described only at abstract level.
- NPU use on consumer laptops (Intel/AMD/Qualcomm NPUs, Apple ANE) for LLM decode: nothing credible found; PowerInfer-2's NPU path is a smartphone research system.

## Key question 2 — Multi-process vs multi-thread vs async engine design; crash isolation; sharing weights across processes; what LM Studio, Ollama, llama-server router, vLLM V1 and MLX do

### Takeaway
Every mature local system has converged on a control-plane process plus one engine process per loaded model (Ollama runner subprocess, llama-server router children, LM Studio's llmster daemon with its "Engine Protocol", vLLM's API-server/EngineCore/worker processes talking over ZMQ), while *inside* an engine the inference loop is a single dedicated thread fed by a queue (llama-server) or a busy loop (vLLM EngineCore) with HTTP/tokenisation on other threads. Weight sharing across processes happens implicitly through the OS page cache when weights are mmapped; no system examined does zero-copy activation passing between processes, and MLX adds a constraint that generation streams are thread-bound.

### Cited Findings

vLLM V1
- V1 (Jan 27 2025) "isolated EngineCore loop that handles only the scheduler and model executor"; tokenisation, multimodal processing, detokenisation and streaming overlap with it; for TP the scheduler and Worker 0 run in separate processes and workers receive only per-step diffs; up to 1.7× throughput over V0 — [vLLM V1 alpha blog](https://vllm.ai/blog/2025-01-27-v1-alpha-release)
- Current architecture: API server process(es) ↔ engine cores over ZMQ in a many-to-many topology; "1 engine core process per data parallel rank" running "a busy loop that continuously schedules requests and dispatches work to the GPU workers"; "Each GPU is managed by a dedicated worker process"; e.g. `-tp 2 -dp 4` on 8 GPUs = 4 API servers + 4 engine cores + 8 workers + 1 DP coordinator = 17 processes — [vLLM arch overview](https://docs.vllm.ai/en/latest/design/arch_overview/)

llama-server (single-model and router modes)
- Single-model mode: `server_context` runs on **one dedicated inference thread**; each HTTP request gets its own cpp-httplib worker thread that does JSON parsing, chat templating and tokenisation; `server_queue` (tasks in) and `server_response` (results out) are the thread-safe hand-offs; all active slots are merged into one `llama_batch` per `update_slots()` and `llama_decode` is "the main computational bottleneck" — [llama.cpp tools/server/README-dev.md](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README-dev.md)
- Router mode: `server_models` "manages backend instances"; children **are separate processes** spawned with `subprocess`; the router reads the child's combined stdout/stderr, state updates arrive as `cmd_child_to_router:state:` JSON lines, stop is `cmd_router_to_child:exit` then force-kill after `DEFAULT_STOP_TIMEOUT`; model downloads also run in a child (`SERVER_CHILD_MODE_DOWNLOAD`); streaming routes are proxied via a `conv_id -> child` map; sleep mode frees a child's `llama_context`/`mtmd_context` after idle and any request wakes it; **no eviction/LRU policy is described** — [llama.cpp tools/server/README-dev.md](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README-dev.md)
- Router flags: `--models-dir PATH` (default disabled), `--models-preset PATH` (INI presets), `--models-max N` "maximum number of models to load simultaneously (default: 4, 0 = unlimited)", `--models-autoload` (default enabled), `--sleep-idle-seconds` (default -1 = disabled), `/props` reports `is_sleeping`; `/metrics` needs `?model=` in router mode — [llama.cpp tools/server/README.md](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)
- A third-party guide's comparison table labels router mode "Single process" versus llama-swap's "one process per model" — this **contradicts** README-dev; treat the README-dev description as authoritative. Same guide estimates a 7B Q5 reload at 3–10 s depending on disk and VRAM bandwidth [unverified estimate] — [glukhov.org router-mode article](https://glukhov.org/llm-hosting/llama-cpp/llama-server-router-mode/)

Ollama
- "The default is 3 * the number of GPUs or 3 for CPU inference" for `OLLAMA_MAX_LOADED_MODELS`; `OLLAMA_NUM_PARALLEL` default 1 (auto-enabled when memory allows); `OLLAMA_MAX_QUEUE` default 512, excess rejected, overloaded server returns 503; models unload after 5 minutes idle by default (`keep_alive`, negative = forever, 0 = unload after response); "As prior models become idle, one or more will be unloaded to make room for the new model"; for concurrent loading "new models must fully fit in VRAM"; `ollama ps` shows a CPU/GPU split such as "48%/52%" when partly in system RAM — [Ollama FAQ](https://docs.ollama.com/faq)
- Per-model runner subprocess: the `ollama` binary is re-launched as a child runner per resident model; the scheduler's `findRunnerToUnload` picks a runner and zeroes its expiry so it unloads immediately; pending requests are re-queued while loads finish — [Ollama server/sched.go @0.9.0 (jsDelivr mirror)](https://cdn.jsdelivr.net/gh/ollama/ollama@0.9.0/server/sched.go) [unverified — described in a search summary; file not opened]

LM Studio
- 0.4.0 (blog) redesigned the app so the interface is separate from the core and `llmster` (the daemon) can run on its own/headless — [LM Studio 0.4.0 blog](https://www.lmstudio.ai/blog/0.4.0); [headless docs](https://lmstudio.ai/docs/developer/core/headless)
- "LM Studio Engine Protocol": enabled by default for supported llama.cpp models in 0.4.17 Build 1 (Jun 26 2026), switched off by default in 0.4.17 Build 4, defaulted ON again in 0.4.19 (Jul 7 2026, Build 2 stable); 0.4.24 (Sep 9 2026) added llama.cpp argument overrides through it. The changelog **does not** say the protocol isolates the engine in a separate process — [LM Studio changelog](https://lmstudio.ai/changelog/lmstudio)
- JIT loading is on by default; JIT-loaded models get a 60-minute idle TTL (per-request `ttl` seconds overrides; `lms load` has no TTL unless `--ttl`); Auto-Evict (default on) unloads previously JIT-loaded models before loading a new one, so at most one JIT model stays resident — [LM Studio TTL and Auto-Evict docs](https://lmstudio.ai/docs/app/api/ttl-and-auto-evict)
- Bug report (0.4.12, Windows): a `SystemResourcesObserver` child process failing at launch coincided with models failing to load on CUDA, Vulkan and CPU, i.e. a separate helper process did not by itself contain the failure — [lmstudio-bug-tracker #1860](https://github.com/lmstudio-ai/lmstudio-bug-tracker/issues/1860) [unverified]

MLX / mlx-lm
- MLX generation streams are thread-local; vllm-mlx "rebinds them at worker-entry boundaries as a correctness guard" — [vllm-mlx continuous batching guide](https://vllm-mlx.is-a.dev/guides/continuous-batching/)
- `mlx_lm.server` is "not recommended for production as it only implements basic security checks"; "The server processes requests one at a time when you set `--kv-bits`" and "A quantized KV cache does not support batching"; a `draft_model` can be set per request (`null` unloads it) — [mlx-lm SERVER.md](https://github.com/ml-explore/mlx-lm/blob/main/mlx_lm/SERVER.md)
- mlx-lm wires model and cache memory on macOS ≥15; if a model exceeds the wired limit it prints a warning and "will likely be slow"; fix is `sudo sysctl iogpu.wired_limit_mb=N` — [mlx-lm README](https://github.com/ml-explore/mlx-lm/blob/main/README.md)

Weight sharing via mmap
- prima.cpp (built on llama.cpp) memory-maps weights and loads on demand; "The OS can evict pages under pressure"; prefetching preloads upcoming layers — [arXiv 2504.08791v2](https://arxiv.org/html/2504.08791v2)
- The llama.cpp RPC server keeps a local tensor cache (`$HOME/.cache/llama.cpp/rpc`, `LLAMA_CACHE`) so weights are not re-sent over the network on each load — [llama.cpp tools/rpc/README.md](https://github.com/ggml-org/llama.cpp/blob/master/tools/rpc/README.md)

Host-side overhead and overlap scheduling
- SGLang v0.4 (Dec 2024, background): in an unoptimised engine host-side batching/allocation/prefix matching "can consume up to half the runtime"; preparing the next batch on the CPU while the GPU runs the current one gave ~1.1× throughput; Nsight showed no idle GPU time across five decode batches — [LMSYS SGLang v0.4 blog](https://www.lmsys.org/blog/2024-12-04-sglang-v0-4)
- TensorRT-LLM's equivalent overlap scheduler costs "one extra decoding step" of latency — [TensorRT-LLM docs](https://nvidia.github.io/TensorRT-LLM/latest/features/overlap-scheduler.html)

### Inferences
- A supervisor process (LLMario already has one) plus **one engine process per loaded model** is the pattern with the most operational evidence: it gives crash isolation per model, lets the supervisor enforce memory budgets by killing/sleeping children (llama-server's `cmd_router_to_child:exit` + force-kill timeout is a good template), and keeps GPU-driver faults from taking down the API.
- Inside the engine, a single inference thread with lock-free/queue hand-offs (llama-server) is simpler and no slower than multi-threaded dispatch, because `decode` is one serialised GPU/CPU graph anyway; use a thread pool only for the CPU compute backend, HTTP, tokenisation and detokenisation.
- Cross-process weight sharing comes for free if the engine mmaps files read-only and does not `mlock` more than one copy; wiring (Metal) and `mlock` defeat sharing, so a supervisor that runs two engines on the same GGUF should wire at most one.
- Zero-copy IPC of activations is not needed for the per-model-process design (activations never cross processes); it would only matter for a multi-process tensor-parallel design, which Q1/Q3 argue against.

### Gaps
- No official statement from LM Studio on whether "Engine Protocol" runs the llama.cpp engine out-of-process; all we have is release-note wording.
- The llama-server router's behaviour when `--models-max` is reached (which child is unloaded) is not documented in the README text retrieved; the README-dev describes only idle sleep.
- No source documents vLLM's recovery behaviour when an EngineCore or worker process dies (whether the API server restarts it); treat as unknown.
- No zero-copy shared-memory (e.g. `memfd`/`shm`/IOSurface) design for inter-process tensors was found in any local inference system.

## Key question 3 — Multi-device on a LAN or Thunderbolt: llama.cpp RPC, exo, prima.cpp, Cake, distributed-llama, Petals, MLX distributed/JACCL, DGX Spark pairs; measured tokens/s; build-in now or design an interface

### Takeaway
Across every measured cluster, splitting a model over a network is a **capacity** win, not a speed win, at batch 1: pipeline (layer) splits never speed decode and usually cost 10–50 %, tensor parallelism only beats a single node when the link latency is tens of microseconds (RDMA over Thunderbolt 5 / 200 GbE) and even then yields ~1.5–1.7× on four Mac Studios; llama.cpp RPC is explicitly "proof of concept… fragile and insecure". The systems that *do* win on consumer hardware (prima.cpp) win by memory-aware placement and prefetch that avoid swapping, not by raw parallelism. Design a device/transport interface now (local devices and remote devices behind the same abstraction, as ggml does), but do not build multi-machine execution into v1.

### Cited Findings

llama.cpp RPC
- `rpc-server` exposes a host's ggml devices over TCP; the main host "distributes model weights and the KV cache across all available devices" proportional to memory (override with `--tensor-split`); the backend is "a proof of concept… fragile and insecure", "Never run the RPC server on an open network"; RDMA is negotiated at handshake (RoCEv2 via libibverbs on Linux; RDMA over Thunderbolt 5 on macOS 26.2+), `GGML_RPC_NO_RDMA` forces TCP; local tensor cache `-c` — [llama.cpp tools/rpc/README.md](https://github.com/ggml-org/llama.cpp/blob/master/tools/rpc/README.md)

- Petals: MIT; volunteer swarm; "up to ~6 tokens/sec" Llama 2 70B and ~4 tok/s Falcon 180B [vendor-claimed]; Llama 3.1 up to 405B, Mixtral 8x22B, Falcon, BLOOM; no release/commit date visible on the README page — [bigscience-workshop/petals](https://github.com/bigscience-workshop/petals)

### Inferences
- Bandwidth is rarely the limiter for decode; latency is. 9.4 Gbps USB4, 10 GbE and 200 GbE all showed flat-to-negative decode scaling with pipeline splits; the only positive decode scaling (exo TP over RDMA) needed <50 µs latency and still lost ~40 % per added node to sync.
- The interface worth designing now: a `Device` trait with memory capacity, bandwidth and *latency* descriptors, and a `Transport` trait with send/recv of tensors plus an optional all-reduce; local CPU/GPU, RPC-over-TCP and later RDMA can all sit behind it. ggml's RPC backend and MLX's `mx.distributed` (no-op at group size 1) are the two reference shapes.
- A memory-aware layer assignment with disk prefetch (prima.cpp's Halda) is the piece most relevant to "no memory blow-ups" even on a single machine: it chooses what to keep resident versus stream from disk under a hard budget, and the ablation (755 vs 674 ms) shows prefetch alone is a small win while the assignment itself is a 30× win (20,848 → 674 ms).
- Cake's licence rules it out as a dependency; distributed-llama (MIT) and prima.cpp (MIT) are the two permissively licensed references for TP and PRP respectively; llama.cpp RPC (MIT) is the simplest to interoperate with.

- No primary written source for Geerling's exact tok/s values (only a video and two secondary articles).
- No clean single-node vs two-node comparison in StorageReview's Spark review, and its tables disagree with its text by ~2×.
- No measured RDMA-over-Thunderbolt numbers for llama.cpp RPC itself (RPC README documents the feature; tests found used exo/MLX).
- No measurements for Cake; no current maintenance status for Petals.
- Nothing credible on Windows/Linux consumer clusters over Thunderbolt-networking other than the Strix Halo pair.

## Key question 4 — Request scheduling: continuous batching, chunked prefill, interleaving, priority/fairness, admission under a memory budget, preemption and KV swap/recompute, multiple models with LRU, bounding worst-case memory; what vLLM V1, SGLang, llama-server and mlx-lm do

### Takeaway
All four servers batch at token granularity with a per-step token budget (vLLM V1's `{request_id: num_tokens}` schedule, SGLang's chunked prefill, llama-server's single shared `llama_batch` across slots), reserve KV memory up front from a static plan (vLLM profiling run / `--kv-cache-memory`, SGLang `--mem-fraction-static`, llama.cpp `-fit` with `--fit-ctx`), and when KV runs out they **recompute** rather than swap (vLLM V1 removed GPU↔CPU KV swapping; SGLang "retracts" requests). Multi-model residency is handled by count caps plus idle timers (Ollama 3/GPU and 5 min; LM Studio 60-min TTL + auto-evict; llama-server `--models-max 4` + sleep), not by a memory-aware LRU.

### Cited Findings

vLLM V1
- Scheduler "does not distinguish prefill from decode"; a step is a dict `{request_id: num_tokens}` under a fixed token budget; chunked prefill falls out of this; prefix caching is on by default because overhead is "under 1% throughput loss at a 0% hit rate" — [vLLM V1 alpha blog](https://vllm.ai/blog/2025-01-27-v1-alpha-release)
- "in V1 the default preemption mode is `RECOMPUTE` rather than `SWAP`, because recomputation has lower overhead"; mitigations are raising `gpu_memory_utilization`, lowering `max_num_seqs`/`max_num_batched_tokens`, or more TP/PP; KV cache is sized by a startup measurement unless `--kv-cache-memory` is given (which "skips the memory-profiling measurement and the CUDA-graph memory estimation pass"); chunked prefill "enabled by default whenever possible" and the scheduler "batches all pending decode requests before scheduling any prefill operations"; guidance: `max_num_batched_tokens` ≈2048 favours inter-token latency, >8192 favours throughput; with chunked prefill disabled `max_num_batched_tokens` must exceed `max_model_len` or startup may crash — [vLLM optimization docs](https://docs.vllm.ai/en/latest/configuration/optimization/)
- V1 removed "GPU <> CPU KV Cache Swapping" ("no longer needed for request preemption"), `best_of`, per-request logits processors; supports prefix caching, chunked prefill, spec decode, LoRA, FP8 KV; priority scheduling via `--scheduling-policy` (FCFS or priority); "Concurrent partial prefills" in progress — [vLLM V1 guide](https://docs.vllm.ai/en/latest/usage/v1_guide/)

SGLang
- Overlap scheduler (Dec 2024, background): CPU plans batch N+1 while GPU runs N, ~1.1× — [LMSYS SGLang v0.4](https://www.lmsys.org/blog/2024-12-04-sglang-v0-4)
- Tuning knobs: `--schedule-policy lpm` (longest-prefix-match reordering for cache hits, adds overhead); `--schedule-conservativeness` — lower to ~0.3 if token usage <0.9 while the queue is non-empty (requests that set large `max_new_tokens` but stop early), raise to ~1.3 if "KV cache pool is full. Retract requests." warnings are frequent; "Occasional retraction, roughly once a minute, is acceptable"; `--mem-fraction-static` (weights + KV pool; leave ~5–8 GB for activations; raise in 0.01 steps until OOM); `--max-running-requests` (lower on decode OOM); `--chunked-prefill-size` (lower to 4096/2048 on prefill OOM); `--cuda-graph-max-bs-decode` (graphs typically for batches <160–256) — [SGLang hyperparameter tuning](https://docs.sglang.io/advanced_features/hyperparameter_tuning.html)
- Pipeline-parallel docs: fixed-size chunks leave pipeline bubbles that worsen with depth, motivating dynamic chunking; start near 4K tokens — [SGLang pipeline parallelism](https://docs.sglang.io/advanced_features/pipeline_parallelism.html)
- NGRAM speculation "disables the overlap scheduler and mixed chunked prefill" — [SGLang speculative decoding](https://docs.sglang.io/advanced_features/speculative_decoding.html)

llama-server (slots)
- `-np, --parallel N` (default -1 = auto); `-kvu, --kv-unified` "single shared KV buffer", default enabled when slots are auto; `-cb, --cont-batching` enabled by default; `--cache-prompt` on by default (request `cache_prompt` defaults true); `--cache-reuse N` (KV shifting for partial prefix reuse, default 0); `--slot-save-path` for `POST /slots/{id}?action=save|restore|erase`; `--context-shift` **disabled** by default; `-sps, --slot-prompt-similarity` default 0.10 (slot selection by prompt similarity); `--cache-ram N` default 8192 MiB with `--cache-idle-slots` on by default (idle slots' KV kept in host RAM); `GET /slots` on by default, `?fail_on_no_slot=1` → 503; `-fit on`, `--fit-target 1024` MiB, `--fit-ctx 4096` — [llama.cpp tools/server/README.md](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)
- One `llama_batch` shared by all slots; slots can batch together only with compatible config (same LoRA); `llama_decode` is the bottleneck; heavy post-processing must stay off the inference thread "since that work affects multi-sequence throughput" — [llama.cpp tools/server/README-dev.md](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README-dev.md)
- Issue reports four slots being created even with `-np 1`, with a log hinting `-kvu` semantics inverted — [llama.cpp issue #17989](https://github.com/ggml-org/llama.cpp/issues/17989) [unverified]
- A third-party Sep 2026 comparison states continuous batching is on by default and `--no-cont-batching` disables it — [cohorte.co](https://cohorte.co/blog/local-llm-openai-compatible-server) [unverified]

Ollama / LM Studio (multi-model residency)
- `OLLAMA_MAX_LOADED_MODELS` 3×GPUs; `OLLAMA_NUM_PARALLEL` 1 (auto when memory allows; "a 2K context with 4 parallel requests will result in an 8K context"); `OLLAMA_MAX_QUEUE` 512 then rejection/503; 5-minute idle unload; idle models evicted to make room — [Ollama FAQ](https://docs.ollama.com/faq)
- LM Studio: JIT load, 60-minute TTL, Auto-Evict on by default (one JIT model resident) — [LM Studio TTL docs](https://lmstudio.ai/docs/app/api/ttl-and-auto-evict)
- llama-server: `--models-max` default 4; `--sleep-idle-seconds` frees a child's contexts after idle — [llama.cpp tools/server/README.md](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md), [README-dev](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README-dev.md)

mlx-lm and MLX-based servers
- `mlx_lm.server`: one request at a time with `--kv-bits`; quantized KV "does not support batching"; quantized-cache attention keeps a `prefill_step_size × context_length` score matrix, so reduce `--prefill-step-size` (default 2048 per README) if that exceeds the memory the quantized cache saves; rotating KV cache via `--max-kv-size`; prompt cache files via `mlx_lm.cache_prompt` — [mlx-lm SERVER.md](https://github.com/ml-explore/mlx-lm/blob/main/mlx_lm/SERVER.md), [mlx-lm README](https://github.com/ml-explore/mlx-lm/blob/main/README.md)
- vllm-mlx (third-party, built on mlx-lm's BatchGenerator) on M4 Max 128 GB [measured, undated]: single → 5 concurrent: Qwen3-0.6B-8bit 328.1 → 1,111.8 tok/s (3.39×); Qwen3-30B-A3B-4bit 98.1 → 233.3 (2.38×); Llama-3.2-3B-4bit 137.6 → 208.1 (1.51×); default "simple" mode is one request at a time; paged KV blocks with ref-counted shared system-prompt blocks ("80%+" savings at 10+ users, claimed) — [vllm-mlx continuous batching](https://vllm-mlx.is-a.dev/guides/continuous-batching/)
- oMLX advertises 4.14× generation throughput at 8 parallel requests [vendor-claimed] — [omlx.ai](https://omlx.ai)

Memory planning before load
- llama.cpp: `-fit` plans weights + `--fit-ctx` context per device minus `--fit-target` headroom (defaults on / 4096 / 1024 MiB) — [llama.cpp tools/server/README.md](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)
- Ollama: GPU loads are all-or-nothing per model for concurrency; partial CPU/GPU splits are reported by `ollama ps` — [Ollama FAQ](https://docs.ollama.com/faq)
- mlx-lm wires model + cache memory and warns when the model exceeds the wired limit — [mlx-lm README](https://github.com/ml-explore/mlx-lm/blob/main/README.md)
- prima.cpp's Halda solves the placement as an ILP under per-device memory limits before running — [arXiv 2504.08791v2](https://arxiv.org/html/2504.08791v2)

### Inferences
- A local engine serving one to a handful of clients should use llama-server's shape (N slots, one unified KV pool, one batch per step) with vLLM-V1-style token budgeting: decode tokens first, then fill the remaining budget with prefill chunks; this bounds per-step latency and memory simultaneously.
- Preempt by recompute, not swap: on consumer GPUs the host copy path is PCIe-bound and both vLLM V1 and SGLang chose recompute/retraction; the only "swap" worth keeping is llama-server's `--cache-ram` idea (park *idle* slots' KV in host RAM so a returning conversation avoids re-prefill).
- Admission control needs a conservativeness knob because clients routinely over-declare `max_tokens`; SGLang's guidance (allow a retraction roughly once a minute) is a usable SLO.
- Worst-case memory is bounded only if (weights + KV for `slots × ctx` + compute buffers + draft/MTP overhead + headroom) is computed from metadata before load; llama.cpp's `-fit` defaults (4096 ctx, 1 GiB headroom) are a reasonable starting policy, but the headroom must scale with OS behaviour (macOS wired limit, Windows WDDM fallback — see Q7).
- Multi-model residency should be budget-based (sum of planned footprints ≤ budget) with idle TTL and explicit sleep (free contexts, keep process) before kill; none of the surveyed systems does memory-aware LRU, which is an opportunity rather than a proven pattern.

### Gaps
- vLLM docs retrieved do not state defaults for `gpu_memory_utilization`, `max_num_seqs` or `max_num_batched_tokens`; SGLang docs do not state defaults for `--schedule-conservativeness` or `--chunked-prefill-size`.
- No source describes a fairness policy (per-client token share) in any local server; vLLM and SGLang offer only FCFS/priority or prefix-match ordering.
- Whether `mlx_lm.server` itself (as opposed to vllm-mlx/oMLX) batches concurrent requests when `--kv-bits` is unset is not stated in SERVER.md.
- Eviction order when llama-server's `--models-max` is hit is undocumented.

## Key question 5 — Speculative decoding on consumer hardware: draft models, EAGLE-3, Medusa, shipped MTP heads (DeepSeek V3, Qwen3-Next, GLM-4.5/4.6, MiniMax M2), n-gram/prompt lookup, suffix decoding, LayerSkip; measured batch-1 speedups on Apple Silicon and RTX; memory cost; engine support

### Takeaway
At batch 1 on consumer hardware the methods that pay off are **model-shipped MTP heads** and **small purpose-trained drafters (DFlash2/EAGLE-3)** on *dense* targets with predictable outputs (code/reasoning: +50–90 %, up to 3.4× on M3 Ultra with new Metal kernels), and **free n-gram/suffix lookup** on repetitive agentic workloads; classic separate draft models often *lose* (−30 % on RTX 3090), MoE targets with ~3 B active parameters gained nothing in llama.cpp, and on Apple Metal MTP was a net slowdown (−12 to −45 %) until llama.cpp b11404's few-row kernels landed (Oct 2026). Memory cost ranges from zero (n-gram) through a few hundred MB plus ~0.5 GB compute buffer (MTP head) to 1–7 GB (draft model); vLLM's MTP path could not even start on a 24 GB card.

### Cited Findings

What ships with models
- DeepSeek-V3 [background, Dec 2024]: MTP depth D=1, module = projection + one Transformer block, sharing the main model's embedding and output head; "the acceptance rate of the second token prediction ranges between 85% and 90%", "delivering 1.8 times TPS"; the MTP module can be discarded at inference — [DeepSeek-V3 technical report](https://arxiv.org/html/2412.19437v1)
- Qwen3-Next-80B-A3B (80 B total / 3 B active, 512 experts, 10 routed + 1 shared, hybrid Gated DeltaNet + gated attention): ships native MTP; MTP not available in Transformers; SGLang ≥0.5.2 `--speculative-algo NEXTN --speculative-num-steps 3 --speculative-eagle-topk 1 --speculative-num-draft-tokens 4`; vLLM ≥0.10.2 `--speculative-config '{"method":"qwen3_next_mtp","num_speculative_tokens":2}'`; no acceptance figures on the card — [Qwen3-Next model card](https://huggingface.co/Qwen/Qwen3-Next-80B-A3B-Instruct)
- MiniMax-M2 (230 B total / 10 B active, modified-MIT tag): card makes **no** mention of MTP or speculative decoding — [MiniMax-M2 model card](https://huggingface.co/MiniMaxAI/MiniMax-M2)

### Inferences
- For a Rust engine the highest-value, lowest-risk order is: (1) n-gram/suffix lookup (zero weights, zero licence issues, big wins on agentic/code loops, must be able to disable itself when acceptance <~30 % because it cost −17 % tg in the long-context test), (2) model-shipped MTP heads (Qwen3.5/3.6/Next, DeepSeek, GLM) with a cap of 2–3 draft tokens, (3) DFlash2/EAGLE-3 drafters from SpecForge/SpecBundle for dense targets, (4) classic draft models only as an opt-in.
- The verification step is the engineering crux on Apple Silicon: speculative decoding is a small-M (2–16 row) GEMM problem, and until the backend has few-row kernels it will lose; budget for this kernel work before promising speedups on Metal.
- Correctness guardrails are needed: the M4 Pro divergence at depth 3 and the RTX 3090 study's 76–100 % divergence from greedy show that implementations drift; the engine should carry a test that spec-decode under greedy sampling reproduces the serial token stream.
- MoE targets with tiny active parameter counts (≈3 B) are poor speculation targets in llama.cpp today; the engine's auto-policy should default speculation off for them unless measured otherwise.
- Memory planning must include the drafter/MTP footprint and the wider verification compute buffers (observed ~0.5 GB), and must detect duplicated embeddings/output projections that made vLLM's MTP unloadable on 24 GB.

## Key question 6 — Parallelism inside one forward pass: operator-level parallelism, MoE experts across cores, overlapping attention and MLP, CUDA graphs / Metal command buffers to cut launch overhead, thread/stream models that avoid oversubscription

### Takeaway
At batch 1 the forward pass is memory-bound and dominated by launch/sync overhead, so the wins that are measured are: kernel fusion plus concurrent streams for independent branches (Q/K/V) — +17 to +43 % tg on RTX 4090/5090 for MoE models; CUDA graphs — up to 1.2× on small models with the remaining ~10 % in CPU-side graph build and sampling; and persistent thread pools that avoid thread start/stop per token — +20–35 % on small CPU models. Oversubscription is avoided by not spinning CPU threads while the GPU owns the step, keeping thread count ≤ physical P-cores, and limiting concurrent streams to a single GPU; MLX shows the same overlap is possible across CPU and GPU streams in unified memory.

### Cited Findings
- llama.cpp CUDA token-generation work (Nov 30 2025): default fusions (GEMV + preceding ADD + gated activation; fused softmax+top-k for MoE routing; RMSNorm+MUL(+ADD); adds; softcap) and opt-in concurrent streams for Q/K/V projections (`GGML_CUDA_GRAPH_OPT=1`, "nothing to do with CUDA Graphs"); race hazard because the ggml graph allocator reuses buffers as soon as they expire, mitigated by interleaving nodes to extend lifetimes (proper fix planned in PR #16991); llama-bench tg128 `-fa 1` [measured]: RTX 5090 Qwen3-30B-A3B Q4_K_M 246.96 → 352.06, gpt-oss-20B MXFP4 329.23 → 419.14 (~80 % of a ~520 tok/s speed-of-light); RTX 4090 198.39 → 271.04 and 232.05 → 271.99; no single PR >10 %; single-GPU only; gains taper with context and are smaller at low bandwidth; a GX10 (GB10) user saw tg128 drop 61.8 → 54.8 with GRAPH_OPT=1 on Nemotron-3-Nano-30B-A3B (Jan 17 2026) — [llama.cpp discussion #17621](https://github.com/ggml-org/llama.cpp/discussions/17621)
- CUDA graphs in ggml [background, Aug 7 2024]: per-token graph capture/instantiate reused across tokens with `cudaGraphExecUpdate` and manual KV-position parameter patching; batch-size-1 only, enabled by default on NVIDIA; best case 1.2× (Llama 7B on H100), gains grow as models shrink and GPUs get faster; remaining idle time is CPU-side ggml graph build and sampling (~10 % more available) — [NVIDIA developer blog](https://developer.nvidia.com/blog/optimizing-llama-cpp-ai-inference-with-cuda-graphs)
- PR #26802 (Aug 11 2026) relaxed an over-broad rule that disabled CUDA graphs for MoE models with unquantized experts: ~13 % for parallel decoding on a quantized MoE, ~5 % for bf16 MoE at batch 1 — [TurinTech write-up](https://www.turintech.ai/blog/inside-llama-cpp-pr-26802) [secondary, unverified against the PR]
- vLLM V1 introduced piecewise CUDA graphs with torch.compile (details deferred to a later post) — [vLLM V1 blog](https://vllm.ai/blog/2025-01-27-v1-alpha-release); SGLang uses CUDA graphs for decode batches below `--cuda-graph-max-bs-decode` (typically <160–256), trading memory — [SGLang tuning docs](https://docs.sglang.io/advanced_features/hyperparameter_tuning.html)
- Threadpool (PR #8672, merged Aug 29 2024, background): persistent pools with per-pool thread count, CPU mask, strict placement, polling vs interrupt wait and priority; separate pools for batch and single-token phases; default thread count now excludes E-cores and hyperthread siblings; M2 Max llama-v2-115m Q4_0 4 threads tg 818 → 1,004 t/s, Snapdragon X-Elite 744 → 1,007 [measured]; cautions: spinning threads slow things when a non-CPU backend is busy (BLAS, partial GPU offload) and "interfere with core boosting" — [llama.cpp PR #8672](https://github.com/ggml-org/llama.cpp/pull/8672)
- Batch pipelining across devices: `n_ubatch` micro-batches, async `llama_decode`, event-based sync, `LLAMA_SCHED_MAX_COPIES` graph copies — 4× prompt throughput on 8 GPUs, nothing at batch 1 [background] — [llama.cpp PR #6017](https://github.com/ggml-org/llama.cpp/pull/6017)
- MLX: independent ops on CPU and GPU streams run concurrently with automatic cross-stream dependencies; GPU for "compute dense", CPU for ops that "would probably be overhead bound on the GPU"; 1.4 ms vs 2.8 ms on M1 Max — [MLX unified memory docs](https://ml-explore.github.io/mlx/build/html/usage/unified_memory.html); `MLX_METAL_FAST_SYNCH=1` lowers CPU-GPU sync latency but can deadlock/wedge the GPU — [MLX distributed docs](https://ml-explore.github.io/mlx/build/html/usage/distributed.html)
- Metal small-M GEMM: b11404's few-row kernels (2–16 rows) share weight reads across activation rows and turned speculative verification from a loss into a 3.4× win on M3 Ultra — [rohitai.com](https://rohitai.com/blog/llama-cpp-b11404-metal-few-row-mma-speculative-decoding)
- MoE on CPU: ktransformers' AMX-specialised kernels, NUMA-aware memory and "Expert Deferral" (overlapping deferred expert work with GPU) lift CPU utilisation from <75 % to ~100 % for +1.45× — [MADSys SOSP 2025 page](https://madsys.cs.tsinghua.edu.cn/publication/ktransformers-unleashing-the-full-potential-of-cpu/gpu-hybrid-inference-for-moe-models/)
- Bandwidth ceilings as a sanity check: a DGX Spark (GB10) user measured ~86 tg32 tok/s for gpt-oss-20B against an estimated 79–86 bandwidth ceiling; ~560 tok/s estimated ceiling for RTX 5090 — [llama.cpp discussion #17621](https://github.com/ggml-org/llama.cpp/discussions/17621)
- Thread count vs bandwidth: four threads beat three by ~13 % at every context length on Raspberry Pi 5 (nothing above core count helps) — [Zenodo record](https://zenodo.org/records/20411979) [unverified]; "Set `-t` to the number of physical cores… threads compete for RAM bandwidth" — [viblo guide](https://viblo.asia/p/running-100b-moe-models-on-a-single-rtx-4090-a-practical-guide-to-expert-offloading-with-llamacpp-yZJZlPyZVjm)

### Inferences
- Build the engine around a per-step compiled graph (capture once per shape, patch KV positions per token) from day one; the 1.2× CUDA-graph result and the ~10 % CPU residual tell you launch overhead is the largest single batch-1 cost on fast GPUs, and the same holds for Metal command encoding.
- Express independent branches (Q/K/V; routed experts; shared expert vs routed experts; attention of layer L+1's CPU part vs GPU part) as graph nodes with explicit buffer lifetimes so a scheduler can run them on separate streams without the allocator-reuse race that bit ggml.
- Thread model: one persistent CPU pool sized to physical P-cores, parked (futex/condvar, not spinning) while the GPU owns the step, with a bounded spin only in CPU-only mode; a separate small pool for tokenisation/HTTP; never more than one thread issuing GPU work per device.
- Keep concurrent-stream optimisations behind per-device heuristics (they regressed on GB10) and benchmark against the bandwidth speed-of-light to know when to stop.

### Gaps
- No source on Metal indirect command buffers or ggml-metal's concurrent command-encoder strategy was retrieved (search budget exhausted); treat Metal launch-overhead mitigation as a to-measure item.
- No measurement of attention/MLP overlap (as opposed to Q/K/V) in any consumer engine.
- No data on Vulkan or ROCm graph/stream overlap beyond the Strix Halo backend comparison.

## Key question 7 — Resource issues to avoid: GPU memory oversubscription (WDDM fallback, Metal wired limits, macOS compression/swap), CPU thread oversubscription with mixed CPU/GPU paths, thermal throttling on laptops, battery/power, memory-pressure handling; concrete incidents

### Takeaway
The recurring incidents are silent degradation rather than crashes: Windows NVIDIA drivers (≥536) spill VRAM into "Shared GPU memory" over PCIe instead of failing; macOS caps Metal at roughly 65–75 % of RAM (`iogpu.wired_limit_mb`) so a model that "fits in RAM" is quietly not on the GPU or thrashes via mmap/swap (llama.cpp at 70B on an 11 GB-VRAM desktop fell to 10 s/token); spinning CPU threads slow the GPU path; and speculative decoding or RPC can raise memory in ways loaders do not plan for. The documented mitigations are static fitting with headroom (llama.cpp `-fit`), explicit limits that fail fast (NVIDIA "Prefer No Sysmem Fallback", vLLM `--kv-cache-memory`, SGLang `--mem-fraction-static`), and parking threads instead of polling.

### Cited Findings

GPU memory oversubscription
- Windows: since driver branch 536 (mid-2023) an oversized CUDA allocation is absorbed by system RAM and shown as "Shared GPU memory", so front-ends display no error; data in system RAM crosses PCIe every token, "roughly ten times slower" (figure unbenchmarked); fix is NVIDIA Control Panel → Manage 3D Settings → "CUDA Sysmem Fallback Policy" = "Prefer No Sysmem Fallback" (global or per-program; restart the app); the toggle has no effect under WSL2; on Linux the same overflow is a hard CUDA OOM — [llmconfigurator Windows guide](https://llmconfigurator.com/en/guides/troubleshooting/windows-shared-gpu-memory-slow), [runaihome 2026 guide](https://runaihome.com/blog/shared-gpu-memory-slow-local-ai-sysmem-fallback-fix-2026/), [NVIDIA forum: cudaMalloc with sysmem fallback](https://forums.developer.nvidia.com/t/cudamalloc-with-sysmem-fallback/347791) [community sources; no official NVIDIA doc retrieved]
- macOS: Metal allocations come from a wired (non-pageable) pool capped by default near 75 % of RAM (another guide says 60–70 %; a 64 GB Mac tops out near 48 GB); llama.cpp honours the limit Metal reports (`recommendedMaxWorkingSetSize`); `sudo sysctl iogpu.wired_limit_mb=N` (Sonoma 14+; older releases used a byte-based debug key; unknown keys fail silently); 128 GB machines are commonly set to 122880 MB; setting it to all RAM "invites freezes and forced restarts"; resets on reboot; Apple does not document it — [llmconfigurator Apple guide](https://llmconfigurator.com/en/guides/troubleshooting/increase-metal-vram-limit-apple-silicon), [devnote: override macOS Metal VRAM cap](https://github.com/ivanopcode/devnote-override-macos-metal-vram-cap), [mehmetbaykar.com](https://mehmetbaykar.com/posts/increase-vram-apple-silicon-local-llm/) [community]; the official mlx-lm README confirms the mechanism: it wires model + cache memory (macOS ≥15) and warns the model "will likely be slow" if it exceeds the wired limit — [mlx-lm README](https://github.com/ml-explore/mlx-lm/blob/main/README.md)
- mmap thrash as the failure mode when a model exceeds memory: llama.cpp on the 11 GB-VRAM/9.7 GiB-RAM desktop took 7,965–10,120 ms/token for 60–70B models versus 468–674 ms with prima.cpp's placement + prefetch, and exo/dllama went OOM — [arXiv 2504.08791v2](https://arxiv.org/html/2504.08791v2)
- llama.cpp mitigation: `-fit on` by default with `--fit-target 1024` MiB per device headroom and `--fit-ctx 4096` — [llama.cpp tools/server/README.md](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)
- vLLM: KV cache measured by a profiling pass at startup unless `--kv-cache-memory` pins it; preemption/recompute when it runs out — [vLLM optimization docs](https://docs.vllm.ai/en/latest/configuration/optimization/); SGLang: `--mem-fraction-static` too high → OOM, too low → wasted capacity; "KV cache pool is full. Retract requests." — [SGLang tuning docs](https://docs.sglang.io/advanced_features/hyperparameter_tuning.html)
- Ollama refuses concurrent loads that don't fully fit VRAM and queues/evicts idle models; queue overflow (>512) → 503 — [Ollama FAQ](https://docs.ollama.com/faq)
- Speculative decoding memory: vLLM MTP arms "could not start on the 24 GB card because of extra bf16 allocations" (duplicated embeddings/output projections) — [hackmd.io/@thc1006](https://hackmd.io/@thc1006/qwen3-8-27b-speculative-decoding-rtx-3090); SGLang warns speculation "can raise GPU memory use, so OOM is possible" — [SGLang spec docs](https://docs.sglang.io/advanced_features/speculative_decoding.html); MTP head needs ~500 MB extra compute buffer in one test — [HF Space](https://victor-mtp-on-hf-endpoints.static.hf.space/index.html)
- RPC/large-model loads: "large models with `--rpc` need `-dio` to avoid load hangs" (Strix Halo pair) — [visorcraft/strix-halo-llm-perf](https://github.com/visorcraft/strix-halo-llm-perf); AppleThunderboltRDMA ~100 MR cap: exceeding it segfaulted on older macOS 26 builds, returns NULL on 26.3 — [mlx issue #3162](https://github.com/ml-explore/mlx/issues/3162)

CPU thread oversubscription and contention
- Spinning worker threads slow down when a non-CPU backend (BLAS, partial GPU offload) is busy; reviewers suggested backing off/yielding; polling "interferes with core boosting"; default thread count excludes E-cores and SMT siblings — [llama.cpp PR #8672](https://github.com/ggml-org/llama.cpp/pull/8672)
- For CPU-resident MoE experts, `-t` above physical cores slows generation because threads "compete for RAM bandwidth"; populating four DIMMs lowers memory clock — [viblo guide](https://viblo.asia/p/running-100b-moe-models-on-a-single-rtx-4090-a-practical-guide-to-expert-offloading-with-llamacpp-yZJZlPyZVjm)
- MLX generation streams are thread-bound; a scheduler must keep each generator on the thread that created it — [vllm-mlx docs](https://vllm-mlx.is-a.dev/guides/continuous-batching/)
- `mlx_lm.server` serialises requests when `--kv-bits` is set; quantized-cache attention allocates a `prefill_step_size × context_length` score matrix — [mlx-lm SERVER.md](https://github.com/ml-explore/mlx-lm/blob/main/mlx_lm/SERVER.md)
- MLX's low-latency CPU↔GPU sync mode can deadlock and "leave the GPU wedged" — [MLX distributed docs](https://ml-explore.github.io/mlx/build/html/usage/distributed.html)

- LMSYS (Oct 13 2025): no throttling on DGX Spark under sustained load; "The Mac Mini [M4 Pro 24 GB] and Mac Studio [M1 Max 64 GB] showed thermal drop-off in similar tests" (qualitative) — [LMSYS DGX Spark review](https://www.lmsys.org/blog/2025-10-13-nvidia-dgx-spark)

### Inferences
- Treat "allocation succeeded" as insufficient: on Windows the engine should query the device's reported free VRAM and refuse/replan when planned residency exceeds it (or detect non-zero shared-memory growth and warn), and on macOS it should read the Metal recommended working-set size and plan against that, never against total RAM; offer the `iogpu.wired_limit_mb` change as explicit, logged, reversible advice rather than doing it silently.
- Every planner input that can raise memory later (more slots, larger ctx, spec-decode buffers, quantized-KV score matrices, RPC caches) must be part of the pre-load plan; incidents above are all cases where a feature added memory the loader didn't count.
- Thread policy: cores = physical P-cores, park on condvar while the GPU owns the step, never spin alongside a GPU backend; expose a power/thermal profile (e.g. "laptop on battery": fewer threads, lower micro-batch, speculation off) because sustained throughput on fanless/thin laptops is qualitatively lower and no engine surveyed adapts to it.
- Make degradation visible: log the fitted plan, the effective device residency per tensor group, per-step preemptions/retractions, and spec-decode acceptance, because every incident above was "slow and silent" rather than "crash with a message".

### Gaps
- No quantified laptop thermal-throttling measurement (tok/s over time on MacBook Air/Pro or thin Windows laptops) was found; only qualitative statements.
- No measured battery-vs-plugged behaviour for LLM inference on macOS or Windows.
- No official NVIDIA or Apple documentation of the sysmem-fallback or wired-limit mechanisms was retrieved; the WDDM "~10×" and macOS "75 %" figures are community numbers.
- No macOS memory-compression/swap incident with hard numbers beyond the prima.cpp swapping measurements (which are Linux + mmap).
- The llama.cpp `-fit` implementation details (how it estimates compute buffers; behaviour when the fit fails) were not retrievable beyond the flag descriptions.
