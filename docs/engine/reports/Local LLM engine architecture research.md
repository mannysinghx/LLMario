# Plan memory first, then chase bandwidth

*Research report for the LLMario from-scratch inference engine (Rust, Apache-2.0), synthesised on 8 October 2026 from nine research notes (engine landscape, CPU execution, GPU/NPU backends, KV cache and attention, OS memory and resource governance, quantization and formats, sharding/parallelism/distributed, internet tools and agents, target models). Every number keeps its provenance label: **measured** = a benchmark with stated hardware and version (third party unless noted "measured by author/vendor"); **vendor-claimed** = the project's or paper authors' own figure without an independent rerun; **community** = forum/blog/issue figure with partial method; **unverified** = seen only in a secondary summary; **background** = pre-2025. Sizes are GiB (1024³) where the source used GiB, GB otherwise. The notes' web-search budget ran out part-way through each area, so the "Open gaps" section lists what could not be confirmed.*

The evidence points to one architectural thesis: the engine should be built around a deterministic memory plan and tensor placement rather than around new kernels, because decode on every consumer device is already memory-bandwidth-bound in existing engines (7B Q4_0 decode reaches ~58 % of peak bandwidth on an M4 Max and ~74 % on an M5 Max in community-measured llama-bench runs, and ~64–72 % on RTX 3090–5090), while the failures users actually hit are silent memory incidents: llama.cpp preallocating KV for the model's full training context until `--fit` landed in December 2025, MLX defaulting its memory limit to 1.5× the GPU working set, NVIDIA Windows drivers spilling VRAM into system RAM at roughly 10× slowdown instead of failing, macOS compressing unwired weights, and every multi-model server evicting by model count rather than bytes. **No existing engine — not llama.cpp's router mode, Ollama, LM Studio, vLLM, SGLang, mistral.rs or oMLX — budgets RAM, VRAM and NPU memory jointly with per-model hard caps across CPU, GPU and NPU on one desktop, and that is the defensible niche.** The recommended design is therefore: a supervisor with one engine process per loaded model; a no-alloc dry-run planner that prints weights, KV and scratch per device before loading and degrades in a fixed order (caches → context → KV precision → host offload → refuse) rather than swapping; read-only mmap weights with bounded prefault, wired through Metal residency sets on macOS; a paged KV arena carved once per device with three cache classes (per-token K/V, sliding-window ring buffers, fixed fp32 recurrent state) and q8_0-K/q4_0-V with Hadamard rotation as the default on small machines; GGUF and safetensors read natively at 4.3–4.9 bits per weight with a disposable repack cache instead of a new format; int8-dot CPU kernels on physical performance cores with parked (not spinning) threads and a rewritten MoE expert path that today runs 3–4× under the bandwidth bound; Metal first, CUDA second, Vulkan as the universal fallback, NPUs only behind a delegate boundary for ≤4B models, embeddings and draft models; tensor-level placement (dense path on the fastest device, routed experts in host RAM with a hot-expert GPU cache) instead of CPU–GPU tensor parallelism, with multi-device support designed as an interface but not built; and a Responses-shaped agent loop with template-driven incremental tool-call parsers, llguidance lazy grammars, MCP 2026-07-28 through the official `rmcp` crate, an SSRF-guarded fetcher and a Rule-of-Two policy gate that requires human approval for any state-changing tool once untrusted web content has entered the context. The single kernel investment with measured 1.6–3.4× batch-1 payoff is speculative decoding (n-gram lookup first, then model-shipped MTP heads capped at 2–3 draft tokens) together with few-row GEMM kernels for verification; sub-4-bit KV codebooks, dense-weight SSD streaming, score-based KV eviction, Rust-native GPU kernel languages and in-machine tensor parallelism should be deferred or avoided.

## Decode already runs at 55–80 % of memory bandwidth; prefill is where engines differ 2–8×

Every measured platform tells the same story, and it fixes the yardstick the engine must use for itself: effective bytes per second, not FLOPs. On Apple silicon the maintainer-curated llama-bench table (Llama-2 7B, `-p 512 -n 128`, Metal; M1–M4 rows pinned to a November 2023 build, M5/M6 rows on 2026 builds, so cross-generation absolutes are not strictly comparable) gives Q4_0 decode of **83.1 tok/s on an M4 Max (546 GB/s), 119.9 on an M5 Max (614 GB/s) and 179.1 on an M5 Ultra (1,228 GB/s)** (community-measured), which for ~3.8 GB of weights per token works out to roughly 58 %, 74 % and 55 % of peak bandwidth ([Source](https://github.com/ggml-org/llama.cpp/discussions/4167)). The CUDA scoreboard on the same test reads **300.4 tok/s on an RTX 5090, 189.0 on a 4090 and 161.9 on a 3090** (community-measured, commit per row), i.e. about 64 %, 72 % and 66 % of their 1,792 / 1,008 / 936 GB/s vendor specifications ([Source](https://github.com/ggml-org/llama.cpp/discussions/15013), [Source](https://images.nvidia.com/aem-dam/Solutions/geforce/blackwell/nvidia-rtx-blackwell-gpu-architecture.pdf)); a current 8B at Q4_K_XL decodes at **185.9 tok/s at 4K context and 111.9 at 32K** on the 5090 (measured, single source with noted internal inconsistencies) ([Source](https://www.hardware-corner.net/rtx-5090-llm-benchmarks/)). On CPUs the roofline is explicit: a Ryzen AI 9 HX 370 laptop with dual-channel DDR5-5600 (~65 GB/s assumed real-world) decoded a 19 GB dense 32B Q4_K_M at **3.54 tok/s against 3.4 predicted** (measured), and thread scaling peaked at 12 physical threads (3.54) and fell to 2.84 with 24 SMT threads ([Source](https://github.com/ggml-org/llama.cpp/issues/19480)). The usable predictor is `tok/s ≈ η · BW_peak / (active_weight_bytes + KV_bytes_read(ctx))` with η ≈ 0.6–0.8 for a well-threaded dense model; the engine should compute this speed-of-light at load time and log it next to the measured rate so any shortfall is visible.

Prefill is the opposite regime and is where hardware-specific work pays. On an M5 Max 128 GB the Metal 4 tensor path took gpt-oss-120b MXFP4 from **877 to 1,833 tok/s at pp2048 (2.09×)** and Step-3.7-Flash IQ3_XXS from 342 to 833 (2.44×) while decode stayed at ~105 tok/s (measured A/B on llama.cpp b9592, toggled with `GGML_METAL_TENSOR_DISABLE=1`) ([Source](https://github.com/lmstudio-ai/lmstudio-bug-tracker/issues/2040)); Apple's own M5-versus-M4 numbers are 3.33–4.06× TTFT and 1.19–1.27× generation, the latter attributed to bandwidth rising from 120 to 153 GB/s (vendor-claimed) ([Source](https://machinelearning.apple.com/research/exploring-llms-mlx-m5)). On x86 the pending VNNI repack kernels lifted Llama-3.1-8B Q8_0 pp2048 on a Ryzen 9 9950X from **176.8 to 572.0 tok/s (3.24×) with tg128 unchanged at 0.99–1.00×** (measured, PR still open) ([Source](https://github.com/ggml-org/llama.cpp/pull/30036)), and SME2 kernels on an M4 Pro took Llama-3.2-1B Q6_K pp512 from 568 to 2,403 tok/s at 8 threads (4.2×; measured, PR open) ([Source](https://github.com/ggml-org/llama.cpp/pull/29219)). Vulkan has quietly become competitive: on the RTX 5090 it reaches **11,796 pp / 273.7 tg** versus CUDA's 14,970 / 300.4 on 7B Q4_0 (community-measured), roughly 79 % of CUDA prefill and 91 % of decode, where an RTX 3080 in December 2024 showed CUDA at 2.6× Vulkan ([Source](https://github.com/ggml-org/llama.cpp/discussions/10879)).

The two findings that should reorder priorities are structural rather than kernel-level. A Qwen3-30B-A3B on the 5090 decodes at only **234.3 tok/s versus 185.9 for the 8B dense — 1.26× faster despite ~2.5× fewer active bytes** (derived from the measured table), and on the HX 370 laptop a Qwen3-Coder-Next 80B-A3B ran at **7.74 tok/s against a 20–30 tok/s bandwidth bound** (measured); MoE decode in llama.cpp is gather-, launch- and barrier-bound, not DRAM-bound ([Source](https://www.hardware-corner.net/rtx-5090-llm-benchmarks/), [Source](https://github.com/ggml-org/llama.cpp/issues/19480)). Two cautions apply to every figure in this report. Wrappers cost real throughput: Ollama 0.18 decoded a qwen3.5 35B-A3B q8_0 at **32.54 tok/s where raw llama.cpp did 53.53** on the same Apple machine (user-reported, open issue) ([Source](https://github.com/ollama/ollama/issues/14861)). And numbers rot within months: one M4 MacBook Pro gained +27 % prefill between two llama.cpp builds ~90 builds apart, and the M2 Ultra F16 prefill row in the Apple table climbed from 1,402 (2023) to 1,628 tok/s (August 2026) on identical hardware ([Source](https://discourse.nixos.org/t/llama-cpp-on-apple-silicon-native-build-much-faster-than-nixpkgs/75309), [Source](https://github.com/ggml-org/llama.cpp/discussions/4167)).

## No engine budgets memory jointly across models and devices, and that gap defines the niche

Every mainstream local engine belongs to one of three lineages, and all three inherited a memory model from somewhere other than the desktop. The ggml lineage (llama.cpp, and through it Ollama, LM Studio, llamafile, bitnet.cpp, PowerInfer) allocates K and V tensors per layer sized `n_embd_k_gqa × kv_size × n_stream` in the cache constructor whether or not cells are used, reserves compute buffers from a worst-case graph with `n_tokens = min(n_ctx, n_ubatch)`, and defaulted `n_ctx` to the model's training context (0 = from model) until automatic fitting landed ([Source](https://github.com/ggml-org/llama.cpp/blob/master/src/llama-kv-cache.cpp), [Source](https://github.com/ggml-org/llama.cpp/blob/master/src/llama-context.cpp), [Source](https://github.com/ggml-org/llama.cpp/blob/master/include/llama.h)); `--fit` (PR #16653, merged 2025-12-15) then needed roughly **twenty follow-up fixes through April 2026** — underflow for dense models, Gemma 3 calculation, last devices with low VRAM, CPU-only context fitting — and its early versions "wasted roughly 5 GiB per GPU on 24 GB cards" before per-tensor placement (measured by PR author/testers) ([Source](https://github.com/ggml-org/llama.cpp/pulls?q=is%3Apr+is%3Amerged+author%3AJohannesGaessler+fit), [Source](https://github.com/ggml-org/llama.cpp/pull/16653)). The MLX lineage (mlx-lm, Ollama's MLX runner, vllm-metal, oMLX) sets its Metal memory limit to **min(1.5 × `recommendedMaxWorkingSetSize`, 0.95 × physical RAM)** with a free-buffer cache that defaults to the same limit, so freed buffers are retained up to the limit and an app will overshoot the GPU budget into swap before failing; a 1M-token request on a 128 GB M2 Ultra held **108 GB of footprint against ~34 GB expected** because freed buffers "are never returned to the OS" when sizes keep growing (self-reported issue, closed without fix) ([Source](https://github.com/ml-explore/mlx/blob/main/mlx/backend/metal/allocator.cpp), [Source](https://ml-explore.github.io/mlx/build/html/python/_autosummary/mlx.core.set_memory_limit.html), [Source](https://github.com/ml-explore/mlx/issues/3350)). The datacenter lineage (vLLM, SGLang, TensorRT-LLM, ktransformers) sizes a fixed KV pool as a fraction of one GPU — vLLM `--gpu-memory-utilization` 0.92 with the multi-instance advice "set 0.5 for each instance", SGLang `--mem-fraction-static` tuned "in 0.01 steps until you hit OOM", TensorRT-LLM 0.9 — and carries a Python control plane whose overhead motivated vLLM V1's process split ("GPU execution can take about 5 ms" for Llama-8B on H100) ([Source](https://docs.vllm.ai/en/stable/cli/serve/), [Source](https://docs.sglang.io/advanced_features/hyperparameter_tuning.html), [Source](https://nvidia.github.io/TensorRT-LLM/features/kvcache.html), [Source](https://vllm.ai/blog/2025-01-27-v1-alpha-release)). The closest existing analogue to LLMario's plan, mistral.rs on candle (both MIT/Apache-permissive), proves a Rust engine can reach CUDA feature parity — PagedAttention, prefix caching, in-situ quantization, FP8/NVFP4, MTP and DFlash drafters, a built-in MCP client and agent loop, multi-model per process — but its memory story is still "90 % of VRAM" per process, Metal and CPU fall back to first-come-first-served equal-length batching without paged attention, and published performance covers only H100/B200 ([Source](https://github.com/EricLBuehler/mistral.rs/blob/master/README.md), [Source](https://docs.mistralrs.dev/guides/perf/paged-attention/), [Source](https://docs.mistralrs.dev/guides/perf/throughput-tuning/)).

Multi-model management converged on process isolation but not on byte budgets. llama-server's router mode (published 2025-12-11) runs each model in its own process ("if one model crashes, the others are unaffected") and evicts by count (`--models-max` default 4) with no cross-model memory budget described ([Source](https://huggingface.co/blog/ggml-org/model-management-in-llamacpp)). Ollama spawns one runner subprocess per model, requires a new model to fit in **80 % of free VRAM** alongside loaded ones, polls every 250 ms for up to 5 s after an unload because "free memory reporting on GPUs can lag", retries OOM loads at 32K then 4K context, and admits in code that its eviction is "not true LRU" ([Source](https://github.com/ollama/ollama/blob/main/server/sched.go)); its September 2025 switch from estimates to exact measurement moved gemma3:12b at 128K context from 48/49 to 49/49 offloaded layers and **52.02 → 85.54 tok/s** on an RTX 4090 (vendor-measured) ([Source](https://ollama.com/blog/new-model-scheduling)). LM Studio refuses loads above a "guardrails" estimate that one user found at **22.92 GB where llama.cpp used ≈11.5 GB** for the same model and context, with no CLI override (user-reported, open) ([Source](https://github.com/lmstudio-ai/lms/issues/499)), and its bundled Metal runtime 2.21.0 silently failed the Metal 4 tensor check and lost the 2–2.4× M5 prefill gain (measured) ([Source](https://github.com/lmstudio-ai/lmstudio-bug-tracker/issues/2040)). The only project with a total-memory contract is oMLX (Apache-2.0, Python on MLX, Apple-only): a process limit defaulting to RAM minus 8 GB, LRU with pin and per-model TTL, copy-on-write prefix blocks and a two-tier RAM/SSD KV cache (vendor description) ([Source](https://github.com/jundot/omlx)). SiliconBench's cross-engine study of nine Apple engines concludes that "explicit memory budgets do not guarantee headroom" (measured) ([Source](https://arxiv.org/abs/2609.19169)).

What should be copied is specific. From ggml: the single tensor library with a backend registry, buffer types that encode host-versus-device identity and usage hints, a scheduler that splits a graph by where the weights live ("backends with low index are given priority"), a graph allocator that reserves once from a worst-case graph, and above all the `no_alloc` simulation mode — `--fit` was only possible because allocation sizes can be computed without allocating ([Source](https://github.com/ggml-org/ggml/blob/master/include/ggml-backend.h), [Source](https://github.com/ggml-org/ggml/blob/master/include/ggml-alloc.h), [Source](https://github.com/ggml-org/llama.cpp/blob/master/include/llama.h)). From vLLM V1: the token-budget scheduler that "does not distinguish prefill from decode", hash-chained SHA-256 prefix caching enabled by default at "<1 % throughput loss at 0 % hit rate" (vendor-claimed), preempt-by-recompute, and the lazy-growth-but-worst-case-charged allocator pattern that fixed vllm-metal's eager per-block state ("wired about 10 GB for Qwen3.5-0.8B at memory fraction 0.5", 19.5 MB → 6.5 MB per block; measured by PR author) ([Source](https://vllm.ai/blog/2025-01-27-v1-alpha-release), [Source](https://docs.vllm.ai/en/stable/design/v1/prefix_caching.html), [Source](https://github.com/vllm-project/vllm-metal/pull/584)). From SGLang: the unified radix tree whose Rust core cut TTFT 5–38 % versus the Python tree (measured by LMSYS) and whose session-aware eviction lifted device hit ratio from ~5 % to ~34 % on a 397B MoE (measured by LMSYS) ([Source](https://www.lmsys.org/blog/2026-08-11-unified-radix-cache/)). From MLX: queryable soft memory, cache and wired limits as desktop-settable knobs. From llama-server: N slots over one unified KV pool with one `llama_batch` per step, `--cache-ram` bounded at 8192 MiB, idle-slot parking in host RAM and the process-per-model router with a stop-then-force-kill timeout ([Source](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md), [Source](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README-dev.md)). What should be avoided is equally specific: re-implementing the inference graph in a managed language (Ollama's Go engine drew a "10× slower" report on Qwen3-30B-A3B, closed as not planned, and GGUF serving is now delegated back to "the upstream llama-server subprocess") ([Source](https://github.com/ollama/ollama/issues/11060), [Source](https://github.com/ollama/ollama/blob/main/llm/server.go)); "fraction of device memory" budgets; worst-case preallocation without a printed plan; caches bounded only by the memory limit; global KV-type environment variables that multiply `NUM_PARALLEL × CONTEXT_LENGTH` ([Source](https://docs.ollama.com/faq)); and backends that "crash for missing ops" rather than falling back, as MLX's CUDA backend did at launch ([Source](https://github.com/ml-explore/mlx/discussions/2422)).

## Memory governance: plan with a no-alloc dry run, keep three budgets, degrade in a fixed order

Weight residency is the first budget and mmap is still the right default, with caveats the notes make concrete. llama.cpp maps the file `PROT_READ, MAP_SHARED`, adds `MAP_POPULATE` only on Linux and only when no lazy ranges exist, applies `POSIX_MADV_WILLNEED` to the prefetch range, and `munmap`s page-aligned fragments that a discrete GPU no longer needs ([Source](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/src/llama-mmap.cpp)). Read-only file mappings "cost nothing" in Linux overcommit accounting because the file is the backing store, and the page cache shares the bytes between a daemon and a CLI ([Source](https://docs.kernel.org/mm/overcommit-accounting.html)). The price is that under pressure the OS drops those pages silently and the next token re-reads from SSD: a 24 GB M4 Pro running MoE models larger than RAM reported kernel panics, page-fault storms and a swap "death spiral" that `iogpu.wired_limit_mb=22000` did not cure (user-reported) ([Source](https://github.com/ggml-org/llama.cpp/issues/19825)); a 128 GB M3 Max loading a 98 GiB model with `--no-mmap` saw long swap/unswap cycles (user-reported) ([Source](https://github.com/ggml-org/llama.cpp/issues/13361)); and the original `--mlock` commit (background, 2023) recorded macOS compressing a 25 GB model's memory and freezing decompression "for a few seconds" ([Source](https://github.com/ggml-org/llama.cpp/commit/563cdc391dde140f1084d1012234e8e6f57f881f)). Load-time numbers favour direct I/O only for cold loads into GPU memory on fast NVMe: on a DGX Spark GPT-OSS-120B went from **~110 s (mmap, first load) to ~10.5 s (direct I/O)**, while on an M4 Pro a cold `--no-mmap` load of GPT-OSS-20B took 4.168 s versus 6.3 s with mmap but a warm mmap load took 2.1 s versus ~4.1 s, and the maintainer refused to make non-mmap the macOS default after a load went 4.6 → 18.0 s (measured by PR author/testers; direct I/O was then disabled by default in January 2026) ([Source](https://github.com/ggml-org/llama.cpp/pull/18012)). fastsafetensors shows the GPU-copy path done right: **4.8–7.5× faster** than the default safetensors deserializer and 26.4 GB/s NVMe reads with GPU Direct Storage (measured by authors) ([Source](https://github.com/foundation-model-stack/fastsafetensors), [Source](https://arxiv.org/abs/2505.23072)). Locking is a scalpel: Linux `mlock` needs `CAP_IPC_LOCK` or a raised `RLIMIT_MEMLOCK`, `MLOCK_ONFAULT` is the cheap variant that never prefaults untouched expert rows ([Source](https://man7.org/linux/man-pages/man2/mlock.2.html)); Windows `VirtualLock` is capped at the process minimum working set, which must be raised with `SetProcessWorkingSetSizeEx` and is granted "first-come, first-served" at the expense of every other process ([Source](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-virtuallock), [Source](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-setprocessworkingsetsizeex)). Because Linux RSS and the Windows working set both count shared file-backed pages and macOS reports mapped weights under "Cached Files", the engine must keep its own ledger (mapped bytes, resident estimate via `mincore`/`QueryWorkingSetEx`, wired bytes, private anonymous bytes, GPU-private bytes) and expose it in the API; the OS process counter cannot be compared against a budget ([Source](https://learn.microsoft.com/en-us/windows/win32/psapi/process-memory-usage-information), [Source](https://support.apple.com/guide/activity-monitor/view-memory-usage-actmntr1004/mac)).

Each OS gives the engine a different budget ceiling and pressure signal, and the recommendation is to plan against the ceiling and use the signal only for emergency back-pressure. On macOS the GPU can wire only up to `recommendedMaxWorkingSetSize` — Apple documents it as "an approximation of how much memory ... this GPU device can allocate without affecting its runtime performance", community evidence puts it at roughly 2/3 of RAM below 32 GB and 3/4 above (e.g. ~96 GB on a 128 GB Mac), and it is raisable only by root with the undocumented, non-persistent `sudo sysctl iogpu.wired_limit_mb` (community; going slightly above 96 GiB on a 128 GB machine produced swap cycles) ([Source](https://developer.apple.com/documentation/metal/mtldevice/recommendedmaxworkingsetsize), [Source](https://github.com/ivanopcode/devnote-override-macos-metal-vram-cap), [Source](https://github.com/ggml-org/llama.cpp/discussions/2182)). Since macOS 15 the OS unwires idle GPU memory after about one second: single-token decode on an M2 Ultra went from **26.34 ms to 472.38 ms after ~2.2 s idle** (F16 8B) and on an M4 Pro from 56 to ~315–338 ms (measured by maintainer), fixed by one `MTLResidencySet` per buffer plus a background thread re-requesting residency every 5 ms while a 3-minute keep-alive counter is positive, which made requests ~250 ms faster with throughput unchanged (measured by maintainer) ([Source](https://github.com/ggml-org/llama.cpp/pull/10119), [Source](https://github.com/ggml-org/llama.cpp/pull/11427), [Source](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/ggml/src/ggml-metal/ggml-metal-device.m)). Memory the engine does not wire is subject to compression: an M1 Max 64 GB running a 35B-A3B Q8 under MLX accumulated **19.69 GB compressed and climbing swap** after eight hours, cut by 91 % after wiring 45 GB and capping the cache at 512 MB (measured by one user) ([Source](https://dev.to/sleepyquant/what-19-gb-of-memory-compression-taught-me-about-mlx-on-m1-max-3eha)). macOS has no byte-count pressure API (`os_proc_available_memory` is not available on macOS); the only signal is the dispatch memory-pressure source with normal/warning/critical ([Source](https://developer.apple.com/documentation/os/os_proc_available_memory.md), [Source](https://developer.apple.com/documentation/dispatch/dispatchsource/makememorypressuresource(eventmask:queue:).md)). On Windows the engine gets a per-process OS budget from `IDXGIAdapter3::QueryVideoMemoryInfo` ("if CurrentUsage is greater than Budget, the application may incur stuttering"), or `VK_EXT_memory_budget` per heap, a system-wide low/high memory event, job objects that cap a child's committed memory (`JOB_OBJECT_LIMIT_PROCESS_MEMORY`, with `PeakProcessMemoryUsed` as a free peak measurement), and EcoQoS opt-in/opt-out through `SetProcessInformation(ProcessPowerThrottling)` ([Source](https://learn.microsoft.com/en-us/windows/win32/api/dxgi1_4/nf-dxgi1_4-idxgiadapter3-queryvideomemoryinfo), [Source](https://docs.vulkan.org/refpages/latest/refpages/source/VK_EXT_memory_budget.html), [Source](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-creatememoryresourcenotification), [Source](https://learn.microsoft.com/en-us/windows/desktop/api/winnt/ns-winnt-jobobject_extended_limit_information), [Source](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-setprocessinformation)). The Windows trap is WDDM: the GPU may use up to half of system RAM as "shared GPU memory" (background, 2017 DirectX blog), and since NVIDIA driver 536.40 (June 2023) the default sysmem fallback lets `cudaMalloc` succeed into system RAM, which NVIDIA's forum calls "expected functionality and not a bug" that the driver cannot report as OOM; the per-app "Prefer No Sysmem Fallback" control-panel policy turns it into a hard failure, does not work under WSL2, and the slowdown is quoted as "5–10×" by third parties (unverified) ([Source](https://devblogs.microsoft.com/directx/gpus-in-the-task-manager/), [Source](https://nvidia.custhelp.com/app/answers/detail/a_id/5490), [Source](https://forums.developer.nvidia.com/t/cudamalloc-with-sysmem-fallback/347791), [Source](https://runaihome.com/blog/shared-gpu-memory-slow-local-ai-sysmem-fallback-fix-2026/)). Linux is the only OS with both a precise signal and an enforceable soft limit: cgroup v2 `memory.high` throttles instead of killing, page cache is charged to the cgroup that instantiated it (so mmapped weights count), PSI `some`/`full` triggers are pollable with 500 ms–10 s windows, `oom_score_adj` lets the engine volunteer itself before the desktop session, and systemd-oomd's field defaults (60 % PSI full avg10 for 30 s) are the only field-tested thresholds ([Source](https://docs.kernel.org/admin-guide/cgroup-v2.html), [Source](https://docs.kernel.org/accounting/psi.html), [Source](https://man7.org/linux/man-pages/man5/proc_pid_oom_score_adj.5.html), [Source](https://man7.org/linux/man-pages/man5/oomd.conf.5.html)). Transparent huge pages help only engine-owned anonymous buffers via `MADV_HUGEPAGE` in `madvise` mode; a read-only data mapping of a weight file is not eligible, and hugetlbfs needs boot-time reservation ([Source](https://man7.org/linux/man-pages/man2/madvise.2.html), [Source](https://docs.kernel.org/admin-guide/mm/transhuge.html)).

Inside the engine, the two reference allocator designs are complementary and should be combined. ggml-alloc plans every activation of a graph once: best-fit over at most 256 free blocks per chunk, in-place reuse only for a whitelist of ops (ADD, MUL, SCALE, ROPE, RMS_NORM, …), inputs never overwritten, outputs never freed, re-reservation only when a chunk must grow ([Source](https://raw.githubusercontent.com/ggml-org/ggml/master/src/ggml-alloc.c)). MLX instead runs a size-bucketed buffer cache under its memory limit with garbage collection at 0.95 × the working set, sub-allocating small buffers from one `MTLHeap` ([Source](https://raw.githubusercontent.com/ml-explore/mlx/main/mlx/backend/metal/allocator.cpp)). CUDA's lesson is the same as PyTorch's June 2026 devlog: without expandable segments "blocks in different segments can never merge" (8×16 MiB then 4×32 MiB reserves 256 MiB for 128 MiB allocated), whereas reserving virtual address space once with `cuMemAddressReserve` and mapping 2 MiB/20 MiB physical pages on demand maps **140 MiB for 128 MiB** and never needs new pages for the second pattern (measured toy example) ([Source](https://docs.pytorch.org/devlogs/eager/2026-06-01-cuda-caching-allocator/), [Source](https://developer.nvidia.com/blog/introducing-low-level-gpu-virtual-memory-management/)); ggml-cuda already reserves a 32 GB VA range and grows it in granularity-sized chunks ([Source](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-cuda/ggml-cuda.cu)). The recommendation: a static per-graph plan with ggml-style lifetimes reserved at admission time from a measured worst-case graph; one virtual reservation per device (`cuMemAddressReserve`, `vm_allocate`/`MTLHeap`, `VirtualAlloc(MEM_RESERVE)`) with physical growth in large fixed pages; a size-bucketed cache with an explicit byte limit counted in the admission budget and purged on pressure; weights, KV and scratch bypassing `malloc` entirely so they can be aligned, locked and accounted individually; mimalloc or jemalloc only for small-object traffic (mimalloc's "~0.2 % meta-data" and bounded worst-case claims are vendor-claimed and its benchmarks date from 2021) ([Source](https://raw.githubusercontent.com/microsoft/mimalloc/master/readme.md)).

Admission control should follow the seven-point synthesis the notes derive from field practice. Plan with a no-alloc dry run, not a formula — llama.cpp's `--fit` and Ollama's new engine both abandoned heuristics (Ollama's old estimator guessed the partial-offload graph as `gqa × kvTotal / 6`) for exact buffer sizes ([Source](https://github.com/ggml-org/llama.cpp/pull/16653), [Source](https://raw.githubusercontent.com/ollama/ollama/v0.11.0/llm/memory.go)). Budget per device with explicit headroom: field defaults are llama.cpp's 1,024 MiB `--fit-target` per device and 4,096-token `--fit-ctx` floor, Ollama's 80 % of free VRAM and max(8 GB, 10 % of RAM) host headroom before it disables mmap, MLX's GC at 95 % of the working set; max(1 GiB, 10 %) per device plus a user-visible "keep N GB free for the OS" is defensible ([Source](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/tools/server/README.md), [Source](https://raw.githubusercontent.com/ollama/ollama/main/server/sched.go)). Degrade in a fixed order before refusing: shrink prompt and buffer caches, reduce context to the floor, quantize KV (q8_0 ≈ half, q4_0 ≈ quarter per Ollama's FAQ) where the attention path supports it, move dense-first layers to host memory (llama.cpp's fitter "first reduces the context size, then moves weights from device memory to system memory. For MoE models, dense weights get priority on the GPU"), then refuse with a structured error naming the per-device shortfall — never fall through to OS swap ([Source](https://docs.ollama.com/faq), [Source](https://github.com/ggml-org/llama.cpp/pull/16653)). Admit per request, not only per model, because `slots × context` is where KV blows up (one llama-server issue reports four slots created despite `-np 1`; unverified) ([Source](https://github.com/ggml-org/llama.cpp/issues/17989)). Keep an idle policy (Ollama 5 min keep-alive and 3 models per GPU, LM Studio 60-minute JIT TTL with auto-evict, router 4 models) and release residency sets after an idle window ([Source](https://docs.ollama.com/faq), [Source](https://lmstudio.ai/docs/app/api/ttl-and-auto-evict)). Subscribe to OS back-pressure (macOS warning/critical, Windows low-memory and DXGI budget change, Linux PSI/cgroup events) and on warning drop caches, unload idle models and stop admitting; on critical cancel queued requests and let the supervisor kill the child. Verify after load by recording real peak (job-object peak, cgroup `memory.peak`, Metal `currentAllocatedSize`) and feeding it back into the estimator, the loop Ollama's blog describes. No engine was found that uses cgroup `memory.high`, job objects or the residency keep-alive as an admission mechanism rather than a crash-avoidance patch; this design is a synthesis, not observed practice.

Two further governance topics have crisp answers. Streaming weights from SSD is viable only for MoE experts: Apple's "LLM in a flash" (background, 2023–24) reached ~1.5 tok/s on an M1 Max CPU and ~12 tok/s on an RTX 4090 for OPT-6.7B only because 90–97 % of FFN neurons were inactive (measured by authors), which SwiGLU-era models lack ([Source](https://arxiv.org/html/2312.11514v3)); a March 2026 experiment ran Qwen3.5-397B-A17B (209 GB on disk, ~6 GB resident) at **4.36 tok/s on a 48 GB M3 Max** by reading four ~6.75 MB experts per layer with parallel `pread()` and trusting a ~35 GB page cache at ~71 % hit rate (user-reported, repository has no licence file) ([Source](https://github.com/danveloper/flash-moe)); FlashMoE's learned cache policy beat LRU by 22 % on OLMoE on a PCIe 5.0 desktop (measured by authors) ([Source](https://arxiv.org/html/2601.17063v1)); and a modelled study puts per-token energy with SSD expert offload at "up to ~12×" an HBM baseline (modelled, not measured) ([Source](https://arxiv.org/abs/2508.06978)). The engine should implement expert-granular `pread`/`O_DIRECT`/io_uring reads in ≥32 KiB chunks under an explicit byte budget with one-layer routing look-ahead, refuse dense models that do not fit, and disable streaming on battery. Power and thermal signals are coarse on every OS — `ProcessInfo.thermalState` nominal/fair/serious/critical and `isLowPowerModeEnabled` on macOS, `GUID_POWER_SAVING_STATUS`/`GUID_ACDC_POWER_SOURCE` and EcoQoS on Windows (Microsoft's 2021 EcoQoS claim is "up to 90 % reduction in CPU power consumption" for background work; vendor-claimed), `/sys/class/thermal` on Linux — and none says how many threads to run ([Source](https://developer.apple.com/documentation/foundation/processinfo/thermalstate-swift.enum.md), [Source](https://learn.microsoft.com/en-us/windows/win32/power/power-setting-guids), [Source](https://devblogs.microsoft.com/sustainable-software/introducing-ecoqos/), [Source](https://docs.kernel.org/driver-api/thermal/sysfs-api.html)). The policy that follows: thread count equals physical performance cores, lower QoS/priority rather than thread count when backgrounded (Apple: utility or lower "at least 90 % of the time" when the user is not active), at *serious* reduce prefill chunk and batch and disable speculation and extra slots, at *critical* or battery-saver cap concurrency to one and stop polling. No measured tokens-per-second-versus-thermal-state data exists for any engine (gap).

## Read GGUF and safetensors natively, target 4.3–4.9 bits per weight, and never invent a third format

GGUF is the only container that bundles weights, quantization block layouts, tokenizer vocabulary and merges, pre-tokenizer id and the Jinja chat template in one 32-byte-aligned little-endian file whose alignment exists "so that tensors can be memory-mapped", with a documented `…-00001-of-XXXXX.gguf` shard convention; safetensors is a simpler zero-copy container (8-byte header length, JSON header, raw buffer, every byte owned by a tensor, no polyglots) that carries no tokenizer or quantization semantics and so relies on `config.json`, `tokenizer.json` and quantization side files, with "zero-copy" true only on CPU when the file is already in page cache ([Source](https://github.com/ggml-org/ggml/blob/master/docs/gguf.md), [Source](https://github.com/huggingface/safetensors)). Every quality-per-byte leader already ships in one of the two: K/I/TQ/MXFP4/NVFP4 quants in GGUF, AWQ/GPTQ/HQQ/EXL3/MLX-affine/compressed-tensors in safetensors. A third distribution format would add zero quality and cost ecosystem reach; what the engine legitimately owns is a *derived* on-disk cache (repacked interleaved tiles, precomputed LUTs, split-expert layouts) keyed by content hash and kernel version, regenerable and deletable. Two loader details matter: the IQ4_XS block size is 136 bytes in gguf-py's table but the C `static_assert` in `ggml-common.h` says 140, so block sizes must be computed from the C struct that the writer actually uses ([Source](https://github.com/ggml-org/llama.cpp/blob/master/gguf-py/gguf/constants.py), [Source](https://github.com/ggml-org/ggml/blob/master/src/ggml-common.h)); and 2026 vendor releases ship encoders and drafters as side-car GGUFs (`mmproj-*`, `mtp-*`, `dflash-*`, e.g. `mtp-Qwen3.8-27B-Q4_0.gguf` 1.68 GB), which the loader should treat as optional components keyed by the base model hash ([Source](https://huggingface.co/ggml-org/Qwen3.8-27B-GGUF/tree/main)). EXL3 (MIT) is the one format whose on-disk trellis layout is "not yet published" and whose kernels are CUDA-only; it is the lowest-priority input ([Source](https://github.com/turboderp-org/exllamav3/blob/master/doc/exl3.md)).

The quality frontier at ~4 bits is now well measured on 2026 models and the ordering is consistent. On Gemma 4 12B (RTX 5090, llama.cpp commit 8172e65, September 2026) EXL3 4.00 bpw scored **mean KLD 0.0248 at a 7.79 GiB file versus Q4_K_M (4.80 bpw) 0.0399 at 6.63 GiB, IQ4_XS (4.25 bpw) 0.0544 at 5.94 GiB, Q5_K_M 0.0172 at 7.84 GiB and Q6_K 0.0092 at 9.11 GiB** (measured, third party); because EXL3 files carry ~2 GiB of unquantized embeddings, Q5_K_M beat EXL3 4.0 at equal *file* size, and llama.cpp decoded 15–21 % faster in size-matched pairs while EXL3 prefilled 2.2× faster at 2K ([Source](https://atomic.chat/blog/guides/exl3-vs-gguf)). On Qwen3.5-35B-A3B Unsloth's table gives **UD-Q4_K_XL 19.17 GB KLD 0.0137, UD-Q4_K_M 18.49 GB 0.0192, bartowski IQ4_XS 17.42 GB 0.0234, MXFP4_MOE 18.17 GB 0.0272**, with the March 2026 recipe revision spending +7.8 % bytes to cut max KLD by 51 % (measured by Unsloth, dataset and hardware unstated) ([Source](https://unsloth.ai/docs/models/qwen3.5/gguf-benchmarks)). In MLX on Qwen3.6-27B, affine 4-bit g64 gave **KLD 0.0227 versus NVFP4 0.0325 and MXFP4 0.0479** (measured by Unsloth), while an independent WikiText-2 KLD study on an M5 Max found plain MLX 4-bit RTN at 0.1132 versus 0.0592 for Unsloth's MLX 4-bit and ~3× worse than Q4_K_M-class GGUF at similar bpw (measured) ([Source](https://unsloth.ai/docs/models/qwen3.6/gguf-benchmarks), [Source](https://smcleod.net/2026/04/measuring-model-quantisation-quality-with-kl-divergence/)). Block floats trade a measurable quality loss for native tensor-core speed: NVFP4 (E2M1, blocks of 16 with an E4M3 scale, ≈4.5 bpw) beats MXFP4 (blocks of 32, E8M0 power-of-two scale, 4.25 bpw) in NVIDIA's own toy MSE (0.08 vs 0.72) and PTQ tables (≤1 % degradation on DeepSeek-R1; vendor-claimed) ([Source](https://developer.nvidia.com/blog/introducing-nvfp4-for-efficient-and-accurate-low-precision-inference)), and on an RTX 5090 llama.cpp's sm_120 FP4 path raised Qwen3.6-27B-NVFP4 pp512 from **3,295 to 5,547 tok/s (+68 %) with decode flat at 73.7 tok/s** (community, via a secondary guide) ([Source](https://insiderllm.com/guides/fp4-inference-llamacpp-nvfp4-mxfp4/)). That last number captures the general rule: decode throughput on bandwidth-bound hardware is set by bytes per token, not by the scheme — Unsloth's llama.cpp table shows ≈90 tok/s for every type except I-quants at ≈85 ("about 5–10 % slower") — so scheme choice is about prefill cost and quality, not tokens per second at batch 1 ([Source](https://unsloth.ai/docs/models/qwen3.5/gguf-benchmarks)). At 8 bits the choice is free: W8A8-FP8 and INT8 recover 99.3–100.3 % of BF16 on Llama-3.1 8B–405B, W4A16 GPTQ recovers 98.7 % (8B), 99.5 % (70B) and 100.0 % (405B), and W4A16 is the most cost-efficient regime for single-stream serving (measured, >500k evaluations) ([Source](https://arxiv.org/abs/2411.02355)). The counterweight is that longer-trained small models quantize worse: Llama-3 8B loses ~2.5× the KLD of Llama-2 7B at q4_K_M (0.031 vs 0.0127; measured, background) and the "low-bit quantization favors undertrained LLMs" scaling law predicts 4-bit degradation becomes material around 4.5T training tokens for 7B and 17T for 70B ([Source](https://github.com/ggml-org/llama.cpp/blob/master/tools/perplexity/README.md), [Source](https://arxiv.org/abs/2411.17691)).

The practical rule per memory tier is "largest model that fits at ≥4.3–4.9 bpw, then spend leftover bytes on Q5–Q6 before stepping up a size". At 8 GB that means 7–9B dense at Q4_K_M/IQ4_XS (Llama-3 8B Q4_K_M 4.58 GiB, IQ4_XS 4.14 GiB) with 2–4 GiB left for KV and the OS; at 16 GB a 12–14B at Q5–Q6 (7.8–9.2 GiB), gpt-oss-20b in its native MXFP4 (12.08 GB resident under MLX on a 24 GB M5; vendor-measured) or a 27B at Q3_K_XL (Gemma 3 27B 12.76 GB scoring MMLU 70.87 against 71.5 BF16; measured by Unsloth); at 32 GB the 27–32B dense class at Q4_K_XL…Q6_K (15.6–20.6 GB), 35B-A3B MoE at Q4_K_XL…Q5_K_XL (20–25 GB), and 70B only at ≈2 bpw with a real hit (Llama-3-70B AQLM 1x16 at 21.9 GB drops MMLU 0.79 → 0.75; authors' numbers); at 64 GB a 70B at Q4_K_M–Q5_K_M (Llama-2-70B 38.5–45.4 GiB at +1.20 % / +0.40 % PPL; measured, background) while gpt-oss-120b MXFP4's 60.8 GiB checkpoint does not fit comfortably without expert offload ([Source](https://github.com/ggml-org/llama.cpp/blob/master/tools/perplexity/README.md), [Source](https://machinelearning.apple.com/research/exploring-llms-mlx-m5), [Source](https://unsloth.ai/docs/basics/unsloth-dynamic-2.0-ggufs), [Source](https://github.com/Vahe1994/AQLM), [Source](https://arxiv.org/html/2508.10925)). Unsloth's own guidance for ≤2-bit files — not for tool calling or agentic work, `presence_penalty ≥ 1.5` against looping, prefer UD-Q2_K_XL over 1-bit — should be surfaced as a model-catalog warning ([Source](https://unsloth.ai/docs/basics/dynamic-3.0-ggufs)).

Mixed precision is applied by the quantizer, so a reader that honours the per-tensor type in GGUF (or per-tensor bits in EXL3/MLX) gets it for free; the engine's only obligation is a kernel for every block type and per-tensor overrides from day one so it can consume UD/EXL3 recipes. The cross-ecosystem pattern is explicit in llama.cpp's `llama_tensor_get_type`: norms and 1-D tensors are never quantized, `output.weight` defaults to Q6_K, `attn_v` and `ffn_down` are promoted to Q6_K in the first and last eighth of layers plus every third middle layer (`use_more_bits`), 70B-class attention V goes to Q5_K because "8 heads share attn_v", and MoE attention gets Q8_0 when `n_expert == 8`, while MXFP4_MOE puts only 3-D expert tensors in MXFP4 and everything else in Q8_0 ([Source](https://github.com/ggml-org/llama.cpp/blob/master/src/llama-quant.cpp)); gpt-oss follows the same boundary, keeping attention, router and embeddings at 16-bit and only the MoE experts ("90+ % of parameters") in MXFP4 ([Source](https://arxiv.org/html/2508.10925)). The kernel priority by installed base is therefore Q4_K/Q5_K/Q6_K/Q8_0 and Q4_0 first; IQ4_XS/IQ4_NL and the codebook I-quants (IQ3_S/XXS, IQ2_*, IQ1_* with 256–2048-entry grids) second because every Unsloth low-bit file needs them; MXFP4 and NVFP4 third; TQ1_0/TQ2_0 only if ternary models matter; MLX affine 2/3/4/5/6/8-bit g32/64/128 in parallel for the Apple ecosystem; AWQ/GPTQ packings converted at load into the engine's own 4-bit tile layout (re-packing, not re-quantizing, so quality is preserved); and in-situ quantization from BF16 safetensors, as mistral.rs does, as the fallback for everything else ([Source](https://github.com/ggml-org/ggml/blob/master/src/ggml-common.h), [Source](https://github.com/EricLBuehler/mistral.rs)). Validation should use KLD against a BF16 reference on chat-templated held-out data, not perplexity (Unsloth and localbench both argue this; KLD on hard long-context chat data runs well above the 0.01–0.03 typical of Wikipedia tests) ([Source](https://localbench.substack.com/p/gguf-benchmark-methodology)). Licensing draws a hard line through the method space: GGUF/ggml, ExLlamaV3, VPTQ, T-MAC, BitNet, ZipNN, llm-awq, MLX are MIT; AQLM, HQQ, GemLite, Marlin, DFloat11, safetensors, GPTQModel (except its AGPL Swordfish kernel) are Apache-2.0; ParetoQ is BSD-3; **QTIP and QuIP# are GPL-3.0 and SpinQuant and any4/tinygemm are CC-BY-NC 4.0**, so only clean-room re-implementations from the papers would be safe and that is a legal question for the project ([Source](https://github.com/Cornell-RelaxML/qtip), [Source](https://github.com/facebookresearch/SpinQuant/blob/main/LICENSE), [Source](https://github.com/facebookresearch/any4)).

## KV cache: carve a paged arena once per device, keep three cache classes, default to 8-bit keys with rotation

Per-token KV cost is `Σ_layers 2 · n_kv_heads · head_dim · bytes` for attention layers, and the 2025–2026 architecture levers — GQA, MLA latents, interleaved sliding windows, and hybrid SSM/linear layers with zero per-token cost — take it from ~130–160 KiB/token down to 6–25 KiB/token ([Source](https://kaitchup.substack.com/p/the-kv-cache-of-small-moes-qwen3)). The worked examples from the notes (computed from `config.json`, BF16, author's arithmetic): Llama 3.1 8B **128 KiB/token → 16 GiB at 128K** (8.5 GiB q8_0, 4.5 GiB q4_0); Qwen3-8B 144 KiB → 18 GiB; Mistral Small 3.2 24B 160 KiB → 20 GiB; Gemma 3 27B 80 KiB plus a fixed 416 MiB of 1024-token windows → 10.4 GiB, but **62 GiB if local layers are cached in full** (what llama.cpp's `--swa-full` does); gpt-oss-20b 24 KiB → 3.0 GiB; Qwen3-Next-80B 24 KiB plus ~37.7 MiB of Gated DeltaNet state → 3.0 GiB; Granite 4.0-H Small 16 KiB plus ~73.7 MiB Mamba-2 state → 2.0 GiB; Nemotron 3 Nano 6 KiB plus ~24 MiB → 0.75 GiB; DeepSeek-V3.2 MLA latent 576-wide → 8.6 GiB at 128K in BF16 against ≈610 GiB if the per-head cache were expanded, which is why MLA must be served absorbed ([Source](https://huggingface.co/unsloth/Llama-3.1-8B-Instruct/blob/main/config.json), [Source](https://huggingface.co/unsloth/gemma-3-27b-it/blob/main/config.json), [Source](https://github.com/ggml-org/llama.cpp/pull/13194), [Source](https://huggingface.co/openai/gpt-oss-20b/blob/main/config.json), [Source](https://huggingface.co/Qwen/Qwen3-Next-80B-A3B-Instruct/blob/main/config.json), [Source](https://huggingface.co/ibm-granite/granite-4.0-h-small/blob/main/config.json), [Source](https://huggingface.co/nvidia/NVIDIA-Nemotron-3-Nano-30B-A3B-BF16/blob/main/config.json), [Source](https://huggingface.co/deepseek-ai/DeepSeek-V3.2-Exp/blob/main/config.json)). Recurrent state is paid per concurrent sequence, not per token (32 Granite H-Small sequences hold 2.3 GiB before any token is cached), every 2026 hybrid declares it in float32 (`mamba_ssm_dtype`), and vLLM's hybrid page alignment shows the cost of a single page size across layer groups: Falcon-H1's Mamba state pins a 1.6 MB page, inflating the attention block to 1,568 tokens so FP8 KV yields only 1.84× capacity at 32K and 1.00× at ≤1K (measured) ([Source](https://github.com/vllm-project/vllm/issues/55196), [Source](https://huggingface.co/nvidia/NVIDIA-Nemotron-3.5-Lightning-30B-A3B-BF16/blob/main/README.md)). The planner therefore needs three cache classes: per-token K/V for full-attention layers, ring buffers bounded by the window for sliding/chunked layers, and fixed fp32 recurrent state per sequence for DeltaNet/KDA/Mamba-2/short-conv layers (50–160 MB for the 2026 hybrid class, 1–4 GB of per-token KV at 128K).

Quantizing the cache is production-safe at 8 bits and model-dependent below. On Qwen2.5-7B (wikitext-2, build 0be8468) **q8_0/q8_0 raised PPL 7.9605 → 7.9940 (KLD 0.00178) while q4_0 keys collapsed it to 1,561** (KLD 5.49) and q4_0 values alone changed 1 of 500 ARC answers against 375/500 for q4_0 on both (measured, hardware unstated); the key/value asymmetry is structural because key error is amplified through softmax ([Source](https://github.com/ggml-org/llama.cpp/discussions/23470)). The Hadamard "attn-rot" merged on 2026-04-01 rotates Q/K/V in 64-wide blocks before caching, is backend-agnostic, does not support MLA, and took gpt-oss-20b AIME25 under Q4_0 KV from **2.0 % to 21.7 %** (Q8_0 KV from 31.7 to 37.1 against 37.9 % at F16) at a decode cost of 0.88–0.93× on CUDA (measured by contributors) ([Source](https://github.com/ggml-org/llama.cpp/pull/21038)). TurboQuant's "3-bit, no loss" claim (vendor-claimed, Google) did not survive vLLM's May 2026 study: FP8 and k8v4 recover >98 % on reasoning, 4-bit-nc ≈96 %, the 3-bit variants drop ≈20 points, latency rises 10–68 % over BF16, and the recommendation is "FP8 is the best default; k8v4 no significant advantage over FP8; avoid 3-bit" (measured); llama.cpp closed its TurboQuant PR as no better than same-bpw formats once the rotation was upstream ([Source](https://research.google/blog/turboquant-redefining-ai-efficiency-with-extreme-compression/), [Source](https://vllm.ai/blog/2026-05-11-turboquant), [Source](https://github.com/ggml-org/llama.cpp/pull/21089)). The speed cost on an A100 for Qwen3-8B Q4_K_M: q8_0 decode at 83 % of f16 at 8K prompt and 66 % at 32K, with VRAM for four 64K slots falling from 41.0 to 25.1 GiB (q8_0) and 16.1 GiB (q4_0) (measured, one model, single runs) ([Source](https://sotaaz.com/post/llamacpp-server-kv-cache-quantization-en)). Backend coverage silently decides whether quantized KV is fast: quantized V requires flash attention in llama.cpp, Metal requires K and V to share a type (so q8_0-K/q4_0-V fails on Apple), and on CUDA an asymmetric pair without `GGML_CUDA_FA_ALL_QUANTS` "silently falls back to CPU-based attention" — prefill 96 → 2,361 tok/s after enabling the flag (self-reported) ([Source](https://github.com/ggml-org/llama.cpp/blob/master/src/llama-context.cpp), [Source](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-metal/ggml-metal-device.m), [Source](https://github.com/ggml-org/llama.cpp/issues/24485)). The recommendation: expose K and V precision separately, default to q8_0 (or FP8 on tensor-core GPUs) for keys and allow q4_0 values, apply block rotation before quantizing, never ship 4-bit keys without a per-model guard (a quick KLD or answer-churn test on load), keep the per-backend kernel matrix (head dims × K type × V type × mask/sink flags) explicit and fail loudly rather than fall back to CPU, and quantize recurrent state to int8 as SGLang and Quamba2 do if FP8/INT8 KV is to pay off on hybrids at short context.

Paging is the right structure on every backend, but the mechanism differs. vLLM V1 hashes full blocks as `hash(parent_hash, token ids, extra keys)` with SHA-256 by default since v0.11 (xxhash "raises collision risk" and may "leak private information in multi-tenant setups"), keeps a pre-allocated block pool with reference counts and an LRU free queue, and groups layers by attention type so SWA blocks outside the window are freed into the shared queue ([Source](https://docs.vllm.ai/en/stable/design/v1/prefix_caching.html), [Source](https://docs.vllm.ai/en/latest/design/hybrid_kv_cache_manager.html)). llama.cpp still preallocates one contiguous `n_ctx × n_seq_max` buffer per layer (unified or split per slot, each slot getting `n_ctx / n_seq_max`), wraps two caches for SWA models (window cache sized `PAD(n_swa · n_seq_max + n_batch)`) and two for DSA models (latents plus indexer keys), has no defragmentation, and a community paged-KV draft showed **unified OOM at 26 sequences versus 247 sequences paged on an A10G** at ≈3 % slower throughput, unmerged and unanswered (measured by proposer) ([Source](https://github.com/ggml-org/llama.cpp/blob/master/src/llama-kv-cache.cpp), [Source](https://github.com/ggml-org/llama.cpp/pull/13194), [Source](https://github.com/ggml-org/llama.cpp/pull/23346), [Source](https://github.com/ggml-org/llama.cpp/discussions/21961)). CUDA VMM growth (vAttention's "up to 1.23×" over paged kernels, vendor-claimed; kvcached's 2 MiB physical pages and "2–28× TTFT reduction" under bursty multi-model load, vendor-claimed) is NVIDIA/ROCm-only ([Source](https://arxiv.org/abs/2405.04437), [Source](https://github.com/ovg-project/kvcached)). On Metal and CPU the allocator itself is the hazard (the MLX 108 GB pool), so the design is: reserve the KV arena once per device from the per-token formula times the admitted budget, carve it into fixed 16–64-token blocks in one `MTLBuffer`/heap or one anonymous mapping, keep separate pools (or integer-multiple block sizes) for recurrent state as llama.cpp, SGLang and TensorRT-LLM do, free blocks by index, grow nothing by reallocation, and let attention kernels take a block table (FlashAttention-2's `block_table` needs page size a multiple of 256; MLX's vector kernel takes contiguous K/V, so the engine's own Metal/CPU kernels should be block-table-aware from the start) ([Source](https://github.com/Dao-AILab/flash-attention)). Prefix sharing should be hash-chained per block with a cryptographic hash; a radix tree buys token-granular reuse for agent branches at scheduling cost.

Runtime eviction research is mostly not what local engines ship. StreamingLLM-style sink-plus-window truncation exists as llama.cpp's `--context-shift` (off by default, discards `n_left / 2` after the kept prefix, impossible on SWA caches) and mlx-lm's `--max-kv-size` rotating cache; gpt-oss bakes a learned sink into the softmax denominator ([Source](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md), [Source](https://github.com/ggml-org/llama.cpp/pull/13194), [Source](https://arxiv.org/abs/2508.10925)). SnapKV ("3.6× generation speed, 8.2× memory efficiency at 16K"), PyramidKV ("12 % of the cache" matches full KV on LongBench) and H2O are vendor-claimed and background, appear only in competitors' tables, and no local engine implements them ([Source](https://arxiv.org/abs/2404.14469), [Source](https://arxiv.org/abs/2406.02069)). What ships instead is lossless tiering: llama.cpp's host-RAM prompt cache with prefix-similarity matching (`--cache-ram` 8192 MiB, idle slots parked, 32 checkpoints per slot at ≥8192-token spacing), vLLM's `OffloadingConnector` to pinned CPU memory, SGLang's HiCache and LMCache's GPU → pinned DRAM → NVMe → remote tiers ([Source](https://github.com/ggml-org/llama.cpp/pull/16391), [Source](https://github.com/LMCache/LMCache)). The field-measured payoff of persistence is large: on an RTX 3090 with a 27B at 100K context, per-message prefill went from **over one minute to ≈0.2 s with slot restore**, at 1 GB for short sessions and ≈4.4 GB near 100K tokens, and SWA models needed `--swa-full` or the restored cache was unusable (self-reported) ([Source](https://github.com/ggml-org/llama.cpp/discussions/20572)). Hybrid models are the sharp edge: partial `seq_rm` on recurrent state fails, so llama-server "forc[es] full prompt re-processing" on Qwen3-Next/Qwen3.5 turns, with one user seeing ≈8-minute stalls per turn and ≈75 MiB checkpoints (self-reported) ([Source](https://github.com/ggml-org/llama.cpp/issues/20225)). The engine should treat a checkpoint (SWA window + recurrent state) as a first-class budgeted object, make truncation an explicit opt-in with chat-boundary-aware cut points, and tier whole prompt states to RAM and SSD keyed by prefix hash — SSD pays off whenever `bytes / disk_bandwidth < prefill_time`, which is true on most consumer GPUs and all CPU-only runs at ≥16K tokens.

Cross-session caching has concrete security facts. A shared cached prefix shortens TTFT measurably: CVE-2025-46570 (vLLM < 0.9.0) gave an attacker on the same backend AUC 0.571 for a 1-token prefix and **0.99 for 8 tokens** (measured), fixed by folding a per-request `cache_salt` into the first block hash at no performance cost ([Source](https://osv.dev/vulnerability/GHSA-4qjh-9fv9-r85r), [Source](https://docs.vllm.ai/en/stable/design/v1/prefix_caching.html)); plaintext KV files can be inverted back to prompts (direct inversion works for MHA, collision/injection attacks for GQA/MLA) per NDSS 2026 (vendor-claimed) ([Source](https://arxiv.org/abs/2508.09442)). The cache key should be `hash(model digest + quant/KV types + RoPE/context params + chat template + block tokens + parent hash + server-derived per-client salt)` with a cryptographic hash, save files written 0600 under the app data directory with a validating header, salt-scoped reuse on by default whenever more than one API key exists, and SWA/recurrent models stored as full checkpoint sets. Because most engines cache post-RoPE keys, changing the YaRN factor invalidates saved caches, so RoPE configuration belongs in the key.

Context extension is a metadata-driven interface, not a feature. Shipping models need plain RoPE with θ from 1e4 to 1e11, partial rotary (Qwen3-Next/3.5 rotate 64 of 256 dims, interleaved mRoPE sections [11,11,10]), YaRN with its attention-scale term (Qwen3 opt-in ×4, gpt-oss ×32, DeepSeek ×40, Mistral Small 4 ×128), Llama-3 piecewise scaling (3.1 ×8, Llama 4 ×16), linear scaling with per-layer bases (Gemma 3 global 1e6 ×8, local 1e4), LongRoPE (Phi-4-mini), and NoPE layers with Llama 4's inference-time attention temperature ([Source](https://huggingface.co/Qwen/Qwen3-8B), [Source](https://huggingface.co/openai/gpt-oss-20b/blob/main/config.json), [Source](https://huggingface.co/unsloth/Llama-4-Scout-17B-16E-Instruct/blob/main/config.json), [Source](https://arxiv.org/abs/2503.19786)). Qwen's card warns that open runtimes "apply a constant scaling factor regardless of input length ... potentially impacting performance on shorter texts" and advises factor 2.0 for ≈65K contexts and none below 32K, so the factor must be a per-request or per-engine setting with a server-side cap, not baked into the model file ([Source](https://huggingface.co/Qwen/Qwen3-8B)). The GGUF spec page lists `rope.scaling.{type,factor,original_context_length}` but not sliding-window keys, per-layer head-count arrays or YaRN betas, which llama.cpp's converter writes; those newer keys must be read from the converter, not the spec (gap) ([Source](https://github.com/ggml-org/ggml/blob/master/docs/gguf.md)).

## CPU execution: int8 dot kernels on physical performance cores, parked threads, and a MoE path that reads only the selected experts

Production CPU inference is int8-dot-product centric and the ISA matrix a Rust engine should target, in priority order, is: AVX2 + FMA with `vpmaddubsw` (every x86 machine); AVX-VNNI (Intel Core 12th gen through Core Ultra 300, which disable AVX-512) and AVX-512 VNNI/VBMI (Zen 4/5, Xeon); NEON dotprod + i8mm (every Apple M-series, Snapdragon X, Cortex-A7xx/X); SME2 for prefill on M4/M5, X2 Elite and Dimensity 9500; AMX only for Xeon workstations ([Source](https://en.wikipedia.org/wiki/Arrow_Lake_(microprocessor)), [Source](https://en.wikipedia.org/wiki/Zen_5), [Source](https://github.com/ggml-org/llama.cpp/issues/26547)). SVE can be skipped: no consumer core has 256-bit SVE, Apple ships SME2 without non-streaming SVE, and llama.cpp's SVE kernels are gated on a 256-bit vector length so they never run on 128-bit Cortex-X925/Neoverse-N2 parts ([Source](https://github.com/ggml-org/llama.cpp/issues/26547)). Rust reachability is the practical constraint: AVX-512 target features and intrinsics stabilised in Rust 1.89 (August 2025), NEON has been stable since 1.59, SVE intrinsics merged into stdarch in April 2026 but are nightly-only, SME intrinsics do not exist in stdarch, AMX intrinsics remain nightly (`x86_amx_intrinsics`), and portable SIMD is still unstable — but `asm!` is stable, so SME2 and AMX paths go through inline assembly or FFI (KleidiAI's SME kernels are `.S` files linkable through `cc`) without forcing nightly ([Source](https://blog.rust-lang.org/2025/08/07/Rust-1.89.0/), [Source](https://github.com/rust-lang/stdarch/pull/2071), [Source](https://github.com/rust-lang/rust/issues/126622), [Source](https://github.com/rust-lang/rust/issues/86656), [Source](https://raw.githubusercontent.com/ARM-software/kleidiai/main/README.md)). Apple's AMX co-processor is not part of the public ISA; reach it through Accelerate `cblas_sgemm`/BNNS for fp32/fp16 prefill (as MLX does — Accelerate routes fp32 GEMM to AMX on M1–M3 and SME on M4+), not directly ([Source](https://arxiv.org/html/2606.25426), [Source](https://raw.githubusercontent.com/ml-explore/mlx/main/mlx/backend/cpu/CMakeLists.txt)).

The winning kernel recipe on every CPU is to keep weights in 4–8-bit blocks, quantize activations to int8 on the fly, run integer dot products, and repack weight blocks into an ISA-specific interleaved tile layout so one SIMD multiply-add consumes 4–16 rows. The measured gains are mostly in prefill: Q4_K block interleaving for AVX2 lifted a Ryzen 7600X 7B pp512 **45.8 → 73.8 tok/s (+61 %) with tg128 −2 %** (measured, merged 2025-03) ([Source](https://github.com/ggml-org/llama.cpp/pull/12332)); AVX-512 VNNI+VBMI on a Ryzen AI MAX+ 395 gave Qwen3-4B pp512 380.5 → 568.1 (+49 %) with tg unchanged (measured, PR open) ([Source](https://github.com/ggml-org/llama.cpp/pull/29397)); VNNI repack kernels gave 2.1–3.9× pp2048 on a 9950X and 1.8–2.8× on a Core Ultra 7 155H at 4 threads with tg 0.99–1.21× (measured, PR open) ([Source](https://github.com/ggml-org/llama.cpp/pull/30036)); and on Arm the original Q4_0 online repack took a Graviton 3 phi-2 from 38.0 → 110.8 pp512 and 17.0 → 39.4 tg128 at 4 threads while regressing x86 decode by up to 31 % on an i5-13600K, which is why the layout is now selected at runtime behind a buffer type (measured, background) ([Source](https://github.com/ggml-org/llama.cpp/pull/9921)). KleidiAI's SME2 Q4_0 path gave a single-thread Llama-3.2-3B ≈1.55× over i8mm on Android (vendor-measured), and SMEPilot reports 4.10–4.44 TFLOP/s prefill GEMM on an M4 Pro, 6–7× ggml CPU, 0.72–0.96× of the M4 Pro iGPU, with the caveats that SME is 4.1× slower than NEON on a fastexp kernel and that naive packing tripled decode GEMV latency (paper) ([Source](https://learn.arm.com/learning-paths/mobile-graphics-and-gaming/performance_llama_cpp_sme2/run_llm/), [Source](https://arxiv.org/html/2606.16332)). The engine should implement per block family a scalar reference, a GEMV on the native block layout for decode (bandwidth-bound; repack buys ≤10 %), and a GEMM on an interleaved layout (4x4/4x8 NEON, 8x8 AVX2, 8x4/16x4 VNNI, mr16×nr64 SME2) used when `n_tokens ≥ ~8–32`, with tile sizes derived from the register file (16 ymm / 32 zmm / 32 NEON v-regs / 512-bit ZA tiles) and cache blocking only in prefill GEMM. Repacking must be a cached artifact, not a per-load transform: llama.cpp pays Phi-4 Q4_K_M load **17 → 77 s and Command-A 109 → 1,221 s on a dual Xeon** (measured), an open PR seeks a KleidiAI weight cache for the same reason, and repacking copies weights into anonymous memory, defeating mmap sharing and page-cache evictability ([Source](https://github.com/ggml-org/llama.cpp/pull/12332), [Source](https://api.github.com/search/issues?q=repo:ggml-org/llama.cpp+is:pr+kleidiai+in:title)). A sidecar keyed by model hash plus layout id, itself mmapped, pays the cost once and keeps resident memory predictable; a mixed strategy keeps packed copies only for tensors touched by prefill GEMM. LUT kernels (T-MAC's 4–5× over 2024 llama.cpp on BitNet-3B, bitnet.cpp's 2.37–6.17× on x86; vendor-measured) pay off only for ≤2-bit or ternary weights; for Q4/Q8 the int8 dot path is within ~1.2× and simpler ([Source](https://raw.githubusercontent.com/microsoft/T-MAC/main/README.md), [Source](https://github.com/microsoft/BitNet)).

Threading is where llama.cpp's own PRs show the losses. Its CPU backend is a fork-join graph executor with one barrier per op and a spin-then-sleep wait: at the default `--poll 50` each thread spins ~6.5 million `pause` iterations (~100 ms) before parking, which is pathological when a GPU owns the critical path ([Source](https://github.com/ollama/ollama/pull/18613), [Source](https://github.com/ggml-org/llama.cpp/pull/8672)). In `--n-cpu-moe` decode the barrier was **~30 % of CPU time**; per-thread activation quantization removed one barrier (30 % → 7 %) and with a fused single-token gated activation, cache-line padding and work stealing gave +4–14 % on x86 hosts but 0.75–0.79× on an M2 Ultra at 2–4 threads (measured, PR open) ([Source](https://github.com/ggml-org/llama.cpp/pull/20596)). A yield-after-2048-spins barrier fix cut a 2-vCPU VM from 147 s to 4.4 s but cost 5.5–9.7 % tg on an uncontended M4 Pro and was closed (measured) ([Source](https://github.com/ggml-org/llama.cpp/pull/29258)). SMT threads reduce decode throughput (HX 370: 12 threads 3.54, 24 threads 2.84 tok/s; 9950X tg falls from 6.25 at 4 threads to 5.91 at 16; measured), and llama.cpp's macOS default took only `hw.perflevel0.physicalcpu` — on an M5 Max that is the 6-core "Super" cluster, so 6 threads gave pp512 27.0 / tg128 9.24 against 56.8–60.1 / 13.0–14.0 with all 18 performance-class cores (measured, fix PR open) ([Source](https://github.com/ggml-org/llama.cpp/issues/19480), [Source](https://github.com/ggml-org/llama.cpp/pull/30036), [Source](https://github.com/ggml-org/llama.cpp/issues/29782)). macOS offers no affinity API; QoS classes are the lever, and Apple recommends utility or lower at least 90 % of the time when the user is not active ([Source](https://developer.apple.com/library/archive/documentation/Performance/Conceptual/EnergyGuide-iOS/PrioritizeWorkWithQoS.html)). NUMA combined with interleaved repack measurably regresses (dual Xeon 4216: tg −7.5 to −15 %; measured) ([Source](https://github.com/ggml-org/llama.cpp/pull/12332)). The design: size the decode pool to the sum of all performance-class clusters on Apple and P-cores on Intel hybrids (2–6 threads often suffice for bandwidth-bound decode on desktop DDR5); bounded spin of tens of microseconds then futex/condvar parking, never spinning when a GPU backend owns the step; one parallel region per fused op (quantize → matmul → gating) with work stealing over row chunks for prefill and static row partitioning for decode so each thread's weight stream stays contiguous; QoS utility/`SCHED_BATCH`/EcoQoS when backgrounded; first-touch per NUMA node with per-node thread groups and no cross-node repack.

The MoE expert path is the biggest unclaimed CPU win. The 80B-A3B model reads 2–3 GB per token and should decode at 20–30 tok/s on the HX 370's ~65 GB/s but measured 7.74 (3–4× short), the EPYC 9454P cross-reference shows 63.1 tok/s for Qwen3-30B-A3B but only 11.76 for Qwen3-Next-80B, and ik_llama.cpp is cited as ~1.9× faster on MoE via fused ops (unverified) ([Source](https://github.com/ggml-org/llama.cpp/issues/19480)). The notes locate the loss in scheduling and overheads, not DRAM: a correct `mul_mat_id` should stream only the k selected experts' rows per token with one activation-quantization pass shared across experts, parallelise across (expert, row-chunk) pairs with work stealing rather than per expert, avoid rebuilding token→expert maps for single-token decode, and prefetch next-layer experts (ProMoE reports 2.07× average decode over reactive offloading; paper) or `madvise(MADV_WILLNEED)` expert pages when the model exceeds RAM (an 8 GB MacBook Air went from thrashing to 0.57 tok/s with router-driven hints; anecdotal) ([Source](https://arxiv.org/abs/2410.22134), [Source](https://huggingface.co/waltgrace/llama-cpp-expert-sniper)). KTransformers' AMX kernels (Apache-2.0) are the reference for Xeon-class prefill — DeepSeek-V3 prefill 255–287 tok/s on dual 32-core Xeons against 10.3 for llama.cpp, with the "AMX for prefill, AVX-512 for decode" dispatch rule and "Expert Deferral" overlapping CPU expert work with GPU attention for up to 1.45× (vendor-measured / paper) ([Source](https://github.com/kvcache-ai/ktransformers/blob/main/doc/en/DeepseekR1_V3_tutorial.md), [Source](https://madsys.cs.tsinghua.edu.cn/publication/ktransformers-unleashing-the-full-potential-of-cpu/gpu-hybrid-inference-for-moe-models/)). Hot/cold neuron systems (PowerInfer, PowerInfer-2) require ReLU-sparse checkpoints that mainstream 2025–2026 models do not ship and are not a near-term lever ([Source](https://github.com/Tiiny-AI/PowerInfer)). CPU prefill needs a proper GEMM with int8-quantised activations, fused QKV, micro-batches of 512–2048 tokens and a CPU flash-attention kernel (throughput falls from pp2048 572 to pp4096 497 on the 9950X as attention cost grows; measured), and a dynamic chunk queue when SME2 and NEON units run together (static splits lost up to 2× at low thread counts; Exynos pp512 2 threads 163.9 → 303.9 with a global chunk queue; measured) ([Source](https://github.com/ggml-org/llama.cpp/pull/30036), [Source](https://github.com/ggml-org/llama.cpp/pull/23819)). The ordered engineering checklist that follows from the measured payoffs is: decode GEMV kernels on native GGUF blocks per ISA (target bytes/token × 0.7 × peak bandwidth), the MoE expert path, prefill GEMM on packed layouts with CPU flash attention, the packed-weight disk cache, the physical-core scheduler with bounded spin, QoS/priority controls, NUMA/CCD awareness, and optional Accelerate/AMX/LUT accelerators. No 2026 source compares any Rust CPU engine (candle, mistral.rs) against llama.cpp on the same machine; that baseline must be measured by LLMario itself (gap).

## GPU and NPU backends: Metal first, CUDA second, Vulkan as the universal fallback, NPUs behind a delegate boundary

On Apple silicon the winning design is already visible in both llama.cpp and MLX and should be copied rather than reinvented. llama.cpp wraps the mmap'd model with `newBufferWithBytesNoCopy` in `MTLResourceStorageModeShared` (page-aligned start, whole-page length, one VM region), splits data larger than `maxBufferLength` into overlapping views sized so any tensor fits one view (capped at 64 buffers), uses no `MTLHeap`, derives capability flags from `supportsFamily:` (simdgroup matrix on Apple7+), and enables the Metal 4 tensor path only when the device name contains "M5", "M6", "A19" or "A20" *and* a small f16/bf16 tensor kernel test-compiles — a gate added after issue #27473 found the tensor API "silently inert on M5+/A19+" because `MTLCompileOptions.languageVersion` was never set ([Source](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-metal/ggml-metal-device.m), [Source](https://github.com/ggml-org/llama.cpp/issues/27473)). The tensor path was gated to M5+ because on an M2 Ultra it was slightly slower than the simdgroup kernels, pipeline-state creation costs 1–2 s per tensor-op kernel (community), and its measured value is prefill: base-M5 Llama-3.1-8B Q4_0 pp512 257 → 609 tok/s with tg128 22.6 → 22.9 (community) ([Source](https://github.com/ggml-org/llama.cpp/pull/16634)). Kernel selection in `ggml_metal_op_mul_mat` runs MMA → a "mat-vec-ext" path for 2–8 query rows → `mul_mm` → `mul_mv`, with fusions for soft_max+top-k MoE routing, SSM conv+SiLU and `mul_mat + add`; b11404 (October 2026) added few-row kernels for 2–16 rows that turned speculative verification from a loss into a 3.4× win ([Source](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-metal/ggml-metal-ops.cpp), [Source](https://rohitai.com/blog/llama-cpp-b11404-metal-few-row-mma-speculative-decoding)). MLX's SDPA dispatch is the pattern for attention: `sdpa_vector` for ≤8 queries with a two-pass split-K variant above 1,024/4,096/8,192 keys, `steel_attention` for prefill (NAX variants for head dims 64–512 on M5), head dims 72/80 zero-padded to 96, and an unfused fallback whenever no fused kernel matches — one correctness report found the fused op giving wrong scores on MLX 0.31.2/M4 (self-reported) ([Source](https://github.com/ml-explore/mlx/blob/main/mlx/backend/metal/scaled_dot_product_attention.cpp), [Source](https://upd.dev/ml-explore/mlx/issues/3585)). A framework-free Metal 4 runtime (BaseRT) reports on an M5 Pro 48 GB: Qwen3-30B-A3B 4-bit decode **105.1 tok/s versus llama.cpp 96.7 and mlx-lm 97.7**, prefill 3,834 versus 1,740 and 2,676, and Qwen3.6-27B dense decode 18.1 / 15.4 / 18.4 (self-reported by authors), using MPP `matmul2d` cooperative-tensor kernels for prefill GEMM, MoE expert GEMM and prefill attention and SIMD GEMV for decode — confirming that single-stream decode should stay on bandwidth-tuned GEMV while tensor ops serve prefill, batched decode, speculative verification and MoE expert GEMMs ([Source](https://arxiv.org/html/2607.19438v1)). From Rust the binding is `objc2-metal` 0.3.2 (Zlib/Apache/MIT; Metal 4 command buffers, `MTLTensor`, residency sets bound; resource/sync APIs `unsafe`); wgpu migrated its Metal backend to it citing soundness bugs in hand-written `objc` sends, and the `metal` crate is deprecated (listing, unverified) ([Source](https://docs.rs/objc2-metal/latest/objc2_metal/), [Source](https://github.com/gfx-rs/wgpu/pull/5641)). Phase 1 therefore is: shared-mode buffers over mmap for weights, a small placement/`MTLHeap` arena for activations and KV, residency sets with a keep-alive thread, a budget from `recommendedMaxWorkingSetSize` with an explicit logged opt-in to raise `iogpu.wired_limit_mb`, simdgroup GEMM plus bandwidth-tuned quantized GEMV plus fused norm/RoPE/attention kernels, a runtime-probed (test-compiled) `matmul2d` path for prefill and MoE on M5/A19+, and MSL compiled to `.metallib` at build time with a `newLibraryWithSource` fallback.

CUDA is the second backend and its patterns are well understood. The RTX 5090 (GB202) carries 32 GB GDDR7 at **1,792 GB/s** with FP4 tensor throughput of 1,676 dense TFLOPS (vendor spec); the 4090 has 1,008 GB/s and no FP4, the 3090 936 GB/s and no FP8 ([Source](https://images.nvidia.com/aem-dam/Solutions/geforce/blackwell/nvidia-rtx-blackwell-gpu-architecture.pdf)). Capturing each token's kernel stream into a CUDA graph gave up to 1.2× at batch 1 (background, NVIDIA on H100), and ggml's current strategy — a warm-up call with unchanged node properties, `memcmp` of tensor structs, `cudaGraphExecUpdate` on change with destroy/re-instantiate on failure, graphs disabled when a `MUL_MAT_ID` needs a stream sync — is the one to copy, together with its fusion list (RMSNorm+mul/RoPE/set-rows, gate/up GLU for `mul_mat` and `mul_mat_id`, top-k MoE routing, MoE weighted reduction) ([Source](https://developer.nvidia.com/blog/optimizing-llama-cpp-ai-inference-with-cuda-graphs), [Source](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-cuda/ggml-cuda.cu)). Quantized decode uses custom MMVQ GEMV and int8 MMQ GEMM with cuBLAS only as the dense fallback; NVFP4 matmuls route to sm_120 FP4 tensor cores since build b8967 (prefill +43–68 %, decode flat; community via secondary) ([Source](https://insiderllm.com/guides/fp4-inference-llamacpp-nvfp4-mxfp4/)). The memory story has two rules: a VMM-backed arena (ggml reserves a 32 GB VA range and grows in granularity-sized chunks) is the simplest way to get predictable KV growth, and CUDA managed memory is a trap even on unified-memory hardware — on a DGX Spark `GGML_CUDA_ENABLE_UNIFIED_MEMORY=1` lowered gpt-oss-120B tg32 from 45.9 to 40.6 tok/s (community) ([Source](https://github.com/ggml-org/llama.cpp/discussions/16578)). From Rust, `cudarc` 0.19.10 (Apache/MIT; CUDA 11.4–13.4 by feature, driver API, NVRTC, cuBLAS/cuBLASLt/cuDNN/NCCL wrappers, dynamic loading by default so users need no toolkit at build time) with NVRTC-compiled, cached PTX is the lowest-friction path; candle's build-time PTX via `cudaforge` is the alternative; NVIDIA's `cuda-oxide`/`cutile-rs` and the rebooted Rust-CUDA are "early-stage research ... expect bugs, incomplete features, and API breakage" and should not carry a production kernel set in 2026 ([Source](https://docs.rs/crate/cudarc/latest), [Source](https://github.com/huggingface/candle/blob/main/candle-kernels/build.rs), [Source](https://github.com/NVlabs/cuda-oxide), [Source](https://github.com/Rust-GPU/Rust-CUDA)).

Vulkan is now a credible single cross-vendor path and belongs third. Its design (NVIDIA's Jeff Bolz, Vulkanised 2025) runs on any Vulkan 1.2 device with scalar, KHR cooperative-matrix and NVIDIA coopmat2 matmul paths, per-format dequantization callbacks, and indirected MoE loads; an optimised coopmat1 GEMM reached ~98 TFLOPS of a ~116 TFLOPS peak on an RTX 4070 against ~8 for a naive kernel (vendor-measured) ([Source](https://www.vulkan.org/user/pages/09.events/vulkanised-2025/T47-Jeff-Bolz-NVIDIA.pdf)). On Strix Halo it wins decode and loses prefill: Qwen3-Coder-30B-A3B Q4_K_S **Vulkan 97.7 tg / 1,115 pp versus ROCm 73.7 / 1,345** (measured, different builds), and RADV leads tg while ROCm leads pp across a 2026 model sweep; leadership flipped between 2025 and 2026 runs, so the engine should keep per-device benchmark-based backend selection cached from a first-run autotune ([Source](https://www.soothill.io/blog/2026/08/03/llamacpp-vulkan-vs-rocm-strix-halo/), [Source](https://slb350.github.io/strix-benchmarks/)). The recurring bugs are driver/coopmat specific — incoherent coopmat2 FA output on a 3090, GPU timeouts on Intel Arc 140V closed "not planned", stale K/V from freed cells on a Radeon 8060S, a build break when glslc lacks `GL_KHR_cooperative_matrix` — so the backend needs a per-device feature allow/deny list, an env/CLI switch to disable coopmat and flash attention, and a numerical self-test at startup ([Source](https://github.com/ggml-org/llama.cpp/issues/11268), [Source](https://github.com/ggml-org/llama.cpp/issues/20554), [Source](https://github.com/ggml-org/llama.cpp/issues/26744), [Source](https://github.com/ggml-org/llama.cpp/issues/29373)). Bind through `ash` (raw Vulkan 1.1–1.4, extensions by namespace) rather than `wgpu`, whose WebGPU abstraction hides cooperative matrices and f16/int8 dot features; compile GLSL (or Slang) to SPIR-V at build time; on macOS use MoltenVK (Apache-2.0, "not fully compliant") or Mesa's Metal-4-based KosmicKrisp (conformant, macOS 26+) only as a portability test path, since Metal is ~10–20 % faster on the one cross-API data point (M4 Max 7B Q4_0: Vulkan 724.8/75.0 vs Metal 885.7/83.1; community) ([Source](https://github.com/ash-rs/ash), [Source](https://github.com/gfx-rs/wgpu), [Source](https://github.com/KhronosGroup/MoltenVK), [Source](https://docs.mesa3d.org/drivers/kosmickrisp.html), [Source](https://github.com/ggml-org/llama.cpp/discussions/10879)). For AMD discrete cards ROCm 7.14 Linux and HIP SDK 7.2 Windows cover RX 7000/9000 and the gfx1151/gfx1150 iGPUs ([Source](https://rocm.docs.amd.com/projects/install-on-linux/en/latest/reference/system-requirements.html), [Source](https://rocm.docs.amd.com/projects/install-on-windows/en/latest/reference/system-requirements.html)); for Intel, the SYCL backend verified on oneAPI 2026.1 gave an Arc B570 3.1× prefill over the 2025.3 build (self-reported), but a second kernel language solely for Intel prefill is hard to justify — Vulkan-first covers Arc A/B with one kernel set ([Source](https://github.com/ggml-org/llama.cpp/blob/master/docs/backend/SYCL.md)). WebGPU/wgpu should stay a test backend: measured per-dispatch overhead is 24–71 µs across Dawn/wgpu/Chrome/Safari (~1,040 µs in Firefox), kernel fusion gave +53 % on Vulkan but nothing on Metal/CUDA, and a fused fp32 Qwen2.5-0.5B decoded at **21.0 tok/s via torch-webgpu against 185.5 via CUDA fp16 on the same 5090** (measured) ([Source](https://arxiv.org/html/2604.02344v1)). DirectML is "in sustained engineering" and Windows ML is a model-level ONNX runtime with vendor execution providers, not a kernel API ([Source](https://learn.microsoft.com/en-us/windows/ai/directml/dml), [Source](https://learn.microsoft.com/en-us/windows/ai/new-windows-ml/overview)).

NPUs in October 2026 are a prefill and small-model accelerator behind static-shape, per-SoC, single-tenant vendor runtimes, and the engine should not write NPU kernels. Measured decode on 8B-class models is 8–12 tok/s on Intel/AMD/Qualcomm NPUs versus 2–4× that on the same machine's iGPU: FastFlowLM on a Ryzen AI 7 350 gives Llama 3.1 8B 12.8 tok/s at 1K context and OOM at 64K, with "the NPU can access only under 50 % of system DRAM" (vendor page); on Strix Halo Lemonade's NPU path decoded Qwen3-8B at 8.2 tok/s while the Vulkan GPU did 19.7 on a 9B, and running both concurrently cost the NPU 5.8 % and the GPU 14.1 % for a **1.42× wall-time gain** (measured by one individual) ([Source](https://fastflowlm.com/docs/benchmarks/llama3_results/), [Source](https://sleepingrobots.com/dreams/lemonade-server-npu-strix-halo/)). Each NPU adds an address or shape limit: Hexagon sessions expose ~3.5 GB of virtual address space, forcing dynamic buffer remapping or layer splits across virtual sessions, and the Windows build requires test-signing the NPU library ([Source](https://github.com/ggml-org/llama.cpp/blob/master/docs/backend/snapdragon/README.md), [Source](https://github.com/ggml-org/llama.cpp/blob/master/docs/backend/snapdragon/windows.md)); OpenVINO GenAI on Intel NPUs needs symmetric INT4 (group 128 or channel-wise), a static `MAX_PROMPT_LEN` 1,024 + `MIN_RESPONSE_LEN` 128 budget, compile-on-load with blob caching, ">16 GB of RAM" for 7B models with prompts over 1,024 tokens, and produced garbled output past ~2,000 tokens with no error in one issue ([Source](https://raw.githubusercontent.com/openvinotoolkit/openvino/master/docs/articles_en/openvino-workflow-generative/inference-with-genai/inference-with-genai-on-npu.rst), [Source](https://github.com/openvinotoolkit/openvino.genai/issues/3255)); Apple's ANE has no public SDK beyond Core ML, its ~32 MB on-chip SRAM overflows at 4096² (5.7 TFLOPS measured at 2048², 4.0 at 4096² on an M4 via a private interface; one individual), and INT8 is no faster than FP16 ([Source](https://arxiv.org/abs/2606.22283), [Source](https://maderix.substack.com/p/inside-the-m4-apple-neural-engine-615)); MNN's Hexagon backend wins prefill 7.9× over the CPU on Qwen3-0.6B but loses decode (68.5 vs 94.3 tok/s; vendor table) ([Source](https://github.com/alibaba/MNN/releases)); Foundry Local NPU models fail under parallel fan-out ([Source](https://github.com/microsoft/Foundry-Local/issues/506)). The practical shape is an optional "NPU runner" boundary delegating to vendor runtimes (OpenVINO GenAI, FastFlowLM/OGA via Lemonade, QAIRT/GenieX or llama.cpp's Hexagon and OpenVINO backends) behind the same device API, treated as a budgeted one-model-at-a-time device, used in priority order for embeddings and speech, draft models ≤2B, prefill offload for 4–8B models on laptops, and full decode only for ≤2B assistants in battery mode. The kernel-authoring conclusion generalises: write kernels in each API's native language (MSL, CUDA C++, GLSL) under `kernels/`, compile at build time into embedded artifacts with runtime JIT fallbacks, bind through `objc2-metal`, `cudarc` and `ash`; track CubeCL (alpha, used by Burn, whose 0.20 dense matmul still trails LibTorch at 639 vs 627 µs; self-reported) for a future shared quantized-GEMV kernel but do not couple v1 to it; rust-gpu is "not yet production-ready" and SPIR-V only ([Source](https://github.com/tracel-ai/cubecl), [Source](https://tracel.ai/blog/release-0.20.0), [Source](https://github.com/Rust-GPU/rust-gpu)). The phase ordering assumes a Mac-heavy user base, which the research did not examine (gap).

## Sharding and scheduling: place tensors instead of parallelising them, recompute instead of swapping, and design the multi-device interface without building it

Inside one consumer machine the splits that demonstrably pay are layer offload of dense models and tensor-level expert placement for MoE; no source shows tensor parallelism between a CPU and a GPU in any mainstream system. The gpt-oss-120B offload guide on an RTX 3090 + 64 GB DDR4-3200 host went from **0.90 tok/s with a 13/32 layer split to 1.81 with `--n-cpu-moe 27`** (attention, router and shared experts on the GPU, routed experts in RAM), and a 5090 host reached 9.60 tok/s at short context and 8.14 at 5,650 tokens with pp 448 (measured, single source with a muddled baseline row) ([Source](https://www.hardware-corner.net/guides/gpt-oss-offloading-moe-layers/)); community reports of a 12 GB card doubling 17 → 34 tok/s and an 8 GB RTX 3070 Ti going from ~8.7 to >40 tok/s on 35B-A3B models as more experts moved to CPU are unverified ([Source](https://aiweekly.co/alerts/qwen3-moe-cpu-expert-offload-doubles-decode-speed-on-12gb-vram), [Source](https://medium.com/coding-nexus/one-flag-tripled-my-tokens-per-second-on-an-8gb-gpu-238f55d1e3bd)). The newest llama.cpp piece (PR #29887, merged 2026-10-07) adds an LRU GPU cache of host-resident experts for batches ≤32 tokens: a 93.7 GiB Qwen3.8-Flash-Next on an RTX 4090 went **25.0 → 40.7 tok/s (1.62×, 77 % hit rate) with an 11,000 MiB cache and a 5090 30.8 → 67.8 (2.20×, 89 % hit)** (measured by author), while with MTP on dual 3090s the cache was 25–34 % slower ([Source](https://github.com/ggml-org/llama.cpp/pull/29887)). The bound is system-RAM bandwidth over active-expert bytes: gpt-oss-120B's ~5B active parameters at 4.25 bpw are ≈2.7 GB/token, capping dual-channel DDR5 at ~20–30 tok/s and DDR4-3200 at ~18 before overheads, so the observed 1.5–1.8 tok/s on the 3090 host means per-layer CPU GEMM efficiency and synchronisation dominate — exactly the gap the CPU MoE path must close. KTransformers' "Expert Deferral" overlap adds up to 1.45× with ≤0.5 % accuracy loss (vendor/paper) ([Source](https://madsys.cs.tsinghua.edu.cn/publication/ktransformers-unleashing-the-full-potential-of-cpu/gpu-hybrid-inference-for-moe-models/)). Against building in-machine CPU+GPU tensor parallelism the evidence is a 200 GbE DGX Spark pair where TP=2 won only at batch 1 and PP=2 beat it 2.20× at batch 128 because "TP all-reduces twice per layer, while PP hands off activations once per token" (measured), and ~0.17 ms per-token round trips over 10 GbE cost 43–47 % of decode (measured) — the same "sequential and latency-bound" argument applies to PCIe hops at batch 1 ([Source](https://www.storagereview.com/review/nvidia-dgx-spark-cluster-review-distributed-inference-on-dell-gigabyte-and-hp), [Source](https://github.com/kjaiswal/llama-cpp-distributed-benchmarks)). Within a GPU, concurrent streams for the independent Q/K/V branches plus default fusion took Qwen3-30B-A3B Q4_K_M tg128 on an RTX 5090 from **246.96 to 352.06 tok/s** (~80 % of a ~520 tok/s speed-of-light) and 198.39 → 271.04 on a 4090 (measured), but regressed a GB10 from 61.8 to 54.8 — keep it behind per-device heuristics ([Source](https://github.com/ggml-org/llama.cpp/discussions/17621)). The Metal backend's rule that CPU-resident weights are offloaded to the GPU only at batch ≥32 (`GGML_OP_OFFLOAD_MIN_BATCH`) is the right default shape: compute on the device that owns the bytes during decode, on the GPU during prefill ([Source](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-metal/ggml-metal.cpp)). The placement rule that follows: decide per tensor which device owns it, keep embeddings/attention/router/shared experts/norms/lm_head on the fastest device, spill routed experts then KV in that order, batch all active experts' activations for a layer into one host↔device transfer, and plan the whole thing deterministically from GGUF/safetensors metadata before load.

The process model has the most operational evidence of any decision here. vLLM V1 runs an isolated EngineCore busy loop per data-parallel rank talking ZMQ to API servers, with one worker process per GPU (17 processes for `-tp 2 -dp 4`); llama-server's router spawns each model as a child process, reads `cmd_child_to_router:state:` JSON lines, stops with `cmd_router_to_child:exit` then force-kills after a timeout, and runs model downloads in a child too; Ollama re-launches its binary as a runner per resident model; LM Studio split the GUI from the `llmster` daemon ([Source](https://docs.vllm.ai/en/latest/design/arch_overview/), [Source](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README-dev.md), [Source](https://www.lmstudio.ai/blog/0.4.0)). Inside an engine the inference loop is a single dedicated thread fed by queues — llama-server merges all active slots into one `llama_batch` per `update_slots()` and keeps heavy post-processing off that thread — while HTTP, templating and tokenisation run elsewhere; MLX adds the constraint that generation streams are thread-bound ([Source](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README-dev.md), [Source](https://vllm-mlx.is-a.dev/guides/continuous-batching/)). Weight sharing across processes comes free through the page cache when weights are mmapped read-only; wiring (Metal) and `mlock` defeat it, so a supervisor running two engines on one GGUF should wire at most one. No local system does zero-copy activation passing between processes, and the per-model-process design never needs it. The recommendation is LLMario's existing supervisor plus one engine process per loaded model, with the supervisor enforcing byte budgets by sleeping (free contexts, keep process) then killing children, and a SGLang/TensorRT-style overlap scheduler (prepare batch N+1 while the device runs N, ~1.1× measured by LMSYS at one extra decoding step of latency) deferred until batch-1 latency work is done ([Source](https://www.lmsys.org/blog/2024-12-04-sglang-v0-4)).

Request scheduling should take llama-server's shape with vLLM V1's token budgeting. All four servers batch at token granularity: vLLM's step is `{request_id: num_tokens}` under a fixed budget with chunked prefill "enabled by default whenever possible" and decodes scheduled before prefills (guidance: `max_num_batched_tokens` ≈2,048 for inter-token latency, >8,192 for throughput); llama-server uses `-b 2048 -ub 512` over N slots and one unified KV pool; mlx-lm's `BatchGenerator` caps each step at ~0.5 s with `--decode-concurrency 32` and `--prompt-concurrency 8` ([Source](https://docs.vllm.ai/en/latest/configuration/optimization/), [Source](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md), [Source](https://github.com/ml-explore/mlx-lm/blob/main/mlx_lm/server.py)). When KV runs out, both vLLM V1 (default `RECOMPUTE`, GPU↔CPU swapping removed) and SGLang ("retract requests"; "occasional retraction, roughly once a minute, is acceptable") recompute rather than swap, and SGLang's `--schedule-conservativeness` exists because clients over-declare `max_tokens` ([Source](https://docs.vllm.ai/en/latest/usage/v1_guide/), [Source](https://docs.sglang.io/advanced_features/hyperparameter_tuning.html)). Multi-model residency everywhere is count-plus-timer (Ollama 3 per GPU and 5-minute keep-alive, LM Studio 60-minute JIT TTL with auto-evict, router 4 models with idle sleep) and no server implements a per-client fairness policy, so budget-based LRU with pin and TTL across heterogeneous devices is an opportunity rather than a proven pattern ([Source](https://docs.ollama.com/faq), [Source](https://lmstudio.ai/docs/app/api/ttl-and-auto-evict)). Multi-request throughput on Apple is real but modest: vllm-mlx on an M4 Max took Qwen3-30B-A3B 4-bit from 98.1 to 233.3 tok/s aggregate at five concurrent requests (2.38×; measured, undated), and vllm-metal's packed prefill+decode forward beat mlx_lm 3.87 s vs 4.52 s on an even batch and 3.64 vs 10.99 s on an uneven one (vendor-measured) ([Source](https://vllm-mlx.is-a.dev/guides/continuous-batching/), [Source](https://vllm.ai/blog/2026-09-22-vllm-metal-v0-28-0)).

Splitting a model across machines is a capacity win, never a batch-1 speed win, so the engine should expose a `Device` trait carrying memory, bandwidth and *latency* descriptors and a `Transport` trait for tensor send/receive with optional all-reduce, and ship no multi-machine execution in v1. The measurements are uniform: an M2 Ultra + DGX Spark pair over 10 GbE decoded Qwen2.5-7B at **52.7 tok/s versus 91.8 locally** and a 72B at 5.9 versus 11.1 (measured); two Strix Halo boxes over USB4 took Qwen3-Coder-Next from 38.7 to ~26.3 tok/s while models that fit neither alone ran at 11.8–15.4 (measured); two DGX Sparks over ConnectX-7 showed "adding a second unit did not speed up token generation" with a practical ~170 GB ceiling (measured); llama.cpp's RPC README calls the backend "a proof of concept ... fragile and insecure" ([Source](https://github.com/kjaiswal/llama-cpp-distributed-benchmarks), [Source](https://github.com/visorcraft/strix-halo-llm-perf), [Source](https://dev.classmethod.jp/en/articles/dgx-spark-two-node-clustering/), [Source](https://github.com/ggml-org/llama.cpp/blob/master/tools/rpc/README.md)). The only positive decode scaling needed RDMA over Thunderbolt 5 (macOS 26.2+, <50 µs versus ~300 µs TCP per Apple TN3205 as relayed; secondary), where exo's tensor parallelism on four Mac Studios gave roughly 1.5–1.7× (Qwen3-235B ~19.5 → ~31.9 tok/s; secondary, unverified) and hit a ~100-memory-region limit in AppleThunderboltRDMA (self-reported) ([Source](https://www.adwaitx.com/apple-tn3205-rdma-over-thunderbolt-low-latency-mac/), [Source](https://www.adwaitx.com/?p=10695), [Source](https://github.com/ml-explore/mlx/issues/3162)). The one distributed result relevant to a single machine is prima.cpp's placement solver: on a four-device home cluster a 70B went from llama.cpp's **10,120 ms/token (swapping) to 674 ms/token**, with the ablation showing the assignment itself worth 30× (20,848 → 674 ms) and prefetch a small extra (755 → 674), i.e. memory-aware layer assignment under a hard budget is what prevents blow-ups (measured by authors) ([Source](https://arxiv.org/html/2504.08791v2)). Cake's "FAIR" licence (non-commercial) rules it out; distributed-llama and prima.cpp (MIT) and llama.cpp RPC are the permissive references ([Source](https://github.com/evilsocket/cake), [Source](https://github.com/b4rtaz/distributed-llama)).

Speculative decoding is the one kernel-level investment with measured batch-1 payoffs on consumer hardware, in a strict order. On an RTX 3090 with Qwen3.8-27B UD-Q4_K_XL (8K context, q8_0 KV, greedy, 25 prompts × 5 passes), model-shipped MTP at n-max 2 gave **41.55 → 66.39 tok/s (+59.8 %)**, DFlash2 n-max 4 +51.9 %, an external 0.8B drafter **−29.8 %**, decode energy −37 % with MTP, per-class DFlash2 gains of +91.8 % on code and −11.1 % on prose, and on the MoE Qwen3.6-35B-A3B "every llama.cpp configuration lost to ordinary decoding"; vLLM's MTP path "could not start on the 24 GB card because of extra bf16 allocations" (measured, one author) ([Source](https://hackmd.io/@thc1006/qwen3-8-27b-speculative-decoding-rtx-3090)). On Apple Metal MTP was a net loss — M1 Max Qwen3.5-9B 25.3 → 21.9 tok/s at n-max 2, M4 Pro Qwen3.6-27B 10.20 → 8.31 with output diverging from greedy at depth 3 (measured, issues) — until b11404's few-row kernels turned Qwen3.8-27B + DFlash2 on an M3 Ultra from below serial to **30.2 → 110.0 tok/s on code (3.4×)** (measured by PR author) ([Source](https://github.com/ggml-org/llama.cpp/issues/23752), [Source](https://github.com/ggml-org/llama.cpp/issues/23302), [Source](https://rohitai.com/blog/llama-cpp-b11404-metal-few-row-mma-speculative-decoding)). N-gram lookup costs no weights but −17 % tg at 32 % acceptance in one long-context test (measured, hardware unknown) ([Source](https://victor-mtp-on-hf-endpoints.static.hf.space/index.html)). The order for the engine: n-gram/suffix lookup with auto-disable below ~30 % acceptance, then model-shipped MTP heads (Qwen3.5/3.6/3.8, Qwen3-Next, GLM, Nemotron 3.5, Gemma 4's 4-layer drafter) capped at 2–3 draft tokens, then DFlash2/EAGLE-3 drafters from SpecForge (MIT) for dense targets, classic draft models only as opt-in; default speculation off for ~3B-active MoE targets; budget the drafter/MTP footprint ("a few hundred MB" plus ~500 MB of verification compute buffers) in the plan; and carry a test that greedy speculative output reproduces the serial stream, because the RTX 3090 study diverged in 76–80 % of 400-token requests ([Source](https://github.com/sgl-project/SpecForge), [Source](https://github.com/FasterDecoding/Medusa)). LayerSkip is CC-BY-NC and must not be used ([Source](https://github.com/facebookresearch/LayerSkip)). For the forward pass itself: build a per-shape compiled graph (capture once, patch KV positions per token) from day one, express independent branches as graph nodes with explicit buffer lifetimes so streams can overlap without the allocator-reuse race that bit ggml, keep one persistent CPU pool sized to P-cores and parked while the GPU owns the step (persistent pools alone gave +20–35 % on small CPU models; measured, background), and never more than one thread issuing GPU work per device ([Source](https://github.com/ggml-org/llama.cpp/pull/8672)).

The incident catalogue is a checklist of what the planner must count. Every entry is silent degradation rather than a crash: WDDM sysmem fallback; the macOS wired cap turning a model that "fits in RAM" into mmap thrash (llama.cpp at 70B on an 11 GB-VRAM desktop fell to 7,965–10,120 ms/token; measured); spinning CPU threads slowing the GPU path; llama-server creating four slots despite `-np 1` (unverified); speculative decoding regressing 12–45 % on Metal and changing committed tokens at depth 3; concurrent streams regressing GB10; vLLM MTP failing to allocate on 24 GB; RPC loads of >100 GiB hanging without `-dio`; exo requiring identical OS builds and a specific unusable Thunderbolt port; LM Studio's `SystemResourcesObserver` helper failing and taking all loads with it (unverified); and an Engine Protocol bug loading on the iGPU under Vulkan on Windows ([Source](https://arxiv.org/html/2504.08791v2), [Source](https://github.com/ggml-org/llama.cpp/issues/17989), [Source](https://github.com/visorcraft/strix-halo-llm-perf), [Source](https://github.com/exo-explore/exo), [Source](https://github.com/lmstudio-ai/lmstudio-bug-tracker/issues/1860), [Source](https://lmstudio.ai/changelog/lmstudio)). The design response is to make degradation visible: log the fitted plan, the effective residency per tensor group, per-step preemptions and retractions, speculative acceptance, shared-GPU-memory growth on Windows and effective bandwidth against speed-of-light, so that "slow and silent" becomes "slow with a reason".

## Internet and tools: template-driven incremental parsing, lazy grammars, MCP 2026-07-28, and a Rule-of-Two policy gate

There is no single open-model tool format in 2026; at least eight wire families coexist and the template must be the source of truth. Qwen3.5 moved from Hermes JSON to XML `<tool_call><function=name><parameter=k>v</parameter></function></tool_call>` with results rendered inside a *user* turn as `<tool_response>` and thinking re-rendered only after the last user query; Qwen3-Coder and Nemotron share that call syntax but declare tools as nested XML; GLM-4.7 uses `<tool_call>name<arg_key>k</arg_key><arg_value>v</arg_value>` with `<|observation|>` results; Gemma 4 uses special tokens `<|tool_call>call:name{key:<|"|>value<|"|>}<tool_call|>` and a `<|channel>thought` thinking channel, and its template *raises* if `arguments` is a JSON string instead of a mapping, as do LFM2's pythonic `<|tool_call_start|>[f(a='b')]<|tool_call_end|>` and Qwen3.5's; Llama 3.x emits JSON after `<|python_tag|>` with single-call-only JSON and Llama 4 pythonic lists; Mistral uses `[TOOL_CALLS]name[ARGS]{json}` control tokens with 9-character call ids; gpt-oss uses Harmony channels (`analysis` is "not safety-tuned, so don't show it to end users"; prior analysis must be passed back during a tool loop and dropped once the turn ends in `final`); Muse Glimmer uses an `<atem:invoke>` protocol ([Source](https://huggingface.co/Qwen/Qwen3.5-9B/blob/main/chat_template.jinja), [Source](https://huggingface.co/zai-org/GLM-4.7-Flash/blob/main/chat_template.jinja), [Source](https://huggingface.co/google/gemma-4-E4B-it/blob/main/chat_template.jinja), [Source](https://huggingface.co/LiquidAI/LFM2-1.2B/blob/main/chat_template.jinja), [Source](https://github.com/meta-llama/llama-models/blob/main/models/llama3_1/prompt_format.md), [Source](https://huggingface.co/mistralai/Devstral-Small-2-24B-Instruct-2512/blob/main/chat_template.jinja), [Source](https://developers.openai.com/cookbook/articles/openai-harmony), [Source](https://huggingface.co/meta-models/Muse-Glimmer-30B/blob/main/chat_template.jinja)). Every serious engine ships a per-family parser table plus an incremental streaming parser — vLLM lists ~30 `--tool-call-parser` values, Ollama parses in Go with `Add(chunk, done)`, mlx-lm has 13 parser modules but its server still documents no `tools` field — and llama.cpp additionally infers a parser from the Jinja template by differential rendering, classifying `tool_format ∈ {NONE, JSON_NATIVE, TAG_WITH_JSON, TAG_WITH_TAGGED}` plus pythonic, which covers every template examined ([Source](https://docs.vllm.ai/en/latest/features/tool_calling.html), [Source](https://github.com/ollama/ollama/blob/main/model/parsers/parsers.go), [Source](https://github.com/ml-explore/mlx-lm/tree/main/mlx_lm/tool_parsers), [Source](https://github.com/ggml-org/llama.cpp/blob/master/common/chat-auto-parser.h)). The engine needs a real Jinja renderer with `tools`, `enable_thinking`, `reasoning_content`, `preserve_thinking`, `truncate_history_thinking` and `clear_thinking` variables, hand-written incremental parsers for the eight families with the `NEED_MORE_INPUT` state and an arguments buffer "to delay arguments until tool name is known", an auto-parser as fallback, argument values kept as JSON objects internally and converted to strings only at the OpenAI boundary, `tool_call_id → name` carried in the message model, and template detection by content hash — a MiMo-V2.6 distill was mis-detected as Qwen3-Coder by substring and its tool calls never completed (closed issue) ([Source](https://github.com/ggml-org/llama.cpp/blob/master/common/peg-parser.h), [Source](https://github.com/ggml-org/llama.cpp/issues?q=is%3Aissue+qwen3.5+OR+gemma-4+OR+nemotron+OR+lfm2)). Reliability below ~4B is poor on every source: the self-reported BFCL-V4 aggregator puts Qwen3.5-27B at 0.685, Qwen3.5-9B 0.661, Qwen3.5-4B 0.503, Qwen3.5-2B 0.436 and 0.8B 0.253, and Epoch AI's audit found defects in **24 of 50 sampled BFCL tasks (48 %)** and rated the benchmark "Flawed" (measured audit), so the engine must assume malformed calls, validate and repair them, default small models to single-call mode with grammar enforcement, and reserve parallel calls for templates that advertise them ([Source](https://llm-stats.com/benchmarks/bfcl-v4), [Source](https://epoch.ai/benchmarks/berkeley-function-calling-leaderboard/review)). Extreme KV quantization also matters here: llama.cpp warns that `-ctk q4_0` "can substantially degrade the model's tool calling performance" ([Source](https://github.com/ggml-org/llama.cpp/blob/master/docs/function-calling.md)).

Constrained decoding has a natural Rust embed. llguidance (MIT, native crate 1.9.1, Rust ≥1.87, ~1.9M downloads) is the backend inside llama.cpp, vLLM, SGLang, mistral.rs and OpenAI, needs no precomputation, and its authors measure **~50 µs of CPU per token on a 128k tokenizer** (MaskBench average, ~2 ms startup; sparse masks ~28 µs, dense-unsliced 0.5 % of cases ~1,577 µs) while characterising other libraries as "10–1000× slower on masks, and about 1000× slower at startup" and llama.cpp's own GBNF as slow for "a lack of a lexer and use of a backtracking parser" (measured by the llguidance authors) ([Source](https://github.com/guidance-ai/llguidance), [Source](https://guidance-ai.github.io/llguidance/llg-go-brrr)). XGrammar-2 (Apache-2.0, C++ with a community `xgrammar-rs` binding) is the alternative with the richest "structural tag" DSL for thinking-then-JSON and per-model tool protocols, claiming up to 80× compilation speedup from cross-grammar caching at 10–500 tools (vendor-claimed) ([Source](https://blog.mlc.ai/2026/05/04/xgrammar-2-fast-customizable-structured-generation), [Source](https://github.com/trymirai/xgrammar-rs)). Because a mask costs tens of microseconds against tens of milliseconds per token on a laptop, the engine can mask every step; the real risk is schema-compile latency with many MCP tools (llama.cpp's grammar build fails with ~60 tools; open issue), which favours llguidance's no-precompute design plus a compiled-grammar cache keyed by tool-set and tokenizer hash ([Source](https://github.com/ggml-org/llama.cpp/issues?q=is%3Aissue+qwen3.5+OR+gemma-4+OR+nemotron+OR+lfm2)). "Thinking then JSON" is solved uniformly by trigger-based (lazy) grammars: unconstrained until `</think>` or a tool-call opener, constrained after — llama.cpp's PEG builder emits "only trigger rules and their descendants", vLLM skips enforcement until the reasoning end token, and a `tool_choice: required` that is advisory rather than grammar-enforced is a known bug class ([Source](https://github.com/ggml-org/llama.cpp/blob/master/common/peg-parser.h), [Source](https://docs.vllm.ai/en/latest/features/reasoning_outputs.html)).

The Model Context Protocol's current revision is 2026-07-28 and it changed the host's shape. It removed protocol sessions and `Mcp-Session-Id`, removed the `initialize` handshake in favour of protocol version and client capabilities in `_meta` on every request, added `server/discover`, replaced server-initiated Roots/Sampling/Elicitation with Multi Round-Trip Requests (`resultType: "input_required"`), moved Tasks to an official extension with `tasks/get` polling, deprecated HTTP+SSE and Dynamic Client Registration, and set a 12-month deprecation window ([Source](https://modelcontextprotocol.io/specification/2026-07-28/changelog)). The official Rust SDK `rmcp` (Apache-2.0, 3.5.1 on 2026-10-05, ~33.7M downloads, used by goose) implements 2026-07-28 with compatibility for 2025-11-25, stdio and child-process clients, Streamable HTTP, OAuth, elicitation and tasks ([Source](https://github.com/modelcontextprotocol/rust-sdk), [Source](https://crates.io/api/v1/crates/rmcp)). The spec's normative duties map directly onto engine features: "there SHOULD always be a human in the loop with the ability to deny tool invocations"; "Show tool inputs to the user before calling the server"; "clients MUST consider tool annotations to be untrusted unless they come from trusted servers"; validate `structuredContent` against `outputSchema`; implement timeouts; "Log tool usage for audit purposes"; for local servers "show the exact command that will be executed, without truncation", warn that servers "run with the same privileges as the client", and "execute MCP server commands in a sandboxed environment with minimal default privileges"; for OAuth metadata fetches block `10/8, 172.16/12, 192.168/16, 127/8, ::1, 169.254/16, fc00::/7, fe80::/10`, "avoid implementing IP validation manually", pin DNS, and use an egress proxy ([Source](https://modelcontextprotocol.io/specification/2026-07-28/server/tools), [Source](https://modelcontextprotocol.io/specification/2026-07-28/basic/security_best_practices)). The field offers contrasting models: llama-server's `--mcp-servers-config` spawns stdio servers with no approval mechanism and the warning "only declare commands you trust", Jan asks per call with arguments shown and a global bypass, LM Studio hosts local and remote servers with "Never install MCPs from untrusted sources" and a context-overflow warning, Claude Desktop requires "explicit approval before execution" with stderr logged per server ([Source](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md), [Source](https://www.jan.ai/docs/desktop/mcp), [Source](https://lmstudio.ai/docs/app/plugins/mcp), [Source](https://modelcontextprotocol.io/docs/develop/connect-local-servers)). The engine should build per-server permission profiles (allow/ask/deny per tool), mandatory argument display, engine-owned read-only/open-world/destructive classification (never trusting `readOnlyHint`/`destructiveHint`), output-schema validation, timeouts, an audit log, and run stdio servers under the same sandbox as its own fetcher.

Built-in web access has three viable back-ends and one proven page model. Self-hosted SearXNG returns JSON only when the format is enabled in `settings.yml` ("many public instances disable these formats") and its DuckDuckGo upstream captchas after rapid searches (secondary); Brave charges **$5 per 1,000 requests with $5 of monthly credit**, requires a card, grants "no rights to third-party content" and forbids storing results without a plan that grants storage rights; Exa is $4/1k instant search and $1/1k page contents with $10 monthly credit and no card; Ollama's hosted `web_search`/`web_fetch` is free with an account, returns at most 10 results, and its reference loop truncates each result to 8,000 characters and recommends ~32K context ([Source](https://github.com/searxng/searxng/blob/master/docs/dev/search_api.rst), [Source](https://brave.com/search/api/), [Source](https://exa.ai/pricing), [Source](https://docs.ollama.com/capabilities/web-search)). The page model to reproduce is gpt-oss's `simple_browser`: 80-column wrap, numbered `L{i}:` lines, `【id†title†domain】` links, **1,024-token view windows** counted with `o200k_base`, a `find` within the page, per-URL caching in a session page stack, citations as `【cursor†L{start}-L{end}】` rewritten to `url_citation` annotations, and "do not quote more than 10 words directly from the tool output" ([Source](https://github.com/openai/gpt-oss/blob/main/gpt_oss/tools/simple_browser/simple_browser_tool.py)). Permissively licensed Rust building blocks exist for every step: `dom_smoothie` (MIT Readability port with Markdown output), `htmd` (Apache-2.0 HTML→Markdown, "about 16 ms to convert a 1.37 MB Wikipedia page on an Apple M4"; vendor-claimed), `texting_robots` (MIT/Apache robots.txt), `chromiumoxide` (MIT/Apache CDP for SPAs, which also enlarges the SSRF/injection surface); trafilatura is Python and GPL before v1.8.0 ([Source](https://github.com/niklak/dom_smoothie), [Source](https://github.com/letmutex/htmd), [Source](https://github.com/Smerity/texting_robots), [Source](https://github.com/mattsse/chromiumoxide), [Source](https://github.com/adbar/trafilatura)). safewebfetch (MIT, Python) is the reference control set: http/https on 80/443 only, blocked private/loopback/link-local/CGNAT/metadata ranges including IPv4-in-IPv6 encodings, every redirect re-validated, connect-to-validated-IP against DNS rebinding, text-only bodies with a 600 KB cap and 20 s deadline, stripping of hidden/off-screen/zero-font/transparent text and invisible Unicode, ~60 injection patterns in ten languages after de-obfuscation, and output wrapped in tags with a random suffix "so page content cannot close the block" — with the author's own caveat that rules "generalize poorly" ([Source](https://github.com/Hwanhui02/safewebfetch)). For retrieval over fetched pages, the 2026 small-footprint embedders are Qwen3-Embedding-0.6B/4B/8B (Apache-2.0, 32K context, matching rerankers) and EmbeddingGemma 2 (Apache-2.0, 270M text-only path, 768-d with Matryoshka truncation to 128, 8K context; vendor-claimed), served through the engine's own GGUF path or `fastembed-rs` (Apache-2.0, ONNX, also rerankers), stored in `sqlite-vec` (MIT/Apache, pre-v1), `lancedb` (Apache-2.0, vector + full-text + SQL) or `usearch` (Apache-2.0 HNSW), chunked Markdown-aware by `text-splitter` (MIT) at ~300–800 tokens with URL/title/heading-path prepended — Anthropic's contextual-retrieval result (retrieval failure 5.7 % → 1.9 % with contextual BM25 plus reranking; vendor-measured, background) is the evidence for the prepended context ([Source](https://qwenlm.github.io/blog/qwen3-embedding/), [Source](https://blog.google/innovation-and-ai/technology/developers-tools/embeddinggemma-2/), [Source](https://github.com/Anush008/fastembed-rs), [Source](https://github.com/asg017/sqlite-vec), [Source](https://github.com/lancedb/lancedb), [Source](https://github.com/unum-cloud/usearch), [Source](https://github.com/benbrandt/text-splitter), [Source](https://www.anthropic.com/news/contextual-retrieval)).

The API surface and agent loop should be Responses-shaped. OpenAI's Responses API uses typed items (`message | reasoning | function_call | function_call_output`), flattened tool definitions, `tool_choice` including `allowed_tools`, strict mode by default, and the rule that "reasoning items from the model's output must be passed back with the tool outputs"; Chat Completions "remains supported" but "Responses is recommended for all new projects" and newer OpenAI models restrict tool calling on it; the industry "Open Responses" spec (backed by vLLM, Ollama, LM Studio, HF, NVIDIA, AWS, Databricks among others) standardises the shape, and llama.cpp already serves `/v1/responses` by converting to chat completions while vLLM serves it natively with cancel ([Source](https://developers.openai.com/api/docs/guides/function-calling), [Source](https://developers.openai.com/api/docs/guides/migrate-to-responses), [Source](https://www.openresponses.org/), [Source](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md), [Source](https://docs.vllm.ai/en/latest/serving/online_serving/)). The engine's canonical transcript should therefore be the Responses item model with Chat Completions as a lossy projection, and the loop should be: render with the per-family thinking-history policy → generate with a lazy grammar → parse incrementally → validate arguments against JSON Schema with one repair retry → policy check → execute tools (MCP or built-in, with timeouts and concurrency for independent calls) → window/truncate results (8,000 characters or 1,024-token windows) → append → repeat until no calls or a step/token budget is hit, with max steps, max tool tokens and reasoning budget (llama.cpp `--reasoning-budget`, vLLM `thinking_token_budget`) exposed as API parameters because small models loop ([Source](https://docs.ollama.com/capabilities/web-search), [Source](https://docs.vllm.ai/en/latest/features/reasoning_outputs.html)). MCP's `isError: true` results SHOULD be fed back for self-correction ([Source](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)).

Security must be designed so an injected instruction *cannot* complete an attack, because detection is not a solution. Willison's "lethal trifecta" (private data + untrusted content + external communication) and Meta's "Agents Rule of Two" (satisfy at most two of: process untrustworthy inputs, access sensitive systems, change state or communicate externally, within a single session, else require human approval or a fresh session) are the operating rules; guardrails with ~95 % detection are "a failing grade in web application security" ([Source](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/), [Source](https://ai.meta.com/blog/practical-ai-agent-security/)). The formal designs are the Beurer-Kellner et al. patterns (Action-Selector, Plan-Then-Execute, LLM Map-Reduce, Dual LLM, Code-Then-Execute, Context-Minimization — once an agent has ingested untrusted input "it is impossible for that input to trigger any consequential actions") and CaMeL, which "solves 77 % of tasks with provable security, compared with 84 % for an undefended system" on AgentDojo (measured, frontier models; no small-model numbers exist) ([Source](https://arxiv.org/html/2506.08837v3), [Source](https://arxiv.org/abs/2503.18813)). OWASP LLM01:2025's controls (constrain behaviour, validate output formats, least privilege, human approval for high-risk actions, "segregate and identify external content") and Anthropic's sandbox design — filesystem isolation via bubblewrap/Seatbelt applied to all subprocesses plus network isolation through a Unix-socket proxy enforcing a domain allowlist that "prompts the user to confirm newly requested domains", both required because without network isolation "a compromised agent could exfiltrate sensitive files such as SSH keys", cutting permission prompts 84 % (vendor-measured) — are the implementation references ([Source](https://genai.owasp.org/llmrisk/llm01-prompt-injection/), [Source](https://www.anthropic.com/engineering/claude-code-sandboxing)). The concrete engine policy: classify every tool from engine-owned metadata; default a browsing session to search + fetch + read-only retrieval; require per-call human approval for any state-changing or exfiltration-capable tool once untrusted content has entered the context; provenance-tag and nonce-wrap every tool result; run the fetcher with an engine-level SSRF guard *and* an OS sandbox with an egress allowlist; keep API keys in the OS keychain and out of prompts and logs; require a token and validate `Origin`/`Host` even on loopback (the MCP spec lists DNS rebinding against local servers; its HTTP transport returns 403 on invalid Origin); and emit OpenTelemetry GenAI spans with message content Opt-In only, since `gen_ai.output.messages` and tool definitions are "likely to contain sensitive information including user/PII data" ([Source](https://modelcontextprotocol.io/specification/2026-07-28/basic/security_best_practices), [Source](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-spans.md)). Reported 2026 sandbox-bypass incidents in Cursor and Claude Code (tool parameters overriding the working directory, an alternate `/proc` path) are secondary and unverified but argue for the two-layer design ([Source](https://www.csoonline.com/article/4191923/sandbox-bypass-flaws-in-cursor-ide-highlight-prompt-injection-as-an-rce-vector.html)).

## Target models: the Qwen3.5 stack unlocks 14 of 37 families, and the operator union is far larger than a plain transformer

As of October 2026 the small and mid open-weight field runs on three architecture templates, verified from each repository's `config.json` through the Hub connector on 8 October. The Qwen3.5 hybrid — 16 × (3 Gated DeltaNet → FFN, 1 gated full attention → FFN) with head_dim 256, 4 KV heads, partial rotary 0.25 with interleaved mRoPE sections [11,11,10], a 248,320-token vocabulary, one MTP layer and fp32 recurrent state — is byte-identical in text config across Qwen3.6-27B and Qwen3.8-27B (Apache-2.0), shared by the 35B-A3B MoE (256 experts top-8 plus one shared) and the 0.8B–9B sizes, and inherited by Ornith 1.5 (MIT), MiMo-V2.6-Distill-9B (MIT) and Cloudflare Clef, so one kernel set covers **14 of LLMario's 37 catalog families** ([Source](https://huggingface.co/Qwen/Qwen3.8-27B/blob/main/config.json), [Source](https://huggingface.co/Qwen/Qwen3.6-35B-A3B/blob/main/config.json), [Source](https://huggingface.co/ornith-ai/Ornith-1.5-9B/blob/main/config.json)). Gemma 4 (all five checkpoints tagged Apache-2.0 on the Hub and in the tech report, which contradicts LLMario's catalog label of "Gemma Terms of Use" for E2B/E4B) uses 5:1 sliding (1,024) to global layers, sets V := K on global attention with `global_head_dim` 512 on the 12B/26B-A4B/31B ("up to 37.5 % global KV reduction"), per-layer embeddings and 18–20 KV-shared layers on the E-series, GeGLU, a 262k SentencePiece vocabulary, logit soft-capping 30, a 4-layer MTP drafter, and ships QAT Q4_0 GGUFs for every size ([Source](https://arxiv.org/html/2607.02770), [Source](https://huggingface.co/google/gemma-4-31B-it/blob/main/config.json), [Source](https://huggingface.co/google/gemma-4-E4B-it/blob/main/config.json), [Source](https://huggingface.co/google/gemma-4-31B-it-qat-q4_0-gguf/blob/main/README.md)). The Mamba-2/short-conv hybrids — Nemotron 3.5 Lightning 30B-A3B (OpenMDW-1.1; 52 layers as 23 Mamba-2 + 23 relu² MoE + 6 attention, 2 KV heads, fp32 SSM cache, 1 MTP block), Granite 4.0-H (36 Mamba-2 + 4 attention, NoPE), Falcon-H1 (parallel SSM + attention in every layer, which does not reduce per-token KV), LFM2.5 (LFM Open License; 18 double-gated short-conv + 6 attention layers, 32 experts top-4) — are the third template ([Source](https://huggingface.co/nvidia/NVIDIA-Nemotron-3.5-Lightning-30B-A3B-BF16/blob/main/config.json), [Source](https://huggingface.co/ibm-granite/granite-4.0-h-small/blob/main/config.json), [Source](https://huggingface.co/LiquidAI/LFM2.5-8B-A1B/blob/main/config.json)). Dense GQA transformers remain (Granite 4.2 8B/3B/30B with μP multipliers, Ministral 3 14B, Devstral 2 24B, Mistral Small 3.2, Llama 3.1, Phi-4, Olmo 3/3.1, SmolLM3, Muse Glimmer 30B with gated attention and NoPE global layers), gpt-oss adds learned attention sinks, clamped SwiGLU (`swiglu_limit` 7, α 1.702), head_dim 64 and MXFP4 experts, and MLA with an absorbed cache appears in GLM-4.7-Flash (MIT, 30B-A3B, kv_lora 512 + rope 64) and Mistral Small 4 119B-A6B ([Source](https://huggingface.co/ibm-granite/granite-4.2-8b/blob/main/config.json), [Source](https://huggingface.co/meta-models/Muse-Glimmer-30B/blob/main/config.json), [Source](https://github.com/openai/gpt-oss/blob/main/gpt_oss/torch/model.py), [Source](https://huggingface.co/zai-org/GLM-4.7-Flash/blob/main/config.json), [Source](https://huggingface.co/mistralai/Mistral-Small-4-119B-2603/blob/main/config.json)). The upper bound of the trend is visible but outside local memory: Qwen3.8-Flash-Next (qwen-community-1.0, 125B + 51B n-gram embeddings, sparse attention indexer, hyper-connections), GLM-5.3-Flash (320B, 34 KDA + 11 sparse-MLA layers), DeepSeek V4.1 Flash (single 512-wide KV head, cross-layer KV reuse, engram tables, 3 MTP layers), Kimi K3 and MiniMax M3 ([Source](https://huggingface.co/Qwen/Qwen3.8-Flash-Next/blob/main/config.json), [Source](https://huggingface.co/zai-org/GLM-5.3-Flash/blob/main/config.json), [Source](https://huggingface.co/deepseek-ai/DeepSeek-V4.1-Flash/blob/main/config.json)). llama.cpp's architecture table covers all of these including `qwen4exp`, `gemma4`, `nemotron_h_moe`, `glm-dsa`, `deepseek4`, `kimi-k3`, `muse-glimmer`, `mellum`, `nanbeige`, `clef`, `dflash` and `eagle3`; mlx-lm has no `qwen4_exp` and neither engine supports Phi-4-mini-flash-reasoning (SambaY/GMU, custom code, no GGUF, 2,085 downloads), which is the one family in the brief the engine can reasonably drop ([Source](https://github.com/ggml-org/llama.cpp/blob/master/src/llama-arch.cpp), [Source](https://github.com/ml-explore/mlx-lm/tree/main/mlx_lm/models), [Source](https://huggingface.co/microsoft/Phi-4-mini-flash-reasoning/blob/main/config.json)).

The operator union a 2026-complete engine must implement, beyond RMSNorm/RoPE/GQA flash attention/SwiGLU/tied-or-untied head, is: Gated DeltaNet chunked scan with conv kernel 4 and separate QK/V head counts; KDA; Mamba-2 SSD scan with grouped states; gated short convolutions with `conv_L_cache` 3; K=V global attention, cross-layer KV sharing and per-layer embeddings; learned sinks and clamped SwiGLU; MLA with compressed-cache attention; five RoPE families (default/partial, interleaved mRoPE, YaRN with attention factors, llama3, LongRoPE) plus NoPE layers with Llama 4's temperature tuning; sliding-window masks of 128/512/1,024/2,048/4,096 and 8,192-token chunks; grouped-expert GEMM with softmax-renormalised, sigmoid-with-bias/`noaux_tc` (with `routed_scaling_factor` 1.8–2.5), `sqrtsoftplus` and top-1-plus-shared-MLP routers; MXFP4 expert weights; MTP/DFlash/DSpark/EAGLE-3 drafter execution; GeGLU, relu², `(1 + w)` norm gains (Gemma, MiniMax, Qwen4Exp — early MLX conversions that folded the +1 twice "degenerate into noise"), μP multipliers, logit soft-capping, gated attention outputs, QK-norm, hyper-connections, looped layers (Nanbeige `num_loops` 2) and n-gram/engram embeddings for the upper-bound families ([Source](https://huggingface.co/mlx-community/Qwen3.8-Flash-Next-4bit/blob/main/README.md), [Source](https://huggingface.co/Nanbeige/Nanbeige4.2-3B/blob/main/config.json)). Two numeric rules follow from the configs: every linear-attention and SSM state is declared float32, so the recurrent cache needs an fp32 path even with 8-bit KV (NVIDIA's fp16 SSM-cache recipe requires stochastic rounding), and attention must accumulate in fp32 on CPU/Metal for head_dim-64 and sink-bearing models — CPU flash attention overflowed to inf/NaN with an F16 accumulator on Nemotron 3 Nano Q8_0 (open issue) ([Source](https://huggingface.co/nvidia/NVIDIA-Nemotron-3.5-Lightning-30B-A3B-BF16/blob/main/README.md), [Source](https://github.com/ggml-org/llama.cpp/issues?q=is%3Aissue+qwen3.5+OR+gemma-4+OR+nemotron+OR+lfm2)). Tokenizers to load span byte-level BPE at 151,936/248,320 (Qwen), SentencePiece at 262,144 (Gemma), o200k variants at 201,088/200,064 (gpt-oss, Phi-4-mini, MiniMax), 128,256 (Llama 3, SmolLM3), 202,048 (Llama 4, Muse), Tekken 131,072 (Mistral), and cl100k-derived 100,352/100,278 (Granite, Phi-4, Olmo).

Memory fit at 4-bit weights and 8-bit KV, computed from the configs with a 2/3-of-RAM usable rule at 8/16/32 GB and 3/4 at 64 GB plus 1.0 GB overhead (assumptions, validated against Gemma 4's published int8-KV figures within 0.02 GB), partitions the catalog cleanly ([Source](https://arxiv.org/html/2607.02770)). The 8 GB class (5.3 GB usable) holds ≤4B dense/hybrid models — Qwen3.5-0.8/2/4B, Gemma 4 E2B, LFM2.5-1.2/2.6B, Granite 4.2 3B, SmolLM3, Llama 3.2 — but 128K context only for the hybrids and Gemma 4 E2B; the GQA-128 dense 4B class should default to ≤32K. The 16 GB class (10.7 GB) covers Qwen3.5-9B/Ornith 9B (8.9 GB at 128K), Gemma 4 12B (8.7) and E4B, LFM2.5-8B-A1B, Mellum2.1, Granite 4.2 8B and Llama 3.1 8B to 32K, and Ministral 3 14B only at 8K. The 32 GB class (21.3 GB) covers the whole 24–31B tier — Qwen3.8/3.6-27B (17.56 GB UD-Q4_K_XL, 22.2 GB at 128K, tight), Gemma 4 31B (21.8 at 128K) and 26B-A4B (16.4), gpt-oss-20b (14.7), GLM-4.7-Flash (22.8 with the compressed MLA cache but off the machine at 32K if expanded), Nemotron 3.5 Lightning (20.4), Muse Glimmer (18.6), Mistral 24B to 32K — while the 35B-A3B MoEs (20.4 GB weights plus overhead) are the first casualties of the 2/3 rule and need a raised working set, a Q3 variant or a few streamed experts. The 64 GB class (48 GB) adds the 35B-A3B models (22.8 GB at 128K) and Qwen3-Next-80B (≈47.5, tight), while gpt-oss-120b (64.4 GB), Qwen3.5-122B-A10B (~71), Mistral Small 4 (~68), Llama 4 Scout (~63), GLM-4.5-Air (~64) and Qwen3.8-Flash-Next (94.9 GB at IQ4_XS) all need expert offload or streaming ([Source](https://huggingface.co/unsloth/Qwen3.8-27B-GGUF/tree/main), [Source](https://huggingface.co/ISTA-DASLab/Qwen3.8-Flash-Next-GSQ-RCO-GGUF/blob/main/README.md)). Hybrid and K=V/MLA designs make 128K nearly free (≤4.3 GB) where classic GQA-8×128 dense models spend 8–17 GB on it.

Model choice per band rests on thin independent evidence. Artificial Analysis' open-weights index (v4.3.2, fetched 8 October) lists only two models ≤40B, **Qwen3.8-27B at 34 and Muse Glimmer at 17**; Arena's text top 40 contains no open model ≤40B; the BFCL and Aider public tables have not been refreshed with 2026 small models; NVIDIA's cross-vendor harness (vendor-run, "may differ from vendors' self-reported numbers") has Qwen3.6-35B-A3B leading SWE-bench Verified (70.12), Terminal-Bench 2.1 (44.38) and GPQA (83.40), Gemma 4 26B-A4B leading IFBench (77.25), and gpt-oss-20b at 52.44/15.17; Epoch rated BFCL "Flawed" ([Source](https://artificialanalysis.ai/models/open-source), [Source](https://arena.ai/leaderboard/text), [Source](https://gorilla.cs.berkeley.edu/leaderboard.html), [Source](https://huggingface.co/nvidia/NVIDIA-Nemotron-3.5-Lightning-30B-A3B-BF16/blob/main/README.md)). Vendor cards claim Ornith-1.5-9B beats Qwen3.5-9B on Terminal-Bench 2.1 (46.2 vs 21.3) and SWE-bench Verified (70.6 vs 53.2), GLM-4.7-Flash beats gpt-oss-20b on SWE-bench Verified (59.2 vs 34.0) and τ²-Bench (79.5 vs 47.7), and Mellum2.1 scores BFCL v4 62.3 (all vendor-claimed) ([Source](https://huggingface.co/ornith-ai/Ornith-1.5-9B/blob/main/README.md), [Source](https://huggingface.co/zai-org/GLM-4.7-Flash/blob/main/README.md), [Source](https://huggingface.co/JetBrains/Mellum2.1-12B-A2.5B-Thinking/blob/main/README.md)). Adoption is unambiguous: gpt-oss-20b 102.1M Hub downloads, Gemma 4 26B-A4B 69.5M, Qwen3.5-9B 68.5M, Qwen3.8-27B the most-liked model in the set. The catalog needs licence flags: Qwen3.8-Flash-Next (qwen-community-1.0), Nemotron 3.5 (OpenMDW-1.1), Nemotron 3 Nano/MiniMax/Kimi/Falcon-H1 ("other"), LFM2.5 (LFM Open License v1.0) and Llama (community licences) are not OSI-permissive, and Gemma 4's label should be rechecked against the Hub's Apache-2.0 tag. The 2026 conversion and runtime pitfalls are mostly template and state bugs: Gemma 4 tool calls breaking on multi-line arguments, Ministral placing tool calls inside the reasoning block, `tool_choice: required` being advisory for Qwen3, co-batched LFM2 sequences corrupting recurrent state (and mlx-lm 0.31.0 being yanked for "Batched KV cache cross contamination"), SYCL Gated DeltaNet producing "token soup" beyond ~2K tokens, and Gemma 4 speculative decoding requiring a QAT drafter of the same precision — each of which maps onto a test the engine should carry ([Source](https://github.com/ggml-org/llama.cpp/issues?q=is%3Aissue+qwen3.5+OR+gemma-4+OR+nemotron+OR+lfm2), [Source](https://pypi.org/project/mlx-lm/), [Source](https://huggingface.co/google/gemma-4-31B-it-qat-q4_0-gguf/blob/main/README.md)).

## Conclusion

The research reframes what "building a new engine" should mean for LLMario. The hard, measurable parts of local inference — bandwidth-bound decode, format and quantization quality, attention kernels, chat-template zoo — are largely solved by reading what already exists under MIT and Apache licences, and the 2025–2026 changes across every lineage (llama.cpp's `--fit`, router mode and MoE expert cache; Ollama's exact-measurement scheduler; vLLM V1's process split and lazy-but-charged allocators; SGLang's Rust radix core; MLX's residency sets and cache limits; mistral.rs's multi-model engines) all travel in one direction: measure instead of estimate, isolate models in processes, make recurrent state a first-class memory type, move per-token work off the host, and treat MoE experts as a cacheable host-resident tier. An engine that starts from that end state and adds the one thing none of them has — a machine-level arbiter with deterministic, printable plans, per-model hard caps across RAM, VRAM and NPU memory, lazy growth charged at admission, and a fixed degradation ladder that never reaches swap — is differentiated by behaviour users feel (no freezes, no silent 10× slowdowns, no "it uses 44 GB" confusion) rather than by benchmark deltas that rot within a quarter.

Three implications follow for the architecture document and the implementation prompt. First, the memory ledger and the plan are product surfaces, not internals: expose them in the API and logs from the first milestone, because every incident in the notes was "slow and silent".
